# 世界与地图（SYS-WORLD）—— "工地的总指挥"

> 📌 进度：📐 图纸画好 —— 确定性 CORE、动态集成和生命周期收口均已完成，完整 24 层语义仍待后续

---

## 一句话讲清楚

**世界与地图系统 = 整张游戏地图的"总指挥"，负责把世界建起来、拆干净，别人要用地图形只找它。**

就像盖一栋楼：谁来打地基、谁来砌墙、谁来装门窗——这些事需要一个总指挥统一调度。总指挥不管"每块砖怎么烧"（那是资源系统的事），也不管"哪面墙该刷什么颜色"（那是图层系统的事），他只负责一件事——**确保这栋楼按正确的顺序建起来，拆的时候按正确的顺序拆干净，中间有人要往里放东西或撤东西，必须是他说了算。**

---

## 它管哪些事

| 管的事 | 大白话 |
|---|---|
| 建世界 | 把整张地图的"地基"建起来——创建 Tilemap、建好所有图层，全成功了才宣布"世界就绪" |
| 放块 | 往世界里放一块地图（28×28 格，24 层），所有层都写入成功才算数，有一层失败就全部回滚 |
| 撤块 | 从世界里撤走一块地图，把对应区域清干净，碰撞重新算 |
| 拆世界 | 把整个世界拆干净——先禁止新写入，再断碰撞监听，最后销毁图层和 Tilemap，不留垃圾 |

**它不管的事**：每块地图数据从哪来、什么时候该放哪块——这些归分块系统管。每层怎么显示、什么颜色、多高——这些归图层系统管。图片文件怎么下载——归资源系统管。

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：统一建/拆的"总指挥"模式

**大白话**：整张地图的建立和拆除，全部由一个"总指挥"经手。别人不能绕过它直接动地图。

就像盖楼必须有项目经理统一调度——不能让瓦工自己决定在哪砌墙、也不能让电工自己决定在哪走线。所有对世界的改动（建、放、撤、拆）都走同一个人，这样出了问题知道找谁、状态不会乱。

**为什么是骨架**：不管什么校园、什么地图、什么引擎，复杂的游戏世界都需要一个唯一的"入口"来建和拆。一个人说了算，就不会出现"A 系统和 B 系统同时改同一层"的冲突。

**实现形态**：代码里叫 `WorldRenderer` 和 `WorldSpec`——所有对 Tilemap 的写操作都经过同一个渲染器，外部只能通过"申请放块/撤块/建世界/拆世界"四个操作来影响世界。

#### 骨架 2：原子操作——要么全成，要么全滚

**大白话**：往世界里放一块地图要同时写 24 层。这 24 层要么全部写成功、要么一层都别动——不会出现"写了 20 层、剩 4 层失败了但前面 20 层留着"的半吊子状态。

就像你去银行转账：钱从你账户扣了但对方没收到？不行。对方收到了但你账户没扣？也不行。要么整个转账完成，要么什么都没发生。放块也一样——24 层全部写入成功，这块才登记为"已渲染"；任一层失败，整块回滚。

**为什么是骨架**：任何复杂操作都可能半路失败。如果不做原子保护，世界会进入"半块地图在、半块不在"的诡异状态，玩家看到的就是地图花屏。

**实现形态**：`applyChunk` 先把 24 层数据全部转换好、校验通过，再一次性写入 Tilemap。写入过程中任一层失败，已写入的全部回滚（清除本次坐标的所有写入痕迹）。

#### 骨架 3：生命周期状态机

**大白话**：世界从"还不存在"到"可以用了"再到"拆掉了"，中间要经过明确的几个阶段。每个阶段能做什么、不能做什么，都有硬规矩。

就像一栋楼的施工阶段：打地基时不能装窗户、验收通过后才能住人、拆楼时必须先断电再拆墙。世界的状态也一样：

```
还不存在 → 正在建 → 就绪（能用）→ 正在拆 → 拆完了
```

在"正在建"的时候，不接受放块请求（楼还没盖好呢，你往哪放东西）。在"正在拆"的时候，禁止新的写入（已经收工了，别再往里塞东西）。只有在"就绪"阶段，放块和撤块才正常工作。

**为什么是骨架**：状态机是人类管理复杂系统最古老也最可靠的办法——灯要么开要么关，门要么锁要么开。游戏世界多几个状态但道理一样。

**实现形态**：代码里用 `uninitialized → creating → ready → destroying → destroyed` 六个状态标记，非 `ready` 状态拒绝写入，`destroy` 可以重复调用（幂等）。

#### 骨架 4：地基模式——别人挂我上面

**大白话**：世界是"地基"，图层、分块、NPC、车辆这些东西都挂在世界上面。世界不在了，上面挂的所有东西都自动失效。

就像一栋楼的地基——地基在，楼上可以装各种东西（水管、电线、家具）。地基拆了，上面的东西都要先撤掉。世界系统拥有 Tilemap 和所有图层实例，其他系统（图层系统定义策略、分块系统决定坐标）只是"使用"这个世界，不"拥有"它。

**为什么是骨架**：所有权清晰是软件工程的铁律——一个东西只能有一个人拥有。世界拥有图层和 Tilemap，销毁时就知道该清理什么；如果所有权分散在多个系统，拆世界时永远拆不干净。

**实现形态**：代码里定义了明确的状态所有权表——`WorldSpec`、`Tilemap 句柄`、`运行时图层实例` 都归 SYS-WORLD 拥有；分块系统只拥有请求和缓存状态；图层系统只拥有策略定义。

#### 骨架 5：安全拆解——反着建的方向拆

**大白话**：拆世界的顺序必须和建世界反着来：先关大门（禁止新写入），再拔线（断碰撞监听），再拆墙（图层），最后推地基（Tilemap）。

就像拆楼不是上来就拿大锤砸——要先断电、断水、断气，再从顶层往下拆，最后才拆地基。如果先拆地基，楼会塌。世界也一样：如果先销毁 Tilemap，图层还在引用它，就会出错甚至崩溃。

**为什么是骨架**：任何有依赖关系的系统，销毁顺序都必须是"先创建的后销毁、后创建的先销毁"（就像括号要先关最里面的）。这个原则换什么项目都不变。

**实现形态**：`destroyWorld` 的销毁顺序固定为：停止调度 → 等待请求收敛 → 等待 mutation 完成 → 移除 collider → 销毁 layer → 销毁 Tilemap。销毁是幂等的，调多次不会出错。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| 世界尺寸 | 140×140 格，tile 16×16 像素，世界 2240×2240 像素 | 可以更大或更小，比如教学楼 80×80，操场 200×200 |
| 分块网格 | 5×5，每块 28×28 格 | 可以 3×3（9 块）或 8×8（64 块），每块大小也可变 |
| 图层数量 | 24 层（layer1~10 + walls + cars + 4 roof + 4 bridge + particles/2/3 + footsteps） | 其他校园可能只有 8 层或 30 层，取决于美术复杂度 |
| 数据来源 | `master.json` + `chunk{0-24}.json`（共 26 个 JSON 文件） | 换校园 = 换一套 JSON 文件，可能文件名和数量都不同 |
| 验证基准 | 25 块拼接后与 `final_map.json` 逐格差异为 0（共 470400 格） | 验证方式一样（拼接 = 整图），但整图本身不同 |
| 拆解顺序 | collider → layer → Tilemap（Phaser 3 特定顺序） | 换引擎后顺序可能不同，但"反着建的方向拆"原则不变 |

## 跟谁接口（它和谁打交道）

```
                         ┌──→ [图层与遮挡]  给它：24 层处理策略
                         │     接收：图层实例的引用和动态状态
                         │
[SYS-ASSET 资源加载] ──→ [SYS-WORLD 世界与地图]
                         │
                         ├──→ [地图分块]    接收：坐标 + 已验证 chunk 数据
                         │     返回：写入成功 / 已存在 / 写入失败
                         │
                         ├──→ [NPC]         挂在世界上，世界就绪后通电
                         ├──→ [车辆与路线]  挂在世界上
                         └──→ [动效与粒子]  挂在世界上
```

世界系统是**整个地图线的中间枢纽**——上面接资源系统（要材料），左右接图层系统（要策略）和分块系统（听调度），下面挂着一堆旁支系统（NPC、车辆、粒子都要等世界就绪）。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 建拆顺序搞反 | 建世界的顺序是 Tilemap → 图层 → 碰撞，拆的时候必须反着来：碰撞 → 图层 → Tilemap。先拆 Tilemap 会导致图层和碰撞引用失效，直接崩溃 |
| 半成品世界 | 建世界到一半失败了（比如缺某个资源），如果没做回滚，已经建好的图层会留在内存里。下次再建会重复创建，越积越多 |
| 拆不干净 | 销毁时忘了取消在途的 HTTP 请求、忘了移除事件监听、忘了清碰撞——每次重开游戏都多漏一点内存，玩久了越来越卡 |
| 晚到数据污染 | 销毁世界后，之前发出的 HTTP 请求可能这时才回来。如果不检查"世界还在不在"，晚到的数据会往一个不存在的 Tilemap 里写，出错甚至崩溃 |
| 原子性幻觉 | "24 层写到一半失败"如果不做回滚，下次放同一块时发现"咦这块已经写了一半了"，状态彻底乱掉 |
| 所有权模糊 | 如果分块系统绕过世界直接操作 Tilemap，世界就不知道"哪些块已经在画面上了"。销毁时漏掉这些、或者重复销毁——都会出问题 |
