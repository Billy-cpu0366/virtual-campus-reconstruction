# 图层与遮挡（SYS-LAYER）—— "24 张透明胶片叠起来的立体画"

> 📌 进度：📐 图纸画好 —— 5 场景实拍通过（遮挡/房顶/桥/脚印 VERIFIED），仅粒子链 Q-LAYER-002 仍开着

---

## 一句话讲清楚

**图层与遮挡系统 = 把 24 张"透明胶片"按一定顺序叠起来，玩家走到不同位置时，有些胶片该透明的变透明、该显示的显示，伪造出"你在楼前面还是楼后面"的 3D 效果。**

2D 俯视游戏没有真正的 3D——但你的大脑看到"小人被房顶遮住了"就会自动觉得"哦，我走进屋了"。图层系统就是那个操纵你大脑的家伙：它通过控制 24 层胶片的叠放顺序和透明度，让你觉得你在一栋真实的楼里走来走去。

就像小朋友玩的"立体贺卡"——一张纸折几层，打开的时候前面的树、中间的人、后面的房子自然就有了远近关系。图层系统用的就是同一个道理。

---

## 它管哪些事

| 管的事 | 大白话 |
|---|---|
| 24 层策略 | 每层是干嘛的——是显示用的（看得见的楼和地）、撞墙用的（看不见的墙壁）、还是存数据的（标记哪里能跑车、哪里冒脚印） |
| 动态遮挡 | 玩家走到一栋建筑的"后面"，建筑顶上的层就遮住玩家；走到"前面"，玩家就遮住建筑 |
| 房顶淡隐 | 玩家走进工厂或音乐厅，房顶在 300 毫秒内慢慢变透明，露出室内；走出去，房顶慢慢恢复 |
| 桥上下切换 | 玩家走上桥，桥的上半层/下半层切换可见，碰撞也随之切换——从桥上过和从桥下过，看到的是不一样的画面 |
| 脚印标记 | 玩家踩到某些格子上，会冒脚印（总共 368 个位置，脚印深度 450） |
| 墙壁碰撞 | walls 层藏着哪些格子是"墙"（GID 69345），玩家撞上去就走不动了 |

**它不管的事**：图层实例本身归世界系统（SYS-WORLD）拥有——图层系统只定义"每层该怎么处理"，不拥有 Tilemap。什么时候放块撤块归分块系统（SYS-CHUNK）决定。车辆怎么跑、NPC 怎么走——那些是旁支系统看了 marker 数据后自己决定的事。

## 🎨 核心：皮与骨架拆分

> **骨架** = 换什么校园都不变的做事方式
> **皮** = 跟 Peter 这个具体项目绑定的内容
> **配置点** = 将来后端管理系统可以改的参数

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：图层策略表——一张表管所有层

**大白话**：不是写死"第 1 层是地面、第 2 层是墙壁"，而是用一张"策略表"来定义——每一层叫什么名字、它是拿来显示的还是撞墙用的还是存数据的、叠多高、写的时候要不要过滤掉某种格子、拆的时候怎么清理。

就像物业管理处有一本"楼层用途登记表"——101 是便利店、102 是理发店、201 是办公室……一目了然。换一栋楼，换一本登记表就行，物业的管理流程不用变。

**为什么是骨架**：任何 2D 游戏只要用了图层系统，都需要知道"每层干嘛的"。把定义用一张表集中管理，换游戏时只换表的内容、不换查询表的逻辑。而且表本身就是"合同"——世界系统看这张表就知道每层怎么写，分块系统看这张表就知道每层怎么处理。

**实现形态**：代码里 `src/layer/` 下有一张 24 层策略表，每层有 `name`、`role`（visual/collision/marker/dynamic-visual/dynamic-collision）、`depth`、`GID 过滤规则`、`apply/remove 行为` 等字段。

#### 骨架 2：Y 排序动态遮挡——越在下面的越遮人

**大白话**：玩家不是固定在一个"高度"上的。他越往下走（Y 坐标越大），深度值就越高，越容易被地图上层的建筑和树木遮住。反过来他往上走，深度值变小，就跑到了建筑前面。

就像你走在街上——离你近的东西遮住离你远的东西。在 2D 俯视游戏里，"远近"用"上下"来假装：Y 坐标越大 = 离镜头越近 = 应该遮住别的东西。玩家的深度按公式 `500 + (Y + 24) × 0.1` 实时计算，这样他走到灌木丛下面时，灌木丛自然就遮住了他的腿。

**为什么是骨架**：Y 排序是 2D 俯视游戏做遮挡的"标准答案"——从 90 年代的 RPG 到现在的手机游戏都在用。换什么校园、什么美术风格，只要还是俯视 2D，就需要这个公式。变的只是公式里的系数。

**实现形态**：代码里玩家 depth 常态按 `500 + (y + 24) * 0.1` 计算，桥上强制拉到 1650。深度计算逻辑在 `src/layer/` 中，由图层系统统一管理，不允许多人各算各的。

#### 骨架 3：区域触发 + 状态切换（进入→改透明度/显示→退出→恢复）

**大白话**：房顶不是一直显示的、桥也不是永远一个状态。玩家进入某个区域 → 图层系统改变相关层的显示状态 → 玩家离开 → 恢复原状。

就像感应门——你走近，门自动开；你走过去，门自动关。图层系统不关心"你怎么走进那个区域的"（那是区域触发系统的事），它只管"你进来了是吧？好，我把房顶变透明。你出去了？好，我恢复。"

房顶淡隐和桥上下切换是这个骨架的两种"皮"——具体表现形式。骨架本身是"进入区域→改状态→退出→恢复"这个模式，换一个校园可能没有房顶，但可能有"走近喷泉→喷泉水花变大"、"走近音响→音乐变响"——都是同一个模式。

**为什么是骨架**：游戏里"到达某处触发某件事"是最常见的模式之一。把"进入/退出区域"和"改什么状态"拆开，区域判定归区域系统、状态修改归图层系统——两个系统各自独立演进。

**实现形态**：roof 以 concert/factory 分组保存 visible/alpha 状态，300ms 淡隐参数硬编码；bridge 保存每座桥的上/下状态，切换时同时更新可见性、tile 碰撞和玩家 depth。状态修改是幂等的（同一个状态设两次不会出问题）。

#### 骨架 4：视觉层和标记层分开

**大白话**：有些层是用来"看"的（layer1~10、roof、bridge），它们的数据会直接画到屏幕上。有些层是用来"查"的（walls、cars、particles、footsteps），它们的数据不直接显示，而是被别的系统读走、然后决定做什么。

就像一本菜单——有些页是顾客看的（带图片和价格），有些页是厨师的备注（"这道菜要大火快炒、3 分钟出锅"）。顾客不需要看备注，厨师必须看。视觉层是给渲染引擎看的，标记层是给 NPC、车辆、粒子系统看的。

walls 层标记了"哪里是墙"，碰撞系统读它来决定玩家能不能走。cars 层标记了"哪里可以跑车"，车辆系统读它来规划路线。footsteps 层标记了"哪里踩上去会冒脚印"，脚印系统读它来决定什么时候生成脚印。

**为什么是骨架**：数据和显示的分离是软件工程的基本法则。标记层存的是"意思"（这格是墙 / 能跑车 / 冒脚印），视觉层存的是"样子"（这格贴什么图）。换一套美术资源，"样子"全换了但"意思"不变——墙还是墙，车子路线还是那些路线。

**实现形态**：`role: visual` 的层写入 Tilemap 显示网格；`role: collision` 的层输出碰撞网格；`role: marker` 的层输出带世界坐标和 chunk 来源的 marker 集合，不直接写 Tilemap。

#### 骨架 5：对称的放块/撤块——怎么放的就怎么撤

**大白话**：放一块地图进去，写了哪些层、登了哪些 marker——撤的时候必须把这些全部反着清理干净。不能出现"放的时侯写了 10 层、撤的时候只清了 8 层"。

就像搭帐篷——搭的时候钉了 8 根钉子，收的时候不能只拔 6 根漏 2 根在土里。图层系统保证：每个 chunk 在 apply 时创建的所有视觉数据、碰撞数据和 marker 登记，remove 时全部撤销，不留残余。

**为什么是骨架**：对称性是防止"内存泄漏 + 状态漂移"的唯一办法。如果 apply 和 remove 不对称，每次重加载都会多留一点垃圾，最终要么画面花屏（旧数据没清干净）、要么越来越卡（内存越占越多）。

**实现形态**：`onChunkApply` 和 `onChunkRemove` 是策略表中每层的固定字段。remove 必须撤销同一 chunk 来源的所有视觉、碰撞和 marker 引用。重复 remove 返回 AlreadyAbsent，不制造错误。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| 24 层具体名称和用途 | layer1~10（视觉）、walls（碰撞）、cars（车辆标记）、4 roof、4 bridge、particles/2/3、footsteps | 层的数量和名称完全不同。可能叫 ground、building、tree、shadow 等 |
| 各层 depth 值 | layer1-5: 100~500、layer6-10: 1500~1900、walls: 550、roof: 3000~3300、bridge: 3500 | depth 值完全看美术怎么设计，只要相对顺序对就行 |
| 玩家深度公式 | `500 + (y + 24) × 0.1`，桥上强制 1650 | 系数会变（取决于地图高度和视角），但公式结构一样 |
| 屋顶区域 | factory（工厂）和 concert（音乐厅）两个区域 | 可能没有屋顶区域，或者有 10 个不同的建筑物 |
| 屋顶淡隐速度 | 300 毫秒（从完全不透明到完全透明） | 可以改成 200ms（更快）或 500ms（更慢） |
| 桥的数量和位置 | bridge1、bridge2 两座桥 | 可能没有桥，或者有 5 座桥 |
| 墙的碰撞 GID | 69345 = 墙（碰撞）、69346 = 不碰撞 | GID 完全不同，但"指定某个 ID 是墙"的逻辑一样 |
| 脚印位置 | 368 个特定格子 | 0 个（没有脚印功能），或者位置完全不同 |

## 跟谁接口（它和谁打交道）

```
                         ┌──→ [世界与地图]    给它：24 层处理策略
                         │     接收：图层实例引用、动态状态句柄
                         │
                         ├──→ [地图分块]      给它：每层的 GID 过滤规则和深度
[SYS-LAYER 图层与遮挡] ──┼      接收：坐标和 chunk 数据
                         │
                         ├──→ [移动与碰撞]    给它：walls 碰撞网格（哪格能走、哪格不能）
                         │
                         ├──→ [玩家]          给它：玩家深度值（影响遮挡关系）
                         │     接收：玩家世界坐标（Y 位置决定深度）
                         │
                         └──→ [车辆/粒子/NPC] 给它：cars/particles/footsteps marker 数据
                                接收：（单向提供数据，不反向依赖）
```

图层系统是**地图线的"翻译官"**——它把原始的地图数据（一堆 tile ID）翻译成"这层怎么显示"、"这格能撞吗"、"这格能跑车吗"——然后分发给各自需要的系统。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 地图 visible 字段不是最终显示状态 | chunk JSON 里每层有 visible 字段，但 Bundle 运行时会主动改某些层的可见性——不能只看 JSON 就下结论，必须以运行为准 |
| 特殊 13 层卸载不一致 | 原站 unloadChunk 只清 layer1~10 和 walls 这 11 层，cars/roof/bridge/particles/footsteps 这 13 层不清——这是原站的 bug 还是有意为之，还没弄清。重构第一版不复制这个行为，所有层对称 apply/remove |
| 层缺失时不能静默跳过 | 如果某个 chunk 少了某一层、或者多了一层不认识的东西，不能"假装没看见"继续走——必须报错并回滚整块，否则数据错位了根本看不出来 |
| GID 过滤不严 | walls 只保留 69345 和 69346，particles 只保留 69355~69359——如果放进了不该有的 GID，渲染出来的画面会有莫名其妙的图块 |
| 深度覆盖冲突 | 桥会强制把玩家深度拉到 1650，如果以后有别的系统（比如剧情抓取）也要改玩家深度，两套逻辑会打架——所以必须规定"深度覆盖必须有进入和退出，退出后恢复常态" |
| particles3 消费者不明确 | particles3 的 GID 69361 marker 存在，但原站代码里找不到直接用它的消费者——不能因为数字凑上了就宣称"做完了"，必须保留为未完成 |
