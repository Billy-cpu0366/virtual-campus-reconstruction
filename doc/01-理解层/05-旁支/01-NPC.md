# NPC 与环境实体（SYS-NPC）—— "校园里的群众演员"

> 📌 进度：📐 画好图纸 —— NPC 类型/数量/路线/裁剪全部落实；寻路为自定义 A* 而非 EasyStar.js

---

## 一句话讲清楚

**NPC 系统 = 校园里所有"不是玩家"的会动的东西。他们就像电影里的群众演员——不需要主角那么多戏份，但没他们，校园就是一座空城。**

你去大商场逛街，身边来来往往的人、坐在长椅上发呆的人、在海滩上跳舞的人——他们都不是你，但他们让商场"活"了。NPC 系统做的就是这件事。

---

## 它管哪些事

|管的事|大白话|
|---|---|
|生成 NPC|在指定区域里"变出"一定数量的路人、舞者、虫子、抗议者|
|沿路线移动|让 NPC 从 A 点走到 B 点，碰到路障知道绕开|
|视口裁剪|屏幕外的 NPC 暂时销毁省性能，回到视野再重建|
|状态控制|每个 NPC 都有固定的生命周期：出生 → 活跃 → 暂停 → 销毁|
|分类管理|不同 NPC 各自独立管，舞者不会干扰路人，喷水器不会影响虫子|

**它不管的事**：NPC 长什么样（精灵图归资源系统管）、NPC 碰到玩家怎么办（碰撞归物理系统管）、NPC 怎么画到屏幕上（渲染归 Phaser 管）。

## 🎨 核心：皮与骨架拆分

> **骨架** = 换什么校园都不变的做事方式
> **皮** = 跟 Peter 这个具体项目绑定的内容
> **配置点** = 将来后端管理系统可以改的参数

---

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：固定生命周期

**大白话**：每个 NPC 都有确定的生老病死流程。就像电影开拍前群演就位（start）、拍摄中他们按剧本走（tick/update）、喊卡后收工（shutdown）。不管什么类型的群演，流程都一样。

**为什么是骨架**：不管哪个校园，NPC 都需要"开始 → 运行 → 停止"这套管理。龙套不能永远赖在片场不走，也不能导演还没喊就开始演。

**实现形态**：每个 NPC 类型都是一个 Runtime 类，统一提供 `start()`、`tick()`、`cancel()`、`shutdown()` 四个方法。状态统一管理（started/dead 标志位），生命周期确定性、可测试。

#### 骨架 2：视口裁剪

**大白话**：只有你看得见的 NPC 才真的"存在"，屏幕外的暂时删掉，省性能。就像舞台剧——灯照到的区域才有演员，暗掉的区域演员就退场了。

**为什么是骨架**：任何大地图游戏都必须做裁剪，不然 500+ NPC 都在内存里，手机直接烫手。换一个校园，可能陌生人更多，更离不开裁剪。

**实现形态**：每个 NPC 实例都有 `materialized` 标志。每帧检查 NPC 位置是否在 viewport 范围内（加安全边距），在 → materialized=true（创建/保持精灵），不在 → materialized=false（销毁精灵，保留数据）。核心层只算标志位，表现层根据标志创建/销毁 Phaser 精灵。

#### 骨架 3：核心逻辑与表现分离

**大白话**：NPC"怎么动"的规则写在纯代码里，"长什么样"交给 Phaser 去画。就像导演的剧本（核心逻辑）和化妆师的道具（表现层），分开管，互不干扰。

**为什么是骨架**：规则不依赖于具体游戏引擎，换引擎（比如从 Phaser 换成 PixiJS）只需要重写表现层，核心逻辑不动。测试也能脱离浏览器跑。

**实现形态**：`src/npc/` 里的 Runtime 类——纯 TypeScript，不碰 DOM、不碰 Canvas、不碰定时器。`game/Phaser*Runtime.ts` 里的类——负责"把 Runtime 的数据变成 Phaser 的精灵"。分层接口全用 `*Like` 抽象（如 `PhaserTrainSceneLike`），表现层"符合接口就行"，不依赖具体实现类。

#### 骨架 4：按区域/路线放置，不逐个写死

**大白话**：NPC 不写"在 (100,200) 放个人"这种死坐标，而是写"在这片多边形区域里随机撒 N 个人"。就像婚庆公司——你只需要说"这个厅放 8 桌"，不需要精确到每把椅子摆哪厘米。

**为什么是骨架**：换校园只需要换一份区域/路线配置，代码一个字不改。区域数据是纯 JSON，跟代码完全解耦。

**实现形态**：静态人群用多边形区域 + 密度公式（`宽度 × 高度 × 系数`）算出人数，区域内随机撒点（保证最小间距、不越界）。路线人群用 start/end 格子数组 + A* 寻路自动算路径，支持随机分流。

#### 骨架 5：可取消、可暂停、可分组管理

**大白话**：不同群演组可以独立控制——"抗议者那组先停一下""虫子组关了""音乐会那组继续"。就像导演的喇叭——对不同组喊不同指令。

**为什么是骨架**：任何校园场景都可能需要"某个区域的 NPC 暂时关掉"（比如剧情触发、玩家进入特殊区域），这种分组管理能力是通用的。

**实现形态**：每个 Runtime 实例独立管理自己的 NPC 队列。`cancel()` 清空所有 NPC 但 Runtime 保留（可以重新 start）。`shutdown()` 彻底销毁（再也不用了）。`pauseGroup()/resumeGroup()` 暂停/恢复特定组（如 train 来临时暂停路线人群的某个组）。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| NPC 类型和数量 | 7 大类：静态NPC(3)、静态人群(~600)、路线人群(~166)、跳舞者(8)、虫子(10)、场馆人群(~490)、喷水器(4) | 换成完全不同的 NPC 阵容，可能含动物、机器人、摊贩 |
| 静态 NPC 配置 | 3 个：special-reading(看书的，坐标72×53，比例0.9)、special-eating(吃外卖的，54×63，0.73)、cat-licking(猫舔毛，12×106，1.0) | 换一批位置、换一批精灵图 |
| 静态人群区域 | 46 个多边形区域（海滩、球场、车站、咖啡店……），密度公式：普通区 0.004×面积，密集区 0.016×面积 | 换校园 = 换区域定义文件 |
| 路线人群配置 | 11 条路线：main-crowd(10人)、loop-crowd(10人往返)、drinkers(5人)、concert_crowd(40人)、beach_crowd_walk(4人)、vertical-crowd(10人)、vertical-crowd-reverse(10人)、walking-crowd(8人)、hazmat-crowd(8人)、outside_concert1(10人)、crowd-train(10人) | 换路线图、换人群规模 |
| 寻路方式 | 自定义 A*（`GridRouteCrowdPathProvider`），每次限 64 步、最多 5 万次迭代、支持对角移动（成本 1.41）、支持随机扰动打破对称 | 可以用其他寻路算法，只要实现 `RouteCrowdPathProvider` 接口 |
| 喷水器逃跑路线 | 4 个喷水器各有预设逃跑坐标串，玩家靠近（垂直 2 格 + 水平 2 格内）触发，逃跑速度 140 px/s，间隔 300ms 依次触发 | 换一批位置和逃跑路径 |
| 场馆配置 | 3 个音乐会区域（共 460 人，间距 18）+ 1 个抗议者区域（30 人，间距 20） | 换区域、换人群 |
| 深度值约定 | 静态NPC/人群 depth=500+y×0.1；跳舞者 depth=500；路线人群按 y 坐标算；喷水器 depth=500 | 不同校园地形不同，深度值会变 |

## 跟谁接口（它和谁打交道）

```
                        ┌──→ [世界与地图]   给它：NPC 实体数据（位置/方向/材质）
[SYS-NPC NPC系统]  ──┼──→ [玩家]          给它：喷水器触发用的玩家坐标
                        ├──→ [资源加载]     找它：NPC 精灵图、动画帧
                        ├──→ [图层与遮挡]   用它：NPC 深度值（谁挡谁）
```

NPC 系统是**玩法线的视觉担当**——没有它，校园就是一座只有建筑的空壳。

## 容易踩的坑

| 坑             | 为什么坑                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| 裁剪时机不对        | 如果 NPC 一走出屏幕就立刻销毁、一回来就立刻重建，会频繁闪烁。所以要设"安全边距"——屏幕外 300px 内先别急着毁，回来后先等 100px 缓冲再建                                    |
| 寻路计算太慢        | A* 在大地图上全量计算会卡帧。原站的做法是：每帧最多 64 步、单次最多 5 万步、分帧计算（`startBatched` 每次 4 个），即使几百条路径也能平摊到多帧完成                           |
| 精灵池不够用        | 有些 NPC 组（如 beach）只有 4 种精灵图，但如果那组要放 8 个人，就循环复用。但要注意：不能每个人长得一样——靠随机方向和位置错开视觉                                        |
| 静态人群一次性生成不退   | 静态人群的 placement 是第一次 start 时算好的，之后只改 materialized 标志。如果中途新增区域（disabledRegionIndexes），placement 不会自动更新——需要重新 start |
| 喷水器触发区域是正方形   | 玩家在喷水器"下方 0~2 格 + 水平 2 格内"才触发，但在上方（y 坐标更小）路过就不会触发。如果调了玩家起始位置，要从下方经过才有效                                            |
| 场馆人群的区域 ID 共享 | 音乐会场里 460 人分成 3 个区域，但抗议者和观众混在同一片区域的不同多边形里，按 id 区分。换校园时要防止 id 冲突                                                   |
