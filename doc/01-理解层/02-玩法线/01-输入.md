# 输入（SYS-INPUT）—— "公司前台统一转接"

> 📌 进度：📐 画好图纸 —— 键盘/WASD/摇杆三输入归一化已定稿；执行层逆向数据齐备

---

## 一句话讲清楚

**输入系统 = 把键盘方向键、WASD、手机摇杆这三种不同的"说话方式"，统一翻译成一句话："往这个方向走，速度这么快"。**

就像公司前台——不管你是打电话、发微信还是亲自上门，前台都只跟老板说一句"有人找"。老板不用管你用什么方式来的。输入系统就是这个"前台"：键盘按↑、按W、手机推摇杆，到了移动系统那里，全都是同一句话："方向=上，速度=150"。

---

## 它管哪些事

| 管的事 | 大白话 | 不管的事 |
|---|---|---|
| 监听键盘 | 盯着方向键和WASD有没有被按下 | 不负责"按下以后怎么走"——那是移动系统的事 |
| 监听摇杆 | 手机上手指拖摇杆，算出方向和力度 | 不负责摇杆长什么样——那是游戏UI的事 |
| 归一化 | 把三种输入都翻译成同一个"方向+速度" | 不负责碰撞检测——那是移动系统的事 |
| 优先级 | 摇杆和键盘同时来听谁的？摇杆优先 | 不负责"什么时候允许输入"——那是玩家的控制门 |
| 降级 | 摇杆加载失败了？键盘照样能用 | 不负责弹窗提示——打一行日志就完了 |

## 🎨 核心：皮与骨架拆分

> **骨架** = 换什么校园都不变的做事方式
> **皮** = 跟 Peter 这个具体项目绑定的内容
> **配置点** = 将来后端管理系统可以改的参数

---

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：多源归一化

**大白话**：不管来路是什么设备，最终都翻译成一种统一的"方向语言"。

就像机场的行李传送带——不管你从北京、上海还是广州飞过来，行李最终都从同一条传送带出来。键盘（方向键+WASD）、手机摇杆，到了移动系统那里，全都是同一个格式：`(dx, dy, 方向名)`。

**为什么是骨架**：任何游戏都有多种输入设备，归一化是通用需求。换一个校园，可能加手柄、加触屏滑动，归一化层接住新设备，下游不用改。

**实现形态**：`src/input/resolve/` 模块做方向仲裁——键盘方向和摇杆方向二选一（摇杆优先），输出统一的 8 方向向量。

#### 骨架 2：死区过滤

**大白话**：手指轻轻蹭了一下摇杆，不算"我要走"。

就像你家门铃——风吹过去不会响，得有人真按下去才响。摇杆有个"最小力度门槛"（forceMin=16），力度不够就当没按，防止角色原地抖动。

**为什么是骨架**：任何摇杆/手柄都有物理抖动，死区是所有输入设备必备的过滤器。

**实现形态**：原生 Phaser pointer 适配器内建 `forceMin` 阈值，摇杆偏移距离小于此值直接返回 null。

#### 骨架 3：优先级仲裁

**大白话**：键盘和摇杆同时来信号，听谁的？摇杆说了算。

就像会议室里只有一个麦克风——谁先抢到谁说话。原站的规则是：摇杆一动（`joystickActive=true`），键盘方向直接忽略；摇杆松手，键盘恢复。

**为什么是骨架**：多输入设备同时激活时的仲裁逻辑是通用的，不限于手机/键盘这对组合。

**实现形态**：`resolveMovement` 检查摇杆激活标志，摇杆激活时跳过键盘读取；摇杆回中时 `joystickActive` 置 false 恢复键盘。

#### 骨架 4：方向量化

**大白话**：摇杆推的角度是连续的（360°任意角度），但游戏角色只能走 8 个方向。

就像你把圆形的披萨切成 8 块——不管你从哪个角度下刀，最终只能落在这 8 块里的某一块。原站用主轴判定（|fx|/|fy| > 1.5 就是单轴方向）和阈值（0.3/0.5）把连续的角度量化成 8 方向。

**为什么是骨架**：连续输入离散化是所有 8 方向游戏的基础能力。

**实现形态**：键盘用 if/else 链做 8 方向优先级（上>下>左>右）；摇杆用 forceX/forceY 比例判定主轴 + 阈值量化成 8 方向向量。

#### 骨架 5：失败降级

**大白话**：摇杆插件没加载出来？没事，游戏继续跑，只是手机上没法用摇杆了（桌面端本来就用键盘）。

就像餐厅的扫码点餐坏了——没事，服务员拿纸笔记，饭照吃。原站摇杆失败只打一行日志，不弹窗、不崩溃、不重试。

**为什么是骨架**：任何外部依赖都可能挂，降级策略是所有系统的标配。

**实现形态**：摇杆插件加载失败 `console.error` 后 return，键盘输入不受影响；摇杆纹理缺失用 `add.circle` 圆形占位。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| 键盘键位 | 方向键 + WASD，两套并行合并 | 可以只留一套，或加 ESDF、手柄 |
| 摇杆插件 | rexVirtualJoystick，radius=15，base=60，thumb=30，fixed，右下角 | 换一个摇杆插件，或改参数适配不同手感 |
| 速度值 | 单轴 150，对角 106（150×0.707） | 可以改成 200，角色走更快 |
| 方向命名 | north/east/south/west + 四斜角 | 方向名随便改，只要动画系统也用同样的名字 |
| 摇杆/键盘优先级 | 摇杆激活时键盘失效 | 可以改成"后按的优先"或"键盘永远优先" |
| 单指 vs 多指 | 只认第一个手指，第二个被忽略 | 可以改成多指跟踪，但会增加复杂度 |

## 跟谁接口（它和谁打交道）

```
                        出 → 方向向量 (dx, dy) + 方向名
  [SYS-INPUT 输入] ──────────────────────────▶ [SYS-MOVE 移动与碰撞]
       ▲                                            │
       │ 入 ← 键盘事件 / 触摸事件                   │ 出 → setVelocity
       │                                            ▼
  硬件/浏览器                                [SYS-PLAYER 玩家]
                                            （走路动画用方向名选帧）
```

输入系统是**玩法线的起点**——它不说话，后面移动和玩家都等着干瞪眼。

与 SYS-CAMERA 也有间接关系：航拍期间相机通知 SYS-INPUT 隐藏摇杆、锁操作。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 三输入归一化丢了优先级 | 键盘和摇杆同时有信号时，如果没定谁优先，角色会"抽搐"——一会儿走键盘方向、一会儿走摇杆方向 |
| 把单指当成多指 | 原站只认第一个手指（`this.pointer === t`），第二个手指被忽略。如果做成多指跟踪，行为和原站不一致 |
| 斜方向速度忘了降 | 单轴 150、对角 106。如果对角也走 150，实际速度是 √(150²+150²)≈212，比直走快 40%——不公平 |
| 摇杆阈值设置不当 | 阈值太低→手指放上去就抖；阈值太高→推了也不走。原站 0.3/0.5 相对 radius=15 极灵敏 |
| 桌面端摇杆没隐藏 | 桌面用户不需要摇杆，但原站还是创建了再用 `toggleJoystick(false)` 隐藏——如果忘了隐藏，桌面上会多个多余的圆圈 |
