# 移动与碰撞（SYS-MOVE）—— "交通警察 + 安检门"

> 📌 进度：📐 画好图纸 —— 碰撞体+墙层+分轴已定稿；执行层逆向数据齐备

---

## 一句话讲清楚

**移动与碰撞系统 = 收到"往北走"的指令后，真的让角色动起来，并且在撞到墙的时候让他停下。**

就像商场的自动门——你走过去它打开（移动），但走到墙前面它会挡住你（碰撞），你不会穿墙而过。这套系统就是两个角色：**交通警察**（把方向指令翻译成实际位移）和**安检门**（遇到障碍物就把你拦下）。

有一个重要的认知要先说清楚：玩家撞墙和 NPC 寻路用的是**两套完全不同的数据**——玩家靠物理引擎实时撞墙，NPC 靠提前算好的一张 0/1 网格表查"这格能走吗"。别搞混。

---

## 它管哪些事

| 管的事 | 大白话 | 不管的事 |
|---|---|---|
| 速度转换 | 把"往北走"翻译成 `setVelocity(0, -150)` | 不负责"往北走"从哪来的——那是输入系统的事 |
| 玩家碰撞 | 控制玩家的脚底撞到墙上就停 | 不负责 NPC 碰撞——NPC 靠寻路查表 |
| 分轴处理 | 斜着走不会卡在墙角——引擎先横后竖 | 不负责自己写分轴——Phaser 引擎自带 |
| NPC 寻路查表 | 判断"第 5 行第 8 列这格能走吗" | 不负责 NPC 往哪走——那是 NPC 系统的事 |
| 撞墙反馈 | 撞墙时走路动画停住、换静止贴图 | 不负责走路动画是什么——那是玩家系统的事 |

## 🎨 核心：皮与骨架拆分

> **骨架** = 换什么校园都不变的做事方式
> **皮** = 跟 Peter 这个具体项目绑定的内容
> **配置点** = 将来后端管理系统可以改的参数

---

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：方向→速度转换

**大白话**：别人告诉你"往北"，你把这个指令翻译成"每秒向上移动 150 像素"。

就像 GPS 导航——你说"我要去北京"，GPS 翻译成"沿 G4 高速向北行驶 300 公里"。移动系统每帧都做这件事：先归零速度（`setVelocity(0,0)`），再按当前方向重新设置速度。

**为什么是骨架**：任何游戏都要把"方向"变成"位移"，这个转换是通用逻辑。换一个校园，速度值可能不同，但"方向→速度"这套翻译本身不变。

**实现形态**：每帧 `preUpdate` 调用 `updateMovement()`，先 `setVelocity(0,0)` 清零，再按 8 方向 `setVelocityX/Y(±150 或 ±106)`。

#### 骨架 2：玩家碰撞体定义

**大白话**：角色真能撞墙的只有脚底一小块，头和身体可以跟建筑重叠——这才是对的。

就像你走路——只有脚底接触地面，你的头可以从树枝下穿过。俯视角 RPG 的标准做法就是：碰撞块只是一条贴在脚底的小扁块（20 像素宽 × 8 像素高），头（精灵剩余 40 像素高度）可以自由穿过天花板、屋檐。

**为什么是骨架**：脚底碰撞体是俯视角游戏的通用模式，换什么风格的校园都不变。

**实现形态**：`this.body.setSize(20, 8)` + `setOffset(14, 36)`——让 20×8 的碰撞块偏移到精灵底部（48-8-4=36）。

#### 骨架 3：分轴碰撞

**大白话**：斜着走不会卡在墙角，因为引擎先处理横向、再处理纵向。

就像你推一个箱子进窄门——先横着挪、再竖着挪，分两步走，就不会卡住。原站没有自己写分轴代码，全靠 Phaser 的 `physics.add.collider`，这个 collider 内部就是先 x 轴再 y 轴。

**为什么是骨架**：分轴碰撞是所有 2D 物理引擎的标配，换什么游戏引擎都躲不开这一点。但 "不手写分轴，交给引擎"这个决策是通用的。

**实现形态**：`physics.add.collider(player, wallLayer)` + 4 个桥墙层的 collider，Arcade 引擎内部逐轴检测。

#### 骨架 4：撞墙反馈

**大白话**：撞到墙了，不是原地踏步，而是"定住"——动画停在那个方向的第一帧。

就像你走路撞到玻璃门——你不会继续原地踏步，你会停下来。原站的做法是：读 `body.blocked`（引擎每帧更新），如果某个方向被挡住，`stop()` 动画并显示 walk 动画的第一帧静态贴图，而不是继续播放走路动画。

**为什么是骨架**：撞墙→停动画是通用规则，换什么游戏都一样。

**实现形态**：`updateMovement` 尾部读 `body.blocked.{up/down/left/right}`，卡墙时 `anims.stop()` + 显示静态帧。

#### 骨架 5：NPC 寻路离线查表

**大白话**：NPC 走之前不每帧去算"这格是墙吗"，而是提前把答案做成一张表，走的时候只查表。

就像你去旅游前打印一份地图——走到路口掏出来看一眼，而不是边走边画地图。`walls-layer.json` 是一张 140×140 的 0/1 表，0=能走、1=墙，是提前从 tilemap 提取出来的。NPC 走每一步只查 `grid[y][x]`，不用去翻 tilemap。

**为什么是骨架**：把实时计算变成预计算，是性能优化的通用思路。换一个校园，表的大小和内容不同，但"提前做好表→走路只查表"这套流程不变。

**实现形态**：`assets/maps/walls-layer.json`（140×140 网格），NPC 消费方用 `cache.json.get("walls-layer")` 后 `grid[y][x] === 0` 判可走。

## 跟谁接口（它和谁打交道）

```
                           出 → 碰撞结果 (body.blocked)
        [SYS-MOVE 移动与碰撞] ──────────────────────▶ [SYS-PLAYER 玩家]
              ▲     │                                  （动画选帧 + 朝向）
              │     │
  入 ← 方向    │     │  查表："这格能走吗"
   (dx, dy)   │     └──────────────────────▶ [SYS-WORLD 世界/地图]
              │                               NPC 寻路消费 walls-layer.json
    [SYS-INPUT 输入]                   
              │                          
              │     墙层数据来源         
              └─── [SYS-LAYER 图层] ──── 创建 wallLayer + 桥墙层
                     [SYS-CHUNK 分块] ── 提供 chunk 中的 walls 层 tile 数据
```

关键认知：移动系统的碰撞墙层（walls + bridge walls）是**图层系统创建好交给它的**，它只管在 collider 里登记。walls-layer.json 是**地图系统提供**的独立文件，NPC 寻路用它，玩家碰撞不用它。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 把 walls-layer.json 当成玩家碰撞数据 | 这是给 NPC 寻路的离线 0/1 表，不是玩家撞墙用的。玩家撞墙靠 tilemap 里的 walls 层（存贴图编号）。两套东西、两套消费者，搞混了 NPC 没法走、玩家撞空气 |
| 以为自己要手写分轴 | Phaser Arcade 引擎 `collider` 内部自带先 x 后 y 的分轴处理。原站没有一行分轴代码。如果自己再写一遍，不仅是重复劳动，还可能跟引擎打架 |
| 碰撞体贴在头而不是脚 | offset(14,36) 是把碰撞体推到精灵底部。如果 offset 设错，碰撞体飘在头上，角色头撞墙脚穿墙——完全反了 |
| 墙层没设不可见 | 碰撞墙层是隐形的（setVisible false / alpha 0），如果忘了设，玩家会看到一堆灰块——那是调试数据不是游戏画面 |
| 斜方向碰撞判断少了一个轴 | 对角方向撞墙要判断两个轴的 blocked（比如右上要判断 up 和 right），如果只判一个，角色会"贴着墙滑"而不是停下来 |
| drag/maxVelocity 数值关系搞反 | maxVelocity(200) > 实际速度(150) 是正常的——它是兜底上限，不是主动限速；drag(300) 负责松手后自然减速。如果 maxVelocity 设小了，角色跑不起来 |
