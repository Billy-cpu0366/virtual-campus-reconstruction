# 地图分块（SYS-CHUNK）—— "走到哪，送到哪的外卖骑手"

> 📌 进度：✅ 确定性 CORE 已有代码，26 测试通过 —— 动态集成和生命周期收口已完成，完整 24 层语义仍待后续

---

## 一句话讲清楚

**地图分块系统 = 把一张巨大的地图切成很多小块，玩家走到哪，就只把他周围那几块送进画面；走远了，就把用不到的小块从画面上撤掉。**

整张地图有 140×140 格，如果一次性全塞进内存，手机会炸。分块系统的思路跟外卖骑手一样——他不会把全城的菜都往你家里送，只送你点的、只送你家附近的。你走到另一条街，新的骑手就负责新区域的配送，旧区域的骑手收工。

这是原站最核心的性能优化，也是整个项目"平台化"最想带走的技术。

---

## 它管哪些事

| 管的事 | 大白话 |
|---|---|
| 算目标集合 | 看一眼玩家站在哪、相机能看到哪，算出"该加载哪几块地图" |
| 加载新块 | 玩家走到了新区域 → 算出哪些块是之前没加载的 → 下载数据 → 交给世界系统放进画面 |
| 卸载旧块 | 玩家走远了 → 算出哪些块已经不需要了 → 通知世界系统从画面上撤掉 |
| 坐标换算 | "玩家站在坐标 (1088, 304)" 翻译成"他在第 (2, 0) 号块里" |
| 防止重复请求 | 同一块地图正在下载中，不重复再发一次请求 |
| 过期守卫 | 如果一块数据下载完时，玩家已经走远了（或者世界都拆了），坚决不能往画面里写 |
| 开场预载 | 游戏开始前的航拍需要看到整张地图，所以一次性预载全部 25 块；航拍结束、玩家可以操控后，切换回动态装卸 |

**它不管的事**：图片文件怎么下载、下载失败怎么办——归资源系统管。数据到手后怎么写入 Tilemap——归世界系统管。每层数据怎么写、怎么转换——归图层系统管。玩家怎么移动、相机怎么跟随——那是玩法线的事，分块系统只管"从玩家和相机那里问一个坐标"。

> **骨架** = 换什么校园都不变的做事方式

> **配置点** = 将来后端管理系统可以改的参数

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：按需加载——不把整张地图一次性全塞内存

**大白话**：不管地图多大，任何时候内存里只保留玩家周围一圈。玩家走到天涯海角，内存使用量始终有上界。

就像你看电子地图 APP——哪怕全中国的地图数据有几 TB，你手机上只加载你屏幕里能看到的那一小块。你滑到别的地方，旧的数据从内存里释放掉，新的数据加载进来。分块系统就是这个电子地图的引擎。

**为什么是骨架**：任何超过屏幕尺寸的游戏地图都需要这个能力。140×140 的 Peter 校园需要它，400×400 的巨型校园更需要它。地图可以变大变小、块的大小可以调，但"只加载玩家周围"的思路不变。

**实现形态**：`ChunkCoordinator` 每约 500ms 计算一次目标集合，对比当前已渲染集合，产出"需要新加载的"和"需要卸载的"两个差集。`ChunkDataStore` 管理下载缓存，`WorldRenderer` 管理画面渲染状态。三种状态严格分开：下载了 ≠ 显示着 ≠ 正在请求。

#### 骨架 2：目标集合公式——玩家邻域 + 相机可见范围

**大白话**：决定"加载哪几块"的依据来自两个源头——玩家站在哪块上（及其周围的 3×3 邻域），加上相机能看到多远（再多加 1 块边距）。两者合并就是目标集合。

就像外卖骑手的配送范围——一是你住的小区（玩家位置），二是骑手覆盖的片区（相机范围）。两个范围一合并，就是"该送餐的区域"。你搬家了、或者换了一家更远的餐厅，这个范围自然就变了——但"小区 + 片区"的计算逻辑不变。

**为什么是骨架**：玩家和相机是两个独立变化的输入。玩家跑得快、相机可能是航拍可能是特写——但不管怎么变，"两个源 → 合并 → 得目标集合"这个三步流程是通用的。

**实现形态**：`ChunkCoordinator` 从玩家拿世界坐标 → 算出当前块 → 加 3×3 邻域并边界裁剪；从相机拿 scrollX/scrollY/width/height/zoom → 算出可见范围 → 外扩 1 块边距；两个集合合并去重。公式在 `src/chunk/targets.ts` 中。

#### 骨架 3：三种状态严格分开——下载了 ≠ 显示着 ≠ 正在请求

**大白话**：一块地图的 JSON 下载到了浏览器，不意味着它已经在屏幕上显示着了。有三种状态要分开记：数据有了吗（缓存）？画面上有吗（渲染）？正在下载中吗（在途）？

就像网购的三种状态："下单了"、"发货了"、"签收了"——它们是三件不同的事。原站代码里两个地方都叫 `loadedChunks`，但实际上一个是"已下载 JSON 的集合"，一个是"已画到屏幕上的集合"——名字一样、东西不一样，巨坑。

**为什么是骨架**：任何做"加载+缓存+显示"的系统都需要这三态分离。混淆了就会出现"以为显示了其实没显示"、"以为下载了其实过期了"之类的 bug。换什么项目都不变。

**实现形态**：`ChunkDataStore` 管"原始数据缓存"（下载了没）、`ChunkCoordinator` 管"在途请求登记"（正在下载中）、`WorldRenderer` 管"已渲染集合"（画面上有没）。三个状态各有一个所有者，不能混。

#### 骨架 4：过期守卫——晚到的数据不准污染世界

**大白话**：HTTP 请求发出去之后，玩家可能已经走到别的地方了，甚至整页都关了。数据回来的时候必须再检查一遍：世界还活着吗？这块还在目标集合里吗？有一个不满足，数据就不准往画面写。

就像你搬家之后，之前点的外卖如果还送到旧地址，骑手应该被告知"地址变了"而不是硬把外卖堆在旧门口。分块系统的过期守卫就是那个告诉骑手"别送了"的人。

**为什么是骨架**：异步请求 + 用户操作 = 必然出现"请求发出时和请求回来时世界已经不一样了"。任何网络请求的代码都需要这种守卫，跟具体项目无关。

**实现形态**：回调中检查 `destroyed` 标志和坐标是否仍在当前目标集合内；`AbortSignal` 支持请求取消；销毁时 `destroyAsync()` 先禁止新写入、等请求收敛、再到 mutation idle、最后释放资源。

#### 骨架 5：首屏预载 + 运行时动态装卸的切换

**大白话**：游戏开场的航拍镜头需要飞到天上俯瞰整个校园——这时候需要看到全部地图，所以一次性预载 25 块。航拍结束、玩家可以操控小人后，切换到"只加载周围"的动态模式。

就像搬家——搬家公司的大卡车一次性把全部家具拉到楼下（预载），然后工人一件一件往房间里搬（动态装卸）。两个阶段用同一套装/卸能力，只是"目标集合"的口径不同：预载阶段的目标集合 = 全部 25 块，正常阶段的目标集合 = 玩家周围。

**为什么是骨架**：很多游戏都有"过场动画需要看到全图"的场景。预载的本质就是把目标集合临时扩大到全部区域——不改变装/卸的基本能力，只是临时换了一个更大的目标集合。这个模式换什么游戏都通用。

**实现形态**：相机展示序列汇总多个视口 → 预载范围额外扩展 2 块边距 → Set 去重 → `requestIdleCallback`（或 `setTimeout` fallback）逐项加载。Play 开始后的目标集合切换回玩家 3×3 ∪ 相机 +1。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| 世界尺寸 | 140×140 格，tile 16×16 像素 | 可以任意大小：80×80、200×200、甚至不规则 |
| 分块大小 | 28×28 格/块 | 可以改成 32×32 或 64×64，取决于性能和网络权衡 |
| 分块网格 | 5×5（共 25 块） | 3×3=9 块 或 8×8=64 块，数学上自动适配 |
| 索引公式 | `index = y * 5 + x`（行主序） | 公式里的 5 换成新的 `nbChunksHorizontal` |
| 目标更新间隔 | 约 500ms | 可以调快（200ms，更灵敏但更耗 CPU）或调慢（1000ms） |
| 玩家邻域大小 | 3×3（9 块） | 可以改成 5×5（如果玩家跑得很快需要预加载更远） |
| 相机额外边距 | +1 块 | 可以 +2 块（更保守，更不容易看到空白） |
| 航拍预载边距 | +2 块（相机序列） | 可能不需要航拍，或航拍范围不同 |
| 数据文件名 | `chunk{index}.json`（chunk0~chunk24） | 文件名格式可以完全不一样 |

### 三、配置点（将来后端改几个数字就能换皮）

| 能改什么 | 啥意思 | 现在 Peter 的值 |
|---|---|---|
| 分块大小（格数） | 每块地图多少格 × 多少格 | 28 × 28 |
| 分块网格维度 | 横向几块、纵向几块 | 5 × 5 |
| 目标更新间隔 | 多久重新算一次"该加载哪些块" | ~500ms |
| 玩家邻域范围 | 以玩家所在块为中心，周围扩展几块 | 3×3 |
| 相机额外边距 | 相机可见范围外再多加载几块 | +1 |
| 航拍预载边距 | 航拍序列中相机范围外多扩展几块 | +2 |
| 最大重试次数 | 同一块加载失败后最多重试几次 | 未定（当前不做无限自动重试） |
| 数据文件 URL 模板 | chunk 文件的下载地址格式 | 硬编码在 `ChunkDataStore` 的 URL 拼装中 |

## 跟谁接口（它和谁打交道）

```
                         ┌──→ [世界与地图]    给它：坐标 + 已验证的 chunk 数据
                         │     接收：写入成功 / 已存在 / 写入失败
                         │
                         ├──→ [图层与遮挡]    给它：（触发写入/清除信号）
[SYS-PLAYER 玩家] ──┐    │     接收：每层的 GID 过滤和深度策略
                    │    │
                    ├──→ [SYS-CHUNK 地图分块]
                    │    │
[SYS-CAMERA 相机] ──┘    ├──→ [资源加载]      给它：数据请求（通过 ChunkDataStore 发 fetch）
                         │     接收：原始 JSON 数据或失败记录
                         │
                         └──→ [验证/诊断]    给它：目标集合、请求状态、缓存、渲染、失败的完整记录
```

分块系统是**地图线的"调度员"**——它接收玩家位置和相机范围两个输入，算出目标集合，然后调度数据请求、画面写入和画面清除。它自己不下载文件（委托资源系统）、自己不操作 Tilemap（委托世界系统）、自己不决定层怎么处理（委托图层系统）——它只管一件事：**什么时侯该加载哪几块、什么时候该撤掉哪几块。**

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 块接缝像素不对齐 | 两块 28×28 拼在一起的缝，如果坐标换算差 1 像素，接缝处会有一根黑线或画面错位。原站用 gradient 边缘来掩盖，但根源是坐标换算必须精确 |
| 两个 "loadedChunks" 名字一样意思不同 | 原站代码里 chunk manager 的 `loadedChunks` 表示"已下载 JSON"，GameScene 的 `loadedChunks` 表示"已画到画面"。名字一样但东西不一样，如果不分开建模，状态一定会乱 |
| 下载了的块 ≠ 画面上的块 | 一块数据下载成功了，不代表它应该立刻显示——可能玩家已经走远了，可能世界正在销毁。必须再检查一次才往画面写 |
| 晚到数据污染已销毁的世界 | HTTP 请求发出后，用户关了网页。数据回来时如果还往 Tilemap 里写——Tilemap 已经销毁了，直接报错或崩溃 |
| 卸载太快导致"回头一片白" | 玩家稍微走远了一点，分块系统立刻把那块撤掉。但如果玩家马上回头——那块还没加载回来，画面闪白。所以卸载要留一点"缓冲区" |
| 预载和动态装卸的切换时机 | 航拍还没结束就开始动态装卸，或者航拍结束了预载还没完毕——过渡时机不对会看到地图"跳变" |
| 同块重复请求不合并 | 同一块被两个目标集合更新周期同时触发加载——如果不做"在途去重"，会发两份 HTTP 请求，浪费带宽 |
