# 世界交互·弹窗（SYS-INTERACT）—— "游戏里的电视遥控器"

> 📌 进度：📐 设计已定稿 + 确定性 CORE 已实现 —— `InteractRuntime` 纯逻辑状态机已通过 14 项测试，`DomModalGameUi` DOM 渲染层已通过 30+ 项测试，11 个 menuId 内容已填充（2026-09-02）

---

## 一句话讲清楚

**弹窗系统 = 游戏里的一台电视——玩家走到特定位置，电视自动打开并暂停游戏，看完关掉，游戏继续。**

你走到一个展品前（区域触发系统告诉你"到了"），电视就打开，显示那个展品的介绍内容。电视一打开，游戏就暂停了——你不能一边看电视一边操控小人，会分心。看完了，你可以按三个地方关掉：电视上的关闭按钮、按 ESC 键、或者点电视外面的黑色遮罩。关掉后游戏恢复，你继续逛。

同一时间只能开一台电视——如果你正看着"About Me"，走进了"Projects"的区域，About Me 会被 Projects 替换掉，不会两台电视一起开。

---

## 它管哪些事

| 管的事 | 大白话 | 不管的事 |
|---|---|---|
| 打开弹窗 | "该显示内容了" | 不判断"什么时候该弹"——那是 SYS-ZONE 的事 |
| 关闭弹窗 | "收起来" | 不判断"什么时候该收"——SYS-ZONE 说 leave 时它才收 |
| 暂停/恢复游戏 | "看电视时不能走路" | 不管暂停的具体实现——lease 只发"停""开"信号 |
| 根据 menuId 找到内容 | "给我看 memo3 的内容" | 不维护内容本身——内容在 resolver 里 |
| 三路关闭 | 按钮 / ESC / 点遮罩 | 不处理其他按键 |
| 手动关闭后不再弹 | "你关了，不烦你"（直到离开区域） | 不管理 visited 统计——那是 SYS-ZONE 的事 |
| 安全销毁 | "页面关了，弹窗也要干净收摊" | — |

> **骨架** = 换什么校园都不变的做事方式
> **皮**   = 跟 Peter 这个具体项目绑定的内容

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：单内容状态机（同时只显示一个）

**大白话**：同一时间屏幕上只有一个弹窗。如果正在看 A，B 来了——A 被 B 替换掉，不叠加。

就像电视——你不能同时看两个频道。换了新频道，旧的就被替换了。

状态机有三个关键判定：
- **已提交的**（committed）：这个 residence 已经显示过了 → 忽略
- **被抑制的**（suppressed）：你手动关了，还没离开区域 → 不弹
- **当前激活的**（active）：屏幕上正显示的这个

**为什么是骨架**：单内容替换模式是所有模态系统的通用做法——换什么校园、什么内容都不变。

**实现形态**：`InteractRuntime` 在 `handleResidenceEvent()` 中做 enter 判定：先查 suppressed → 再查 committed → 再尝试 show。如果有已激活的内容，新内容替换时不重新获取 lease。

#### 骨架 2：内容查找（menuId → 标题+正文+图片）

**大白话**：弹窗系统自己不知道 memo3 里面写的是什么——它问"内容解析器"要。

就像去图书馆，你告诉管理员"我要借 ISBN 978-xxx 那本书"，管理员去书库里把书找出来给你。弹窗系统只负责把书"摆到桌面上"，不负责书里写了什么。

内容解析器是一个接口（`ContentResolverPort`），只有一个方法：`resolve(menuId)` → 返回 `{ title, body, sections? }`。

**为什么是骨架**：触发和内容分离是通用设计——换校园不用改弹窗逻辑，只换 resolver 的内容就行。

**实现形态**：`InteractRuntime` 通过构造函数注入的 `resolver: ContentResolverPort` 查找内容。resolve 返回 `"resolved" | "missing" | "invalid"` 三种状态。

#### 骨架 3：游戏控制租约（暂停/恢复）

**大白话**：弹窗打开时，需要"借走"游戏控制权——玩家不能走动。关闭时"还回去"。

就像你去银行办事，柜员说"请稍等，我查一下"——你暂时不能办其他业务。弹窗系统通过"租约"模式管理这个过程：

- `acquire("modal-open")` → 拿到一把"钥匙" → 游戏控制被暂停
- `release(token)` → 归还钥匙 → 游戏控制恢复

租约可能失败（比如游戏正在关机），弹窗系统对此有完整的防御：如果 lease 获取失败，弹窗就不打开。

**为什么是骨架**：任何"弹窗覆盖游戏"的场景都需要暂停/恢复机制。

**实现形态**：`InteractRuntime` 通过构造注入的 `lease: GameplayControlLeasePort` 管理控制权。`acquire()` 返回 `{ ok: true, token }` 或 `{ ok: false, reason }`。release 失败时 token 进入 `pendingReleaseTokens` 队列等待重试。

#### 骨架 4：三路关闭 + 安全防护

**大白话**：弹窗可以通过三条路关闭——关闭按钮、ESC 键、点击遮罩。不管走哪条路，关闭流程都是统一的。

关闭流程：
1. 收到关闭信号 → 校验：这是当前激活的弹窗吗？（menuId + residenceId 双重校验）
2. 调用 UI 的 `hide()` → 从屏幕上移除
3. 把这个 residence 写入抑制集合 → 同一 residence 不重弹
4. 释放游戏控制租约 → 恢复游戏

双重校验（menuId + residenceId）是安全关键——防止"旧的关闭事件"误关"新的弹窗"。比如你从 About 换成了 Projects，此时 About 发送的关闭事件会被忽略（residenceId 不匹配）。

**为什么是骨架**：关闭机制 + 防误关的校验是所有模态系统的通用需求。

**实现形态**：`DomModalGameUi` 监听 closeButton click、backdrop click、ESC keydown 三种事件。`InteractRuntime.handleUserClose()` 做 identity 校验（`sameIdentity` 比对 menuId+residenceId）。`suppressedResidences` 集合在 `handleUserClose()` 中写入，在 `handleLeave()` 中清除。

#### 骨架 5：安全生命周期（销毁不泄漏）

**大白话**：弹窗系统销毁时——不管是用户关网页、场景切换、还是出错——必须把所有东西收干净，不能留"僵尸"。

销毁顺序：
1. 取消订阅（不再监听关闭按钮、键盘、窗口大小变化）
2. 如果还有弹窗开着 → `hide()` 关掉
3. 销毁 UI 层
4. 释放所有租约（包括之前 release 失败、还在重试队列里的）
5. 清空所有内部状态

每一步都可能失败（因为依赖的外部模块可能已经挂了），但失败不能阻断后续清理——这是"尽力而为"清理模式。

**为什么是骨架**：任何 UI 系统的生命周期管理都需要这套安全销毁流程。

**实现形态**：`InteractRuntime.destroy()` 和 `DomModalGameUi.destroy()` 都实现了幂等（重复调用安全）和 best-effort（单步失败不阻断整体）的清理流程。

## 跟谁接口（它和谁打交道）

```
                    ┌──→ [SYS-GAME-UI 弹窗渲染]
                    │    给它：GameUiShowRequest { menuId, residenceId, payload, presentation }
                    │    要它：ShowResult | HideResult
                    │
[SYS-ZONE] ──→ [SYS-INTERACT] ──→ [SYS-GAME-UI / 内容层]
  区域触发         弹窗系统         给它：渲染指令
  给：事件           │
                    ├──→ [ContentResolver]
                    │    问它：resolve(menuId) → { title, body, sections }
                    │
                    └──→ [GameplayControlLease]
                         借：acquire("modal-open") → token
                         还：release(token)
                         重试：retryPendingReleases()
```

**一句话**：SYS-INTERACT 是"中间人"——它不产内容、不画 UI、不管游戏暂停怎么实现。它只是把 Zone 的触发信号翻译成 Render/Resolve/Lease 三条指令，并确保不会开两台电视、不会误关、不会泄漏。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 误用 residenceId 校验 | 关闭/离开事件必须同时匹配 `menuId` 和 `residenceId`。如果只匹配 menuId——比如你从 About 换到了 Projects，About 的关闭事件会误关掉 Projects 弹窗 |
| 手动关闭后忘了抑制 | 用户点了 × 但你忘了设 suppressed → 下一帧（100ms 后）Zone 又检测到玩家在范围内 → 又弹出来 → 用户再关 → 再弹……循环闪烁 |
| 遮罩点不了的弹窗没遮罩 | sunburn 类弹窗 backDrop 是 "none"，但它们仍然可以点 backdrop 关闭。如果 backdrop click handler 不检查当前弹窗的 backdrop 类型 → 点空白区域关了不该关的弹窗 |
| 销毁时泄漏 lease | `destroy()` 时如果 activeToken 或 pendingReleaseTokens 没有被释放 → 游戏控制永远不恢复 → 玩家动不了 |
| hide 失败了也不回滚 | 关闭流程中 hide 返回 `target-mismatch` 或 `destroyed` 时，不能继续清除 activeState 和释放 lease——必须先修好"屏幕上的东西"才能清状态，否则状态和数据不一致 |
| DOM 元素缺失 | `DomModalGameUi` 依赖 6 个 DOM 元素（root/backdrop/modal/title/body/closeButton），缺任何一个 `show()` 返回 `"missing-target"`——如果 HTML 模板改了但忘了同步，弹窗静默失效 |
| 图片 404 不兜底 | memo 卡片有图片，图片加载失败时 `handleRichImageError` 会隐藏 img 显示 fallbackText。但如果 fallback 也没设 → 空白区域 |
| 替换时多拿了 lease | 有 activeState 时替换内容不应再 `acquire()` —— 已经借过钥匙了。如果每次替换都 acquire → 一个弹窗持有多个 lease → release 时可能少还，游戏永远暂停 |
