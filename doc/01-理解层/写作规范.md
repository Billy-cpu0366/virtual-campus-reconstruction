# 系统文档写作规范

> 本文档定义了"理解层"和"执行层"两套文档的标准写法。
> 新对话拿到这份规范，就能把任意一个系统写到和 SYS-ASSET 同等质量。

---

## 核心原则

```
理解层 = 人话 + 框架（给人类建立心智模型，分清骨架和皮）
执行层 = 精确 + 落位（每个骨架和皮落到代码位置）

理解层不堆砌细节，执行层不堆砌术语。
两份文档用"骨架/皮/配置点"三件套对齐。
```

---

## 一、写之前必须读的东西

拿到一个系统（如 SYS-WORLD），先按顺序读：

| 顺序 | 文件 | 目的 |
|---|---|---|
| 1 | `AGENTS.md` | 了解项目定位和规则 |
| 2 | `01-理解层/00-系统地图.md` | 看清 16 系统全貌、串并行关系、优先级 |
| 3 | `01-理解层/00-进度总览.md` | 知道当前系统处于什么状态 |
| 4 | `03-执行层/00-总账.md` | 了解本系统的理解/工程/验证状态和未知队列 |
| 5 | 本规范 | 知道怎么写 |
| 6 | 本系统现有的理解层卡 | 知道已经写了什么 |
| 7 | 本系统现有的执行层卡 | 知道已经细化了什么 |
| 8 | 实际代码（`src/`、`game/`、`tests/`） | 验证"代码实际做了什么"和"文档说的"是否一致 |

---

## 二、理解层的写法

### 定位

```
理解层 = 给人类看的大框架。
一个完全不懂技术的人读完，应该能说出：
  1. 这个系统是干嘛的
  2. 它怎么跑通的
  3. 哪些东西是通用的（骨架），哪些是 Peter 专属的（皮），哪些将来可以改（配置点）
```

### 固定结构

```markdown
---
tags: [虚拟校园, 理解层, 系统卡]
system: SYS-XXXX          ← 系统编号
priority: P0 / P1 / P2    ← 优先级
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# 系统名（SYS-XXXX）—— "一句话比喻"

> 📌 进度：当前状态图标 + 一句话

---

## 一句话讲清楚

**用最通俗的一句话 + 一个生活比喻说清楚这个系统是干嘛的。**
比喻要选日常生活中人人都懂的场景（物流、餐厅、快递、工地……）。

---

## 它管哪些事

一个表格，三列：管的事 | 大白话 | （可选）不管的事
边界要说清楚——这个系统到哪为止，后面归谁管。

---

## 走一遍（从用户视角）

用 ASCII 流程图，从用户打开网页/进入游戏开始，
一步一步画到本系统的工作完成。
每步用大白话，不出现技术名词。

---

## 🎨 核心：皮与骨架拆分

> 骨架 = 换什么校园都不变的做事方式
> 皮   = 跟 Peter 这个具体项目绑定的内容
> 配置点 = 将来后端管理系统可以改的参数

### 一、骨架（5 项左右）

每个骨架分三段写：
1. **大白话**：用日常比喻解释（不许出现代码/技术名词）
2. **为什么是骨架**：一句话说明为什么换校园它不变
3. **实现形态**：一句话说代码里大概是怎么做的（可以说技术名词）

### 二、皮（和骨架数量对应）

一个表格，三列：
| 皮 | 当前值（Peter） | 换成其他校园会怎样 |

### 三、配置点

一个表格，三列：
| 能改什么 | 啥意思（大白话） | 现在 Peter 的值 |

### 四、骨架总结图

一张 ASCII 图，左右或上下对齐：
左边/上面是骨架（通用流程），右边/下面是皮（具体内容），
用箭头表示皮怎么接到骨架上。

---

## 跟谁接口

ASCII 图 + 文字说明：本系统给谁提供什么，从谁那里接收什么。

---

## 容易踩的坑

表格：| 坑 | 为什么坑 |
每个坑用大白话解释，不堆技术名词。
```

### 语言标准

- ✅ "就像你去餐厅吃饭，不管什么菜系，流程都是进门→点菜→等餐→开吃"
- ❌ "采用状态机模式管理加载生命周期，通过回调接口驱动 UI 更新"
- ✅ "货拉不回来怎么办？原站的做法是吼一嗓子，然后不管了"
- ❌ "失败处理策略为 console.error，无重试/降级/fallback 机制"
- ✅ "代码里不写死'下载第1到第16块'，而是读一份清单，清单上有什么就下载什么"
- ❌ "通过元数据驱动的资源发现机制，从 tilesets 数组动态推导切块集合"

---

## 三、执行层的写法

### 定位

```
执行层 = 骨架和皮落到代码上。
每个骨架 → 精确到文件路径 + 行号 + 关键代码片段。
每张皮 → 精确到常量名 + 所在文件。

但！仍然要保持人话，不要变成代码堆砌——
每个代码片段前面，先用一句话说清楚"这一段在干什么"。
```

### 固定结构

```markdown
---
tags: [虚拟校园, 执行层, 系统卡]
system: SYS-XXXX
status: designed / implemented / verified
updated: YYYY-MM-DD
---

# 系统名（SYS-XXXX）—— 执行层细化

> 对照理解层的 X 个骨架 + X 张皮，逐一落到代码位置。

---

## 👀 先看这里（给 Human 的人话总结）

**当前状态**：一句话说清楚现在做到哪了。
**还没做的**：一句话说清楚还缺什么。

---

## 总览图：骨架→代码 对照

一张 ASCII 图，把理解层的骨架总结图"翻译"成代码视角：
左边/上面是骨架名称 → 右边/下面是对应的代码文件。

示例：
```
骨架                          代码
─────────────────────────    ─────────────────────────
① 固定的流水线               src/app/runtime.ts
② 实时报进度                 game/CampusScene.ts (preload)
③ 图片和数据分开运输           Phaser Loader + fetch
④ 按清单下载                 src/asset/tilesets.ts
⑤ 取消 / 清理 / 重来          src/app/runtime.ts (cleanup)
```

---

## 一、骨架落地

### 骨架 1：[理解层的骨架名]

> 引用理解层的人话解释。
> 在代码里，这个东西叫 [模块名]。

**它怎么工作的**：
用纯文字/简单图示解释这段代码的逻辑，不贴代码。
讲清楚"输入是什么 → 做了什么 → 输出是什么"。

**代码在哪**：
一个表格，| 做什么 | 文件路径 + 行号 | （可选）关键常量/函数名 |

**怎么验证它做对了**：（可选）
有测试就说测试文件，没测试就说怎么手动验证。

（骨架 2 ~ 骨架 N 重复上述结构）

---

## 二、皮落地

一个表格：
| 皮 | 精确值 | 在哪（文件路径+行号） |

---

## 三、配置点

一个表格：
| 能改什么 | 现在硬编码在哪 | 现在的值 | 将来 |

---

## 四、测试覆盖（如果有的话）

| 测试文件 | 测什么 |

---

## 五、所有代码位置一页速查

```
src/xxx/
  file1.ts  — 一句话说明
  file2.ts  — 一句话说明

game/
  file3.ts  — 一句话说明

tests/xxx/
  file4.test.ts — 一句话说明
```
```

### 语言标准

执行层的"怎么做"部分可以出现技术名词（状态机、回调、接口），但**必须先用一句人话解释它是什么**。

- ✅ "在代码里，这条流水线叫 AppRuntime。它就像一个交通指挥员——管着'现在是什么状态'和'能不能从 A 状态跳到 B 状态'。"
- ❌ "AppRuntime 管理 AppStatus 状态机的状态迁移，通过 AppRuntimeEffects 注入副作用。"
- ✅ "进度值只能增加不能倒退。如果有代码试图报一个比之前小的值，reportProgress() 直接忽略它——防止进度条倒着走。"
- ❌ "reportProgress 实现单调递增校验，非法 ratio 被拒绝。"

## 四、写作检查清单

写完一个系统的理解层 + 执行层后，逐项检查：

### 理解层检查

- [ ] 办公室大妈能读懂"它是什么"和"走一遍"吗？
- [ ] 骨架数量 5±2 个，每个都有大白话 + 日常比喻吗？
- [ ] 皮的和骨架一一对应吗？（骨架有"进度汇报"，皮就有"进度权重"）
- [ ] 配置点都答了三个问题：能改什么？现在多少？将来怎么改？
- [ ] 跟谁接口画了 ASCII 图吗？
- [ ] 容易踩的坑说了"为什么坑"吗？

### 执行层检查

- [ ] 开头有"总览图：骨架→代码对照"的 ASCII 图吗？
- [ ] 每个骨架落到了具体文件路径 + 行号吗？
- [ ] 每张皮落到了具体常量/字符串/函数名吗？
- [ ] 每个代码片段前面有一句人话解释吗？
- [ ] 代码位置汇总可以当速查表用吗？
- [ ] 理解层的骨架/皮/配置点数量和执行层一致吗？

## 六、新对话启动流程

新对话开始，拿到一个系统名（如 SYS-WORLD），按以下步骤走：

```text
1. 读本规范（这个文件）
2. 读 AGENTS.md（了解项目结构）
3. 读 01-理解层/00-系统地图.md（知道串并行关系）
4. 读 03-执行层/00-总账.md（知道当前状态）
5. 读本系统现有的理解层卡 + 执行层卡（知道已经写了什么）
6. 读本系统的实际代码（src/ + game/ + tests/ 中相关文件）
7. 按本规范 §二 写理解层
8. 按本规范 §三 写执行层
9. 按本规范 §四 自查
```

**禁止**：没读代码就写执行层；没读系统地图就写理解层；没读本规范就开始动笔。
