## 一句话讲清楚

**实体生命周期系统 = 游戏里所有"活的东西"（玩家、NPC、车辆、粒子……）从出生到死亡的统一管理规则。**

就像一个剧组的场务——他的工作不是演戏，而是保证：开拍前演员到场（创建）、拍摄中演员在状态（活跃）、拍完后演员离场（销毁）、道具和灯光全部归位（清理）、万一中途停拍也能把现场收干净（回滚）。不管拍什么戏、换什么剧组，这套"进场→工作→退场→收工"的流程是一样的。

---

## 它管哪些事

| 管的事    | 大白话                                      | 不管的事                                 |
| ------ | ---------------------------------------- | ------------------------------------ |
| 实体创建   | 一个新东西（NPC/车辆/粒子效果）怎么"出生"——需要什么资源、注册到哪些系统 | 不管具体这个NPC长什么样——那是SYS-NPC的事           |
| 实体活跃期  | 实体在游戏里"活着"时怎么更新、怎么和别的系统互动                | 不管具体怎么移动——那是SYS-MOVE的事               |
| 实体销毁   | 一个实体"死了"之后怎么清理——移除监听器、销毁Phaser对象、释放内存    | 不管"什么时候该死"——那是各自系统的业务逻辑              |
| 有序清理序列 | 游戏关停时，先关谁后关谁有固定顺序（比如先关玩家再关相机再关地图），不能乱    | 不管具体每个系统怎么关自己——每个Runtime自己实现shutdown |
| 代际隔离   | 点Retry后，旧一代的所有东西全部作废，新一代从头开始。旧的回调不能影响新一代 | 不管具体每一代里加载什么——那是SYS-ASSET的事          |
| 清理收据   | 关停完成后出一份报告，说清楚关了哪些东西、有没有残留               | 不管报告的格式和存储                           |

**它不管的事**：具体每个实体怎么渲染（归各Runtime）、实体之间怎么碰撞（归SYS-MOVE）、什么时候创建/销毁实体（归各业务系统）。

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：统一的生命周期接口

**大白话**：游戏里每一种"活的东西"——不管是玩家、NPC、车辆、还是粒子效果——都要遵守同一套规矩："会创建、会更新、会销毁、关了能清干净"。

就像公司里所有员工——不管你是前台还是程序员还是经理，入职（创建）、上班（活跃）、离职（销毁）、交接（清理）的流程是一样的。具体干什么活不一样，但"入职表"和"离职手续"是统一的。

**为什么是骨架**：任何有大量动态对象的游戏都需要统一的生命周期管理。否则每个对象"怎么生、怎么死"各写各的，必然有人漏清理。

**实现形态**：所有 Runtime 都提供 `shutdown()` 或 `destroy()` 方法。每个方法负责清理自己管理的 Phaser 对象（sprites、colliders、emitters、timers、listeners）。没有统一的抽象基类，但接口约定一致。

#### 骨架 2：有序清理序列

**大白话**：关停游戏时不能乱关——必须先关"被依赖的"再关"依赖别人的"。比如先关玩家（依赖输入系统），再关输入系统（没人依赖它了）。

就像拆楼——不能先拆一楼的地基再拆二楼的墙。得从上往下拆：先拆家具→再拆墙→最后拆地基。否则楼会塌。

**为什么是骨架**：任何有依赖关系的系统集合都需要有序关闭。顺序不对会导致"被依赖方已销毁、依赖方还在引用它"的崩溃。

**实现形态**：`CampusScene.performShutdown()` 按写死的顺序逐个清理，共 **30 个 `cleanup()` 步骤**：入场动画→喷水器→路线人群→静态NPC→静态人群→虫子群→场馆人群→跳舞人群→AI烟雾→雾效→警车碰撞器→车辆→工厂烟→火车→入场相机→入场火车→相机→相机租约→地图→区域触发→世界交互→内容租约→屋顶补间→脚印→玩家→玩家插值器→摇杆→移动→mutation 调度器→测试钩子；之后摘 4 个原生监听器、`await shutdownDynamicWorld()`（世界数据）、`scene.stop()`。完整顺序见[执行层卡 §一·骨架2](../../03-执行层/04-独立件/03-实体生命周期.md)。

**容错方式**：每一步都包在 `cleanup(name, op)` 里——单步抛错只记一笔（`failures` + `sideFailures`），**不中断后续**；全部跑完后若有失败，统一抛 `AggregateError`（此时收据不产出）。

#### 骨架 3：代际隔离

**大白话**：每一代加载有一个编号。旧代的回调（比如下载完了该更新进度条了）如果发现自己在旧代，就自动忽略——不污染新一代。

就像餐厅排队叫号——你拿的是12号，如果餐厅已经叫到15号了，12号的菜就不会再上了。每次Retry就是新一代，旧代的"菜"全部作废。

**为什么是骨架**：任何涉及异步操作和重试的系统都需要代际隔离。否则旧异步回调在Retry后继续执行，会把新状态搞乱。

**实现形态**：`AppRuntime` 的 `generation` 字段每次 `beginLoading()` 自增1。`game/main.ts` 中所有回调在执行前先调 `isCurrent(generation)` 检查。`CampusScene.sceneDestroyed` 标志位也在 `performShutdown()` 中被设为 `true`，后续异步操作检查此标志并提前退出。

#### 骨架 4：引用计数控制租约

**大白话**：当弹窗打开时，玩家不能动。但弹窗可能不止一个来源——内容弹窗、地图弹窗都可能导致"停住玩家"。怎么知道什么时候该停、什么时候该恢复？用引用计数——每开一个弹窗计数+1，每关一个弹窗计数-1，计数归零时恢复玩家控制。

就像会议室预订系统——第一个预约的人开灯，最后一个离开的人关灯。不是每个人离开都关灯，只有最后走的人才关。

**为什么是骨架**：任何有多来源共享资源的系统都需要引用计数。否则A关了某个资源，B还在用，就冲突了。

**实现形态**：`GameplayControlLeaseRuntime` —— `acquire()` 创建token（计数+1，首次时调用 `disableControls`），`release(token)` 释放（计数-1，归零时调用 `enableControls`），`shutdown()` 强制全部释放。租约带"来源标签"，目前 **4 种**都已实际使用：`modal-open`（世界交互弹窗）、`map-open`（地图）、`camera-tour`（相机航拍）、`entry-transition`（入场转场）。已释放的旧凭证用 `WeakSet` 记录，判定 stale 的同时不会拖住内存。

#### 骨架 5：清理收据

**大白话**：关停完成后，系统出一份"账本"——关了哪些、剩了什么、有没有异常。这份报告用于验证"是不是真的清干净了"。

就像退房时的检查清单——"床单换了✓、毛巾补了✓、垃圾倒了✓、窗户关了✓"。每项打钩后，才算确认退房完成。

**为什么是骨架**：任何需要验证清理结果的系统都需要结构化收据。否则"关了但没关干净"的bug极难排查——它只会在下次运行时才暴露（内存泄漏、幽灵对象）。

**实现形态**：`CampusScene.performShutdown()` 返回 `CampusSceneShutdownReceipt`，包含 trainColliderActive、sprayerSpriteCount、smokeEmitterActive、footstepActiveCount、physicsColliderCount 等 **18 个**字段。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| 有多少个东西需要清理 | **30 个清理步骤**（25 个对象 + 5 个方法调用）：25 个对象是 entryRuntime、sprayerRuntime、routeCrowdRuntime、staticNpcRuntime、staticCrowdRuntime、bugCrowdRuntime、venueCrowdRuntime、dancingCrowdRuntime、stopAiSmokeRuntime、fogRuntime、vehicleRuntime、smokeRuntime、trainRuntime、entryCameraRuntime、entryTrainAdapter、cameraRuntime、mapRuntime、zoneRuntime、interactRuntime、contentLeaseRuntime、footstepRuntime、playerRuntime、playerVisualInterpolator、joystick、mutationScheduler | 数量会变——有的校园没火车、没烟雾、没跳舞人群 |
| 清理顺序 | 入场动画→喷水器→路线人群→静态NPC→静态人群→虫子群→场馆人群→跳舞人群→AI烟雾→雾效→警车碰撞器→车辆→工厂烟→火车→入场相机→入场火车→相机→相机租约→地图→区域触发→世界交互→内容租约→屋顶补间→脚印→玩家→玩家插值器→摇杆→移动→mutation调度器→测试钩子 → 摘4个原生监听器 → 世界数据 → 停场景 | 不同的依赖关系会导致不同的顺序——比如如果玩家依赖NPC，就应该先关NPC再关玩家 |

### 三、配置点（将来后端改几个数字就能换皮）

> **字段级明细见** [换皮配置总表 §13 SYS-ENTITY 实体生命周期](../../换皮配置总表.md#13-sys-entity-实体生命周期)。
> 本表只回答「这一类能不能配」；逐字段的**配置键、类型、默认值、生效时机、作用域、交付形态**，以及**实例数据**（每个对象的具体值），都在总表那一节。

| 能改什么 | 啥意思 | 现在 Peter 的值 |

| 清理时是否保存状态 | 关停前是否自动保存玩家位置 | 不保存 |
| 异步清理的重试次数 | shutdown中的异步操作失败了重试几次 | 不重试 |

## 跟谁接口（它和谁打交道）

```
                         ┌──→ [SYS-APP 应用启动]   提供：shutdown触发信号
                         │                        接收：清理收据
[SYS-ENTITY 实体生命周期] ─┼──→ [所有Runtime系统]     提供：shutdown/destroy调用
                         ├──→ [SYS-PLAYER 玩家]     提供：控制租约(暂停/恢复移动)
                         ├──→ [SYS-WORLD 世界]      提供：Tilemap/world data销毁
                         └──→ [SYS-ASSET 资源加载]   提供：取消进行中的下载
```

实体生命周期是**所有系统的"退场导演"**——它不管演出内容，但确保演出结束后台上不留任何东西。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 漏清理事件监听器 | Phaser的sprite.destroy()不会自动移除window上的事件监听。如果忘了手动 `removeEventListener`，关了游戏后键盘事件还在回调——但sprite已经没了，就会报错 |
| 清理顺序不对导致引用崩溃 | 如果先销毁了世界数据再关玩家——玩家shutdown时可能还要查询"当前在哪个chunk"，但chunk数据已经没了→空指针崩溃 |
| 旧代异步回调污染新代 | `performShutdown()` 中有 `await this.dynamicWorldShutdown`。如果用户在异步等待期间又点了Retry，新代的初始化可能和旧代的销毁同时跑→竞态条件。`sceneDestroyed` 标志位和 `isCurrent(generation)` 就是防这个的 |
| 控制租约泄露 | 弹窗打开时 `acquire()` 拿了token，但如果弹窗因为某种原因没正常关闭（比如直接destroy了modal但没调hide），token永远不会被 `release()`→玩家永远不能动。`GameplayControlLeaseRuntime.shutdown()` 是最后的安全网 |
| Phaser物理碰撞器残留 | `performShutdown()` 中逐个关Runtime时，trainRuntime关了但Phaser的碰撞器可能还活着。收据中的 `physicsColliderCount` 字段就是用来检查这个的——如果关完后碰撞器数量>0，说明有残留 |
| 没有统一的实体基类 | 当前每个Runtime独立实现shutdown，没有强制接口。这意味着加一个新的Runtime时可能忘了实现shutdown→那个Runtime的实体永远不会被清理。`Q-ENTITY-001` 已查清：**原站也没有统一实体基类**（公开 Bundle 的 13 个类全部直接继承 Phaser 内置类），所以这是刻意保留原站做法，不是遗漏 |
| 清理有失败时收据不产出 | 每一步都有 try/catch，失败**不会**中断后续；但 30 步全部跑完后会统一抛 `AggregateError`，而抛点在收据构造**之前**——只要有一处失败，调用方就拿不到收据。"是不是清干净了"这个问题在有失败时没法用收据回答，得改看 `AggregateError.errors` 或 `sideFailures` 里的 `cleanup:<名字>` 条目 |
| 失败后重试是"补跑"不是"重跑" | 第一次失败时，一部分引用已经被置空（`entryRuntime`、`cameraRuntime`、`mapRuntime` 等），第二次调用不会碰它们。如果那些引用在失败前其实没清干净，补跑补不上，理论上会残留 |
