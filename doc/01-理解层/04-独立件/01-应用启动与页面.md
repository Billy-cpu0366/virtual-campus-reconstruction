# 应用启动与页面（SYS-APP）—— "大楼的前台"

> 📌 进度：🟡 懂一半 —— 状态机和DOM壳已定稿；完整错误恢复和页面生命周期未确认

---

## 一句话讲清楚

**应用启动系统 = 从你打开网页到游戏能玩的整条入口流水线。**

就像一栋大楼的前台——你进门后不是直接冲到办公室，而是先经过前台登记（加载页）→ 拿访客牌（进度条跑满）→ 等叫号（Play按钮亮起）→ 进去（点Play进游戏）。不管这个大楼是Peter的校园、某学校的官网、还是某公司的展厅，"进门→登记→等待→进入"这条流水线都是一样的。不同的是前台墙上挂什么画、登记表长什么样。

---

## 它管哪些事

| 管的事 | 大白话 | 不管的事 |
|---|---|---|
| 页面状态流水线 | 从"刚打开网页"到"正在玩游戏"，一共9种状态，每种状态之间能不能跳、怎么跳，这个系统说了算 | 不管游戏里面怎么渲染地图、不管小人怎么走 |
| DOM外壳渲染 | 加载页（白底+GIF+进度条）、Ready页（Logo+Play按钮）、错误页（Retry按钮）——这些网页元素归它管 | 不管Canvas里面画什么 |
| Phaser游戏实例的生与死 | 点Play创建游戏实例，关网页/出错时销毁游戏实例 | 不管游戏实例内部的逻辑 |
| 视口自适应 | 窗口大小变了，通知游戏引擎刷新缩放 | 不管具体怎么缩放 |
| 加载失败恢复 | 加载出错了显示Retry按钮，用户点了清干净旧的重来 | 不管具体哪个文件加载失败、为什么失败 |

**它不管的事**：游戏UI的内容弹窗、地图HUD、引导浮标——那些归SYS-GAME-UI管。游戏里的小人怎么走、相机怎么跟——归玩法线管。

## 🎨 核心：皮与骨架拆分

> **骨架** = 换什么校园都不变的做事方式
> **皮** = 跟 Peter 这个具体项目绑定的内容
> **配置点** = 将来后端管理系统可以改的参数

---

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：一条固定的页面状态流水线

**大白话**：从打开网页到能玩游戏，中间要经过的状态是固定的，不能跳步、不能倒退。

就像你去医院看病：
```
挂号 → 排队候诊 → 进诊室 → 看医生 → 拿药走人
```
你不能跳过挂号直接冲进诊室，也不能看完医生又退回排队。每个状态之间只有特定的路可以走。

游戏也一样：
```
BOOT → LOADING → READY → ENTERING_GAME → PLAYING ⇄ MODAL_OPEN
                   ↑                            │
                   └──────── ERROR ←─────────────┘（出错时）
```
不管这个应用是Peter的校园、某学校的官网、还是某公司的产品展示，这条状态流水线都是通用的。

**为什么是骨架**：换任何需要"加载→等待→进入"的网页应用，状态机模式不变。变的只是每个状态显示什么内容。

**实现形态**：`AppRuntime` 是一个纯逻辑状态机——不碰DOM、不碰Phaser、不碰定时器。谁想让它做实际的事（比如创建游戏、渲染页面），就通过 `effects` 注入。

#### 骨架 2：网页壳与游戏画布分层

**大白话**：网页UI（DOM）和游戏画面（Canvas）是两层独立的画布，叠在一起但互不干扰。

就像一张透明塑料片盖在一幅画上。塑料片（DOM壳）负责显示按钮、进度条、错误提示；画（Canvas）负责显示游戏世界。需要显示加载页时把塑料片变不透明，盖住画；加载完了把塑料片变透明，露出画。

不管哪个校园项目，网页壳和游戏画布分层这个架构是不变的。

**为什么是骨架**：任何用Canvas做游戏、用DOM做UI的Web项目都需要这两层。z-index 分层是Web的基本能力。

**实现形态**：`#app`（z-index默认）放Canvas，`#app-shell`（z-index:9000）放DOM壳。壳的状态由 `document.body.dataset.appState` 驱动CSS样式变化。

#### 骨架 3：Phaser游戏实例的"生"与"死"

**大白话**：点Play时创建游戏引擎实例，关网页或出错时完整销毁——这套"生老病死"有统一规矩。

就像剧场的舞台——开演前搭台（创建Phaser.Game），演出结束拆台（game.destroy(true)）。不能只拆一半留一半，否则下次搭台时地上还有旧的道具（内存泄漏）。

**为什么是骨架**：任何Phaser项目都要面对"创建→销毁→再创建"的循环。不管什么校园，这个生灭模式是一样的。

**实现形态**：`game/main.ts` 中的 `effects.startLoading` 创建 `new Phaser.Game()`，`effects.cleanup` 调用 `game.destroy(true)` 并移除canvas。

#### 骨架 4：视口自适应

**大白话**：窗口大小变了（比如手机横过来、浏览器拉大），页面和游戏都能跟着适配。

就像一件有弹性的衣服——人胖了瘦了衣服都能跟着变。游戏画布按固定逻辑尺寸（480×270）渲染，然后按窗口比例自动缩放填满屏幕。

**为什么是骨架**：响应式布局是任何Web项目的基本需求，不管什么校园都需要。

**实现形态**：`DomAppViewport` 接口订阅 `window.resize` 事件 → `DomAppUi` 更新DOM布局 → `Phaser.Scale.refresh()` 刷新画布缩放。

#### 骨架 5：取消、清理、重来

**大白话**：加载到一半不想要了（出错、关网页、点了Retry），系统知道怎么"收摊"——取消旧的→清干净→可以重新开始。而且是"按代管理"——每一代加载有自己的编号，旧代的回调不会搞乱新一代。

就像餐厅的翻台——上一桌客人走了，服务员必须把桌子擦干净（cleanup）、收走旧碗筷（cancel旧请求）、铺上新桌布（retry），下一桌客人才能坐下。

**为什么是骨架**：任何涉及异步加载和重试的Web应用都需要"取消旧操作+清理+重来"这套机制。代际隔离防止旧回调污染新状态，是通用的工程模式。

**实现形态**：`AppRuntime` 的 `generation`（代次）每次加载+1，所有回调先检查 `isCurrent(generation)`。`cleanupGeneration()` 先cancel旧handle，再调 `effects.cleanup()`。

### 二、皮（跟 Peter 项目绑定的东西）

| 皮 | 当前值（Peter 项目） | 换成其他校园会怎样 |
|---|---|---|
| 页面状态的精确数量 | 9 种（BOOT / LOADING / READY / ENTERING_GAME / PLAYING / MODAL_OPEN / ERROR / RETRYING / SHUTDOWN） | 可以砍掉 MODAL_OPEN（没弹窗的简单项目）；可以加 TUTORIAL（新手引导状态） |
| DOM壳的HTML结构 | `index.html`：加载页（GIF+红色进度条+百分比）、Ready页（Logo+Play按钮）、错误页（Retry按钮） | 换一套完全不同的DOM和CSS（比如换成某学校的品牌色、Logo） |
| Phaser游戏配置 | 逻辑分辨率 480×270、Arcade 30FPS、ENVELOP缩放、pixelArt+roundPixels | 分辨率、帧率、缩放模式都可以按需改 |
| 移动端断点 | ≤767px（DOM壳padding缩小、地图HUD缩小） | 可以换断点值，或者加减断点 |
| 可选图片及降级 | `peter-oravec.gif`（加载动画）和 `peteroravec-logo.webp`（Logo），加载失败自动隐藏并替换alt文字 | 换成其他项目的图片资源 |
| 出错后怎么办 | 显示"Unable to enter campus" + Retry按钮，不自动重试 | 可以改成自动重试3次 / 放一张灰色占位图 / 弹窗提示 |
| 页面关闭时的行为 | `pagehide` 事件触发 `shutdown()` 销毁游戏实例 | 可以加"是否确认离开"弹窗、自动保存进度 |

### 三、配置点（将来后端改几个数字就能换皮）

| 能改什么 | 啥意思 | 现在 Peter 的值 |
|---|---|---|
| 逻辑分辨率 | 游戏世界的"设计尺寸" | 480×270 |
| 物理帧率 | 物理引擎每秒算几次 | 30 FPS（Arcade fixedStep） |
| 缩放模式 | 画布怎么适配窗口 | ENVELOP（等比拉伸填满，不裁剪） |
| 移动端断点 | 手机/电脑的分界线 | 767px |
| 是否显示错误详情 | 错误信息要不要展示给用户看 | 显示（`#app-error-text`） |
| 是否开启pixelArt | 像素风渲染（关闭抗锯齿） | 是 |
| favicon | 浏览器标签上的小图标 | inline SVG（蓝色三角形） |
| 出错后是否自动重试 | 加载失败是自动重来还是等人点 | 不自动，等人点Retry |

## 跟谁接口（它和谁打交道）

```
                    ┌──→ [游戏UI SYS-GAME-UI]  给它：AppSnapshot → 渲染哪个视图
[SYS-APP 应用启动] ──┼──→ [资源加载 SYS-ASSET]  从它：onProgress → 更新进度条
                    ├──→ [Phaser引擎]          创建/销毁 Phaser.Game 实例
                    └──→ [浏览器]              监听 resize / pagehide
```

SYS-APP 是整个应用的**入口调度员**——它不亲自加载资源、不渲染游戏画面、不显示弹窗，但它决定"现在该干什么、谁来干"。

## 容易踩的坑

| 坑              | 为什么坑                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------ |
| Canvas和DOM壳叠反了 | `#app-shell` 的 z-index 是 9000，Canvas 在下面。如果壳没有正确隐藏（比如 READY 状态时 `#app-shell` 的 `hidden` 属性没生效），Play按钮会挡住游戏画面 |
| 旧代的回调污染新一代     | 用户点了Retry，如果上一代的下载回调还在跑，可能会更新新一代的进度条。`isCurrent(generation)` 就是防这个的——旧代回调检查发现代次不对，直接忽略                       |
| Phaser实例没清干净   | `game.destroy(true)` 删Canvas，但如果场景内部的定时器、事件监听、物理碰撞器没关，销毁后可能还有残留。CampusScene的 `performShutdown()` 负责逐项清理      |
| 进度条倒着走         | `AppRuntime.reportProgress()` 只接受递增的进度值。如果谁报了比之前小的值，直接忽略——防止用户在Retry时看到进度从80%"跳"回0%再涨上去                      |
| 页面关闭时没停掉游戏     | `pagehide` 事件触发 `shutdown()`，但如果用户直接关浏览器标签，Phaser不一定会收到通知。所以每个Runtime的清理逻辑必须能容忍被"暴力终止"                       |
