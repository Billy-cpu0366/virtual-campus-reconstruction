# 文档完整拆解与复用治理方案

> [!warning]
> 本文是历史提案 `DEC-DOC-GOV-000`，已由 [[文档治理补漏方案-最终方案|DEC-DOC-GOV-001]] 替代，不再作为当前规则执行。需求来源、Human 决定和替代关系统一维护在 [[需求来源与决策台账]]。

## 1. 背景与问题

当前项目已经建立需求分析、概要设计、详细设计、验证和逆向计划框架，也明确了证据边界和实践驱动的复用规则。但现有体系更强调“不要提前抽象代码”，没有充分落盘另一项核心要求：

> 框架阶段可以相对粗，但必须覆盖当前已知板块；逆向过程中持续发现和细拆；最终把当前范围内的重要内容拆到最小有意义设计单元，才能准确理解、实现、验证并判断复用。

“让 AI 全面考虑”不能证明文档真的全面。完整性必须通过节点总账、状态、追溯关系、验收标准和一致性检查证明。

## 2. 需求依据

### 2.1 Human 当前明确需求

- 每个板块、对象、事件、数据和约定都要进入设计视野；
- 初始框架可以不包含全部细节；
- 逆向过程中不断补充和递归细拆；
- 最终必须拆到足够细，才能判断具体复用什么；
- 文档可以先拆，代码不能凭未来设想提前抽象；
- 未来虚拟校园需要能够消费经过实践证明的成果。

### 2.2 会议录音中的既有结论

`C:\Users\inertnet\Desktop\项目讨论\luyin.txt` 明确讨论了：

- 先建立正向工程思维导图和文档框架；
- 将地图、玩家、NPC、图层、车辆、任务等关键词放入合适节点；
- 逆向工程持续给节点填充证据和实现知识；
- 详细设计需要继续拆分系统、对象和事件；
- 重要节点最终形成可供 Human 理解、AI 执行和测试验证的文档；
- 拆分的重要目的之一是识别稳定逻辑，并为未来校园迁移和复用提供基础。

录音中的 Rust、数据库、后台、API 和工期等内容属于其他商业项目示例，不自动成为当前公开前端复刻的范围。

## 3. 最终判断

### 3.1 对现有文档的判断

当前文档体系只部分满足需求：

- 已满足：证据驱动、逐系统推进、Human Gate、不提前抽象代码、实现后验证；
- 尚未满足：初始已知范围覆盖、持续新增节点、最终原子化、全范围收尾、可证明的文档完整性。

### 3.2 推荐总原则

> 结构先覆盖，内容渐进求证，最终原子化，代码复用后判定。

具体含义：

1. 初始框架覆盖当前已经知道的主要分支，但不假装已经达到最终完整；
2. 新证据和新关键词必须持续进入节点总账；
3. 研究某个分支时递归拆到最小有意义设计单元；
4. 候选结构可以没有完整证据，但必须标记为未知；
5. 原站事实必须由公开证据证明；
6. 正式实现必须通过详细设计和验收门禁；
7. 代码提取必须经过真实重复、稳定/变化分析和 Human 确认；
8. 最终虚拟校园实际使用后，才能证明跨项目复用。

## 4. 范围边界

### 4.1 当前范围

- Peter Oravec 原站完整公开前端；
- 网站应用部分；
- Phaser 虚拟世界；
- 必要的公共支撑、资源规则、工具和验证能力；
- 当前复刻代码，仅作为实现对照。

### 4.2 当前不在范围

- 未公开源码、私有仓库、服务端和数据库；
- 尚未定义的完整校园业务；
- 为证明复用而虚构第二套实现；
- 适用于所有游戏的万能引擎；
- 将录音中的其他商业项目结构机械复制到当前项目。

最终完整是指：在公开证据和已确认重构范围内完成结构覆盖与原子设计；无法确认的内容明确保留为 `UNKNOWN`，不伪造原站内部结构。

## 5. 需求达成目标

| ID | 需求 | 达成目标 |
|---|---|---|
| R1 | 当前范围明确 | 每个候选节点最终标记 `in-scope / out-of-scope / not-applicable`，不能无声消失 |
| R2 | 框架覆盖已知板块 | 当前已知系统、对象、事件、数据、约定、界面和验证能力均有入口 |
| R3 | 持续补充节点 | 新发现必须回写思维导图、节点总账及必要的未知/证据文档 |
| R4 | 最终拆到最细 | 每个范围内原子设计节点有唯一主要详细定义 |
| R5 | 不把猜测写成事实 | 候选节点允许 `UNKNOWN`，FACT 必须有公开证据 |
| R6 | Human 和 AI 都能理解 | 详细文档包含通俗解释、边界、状态、流程、证据和验收 |
| R7 | 每个节点可验证 | 系统有行为验收、事件有测试场景、数据有合约检查、对象状态可验证 |
| R8 | 能精确判断复用 | 原子节点能描述实际场景、稳定部分、变化部分、依赖、收益和风险 |
| R9 | 不提前抽象代码 | 真实重复和 Human 确认前不得提取通用模块 |
| R10 | 未来校园可消费 | 复用成果有稳定契约、版本、集成条件和跨项目验证记录 |
| R11 | 完整性可以证明 | 建立需求到节点、证据、实现、测试和复用观察的追溯链 |
| R12 | 项目可以结束 | 未知项可以显式保留，不因私有信息不可得而无限延期 |

## 6. 节点与状态模型

不同问题必须使用不同状态线，不能用一个“完成”混合表示。

### 6.1 范围状态

```text
candidate → in-scope
          → out-of-scope
          → not-applicable
```

### 6.2 原站理解状态

```text
unknown → discovered → partial → confirmed
```

### 6.3 文档与工程状态

```text
indexed → documented → designed → implemented → verified
```

### 6.4 复用状态

```text
未评估 → 观察中 → 待 Human 确认
                    ├─ 已拒绝
                    └─ 已批准 → 已提取 → 已跨项目验证
```

文档自身的 `draft / approved` 只表示文档治理状态，不能替代以上状态。

## 7. 什么叫“拆到最细”

“最细”是最小有意义设计单元，不是每行代码、每个函数或每个实例一份文档。

原子节点应满足：

1. 只有一个主要职责和变化原因；
2. 明确负责与不负责什么；
3. 输入、输出或状态变化明确；
4. 状态唯一拥有者明确；
5. 依赖方向明确；
6. 能独立定位证据；
7. 能独立实现、修改和验证；
8. 能判断稳定部分和变化部分；
9. 继续拆分只剩内部步骤、字段或普通数据实例。

最终每个 `in-scope` 原子节点必须有唯一主要详细定义。普通实例和内部步骤保留在所属主文档中，避免文档碎片化。

## 8. 文档组织方式

### 8.1 概要设计：覆盖和导航

概要设计负责：

- 当前已知系统全景；
- 对象、事件、数据和约定全景；
- 节点总账；
- 依赖关系；
- 当前覆盖和优先级。

框架期不批量生成大量空详细文档，但所有已知候选必须有登记入口。

### 8.2 详细设计：原子节点主定义

详细设计负责：

- 系统与子能力；
- 对象模型；
- 事件和流程；
- 数据、契约和工程约定；
- 必要的界面或组件设计。

复杂事件或状态机必须包含或链接 Mermaid 流程图；简单事件可以在主文档内表达。每个事件都必须有验证归属。

### 8.3 验证：证明理解和完整性

验证负责：

- 原站行为基准；
- 当前复刻行为；
- 节点到证据和实现的追踪；
- 事件、对象状态和数据合约验证；
- 思维导图、节点、文档和状态一致性检查。

### 8.4 复用成果：实践后的晋升层

普通详细设计不等于复用成果。只有进入“待 Human 确认”的候选才建立复用成果主定义；获批后才能提取和维护稳定契约。未来校园的具体适配写在校园项目文档中，当前项目只记录采用和验证链接。

## 9. 执行流程

```text
A. 修正权威需求和状态模型
   ↓
B. 建立当前已知节点框架
   ↓
C. 检查当前已知范围是否有整类遗漏
   ↓
D. 选择一个分支进行逆向
   ↓
E. 发现新节点并回写总账
   ↓
F. 将该分支递归拆到原子节点
   ↓
G. 填充证据、边界、状态、异常和验收
   ↓
H. Human 确认后实现
   ↓
I. 与原站比较并回写差异
   ↓
J. 检查真实重复和复用观察
   ↓
K. 继续下一分支
   ↓
L. 最终执行全范围覆盖与原子化审计
```

最终每个候选节点必须：

- 完成并进入 `in-scope`；或
- 合并到另一个主节点并保留映射；或
- 标记 `out-of-scope / not-applicable` 并说明理由；或
- 保留明确 `UNKNOWN`、影响和后续处理方式。

不能无声遗漏。

## 10. 完整性验证

不能再用“AI 已全面考虑”作为验收结论，必须检查以下关系：

```text
需求
→ 思维导图
→ 节点总账
→ 原子详细设计
→ 原站证据
→ 重构决定
→ 实现代码
→ 测试结果
→ 复用观察
```

至少验证：

- 思维导图节点是否进入总账；
- 节点是否有唯一 ID、父节点、类型和范围状态；
- `in-scope` 原子节点是否有唯一主定义；
- 是否存在孤儿文档和重复主归属；
- 状态值是否合法；
- 未知项是否有去向；
- 实现和测试是否能反向映射；
- 复用成果是否有真实场景和 Human 批准；
- `task_plan.md` 是否只有一个真实当前阶段；
- Markdown 链接和必要文件是否一致。

结构覆盖、证据成熟度、工程完成度和复用成熟度必须分别汇报，不能合并成一个百分比。

## 11. 优点

1. **复用判断更精确**：能区分整个系统、局部算法、数据格式、事件流程和项目配置；
2. **减少遗漏**：所有已知板块都有登记和回写入口；
3. **保护事实边界**：候选结构和已证明事实分离；
4. **Human 可理解**：从全景逐层进入原子细节；
5. **AI 可执行**：换会话后可以根据节点和状态继续；
6. **支持并行**：原子节点边界清楚后可以独立调查和实现；
7. **修改可追踪**：契约变化可以追到受影响代码和测试；
8. **形成长期资产**：保留代码之外的数据、算法、UI、工具、测试和约定。

## 12. 缺点、成本和控制方式

| 缺点或风险 | 影响 | 控制方式 |
|---|---|---|
| 文档数量增加 | 维护成本上升 | 只为原子设计节点建主文档，实例和内部步骤不独立建文档 |
| 前期整理变慢 | 延迟直接编码 | 这是恢复系统知识和未来复用所需的必要成本 |
| AI 机械填模板 | 形式完整、内容空洞 | 必须引用证据或明确写 UNKNOWN，并执行 Human 抽查 |
| 状态维度较多 | 容易漂移 | 节点总账作为中央状态入口，其他文档只链接 |
| 过度拆分 | 阅读和修改困难 | 使用原子停止标准，不以文件数量衡量完整度 |
| 公开证据有限 | 无法恢复全部内部实现 | 完成范围限定为公开行为和我们的重构决定 |
| 复用收益延后 | 很多节点可能不被提取 | 未复用的文档仍服务于理解、实现和验证 |
| 校园需求污染通用成果 | 形成伪通用模块 | 校园适配留在校园文档，通用成果只维护稳定契约 |

## 13. 当前阶段最合适的动作

在 Human 确认本方案后：

1. 将核心原则同步到 `AGENTS.md`、文档入口和需求范围；
2. 修正思维导图、节点总账、详细设计门禁和工作流程；
3. 明确候选节点登记与详细文档创建不是同一门禁；
4. 修正 `task_plan.md` 的当前阶段漂移；
5. 建立文档覆盖与一致性检查；
6. 用一个成熟分支（地图分块）和一个未知分支（如 NPC）验证流程；
7. 通过后继续阶段 6C 的首个系统详细逆向。

当前不应立即批量生成所有详细文档，也不应建立通用代码模块。
