# SYS-CHUNK 地图分块：详细设计候选

> 这是根据 [[SYS-CHUNK-地图分块-逆向工作稿]] 形成的**重构设计候选**。其中 FACT 描述原站公开证据；`DECISION（proposed）` 是我们为可控重构提出的方案，尚未获 Human 批准。本文件不是唯一主定义，不改变节点 `undesign`，不授权正式 `src`。

## 1. 说人话解释

地图分块系统负责回答一件事：玩家和相机现在走到哪里了，哪些地图块必须显示，哪些可以从场景中移除。

它不负责玩家怎么移动、相机怎么跟随、每个图层到底怎样遮挡，也不负责把所有资源加载都做成通用框架。

## 2. 结论摘要

| 性质 | 当前结论 |
|---|---|
| FACT | 原站地图是 5×5 个、每块 28×28 的 JSON chunk；文件索引为 `y * 5 + x` |
| FACT | 原站玩家 3×3 邻域与相机范围加 1 块边距合并为目标集合；约每500ms更新 |
| FACT | 原站 manager 缓存原始 JSON，场景另有已写入 Tilemap 的集合；在已定位动态路径中，场景卸载未删除 JSON 缓存 |
| FACT | Play 前相机序列以不同策略预载，现有 1920×1080 证据覆盖全部25块 |
| DECISION（proposed） | 重构中保持“原始数据缓存 / 场景渲染状态 / 请求中的工作”三类状态分离 |
| DECISION（proposed） | 一个坐标同一时刻只允许一个在途请求；请求完成后只在该坐标仍属于当前目标集合时写入场景 |
| DECISION（proposed） | 失败显式记录；不做无界自动重试；由下一次目标更新或明确重试操作触发有限重试 |
| UNKNOWN | 原站的并发合并、取消、重试、销毁清理及13个未定位图层的完整卸载语义尚未确认 |

## 3. 原站可观察行为

- 首次进入游戏会请求 master 和分块；在已采集桌面视口中，Play 前相机展示导致25块均被预载；
- 玩家阶段按玩家邻域和相机范围动态维护场景中的块；
- 场景卸载会清除已定位图层的对应 Tilemap 区域；
- 原站公开产物显示数据缓存与场景显示状态不是同一层；manager 虽定义淘汰方法，但当前发布 Bundle 未定位外部调用入口，不能断言其缓存永远不淘汰。

可定位证据见 [[SYS-CHUNK-地图分块-逆向工作稿#2. 证据定位]]。

## 4. 职责边界

### 负责

1. 读取并校验 master 与 chunk 的基本契约；
2. 将玩家位置、相机视口转为“需要哪些 chunk”的目标集合；
3. 去重管理单块请求、原始 JSON 缓存和场景写入；
4. 使场景中的已渲染集合最终收敛到目标集合；
5. 记录可定位的加载失败和未解决图层边界；
6. 在场景退出时停止本系统拥有的定时、空闲任务和后续场景写入。

### 不负责

- 玩家输入、速度和碰撞参数；
- 相机跟随、缩放和镜头脚本本身；
- `SYS-LAYER` 的完整 depth、roof、bridge、cars、particles 等图层语义；
- 通用资源加载框架、NPC、车辆和路线；
- 将本系统抽象为未来校园通用模块。

## 5. 子能力与输入输出

| 子能力 | 输入 | 输出 | 当前依据 |
|---|---|---|---|
| 数据目录 | master、坐标 | 块尺寸、地图边界、文件索引 | FACT |
| 目标集合计算 | 玩家世界位置、相机视口 | 坐标集合 | FACT；原站默认玩家3×3与相机+1边距 |
| 首屏预载 | 相机展示位置与视口 | 预载坐标集合 | FACT；原站默认额外2块边距 |
| 请求与缓存 | 坐标、目录 | 原始 chunk 数据或结构化失败 | FACT 有缓存；失败策略为 proposed |
| 场景写入/清除 | chunk 数据、坐标、图层策略 | Tilemap 区域变化 | FACT 有局部清除；完整图层策略 UNKNOWN |
| 生命周期收敛 | 新目标集合、场景销毁 | 加载、保留、清除或停止后续写入 | FACT + proposed |

这些是 `SYS-CHUNK` 内部子能力，不因可能相似就拆成独立复用系统。

## 6. 数据与状态所有权（DECISION，proposed）

| 状态 | 唯一拥有者 | 读取者 | 允许修改者 | 说明 |
|---|---|---|---|---|
| master 数据与已成功原始 chunk JSON | ChunkDataStore | ChunkCoordinator、WorldRenderer | ChunkDataStore | 已下载不等于已显示 |
| 当前目标 chunk 坐标集合 | ChunkCoordinator | WorldRenderer、诊断/验证 | ChunkCoordinator | 来自玩家邻域与相机集合并集 |
| 在途请求登记 | ChunkCoordinator | ChunkDataStore、诊断/验证 | ChunkCoordinator | 同坐标只保留一个在途工作，防止重复请求 |
| 每块失败记录与尝试次数 | ChunkCoordinator | UI/诊断、验证 | ChunkCoordinator | 不把失败伪装成已加载 |
| 已写入 Tilemap 的 chunk 集合 | WorldRenderer | ChunkCoordinator、诊断/验证 | WorldRenderer | 只表示场景当前显示状态 |
| 系统是否已销毁 | ChunkCoordinator | 所有异步回调 | ChunkCoordinator | 销毁后回调不得继续写入场景 |

`ChunkDataStore`、`ChunkCoordinator`、`WorldRenderer` 是职责名称，不预先要求对应三个代码目录或三个可复用类。

## 7. 协作与流程（DECISION，proposed）

```text
玩家位置 + 相机视口
        ↓
ChunkCoordinator 计算目标集合
        ↓
对每个目标：数据已缓存？已渲染？正在请求？失败可否有限重试？
        ↓
ChunkDataStore 获取或返回原始 JSON
        ↓
仅当系统未销毁且该块仍在当前目标集合时
        ↓
WorldRenderer 写入对应 Tilemap 区域，登记已渲染
        ↓
对不再属于目标集合的已渲染块清除对应区域
```

### 失败、重复与取消

- **重复**：同坐标在途时复用同一在途结果，不再发第二次请求；
- **失败**：记录坐标、错误类别和尝试次数；当前轮不无限自动重试；
- **重试**：只在仍属于目标集合时，经过有限次数或明确触发后重试；具体次数和退避参数在实现 Gate 前确定；
- **取消**：不把“取消 HTTP 请求”假装成原站事实。若环境无法安全取消，请求可完成进入原始缓存，但结果只有在坐标仍是目标且系统未销毁时才能写入场景；
- **销毁**：停止本系统安排的轮询、空闲预载和后续场景写入；未完成结果不得访问已销毁场景。

这是为重构可控性提出的设计，并非声称原站也有同样错误策略。

## 8. 对象、事件与依赖

### 输入依赖

- `SYS-WORLD`：Tilemap 和世界坐标空间；
- `SYS-PLAYER`：只提供玩家世界位置；
- `SYS-CAMERA`：只提供相机视口；
- `SYS-ASSET`：仅提供分块所需的请求能力，不在此定义通用 Loader；
- `SYS-LAYER`：定义完整图层策略前，分块只能按已确认范围写入/清除。

### 对象与事件定位

- [[../对象/README]] 中的 `OBJ-CHUNK` 是分块数据/实例的对象归属；本候选只定义系统怎样协调它们，不复制对象字段定义；
- 当前没有独立事件节点；加载完成、失败和销毁先作为系统状态通知记录，只有出现多个实际消费者后再评估独立事件文档。

### 输出边界

- 对 WorldRenderer：坐标和已验证的 chunk 数据;
- 对验证：目标集合、请求、缓存、渲染、失败和销毁的可观察记录；
- 不直接修改玩家、相机、NPC 或 UI 的私有状态。

本候选不要求事件总线。立即需要加载结果或状态时使用直接调用；加载完成、失败、场景销毁等已发生状态才可作为通知记录。

## 9. 现有复刻映射与差距

旧 Phaser 复刻直接加载一张整图，不读 master，不按块加载或卸载。因此它可用于局部 Tilemap API 实验，不能作为本系统行为正确性的证明。

主要差距：原始数据目录、目标集合、场景/数据状态分离、有限失败处理、销毁边界、可重复验收，以及13个未确认图层的策略。

## 10. 验收候选

正式实现前应至少能验证：

1. 读取 master 后，坐标 `(x,y)` 对应 `chunk{y*5+x}.json`；
2. 拼接25块后，已确认的24层与 `final_map.json` 数据一致；
3. 给定玩家位置和相机视口，目标集合符合“3×3 + 相机范围+1”的边界裁剪规则；
4. 同一坐标重复触发时，不产生多个在途请求；
5. 目标改变后，不再需要的**已渲染**块被清除，但数据缓存策略可单独观察；
6. 失败、销毁和过期异步结果不会把数据写入错误或已销毁的场景；
7. 验收用例显式断言13个未确认图层不进入“已正确支持”的写入/清除覆盖结论。

原站首屏预载的多视口时序与完整图层语义另列为后续验证，不以当前猜测强行通过。

## 11. 复用观察

当前只有地图分块这一项真实场景，状态为：**未发现**。本候选没有申请提取任何通用加载器、坐标系统或缓存框架。

## 12. 请 Human 审查的决定

1. 是否接受“数据缓存 / 目标协调 / 场景渲染”三类状态分离；
2. 是否接受同坐标单一在途请求、有限重试、过期结果不写场景的重构策略；
3. 是否接受先只支持已证实边界，并把13个图层语义单列为后续工作；
4. 是否允许将本候选升级为 `SYS-CHUNK` 的正式主定义；
5. 是否在正式设计确认后，再单独讨论实现授权。
