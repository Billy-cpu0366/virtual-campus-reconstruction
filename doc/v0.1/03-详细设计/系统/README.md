# 系统详细设计

一个系统是一组共同完成某种任务的规则和能力。只有达到节点晋升条件时才创建文件。

## 文件命名

```text
SYS-领域-编号-系统名称.md
```

## 统一模板

```markdown
# 系统名称

## 1. 说人话解释
这个系统解决什么问题。

## 2. 结论摘要
列出 FACT、INFERRED、DECISION、UNKNOWN。

## 3. 原站可观察行为
用户或浏览器实际能看到什么。

## 4. 职责边界
负责什么；明确不负责什么。

## 5. 子能力
每项能力的输入、输出和已经观察到的实际使用场景；不得根据未来设想填写复用场景。

## 6. 数据与状态
系统拥有或读取哪些数据，状态如何变化。

## 7. 对象与事件
管理哪些对象，发布或响应哪些事件。

## 8. 依赖关系
依赖谁，被谁使用，禁止依赖谁。

## 9. 原站证据
文件、字段、Bundle、Network、浏览器步骤。

## 10. 现有复刻映射
当前 Phaser 代码对应哪里，已完成什么。

## 11. 差距
缺失、错误或尚未验证的内容。

## 12. 重构决定
我们准备怎样实现，为什么。

## 13. 未知问题
还需要调查什么，是否阻塞。

## 14. 验收方式
怎样证明该系统达到目标。

## 15. 复用观察
是否出现第二个独立实际场景、复制逻辑或重复修改；没有真实证据时写“未发现”，并同步详细设计入口的观察表。
```

## 拆分规则

子能力先写在所属系统文档中；只有被多个系统实际使用或自身明显复杂时，才拆为独立文档。
