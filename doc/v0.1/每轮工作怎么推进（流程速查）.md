# 每轮工作怎么推进（流程速查）

> **一句话：这是执行时的简明流程卡，告诉 AI 和人每一轮该先做什么、后做什么。**

> [!summary]
> 先研究原站并写清楚，再根据文档重写代码；实现后与原站比较，结果继续补回文档。

相关文档：[[项目为什么这样做（通俗说明）]]｜[[项目全貌怎么串起来（思维导图）]]｜[[谁确认过什么（来源与决策记录）]]

## 节点与工作项不是一回事

```text
节点：项目由哪些系统、对象和事件组成，例如 SYS-CHUNK
工作项：这一轮具体要完成什么，例如 WI-SYS-CHUNK-CORE-001
```

一个节点可以产生调查、设计、实现和验证等多个工作项；一个工作项也可以协调多个节点。节点状态维护在功能总目录，当前工作项只维护在项目根 `task_plan.md`。

候选工作可以来自节点、未知问题、验证失败、实现差距、缺陷、治理任务或 Human 新需求。AI 可以整理和推荐，但不能在多个重要候选中暗自扩大范围。

## 整体流程

```text
1. 建立游戏整体由什么组成（系统全景）
   ↓
2. 选择一个要研究的系统
   ↓
3. 从 `sample/`、Bundle、Network、浏览器和现有代码中找证据
   ↓
4. 写清原站事实、合理推断、未知项和必要的重构决定
   ↓
5. 拆清系统职责、对象、事件、数据和行为边界
   ↓
6. 确认系统边界、实现方案和验收标准
   ↓
7. Human 确认后按文档编写对应正式 src
   ↓
8. 与原站运行效果进行对比验证
   ↓
9. 检查是否出现真实重复，并更新复用观察
   ↓
10. 将发现的问题补回文档并关闭当前工作项
   ↓
11. 从正式候选来源滚动选择下一工作项
```

## 一句话版本

```text
搭框架 → 找证据 → 填文档 → 拆边界 → 定方案
→ Human确认 → 写代码 → 做对比 → 观察重复 → 改文档 → 下一圈
```

## 每一圈必须留下什么

| 阶段 | 最少产物 |
|---|---|
| 找证据 | 可定位的文件、请求或浏览器行为 |
| 填文档 | `FACT`、`INFERRED`、`DECISION`、`UNKNOWN` |
| 拆边界 | 系统职责、子能力、对象、事件和数据 |
| 定方案 | 边界、依赖、验收标准和 Human 确认 |
| 写代码 | 与本圈文档对应的正式实现 |
| 做验证 | 原站与复刻的差异结果 |
| 观察重复 | 真实重复场景或“未发现”的记录 |

## 轻量分级

| 级别 | 什么时候使用 | 最少要求 |
|---|---|---|
| 工作项内部步骤 | 已授权范围内的实现、测试、修复和回写 | AI 直接推进；不新增 WI、Gate 或独立授权包 |
| `level-1` 普通工作项 | 跨会话、有独立产物或需要追溯 | `WI-*`、简短任务卡、范围、退出标准、普通原子提交和一行关闭记录 |
| `level-2` Human Gate 工作项 | 正式代码、技术栈、新系统实现或明显扩大范围 | level-1 全部内容，加一页授权包、Human 确认和一次原子激活提交 |
| 严格 P/A 升级 | 破坏性或不可逆操作、真实数据、安全/生产、并行写入或跨仓库高风险迁移 | 单独取得 Human 确认后才增加 prepared/activation 双提交 |

工作项内部步骤不是持久化状态。没有触发严格条件时，不得自行升级为完整 P/A。

## 下一工作项怎样选择

先过滤：属于当前范围、前置依赖具备、有证据可研究或能解决阻塞、可形成有界验证闭环、没有越过授权。再比较 Human 优先级、关键依赖路径、解除阻塞数量、证据成熟度、成本和风险。

- 已有 accepted 决定预授权唯一下一项，且退出标准客观通过时，AI 可以继续；
- 没有预授权、出现多个重要候选、范围变化或进入新代码/风险 Gate 时，AI 最多提出三个候选及代价，由 Human 决定；
- 候选短名单不是第二套全局待办，必须链接到节点、未知、差距、验证失败或 Human 需求。

## 工作项状态和收尾

- `active`：正在授权范围内执行；
- `awaiting-authorization`：正在准备或等待 Human Gate，不能写正式代码；
- `blocked / paused`：可恢复，不属于已关闭；必须记录 blocker、恢复条件和允许动作；
- `completed / cancelled / rejected / superseded`：终态，进入轻量关闭索引。

Human 拒绝某次方案不自动等于拒绝整个工作项；要求修订时，工作项继续保留。正式工作项关闭时只登记工作项 ID、结果、节点、产物、结果提交和必要的 Human 决定。

## 没有预授权下一项时

正式工作项允许为零或一个。当前工作项满足退出标准且没有 accepted 的唯一预授权下一项时，应正常关闭，不得伪造 `active`、`blocked` 或虚假的选择工作项。

```text
关闭当前工作项并登记结果
→ current-work-item: none
→ current-phase: work-item-selection
→ 从既有权威来源整理最多三个候选
→ 涉及新范围或新 Gate 时交 Human 决定
```

`current-work-item: none` 不是新的工作项状态，只表示当前没有激活的正式 WI。此时不填写工作项级别、类型、状态、节点、范围、退出标准或授权引用；正式代码一律禁止。候选继续来自功能总目录、P0顺序、系统依赖、未知问题、证据与差距、验证失败或 Human 需求，不建立第二套全局待办。

## 正式代码怎样激活

`level-2` 工作项的审查材料可以提前提交，但 `proposed` 不等于授权。Human 接受后，AI 在同一事务中按以下顺序执行：

```text
记录 accepted 决定
→ 授权包改为 approved
→ 同步工程入口和相关状态
→ 最后更新 task_plan 为 active
→ 运行结构检查
→ 形成一次原子激活提交
→ 确认 HEAD 包含当前状态且工作区 clean
→ 才开始正式代码
```

开始正式代码必须同时满足：授权包 `approved`、授权决定 `accepted`、当前 WI 与决定的节点/范围一致、`task_plan` 的授权引用可定位、激活状态已进入 HEAD、工作区 clean。范围扩大时立即停止并重新审查。

如果事务中断且工作区 dirty，下一位 AI 必须先恢复或回退同步，不能依据未提交的 `active` 状态开始代码。建议同时检查：

```bash
git diff --quiet
git status --short
```

## 当前所在位置

当前阶段、当前 Human Gate、允许/禁止操作和下一步只维护在项目根 [`task_plan.md`](../../task_plan.md)。本速查不复制动态状态。

> [!important]
> “文档先行”不是一次写完整个项目，而是每一圈写代码之前，先把这一圈研究和设计清楚。
