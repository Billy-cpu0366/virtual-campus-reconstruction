# 02-整体怎么运作

> **说人话：把游戏当作一张总地图，看清地图、玩家、相机、图层等部分各管什么、怎样配合。**
>
> 想知道“现在做到哪一个功能”或“为什么先做地图分块”，看这里。

## 先用人话理解

可以把这部分看成整个项目的“结构地图”：

```text
01 说明原站有什么、这次要复刻什么
02 把这些能力整理成系统、对象和事件，说明各部分怎样配合
03 再挑一个已经研究成熟的部分，写清它具体怎样工作
```

02只讲整体组成、职责边界和关系，不展开具体算法。比如02只说明“存在地图分块系统、它依赖世界和相机”；地图块怎样计算、加载、卸载和处理失败，进入03的正式设计说明。

## 你先看这三份

普通阅读只需要先看：

1. [[游戏整体由什么组成（系统全景）]]：游戏大体分成哪些系统，各管什么；
2. [[游戏里有哪些东西和事情（对象与事件）]]：游戏里有哪些东西，会发生哪些事情；
3. [[各部分怎样配合（系统依赖）]]：这些部分谁先谁后、谁依赖谁。

看完这三份，就能理解02表达的项目全貌。其余文档只在遇到对应问题时读取。

## 其他文档什么时候看

- [[功能总目录（节点清单）]]：给AI维护节点身份和状态的总台账；需要查询某个系统是否已理解、设计、实现或验证时再看。
- [[旧版本现在做到什么（现有实现盘点）]]：需要知道旧 Phaser 复刻做了什么、缺了什么时再看；它不是原站事实或新工程状态。
- [[先做什么（P0系统对照与顺序）]]：需要知道为什么先调查地图分块、其他重要系统为何这样排序时再看；当前工作项和阶段不在这里维护。

## 02与03怎样接力

```text
02发现并登记一个系统
→ 证据、边界和近期研究价值足够
→ 进入03建立详细设计
→ 03说明具体规则、失败情况和验收方式
```

例如，02在节点清单登记 `SYS-CHUNK`；03的 [[../03-具体怎么做/系统/地图分块：玩家移动时怎样加载地图（SYS-CHUNK）#SYS-CHUNK|地图分块正式设计]] 才说明它具体怎样工作。02不能替代03，03也不重复维护整个项目全景。

## 后续怎样维护

- 新发现原站可观察能力：先更新01的能力清单，再在功能总目录中给它找到负责的节点或明确去向；
- 发现新的重要系统边界：更新系统全景和功能总目录；
- 发现新的对象或运行事件：更新对象与事件；
- 确认依赖关系变化：只更新系统依赖；
- 节点理解、设计、实现或验证状态变化：只以功能总目录为状态所有者，再同步对应03主定义；
- 当前工作项、阶段和Human Gate变化：只更新项目根 `task_plan.md`，不复制到本目录的静态说明中。

## 重要规则

这里的系统结构是逆向建模结果，不等于原作者源码目录。每个结论必须标注 `FACT / INFERRED / DECISION / UNKNOWN`。
