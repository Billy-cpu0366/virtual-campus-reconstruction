# 用地图分块看懂01到05（SYS-CHUNK 人话解读）

> **一句话：用已经走过一轮的地图分块系统，说明01到05各自做什么、怎样接力，以及目前究竟完成了多少。**

## 先说明这份文件的地位

这是一份给 Human 看的导航和翻译，不是新的设计，也不是地图分块的第二份正式定义。

如果本文与正式文档不一致，以链接的正式文档为准：

- 地图分块的唯一正式设计：[[03-具体怎么做/系统/地图分块：玩家移动时怎样加载地图（SYS-CHUNK）#SYS-CHUNK]]；
- 当前节点状态：[[02-整体怎么运作/功能总目录（节点清单）]]；
- 当前工作项和阶段：[[../../task_plan|task_plan.md]]；
- 验证结果：[[04-怎么验证与还差什么/地图分块：怎样验证做对了（SYS-CHUNK 验证计划）]]。

## 它是否具有代表性

**具有代表性，但不是所有情况的完整模板。**

它具有代表性，是因为地图分块已经走过：

```text
01发现原站能力
→ 02登记系统、关系和优先级
→ 03调查证据、形成正式设计、限定实现范围
→ 04建立验收并记录实现结果
→ 05关闭对应未知问题
→ 实现并验证一个有边界的CORE子集
```

它不能代表全部情况，因为：

- 它主要示范“系统”，没有完整示范独立对象、事件和数据约定文档；
- 完成的是 `SYS-CHUNK CORE`，不是整个地图分块系统；
- Phaser、网络、缓存、渲染和完整生命周期仍未实现；
- 当前没有发现可提取的复用模块。

## 先记住这几个编号

| 编号 | 人话 |
|---|---|
| `CAP-MAP-001` | 原站具有地图分块这项可观察能力 |
| `SYS-CHUNK` | 负责地图分块规则的系统 |
| `BASE-MAP-001` | 用来对照的原站地图分块行为证据 |
| `Q-MAP-001`至`003` | 调查地图分块时必须回答的问题 |
| `WI-SYS-CHUNK-CORE-001` | 已经完成的一次有边界实现工作 |
| `DEC-SYS-CHUNK-CORE-001` | Human对这次CORE实现范围的授权决定 |

编号只是为了让不同文档准确指向同一件事。阅读时把`SYS-CHUNK`直接理解成“地图分块系统”即可。

# 第一站：01说明原站有什么

查看：[[01-目标与范围/原站有哪些功能（能力清单）]]中的`CAP-MAP-001`。

这里说的是：

> 原站不是只加载一张完整地图，而是存在一个master索引和多个地图分块。

01只负责确认“原站有这项能力，而且当前要复刻”。它不决定代码怎样写，也不解释完整算法。

这一步的作用是防止我们凭想象创造功能，或者研究了一个不在当前范围内的东西。

# 第二站：02确定由谁负责、与谁配合

主要查看：

1. [[02-整体怎么运作/功能总目录（节点清单）]]中的`SYS-CHUNK`；
2. [[02-整体怎么运作/先做什么（P0系统对照与顺序）]]中的地图分块部分；
3. [[02-整体怎么运作/各部分怎样配合（系统依赖）]]。

02把01的一项用户能力翻译成工程职责：

```text
原站有地图分块能力
→ 由SYS-CHUNK负责协调
→ 它属于世界与地图
→ 它读取玩家位置和相机视口
→ 它需要地图数据和图层规则
```

02还说明为什么先研究它：公开证据相对完整、旧复刻明确缺失，而且它是后续世界和图层工作的基础。

02到这里停止，不展开请求去重、坐标公式、失败处理等完整做法。这些进入03。

# 第三站：03把一个系统研究和设计清楚

地图分块在03有三份不同作用的文件。

## 3.1 调查记录：原站到底是什么样

查看：[[03-具体怎么做/系统/地图分块：从原站查到了什么（SYS-CHUNK 调查记录）]]。

它负责保存证据调查过程，例如：

- master描述5×5个分块；
- 每块是28×28格；
- 文件采用行优先索引，即`index = y * 5 + x`；
- 玩家周围3×3与相机可见范围加1块边距共同形成目标集合；
- Play前的相机展示会执行另一段预载流程。

它回答“从原站查到了什么”，但调查记录本身不是最终重构方案。

## 3.2 正式设计：我们决定怎样做

查看：[[03-具体怎么做/系统/地图分块：玩家移动时怎样加载地图（SYS-CHUNK）#SYS-CHUNK]]。

它是`SYS-CHUNK`的唯一正式设计，主要回答：

- 系统负责什么、不负责什么；
- 玩家和相机位置怎样变成目标分块；
- 原始数据缓存、当前目标和场景显示状态怎样分开；
- 重复请求、失败、过期结果和场景销毁怎样处理；
- 需要与世界、玩家、相机、资源和图层怎样协作；
- 怎样才算设计正确。

这里既有原站事实，也有我们的重构决定，两者必须分开标记。

## 3.3 实施授权包：这次到底允许写多少代码

查看：[[03-具体怎么做/系统/地图分块：本轮准备实现什么（SYS-CHUNK CORE 实施授权包）]]。

完整设计很大，所以第一次没有一次性实现全部地图分块，只批准确定性的纯逻辑CORE：

- master关键契约；
- 分块索引和坐标边界；
- 玩家3×3目标；
- 相机范围加1块边距；
- 两类目标的确定性去重并集。

没有批准网络、缓存、Phaser、Tilemap和完整生命周期。

这说明“03已经设计清楚”不等于“可以随意实现全部内容”。

# 第四站：04证明做对了多少

主要查看：

1. [[04-怎么验证与还差什么/原站实际表现是什么（行为基准）]]中的`BASE-MAP-001`；
2. [[04-怎么验证与还差什么/原站和旧版本差在哪（证据与差距）]]中的`CAP-MAP-001`；
3. [[04-怎么验证与还差什么/地图分块：怎样验证做对了（SYS-CHUNK 验证计划）]]。

可以把它们理解成：

```text
原站行为基准 = 标准答案
证据与差距     = 对照后还差什么
验证计划       = 新实现的考试题和评分规则
```

本轮CORE已经通过：

- TypeScript strict类型检查；
- 3个测试文件、26项单元测试；
- npm官方源审计0漏洞；
- 独立只读复核。

但这些结果只证明CORE，不证明完整地图分块已经实现。

# 第五站：05保存调查时还没有答案的问题

查看：[[05-还不清楚什么/还缺哪些答案（未知问题队列）]]中的：

- `Q-MAP-001`：原站是一次加载还是动态装卸；
- `Q-MAP-002`：master与chunk的数据关系；
- `Q-MAP-003`：为什么Play前请求了全部25块。

这三个问题已经找到证据并关闭。完整答案已经写入02、03和04；05只保留关闭摘要、证据位置和残余未知。

地图分块仍有更窄的未知，例如并发实现细节、取消、重试、销毁清理和13个图层的完整语义。这些不能因为CORE通过就假装已经解决。

# 以后研究其他系统时怎样照着走

地图分块提供的是一条轻量检查路线，而不是要求复制所有文件：

```text
1. 在01确认原站确实有这项能力
2. 在02找到负责它的系统、对象或事件
3. 只在证据和边界足够时进入03详细研究和设计
4. 实现前先在04写清怎样算做对
5. 没有证据的重要问题进入05
6. Human只授权当前明确范围
7. 实现后把代码、测试、差距和残余未知回写
```

简单功能可以保留在父系统章节，不必机械创建与地图分块同样多的文件。
