# 文档治理补漏方案：最终方案

> 本文是 Human 选定的文档治理最终方案。第二轮权威同步曾在 clean 内容提交 `63831821b35cd60d37a3955db642695809c9f889` 上通过验证；阶段6B Gate 随后变化，依照失效规则正在新基线上复验。该复验不改变本决定只授权治理同步的边界；阶段6C 的授权由 `DEC-STAGE6B-001` 单独记录，仍不授权旧 Phaser 或正式 `src`。

## 1. 决定摘要

本方案保留当前已经正确的五类文档、证据边界、Human Gate 和实践驱动复用规则，只补齐真正发生的治理断链：

- 需求来源和 Human 决定难以稳定追溯；
- 已知节点是否都有去向无法证明；
- 原站事实、重构决定和未来设想可能混淆；
- 接受、落盘、验证和实施授权可能被误认为同一状态；
- 当前治理机制验收和项目最终覆盖验收可能互相阻塞；
- 验收结论缺少可复现的版本、范围和证据基线。

最终原则：

```text
所有候选设计关注点都有去向；
已知职责必须在证据边界内拆清；
原站未知边界如实保留，不推测原站结构；
我们的重构结构可以作为 DECISION 主动设计；
决定、落盘、验证和实施授权分别记录；
当前治理与最终覆盖分层验收；
正式验收固定版本、范围和证据基线；
新增治理能力必须由真实试点触发；
代码复用仍由真实实践和 Human 决定。
```

## 2. 方案目标

1. 让 Human 能从思维导图和主题文档理解项目；
2. 让 AI 能从节点总账、来源引用和唯一主定义继续执行；
3. 让会议需求、培训示例、AI 建议和 Human 正式决定可以区分；
4. 让已知系统、对象、事件、数据和约定不能无声遗漏；
5. 让已知职责最终拆到足以理解、设计、实现和验证；
6. 不把公开证据无法证明的原站内部结构写成事实；
7. 允许我们的重构根据需求主动设计合理边界；
8. 让需求、证据、设计、代码和验证可以追溯；
9. 让未来复用判断基于真实场景，而不是提前制造通用系统；
10. 让当前治理先投入使用，项目后期再完成全范围覆盖收尾。

## 3. 保留现有体系

继续使用：

```text
sample/    原站公开证据、运行记录、分析和采集工具
doc/v0.1/  当前版本权威工程知识
src/       通过文档和 Human Gate 后的正式实现
```

继续保留：

- 需求分析；
- 概要设计；
- 详细设计；
- 验证；
- 逆向计划；
- `FACT / INFERRED / DECISION / UNKNOWN`；
- 原站理解状态；
- 重构工程状态；
- Human Gate；
- 实践驱动复用观察。

当前不新建重型顶层目录，不推倒现有体系。

## 4. 原站结构与重构结构分开

### 4.1 原站结构

描述原站实际采用的结构时，只能使用：

```text
FACT / INFERRED / UNKNOWN
```

必须受公开文件、运行时行为、Bundle、Network 等证据约束。不得无证据宣称原作者存在：

- 某个 TypeScript 类或源码目录；
- 统一实体基类；
- 统一事件总线；
- 私有状态；
- 未公开接口。

公开 Bundle 可以证明发布后的运行逻辑，但不能自动证明原始源码组织。

### 4.2 我们的重构结构

正式重构可以根据：

- 已确认的原站行为；
- 当前复刻目标；
- 状态所有权；
- 依赖方向；
- 生命周期和清理要求；
- 实现、测试与维护成本；
- Human 确认；

主动设计更清晰的模块边界。

这些结论必须标记：

```text
DECISION
```

并说明理由、影响和验收方式，通过对应 Human Gate。我们的设计不得冒充原站事实，公开证据不足也不能错误禁止合理重构。

## 5. 需求来源与决策台账

### 5.1 决策唯一标识

每条进入台账的结论必须具有唯一决策 ID，例如：

```text
DEC-DOC-GOV-001
```

ID 用于来源引用、Human 确认、拒绝记录、替代关系、持久化和验证追踪。

### 5.2 Human 接受依据

每条决策至少记录：

- Human 原始表述或可定位的会话记录；
- 接受日期；
- 接受者；
- 适用版本、阶段和节点；
- 是否涉及代码、破坏性操作或独立 Human Gate。

本决定的接受依据：

```text
Human 于 2026-08-10 要求：
“把这个给填充进去文档。定一个最终的方案文档放入 Obsidian。”
```

该表述确认选择当前收敛方案并要求形成最终方案文档，但没有授权修改旧 Phaser 项目、正式 `src` 或越过阶段 6B Gate。

### 5.3 多维字段

| 字段 | 可用值 | 回答的问题 |
|---|---|---|
| 内容性质 | `requirement / suggestion / example` | 这条材料是什么 |
| 决策状态 | `proposed / accepted / rejected / superseded / not-applicable` | Human 如何决定 |
| 持久化状态 | `pending / persisted` | 是否写入权威文件并进入必读链 |
| 验证状态 | `pending / verified` | 模板、阶段、链接和检查是否一致 |
| 替代关系 | 决策 ID 或链接 | 旧决定由谁替代 |
| 适用范围 | 版本、阶段或节点 | 在哪里有效 |
| 实施授权 | 由对应 Human Gate 记录 | 是否允许代码或其他受控操作 |

### 5.4 决策状态

```text
proposed
→ 只能讨论和比较，不能作为当前规则执行

accepted
→ Human 已确认，当前会话立即遵守

rejected
→ 不执行，保留记录和理由

superseded
→ 旧决定不再执行，必须跳转到替代决定

not-applicable
→ 对当前版本、阶段或节点不适用
```

## 6. 规则生效、持久化、验证和授权

### 6.1 当前会话生效

Human 明确接受后，只要没有被后续决定拒绝或替代，且版本、阶段和范围匹配，新决定在当前会话立即生效。

AI 必须停止执行与新决定冲突的旧规则，不能因为尚未落盘或验证而继续执行旧规则。

### 6.2 跨会话持久

决定写入权威文件并能由 AI 必读入口发现后，成为跨会话可发现的持久规则。

如果决定已接受但尚未完成权威同步，只能报告：

```text
已接受，待落盘
```

### 6.3 同步闭环完成

只有以下工作均完成后才能报告同步闭环完成：

```text
accepted + persisted + verified
```

其中 `verified` 至少包括：

- AI 必读链能够发现新规则；
- 受影响模板和状态已经同步；
- Human Gate 和当前阶段一致；
- 必要的一致性检查通过。

### 6.4 实施授权独立

规则生效不等于获得代码或破坏性操作授权。

例如：

```text
文档治理规则已经 accepted
但阶段 6B 尚未通过
所以不能进入阶段 6C 或写正式 src
```

代码实现、阶段推进、真实数据、安全、破坏性和不可逆操作继续由对应 Human Gate 和更高层安全规则决定。

## 7. 节点与证据治理

### 7.1 候选设计关注点

从权威输入中识别出的、可能具有独立职责、状态、行为、数据契约、验证价值或当前研究价值的内容，都属于候选设计关注点，必须有去向。

以下内容默认不机械创建独立节点：

- 单张图片和普通资源；
- 单个 NPC、车辆或地图块实例；
- 普通字段和常量；
- 函数内部步骤；
- 没有独立设计意义的局部变量；
- 已完整归属父节点的内部细节。

### 7.2 节点总账最小字段

节点总账维护：

- ID、名称、类型和父节点；
- 范围处置；
- 原站理解状态；
- 重构工程状态；
- 来源引用；
- 唯一主定义；
- 处置理由或合并目标；
- 优先级。

当前不增加：

```text
表达处置字段
定义状态线
```

只有地图分块或 NPC 试点出现现有字段无法表达的真实案例时，才允许提出最小新增。

### 7.3 思维导图与节点总账分工

```text
思维导图：Human 可读的系统级和重要分支导航
节点总账：AI 可检查的节点身份、关系、来源、状态和主定义
```

不把全部原子节点复制进思维导图。

### 7.4 唯一主定义

节点主定义可以是：

- 独立详细设计文件；或
- 父文档中带节点 ID、可独立链接的章节。

普通实例、字段和内部步骤不机械创建文件。

## 8. 证据边界下的拆分

### 8.1 UNKNOWN 不能掩盖已知职责

当公开证据证明一个粗节点包含多个独立职责时，必须进入节点总账或形成明确子定义，不能只在父节点写 `UNKNOWN` 后停止。

### 8.2 不得为原子化推测原站结构

证据不足时记录：

```text
原子边界未确认
+ 已有证据
+ 证据限制
+ 对设计或验收的影响
+ 后续调查条件
```

不得为了形式完整猜测原作者的类、模块、目录和私有状态。

### 8.3 分类停止指南

#### 系统

职责边界、依赖方向、状态所有权、公开协作方式和验收方式清楚；继续拆分只剩内部实现步骤时停止。

#### 对象

属性、状态、生命周期、管理系统和相关事件清楚；继续拆分只剩普通实例或字段时停止。

#### 事件

触发条件、参与者、正常流程、异常分支、状态变化和验证方式清楚时停止。事件不强制拥有独立状态或独立实现。

#### 数据与约定

适用范围、字段或规则、约束、使用者和验证方式清楚时停止。无状态约定不要求状态所有者。

#### 复用判断

稳定部分和变化部分只在第二个实际场景、复制逻辑或重复修改后分析，不作为普通节点拆分的前置门禁。

## 9. 文档唯一所有权

| 文档 | 唯一负责 |
|---|---|
| 需求来源与决策台账 | 材料性质、Human 决定、落盘、验证和替代关系 |
| 思维导图 | Human 可读的高层全景 |
| 节点清单 | 节点身份、关系、范围、状态、来源和主定义 |
| 证据追踪与实现差距 | 完整证据、旧代码、新代码和测试映射 |
| 未知问题队列 | 阻塞理解或设计的调查问题 |
| 复用观察表 | 真实重复、提取建议和 Human 决定 |

同一结论只在一个位置完整维护，其他位置使用 ID 或链接。

## 10. 两层验收

### 10.1 第一层：当前治理机制验收

用于证明机制能够运行，不要求整个原站已经逆向完成：

- [ ] 需求材料有稳定入口；
- [ ] 决策具有唯一 ID、Human 接受依据和日期；
- [ ] 内容性质、决策、持久化、验证和替代关系可以区分；
- [ ] 当前会话生效、跨会话持久和同步闭环的规则明确；
- [ ] 实施授权继续由独立 Human Gate 决定；
- [ ] 原站事实与重构决定不会混淆；
- [ ] 节点最小字段可以表达地图分块与 NPC 抽查；
- [ ] 最小一致性检查可以执行；
- [ ] AI 必读链、模板、当前阶段和 Human Gate 已同步；
- [ ] 验收版本、范围和证据基线已记录；
- [ ] Human 验收治理机制和试点结果。

完成后只能报告：

> 基于指定版本、范围和证据基线，当前治理机制已建立并通过试点验证。

### 10.2 第二层：项目最终覆盖验收

项目后期检查：

- [ ] 权威输入中的候选设计关注点均有去向；
- [ ] 已知职责达到分类停止指南；
- [ ] 原子边界未知记录证据限制、影响和后续条件；
- [ ] 合并、排除和不适用有理由；
- [ ] 已设计节点具有唯一主定义；
- [ ] 已实现节点具有代码和验证映射；
- [ ] 已关闭问题不再被权威文档当作开放 UNKNOWN；
- [ ] 复用候选具有真实场景和 Human 决定；
- [ ] 最终验收固定版本、范围和证据基线；
- [ ] 最终覆盖审计没有无声遗漏。

## 11. 正式验收基线

每次正式验收记录：

- 文档版本；
- Git 提交；
- 节点总账文件版本或哈希；
- 证据清单版本、哈希或提交；
- 当前范围；
- 验收日期；
- 已知例外；
- 未解决项；
- Human 验收结论。

禁止声称永久恢复了原站全部未知内容。

## 12. 最小一致性检查

优先自动检查可客观判断的内容：

1. 决策 ID 和节点 ID 唯一；
2. 父节点存在；
3. 范围状态合法；
4. 来源引用可以定位；
5. 已设计节点具有唯一主定义；
6. 主定义路径和 Markdown 链接存在；
7. 已关闭问题不再被权威文档写成开放 `UNKNOWN`；
8. `task_plan.md` 只有一个真实当前阶段；
9. 已实现节点有代码和验证映射；
10. 复用候选有真实场景和 Human 决定；
11. superseded 决策具有替代链接；
12. 当前有效规则的版本、阶段和范围匹配。

设计质量和事实判断继续由 Human 与 AI 语义评审。

## 13. 真实试点

### 13.1 地图分块

阶段 6B 经 Human 通过后，用 `SYS-CHUNK` 验证：

- 原站证据与重构决定正确分开；
- 已知职责按证据拆清；
- 节点最小字段足够；
- 分类停止指南可执行；
- 主定义、未知项和验收形成闭环。

### 13.2 NPC

只抽查：

- 候选来源和范围如何记录；
- 证据不足和边界未知如何表达；
- 非节点实例和仅证据内容如何归属；
- 是否真实需要新增表达处置。

当前不展开 NPC 详细逆向或实现。

## 14. 收敛规则

从本方案开始，不再因为理论上的“可能需要”增加字段、目录、状态或流程。

只有出现以下真实情况时才能提出新增：

1. 地图分块或 NPC 试点无法表达必要状态；
2. 一致性检查无法判断已经发生的断链；
3. Human 无法根据现有入口完成验收；
4. 换会话后 AI 无法发现或正确执行已接受规则；
5. 出现当前结构无法记录的真实重复、冲突或替代关系。

新增提案必须报告：

- 真实案例；
- 现有结构为什么无法表达；
- 最小修改；
- 收益；
- 成本；
- 迁移影响；
- 验证方式。

## 15. 实施顺序与授权边界

本方案已被 Human 选择为最终方案，当前会话应遵守本方案。接下来仍需单独完成：

1. 将决定同步到 AI 必读链和现有权威规则；
2. 建立正式需求来源与决策台账；
3. 同步受影响模板和状态；
4. 修正已经确认的状态漂移；
5. 建立最小一致性检查；
6. 完成持久化和验证后报告治理同步闭环；
7. 单独处理阶段 6B Human Gate；
8. Gate 通过后执行地图分块和 NPC 试点；
9. 固定基线并完成当前治理机制验收；
10. 继续逐系统逆向、设计、实现和验证；
11. 项目后期固定最终基线并完成覆盖验收。

当前授权已扩展为 `governance-sync-only`，只允许完成第18节规定的台账、入口、模板、状态、检查器和验证报告同步。当前仍然禁止：

- 修改旧 Phaser 项目；
- 写正式 `src`；
- 自动通过阶段 6B；
- 批量生成详细文档；
- 提取通用代码；
- 执行破坏性或不可逆操作。

## 16. 利益、代价与风险

### 16.1 主要收益

1. Human 当前决定在会话内立即得到遵守；
2. 跨会话规则可以稳定发现；
3. 完成性不会被提前虚报；
4. 原站事实和重构设计不会混淆；
5. 已知职责可以拆清，未知边界不会被伪造；
6. 节点和文档数量保持可控；
7. 当前治理不阻塞项目主线；
8. 正式验收可复现；
9. 历史拒绝和替代关系可追溯；
10. 新治理能力必须由真实案例触发。

### 16.2 代价和控制

| 代价或风险 | 影响 | 控制方式 |
|---|---|---|

## 18. 实施合同

> 本节是 Human 在第一轮修订中接受的最小实施合同，用于消除前文在台账位置、字段语义、迁移顺序和验收口径上的执行歧义。若本节与前文的概括性描述存在冲突，以本节的具体约束为准。具体治理文件的同步授权以 [[#18.9 当前同步授权边界]] 为准；本节不授权修改旧 Phaser 项目、正式 `src` 或阶段 6B 状态。

### 18.1 文档状态与决策状态

不同状态必须使用不同字段：

| 维度 | 字段 | 可用值 | 说明 |
|---|---|---|---|
| 文档治理 | `status` | `draft / proposed / approved` | 只表示文档本身是否成熟、是否经过评审 |
| Human 决策 | `decision-status` | `proposed / accepted / rejected / superseded / not-applicable` | 只表示 Human 对决定内容的处理 |
| 跨会话持久化 | `persistence-status` | `pending / persisted` | 只表示决定是否进入权威位置和 AI 必读链 |
| 同步验证 | `verification-status` | `pending / verified` | 只表示指定基线上的入口、模板、状态和检查是否一致 |
| 实施授权 | `implementation-authorization` 或对应 Human Gate | 由具体决定定义 | 只表示是否允许执行受控操作 |

因此本文使用：

```text
status: approved
decision-status: accepted
persistence-status: persisted
verification-status: pending
```

v0.2 接入必读链前的 `persistence-status` 为 `pending`；v0.3 已接入 `AGENTS.md` 与 `doc/v0.1/README.md`，因此为 `persisted`。`approved` 本身只证明本文内容已由 Human 评审，不单独证明权威同步、治理试点或代码实施完成。

### 18.2 需求来源与决策台账合同

正式台账的唯一权威路径为：

```text
doc/v0.1/需求来源与决策台账.md
```

当前不为治理单独新建重型顶层目录。台账必须进入 `doc/v0.1/README.md` 阅读链，并由项目机器入口指向该阅读链；v0.3 第二轮同步已完成该接入。

#### 来源最小字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 来源 ID | 是 | 格式 `SRC-YYYYMMDD-NNN`，创建后不得重编号或复用 |
| 内容性质 | 是 | `requirement / suggestion / example` |
| 标题与来源者 | 是 | 能识别材料及其提供者 |
| 来源日期 | 是 | 原始材料或沟通发生日期 |
| 权威位置 | 是 | 项目内相对路径、稳定外部 URI 或受控私有位置 |
| 版本或 SHA-256 | 是 | 文件使用 SHA-256；会话使用会话 ID 与消息定位 |
| 信任性质 | 是 | `human-original / project-authority / external-reference / ai-summary` |
| 访问级别 | 是 | `normal / restricted` |
| 备注 | 否 | 转写限制、图片缺失、隐私或保留期限 |

录音、图片和外部文件不能只记录桌面临时路径。允许因隐私不复制原始材料进 Git，但必须记录稳定受控位置、哈希和访问级别。AI 生成的会议摘要只能标记为 `ai-summary`，不得代替 Human 原文。原始外部材料不直接进入 AI 必读链；AI 必读链只进入经过评审的决定和必要索引。

#### 决策准入条件

出现下列任一情况时必须进入台账：

1. 改变项目范围、当前有效规则、状态模型或 Human Gate；
2. 影响多个权威文件的架构或治理决定；
3. Human 明确接受、拒绝、判定不适用或替代一个方案；
4. 授权或禁止代码、真实数据、破坏性、安全或不可逆操作；
5. 形成必须跨会话继续执行的重要例外或约束。

纯排版、错别字、局部非语义调整和不影响其他文件的普通维护不进入决策台账。

#### 决策最小字段

每条决策至少记录：

- 决策 ID、标题和准入理由；
- 来源 ID 与可定位的 Human 原文；
- 决策、持久化和验证状态；
- 适用版本、阶段和节点；
- Human Gate 或实施授权；
- 接受者、接受日期；
- 被替代决定或替代决定；
- 受影响文件清单；
- 验证基线和验证报告。

决策 ID 使用 `DEC-领域-NNN`；同一领域取下一个未使用编号。ID 创建后不得因排序、改名或替代而修改。

### 18.3 节点总账机器合同

节点总账统一维护以下列：

```text
ID / 名称 / 类型 / 父级引用 / 范围处置
/ 原站理解状态 / 重构工程状态 / 证据等级
/ 来源引用 / 唯一主定义 / 处置理由或合并目标 / 优先级
```

#### 合法值

```text
类型：系统 / 对象 / 事件 / 能力 / 数据 / 约定
范围处置：candidate / in-scope / out-of-scope
          / not-applicable / merged
原站理解状态：discovered / partial / confirmed
重构工程状态：undesign / designed / implemented / verified
证据等级：FACT / INFERRED / UNKNOWN，可用 `+` 组合
```

能力节点继续受现有门禁约束：只有原站证据或实际实践表明具有独立研究价值时才能登记。

#### 父级引用

父级只能使用：

- 已存在的节点 ID；
- 节点清单中概念分组表登记的 `GRP-*` ID；
- 根节点使用 `ROOT`。

`GRP-*` 只用于 Human 导航和层级校验，不是设计节点，不进入理解、工程或最终覆盖统计。禁止继续使用无法唯一解析的显示名称作为父级。

#### 来源引用

来源引用必须至少使用一种可解析形式：

- `SRC-*` 来源 ID；
- `CAP-* / BASE-* / Q-*` 等已有权威 ID；
- 项目相对路径加稳定定位符；
- 固定证据文件路径加哈希或 Bundle 搜索锚点。

检查器必须验证 ID 能在唯一所有者中解析，或路径、定位符和必要哈希存在；非空自然语言不能自动视为可定位来源。

#### 主定义与处置条件

- `undesign` 节点允许唯一主定义为 `—`；
- `designed / implemented / verified` 节点必须具有唯一主定义；
- 独立文件使用项目相对路径；
- 父文档章节使用 `相对路径#节点ID`，章节前必须有稳定显式锚点，例如 `<a id="SYS-CHUNK"></a>`；
- `out-of-scope / not-applicable / merged` 必须填写处置理由；
- `merged` 还必须填写唯一合并目标 ID；
- 其他状态的处置理由可以为 `—`。

### 18.4 持久化事务与中断恢复

每次已接受决定按以下固定顺序同步：

```text
1. 建立决策记录，列出受影响文件和决定优先级
2. 将决定接入 AI 必读链
3. 标记 persistence-status: persisted
4. 逐项同步受影响模板、状态和链接
5. 运行结构检查与语义审查
6. 在 clean Git 基线上固定验证报告
7. 标记 verification-status: verified
```

受影响文件清单逐项使用：

```text
pending / updated / verified
```

如果任务中断，下一会话先读取已持久化决定及该清单，继续未完成项。已接受且已接入必读链的决定优先于尚未迁移的旧模板；在冲突修复前，不执行依赖冲突部分的代码或阶段推进。

### 18.5 验证基线与失效规则

正式验证默认要求：

- Git 工作区 clean；
- 治理变更已经提交；
- `verified-commit` 指向实际受检提交；
- `verification-report` 指向可复核报告；
- `verified-at` 记录验证日期；
- Markdown 哈希优先使用 Git blob/tree，避免工作区换行转换造成差异。

只有 Human 明确批准例外时，才允许在 dirty 工作区验收；此时必须记录 HEAD、完整 diff 哈希、全部未跟踪文件哈希和例外理由。

以下任一受覆盖内容在 `verified-commit` 后发生变化时，相关 `verification-status` 必须回到 `pending`：

- 决定内容或适用范围；
- AI 必读入口；
- 受影响模板或状态；
- Human Gate；
- 一致性检查器或验收基线。

仅更新 `verified-at / verified-commit / verification-report / verification-status` 的验证证明提交，不使其所引用的受检基线失效；其他语义修改均需重新验证。

### 18.6 一致性检查分级

未来最小检查器的约定路径和命令为：

```text
sample/tools/check-doc-governance.py
python sample/tools/check-doc-governance.py --mode sync
python sample/tools/check-doc-governance.py --mode pilot
python sample/tools/check-doc-governance.py --mode final-coverage
```

检查模式：

| 模式 | 用途 | 最小范围 |
|---|---|---|
| `sync` | 决策权威同步 | 决策/节点 ID、入口链接、状态合法性、受影响文件、唯一当前阶段 |
| `pilot` | 当前治理机制试点 | `sync` 全部内容，加地图分块和 NPC 试点节点、主定义、来源与处置 |
| `final-coverage` | 项目最终覆盖验收 | `pilot` 全部内容，加固定输入清单中的全部候选去向、实现和验证映射 |

自动检查只判断结构化事实，例如 ID、枚举、路径、链接、父级和条件必填。以下内容必须进入独立语义审查：

- FACT、INFERRED、DECISION、UNKNOWN 是否判断正确；
- 职责是否拆到分类停止指南；
- 两个场景是否真的独立；
- 复用、排除和验收理由是否成立；
- 已关闭问题是否只是转化为更窄的新未知。

检查报告的权威位置为：

```text
doc/v0.1/怎么验证与还差什么（04）/文档治理一致性报告.md
```

报告必须分别列出自动检查和语义审查，不能用一个 PASS 代替两者。
