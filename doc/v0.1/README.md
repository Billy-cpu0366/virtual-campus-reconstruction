## 文档结构

| 目录 | 回答的问题 |
|---|---|
| `01-需求分析/` | 原站有什么、当前复刻什么 |
| `02-概要设计/` | 有哪些系统、对象和事件，它们如何协作 |
| `03-详细设计/` | 某个系统、对象、事件或数据具体怎样工作 |
| `04-验证/` | 证据在哪里，复刻与原站是否一致 |
| `05-逆向计划/` | 还有哪些问题没有弄清楚 |

## 结论性质

| 标记 | 含义 |
|---|---|
| `FACT` | 原站文件或运行时行为已直接证明 |
| `INFERRED` | 有证据支持，但仍包含推断 |
| `DECISION` | 我们重构时主动采用的设计 |
| `UNKNOWN` | 尚未弄清，需要继续逆向 |

## 两条状态线

```text
原站理解：discovered → partial → confirmed
重构工程：undesign → designed → implemented → verified
```

二者必须分开记录。确认原站行为，不等于已经完成自己的重构设计。`原站能力与行为清单` 记录可观察能力的理解状态，`节点清单` 记录系统/对象/事件节点的理解与工程状态，`证据追踪与实现差距` 记录证据到实现映射的调查状态；三者含义不同，不得相互代替。

## 当前有效原则

1. 当前先准确逆向和复刻原站，不提前设计完整校园产品或万能引擎。
2. `系统 / 对象 / 事件 / 数据与约定` 是中性研究分类，不代表最终代码目录。
3. 不预设哪些内容可复用；第一次出现先正确研究和实现。
4. 第二个独立实际场景出现相同行为，或同一逻辑被重复修改时，才登记复用观察。
5. 多个真实场景显示出稳定部分和变化部分后，才能提出提取方案；未经 Human 确认不得自行抽象。
6. 可复用成果不限于系统，也可能是数据格式、算法、UI、工具、测试能力或工程约定。
7. 原站复刻可以证明理解和当前实现，未来校园的真实使用才证明跨项目复用。

## 按需门禁触发表

未触发的规则不增加当前流程；一旦触发，AI 必须先补齐对应约束再继续。

| 触发条件 | 必须启用的规则 |
|---|---|
| 开始第一份正式详细设计 | 精确定位关键证据，说明节点状态和阻塞未知项 |
| 准备建立正式 `src/` | 明确实现范围、行为基准、失败路径和 Human 准入 |
| 实现拥有对象、监听器或计时器的模块 | 定义创建、销毁、失败回滚和清理路径 |
| 实现异步资源加载或网络请求 | 定义超时、失败、重试、取消和降级路径 |
| 出现第二个独立相似场景 | 更新详细设计入口中的复用观察表 |
| 准备提取复用成果 | 报告真实场景、稳定部分、变化部分、收益、成本和风险，并取得 Human 确认 |
| 出现正式代码 | 建立对应节点、设计、代码和验证结果的映射 |
| 出现并行写入 | 指定唯一写入者，禁止同时修改同一文件或节点 |
| 文档框架验收后再次发生断链、漏更新或状态漂移 | 建立相应的自动文档一致性检查 |
| 进入性能敏感系统 | 定义加载、内存、帧率或资源清理基准 |
| 进入校园真实开发 | 验证哪些候选完成了跨项目复用 |

## 维护规则

1. 一个结论只保留一个主要归属，其他文档使用链接。
2. 推断不能写成事实，重构决定不能冒充原站结构。
3. 节点有证据且近期需要研究时，才晋升为独立详细文档。
4. 每轮实现前先确认对应文档和验收标准，实现后回写差异。
5. 每次详细设计或实现任务开始和结束时，检查 [[03-详细设计/README]] 中的复用观察。
6. 检查是否触发按需门禁；未触发时不得自行增加额外流程。
7. 当前文档均为 `draft`；Human 验收后再改为 `approved`。
