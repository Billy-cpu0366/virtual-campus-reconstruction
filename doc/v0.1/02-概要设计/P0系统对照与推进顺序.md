# P0系统对照与推进顺序

本文回答：原站P0系统与旧 Phaser 复刻相比，哪里已经有参考实现、哪里明确缺失、哪里仍需逆向，以及下一步先研究什么。这里的顺序是调查顺序，不是最终源码目录或实现顺序。

## 1. 判断口径

- `FACT`：公开文件、运行时Network、Bundle或旧代码直接证明；
- `INFERRED`：证据支持但仍需运行验证；
- `DECISION` + `decision-status: proposed`：阶段6B提出的推进建议，Human确认后才进入下一阶段；
- 旧代码“已有”只表示存在实现，不表示与原站一致；
- 旧代码“缺失”也不等于必须照搬原站内部写法。

## 3. 地图分块新增事实

### 数据关系（FACT）

- `master.json`：`chunkWidth=28`、`chunkHeight=28`、横向5块、纵向5块、原图140×140；
- 每个chunk：28×28、16px tile、24个同名图层、相同3个tileset；
- 文件名公式：`chunk{y * nbChunksHorizontal + x}.json`；
- 按行优先顺序拼接25块，24个图层与`final_map.json`逐格完全一致，错位数为0；
- 按列优先拼接会导致24层全部不匹配。

### 运行机制（FACT）

Bundle显示：

1. ChunkManager读取master并缓存已加载数据；
2. GameScene计算玩家当前chunk周围3×3集合；
3. 同时计算相机可见范围，并额外扩展1块边距；
4. 加载目标集合中尚未加载的chunk；
5. 卸载目标集合外chunk，并从Tilemap相应区域清除格子；
6. chunk索引、缓存键和世界坐标均使用`x_y`或`y*横向数量+x`关系。

### Network表现（FACT）

本次1920×1080采集中：

- master在导航后约5.194秒返回；
- 首个chunk约在5.800秒、最后一个约在6.730秒返回；chunk响应自身跨度约0.930秒，master到最后一个chunk约1.536秒；
- 这些请求发生在采集脚本14秒Ready检查和Play点击之前；
- 四方向输入期间没有新chunk URL。

Bundle同时显示：`startCameraSequence()` 在Play前启动相机展示，并延迟100ms调用 `preloadChunksForCameraSequence()`；该方法汇总六个相机位置、视口范围和2块边距，通过空闲回调依次预载。其有效坐标覆盖当前5×5地图，因此解释了首屏请求全部25块。Q-MAP-003已关闭。

## 4. 建议调查顺序（DECISION，decision-status: proposed）

```text
1. 地图分块
2. 世界装配与图层边界
3. 分块所需资源加载与失败路径
4. 玩家、输入、移动与碰撞
5. 相机完整行为
```

判断理由：

- 分块公开证据最完整；
- 旧复刻对分块完全缺失，差距最大且最明确；
- 世界和图层依赖分块坐标与生命周期；
- 玩家、碰撞和相机已有可运行参考，可以在地图基础稳定后量化；
- 先做通用资源系统会扩大范围，因此第一圈只处理分块所需接口。

代价与风险：

- Bundle只能证明公开发布实现，不能恢复原始TypeScript边界；
- 图层装卸与分块紧密相连，第一份文档必须明确边界，避免把所有地图逻辑塞入分块系统；
- 已确认首屏相机序列会预载全部25块，但尚未建立首次加载耗时和内存验收指标；
- 第一系统设计通过前仍不能写正式`src/`。

## 5. 首个详细逆向任务（DECISION，decision-status: proposed）

建议首个系统：`SYS-CHUNK 地图分块`。

### 纳入范围

- master与chunk数据契约；
- 世界坐标、chunk坐标和文件索引换算；
- 当前chunk、目标集合和已加载集合；
- 加载去重、缓存、失败和取消边界；
- 相机可见范围与玩家邻域作为输入；
- chunk写入和清除Tilemap的职责边界；
- 创建、卸载和销毁路径；
- 对应原站行为基准。

### 不纳入范围

- 所有图层的最终depth和视觉规则；
- NPC、车辆和路线；
- 玩家移动参数；
- 通用资源加载框架；
- 最终源码目录和复用提取。

### 进入详细设计前的验收点

- 关键Bundle位置可通过搜索锚点重复定位；
- 25块重组测试结果可重复；
- 首屏相机序列预载与玩家阶段动态装卸的边界已写清；
- 分块系统负责与不负责的内容获得Human确认。

## 6. 当前结论

阶段6B建议先选择地图分块，不是因为它未来一定可复用，而是因为它证据最完整、旧代码缺口最大、能最早验证当前逆向流程。详细差距主表仍维护在 [[../04-验证/证据追踪与实现差距]]，未知问题维护在 [[../05-逆向计划/未知问题队列]]。
