## 一、骨架落地

### 骨架 1：图层策略表——一张表管所有层

> 理解层说的是"不是写死每层干嘛的，而是一张策略表集中定义"。
> 在代码里，这张表叫 **`LAYER_STRATEGIES`**，是 24 层的唯一合同。

**它怎么工作的**：

`LAYER_STRATEGIES` 是一个 24 项的数组，顺序与 chunk JSON 的层顺序严格一致（25 个 chunk 的层名和顺序完全相同，已通过逐文件验证）。每项定义了：

```
{
  name: "layer1",          // 层名（与 chunk JSON 中的 name 字段对应）
  role: "visual",          // 角色：visual | collision | marker | dynamic-visual | dynamic-collision
  depth: 100,              // 设计默认 depth
  // marker 层特有：
  markerGids: [69345, ...] // 允许的 marker GID 白名单
  // raw visual 层特有：
  rawGids: [69355, ...]    // 允许直接写入 Tilemap 的 GID 白名单
}
```

其他代码通过 `layerStrategy(name)` 按名查询策略、通过 `layerRole(name)` 查询角色——不直接操作数组。这意味着策略表的内容可以随便改，查询逻辑不变。

**24 层全景**：

| 索引    | 层名                         | 角色                | depth     | 备注                          |
| ----- | -------------------------- | ----------------- | --------- | --------------------------- |
| 0-4   | layer1~5                   | visual            | 100-500   | 静态视觉，地面与建筑底层                |
| 5-9   | layer6~10                  | visual            | 1500-1900 | 玩家上方视觉层                     |
| 10    | cars                       | marker            | 550       | 车辆路线 marker（8 个 GID）        |
| 11-14 | roof_concert~roof_factory2 | dynamic-visual    | 3000-3300 | 屋顶动态淡隐                      |
| 15-18 | bridge1/2_up/down_wall     | dynamic-collision | 3500      | 桥上下碰撞/遮挡                    |
| 19    | walls                      | collision         | 550       | 隐藏碰撞层（GID 69345 是墙）         |
| 20    | particles                  | visual            | 0         | raw visual（GID 69355-69359） |
| 21    | particles2                 | visual            | 0         | raw visual（GID 69355-69359） |
| 22    | particles3                 | marker            | undefined | marker（GID 69361），消费者未知     |
| 23    | footsteps                  | marker            | undefined | 脚印 marker（GID 69345）        |

### 骨架 2：Y 排序动态遮挡——越在下面的越遮人

> 理解层说的是"玩家越往下走、深度值越高、越容易被上层遮住"。
> 在代码里，玩家深度公式在 **`playerDepth()`** 中。

**深度公式**：

```typescript
// src/layer/depth.ts 第 6-8 行
export function playerDepth(worldY: number): number {
  return 500 + (worldY + 24) * 0.1;
}
```

- 玩家出生点在 Y≈304 时：depth ≈ 500 + (304+24)×0.1 = 532.8
- 走到地图最底 Y≈2240 时：depth ≈ 500 + (2240+24)×0.1 = 726.4
- 常态范围在 500~726 之间，位于 layer5（depth 500）和 layer6（depth 1500）之间
- 所以在 layer6-10 的视觉元素（上层灌木、建筑顶部）会遮住玩家下半身

**桥上例外**：

```typescript
// src/layer/depth.ts 第 10 行
export const BRIDGE_PLAYER_DEPTH = 1650;
```

玩家上桥时，depth 被强制拉到 1650——介于 layer6（1500）和 layer7（1600）之上、layer8（1700）之下。这是为了让玩家正确出现在桥的上层。

**walls 深度来源**：

```typescript
// src/layer/depth.ts 第 15-19 行
const wallsDepth = layerStrategy("walls").depth;
export const WALLS_DEPTH = wallsDepth; // 550
```

walls 的深度不是硬编码的，而是从 LAYER_STRATEGIES 中派生——保证单一来源。

### 骨架 3：区域触发 + 状态切换

> 理解层说的是"玩家进入区域→改状态→退出→恢复"。
> 在代码里，屋顶淡隐和桥上下切换是两个独立的实现。

**屋顶淡隐**：

```typescript
// src/layer/depth.ts 第 11 行
export const ROOF_FADE_MS = 300;

// src/layer/depth.ts 第 34-36 行
export functoin roofAlpha(state: RoofState): number {
  return state === "visible" ? 1 : 0;
}````

屋顶状态有两个值：`"visible"`（alpha=1，不透明）和 `"faded"`（alpha=0，透明）。切换时长 300ms（来自原站 Bundle 的 tween 参数）。

四个 roof 层分两组：concert（roof_concert + roof_concert2）和 factory（roof_factory + roof_factory2）。同一组的两层同时淡隐/恢复。

**桥上下切换**：

桥区域定义在 `bridge-zones.ts` 中，以 16px tile 坐标为单位的矩形区域：
- bridge1：entry zone 4 个矩形、exit zone 4 个矩形
- bridge2：2 个矩形区域（进入即翻转）

入口/出口判定用 `containsAny()` 逐矩形检查。bridge1 的入口与出口有重叠格——入口优先。

桥状态 `"up"` / `"down"` 切换时，三件事同步更新：
1. 上/下墙图层的可见性切换
2. 对应 tile 的碰撞属性翻转
3. 玩家 depth 被覆盖为 BRIDGE_PLAYER_DEPTH（桥区）/ 恢复常态（离开）

### 骨架 4：视觉层和标记层分开

> 理解层说的是"有些层是看的、有些层是查的，数据和显示分离"。
> 在代码里，通过 **`LayerRole`** 区分五种角色。

**五种角色的处理方式**：

| 角色 | 处理方式 | 写入去向 |
|---|---|---|
| `visual` | 28×28 tile 数据直接写入 Tilemap | Phaser Tilemap layer |
| `collision` | 提取碰撞 GID，输出碰撞网格 | 物理引擎碰撞面 |
| `marker` | 提取白名单 GID，输出 marker 集合（含世界坐标） | 给消费者系统（车辆/粒子/脚印） |
| `dynamic-visual` | 同 visual + 额外动态状态（可见性/alpha） | Tilemap layer + 状态管理 |
| `dynamic-collision` | 同 collision + 桥上下切换逻辑 | 碰撞面 + 桥状态管理 |

**marker 提取流程**：

```
extractMarkerRecords(layerName, data, chunk, ...)
        │
        ├─ ① 校验层角色必须是 "marker"
        ├─ ② 遍历 data 数组（28×28=784 格）
        │     gid === 0 → 跳过（空格）
        │     gid ∈ markerGids 白名单 → 生成 LayerMarkerRecord
        │         含：layerName, gid, localTile, worldTile, worldPixel, chunk
        │     gid ∉ markerGids → 抛出错误（未知 marker GID）
        │
        └─ ③ 返回只读 marker 记录数组（用于后续写入 World）
```

**particles3 诊断**：

```typescript
// src/layer/markers.ts 第 134-149 行
export function diagnosticForMarker(
  marker: LayerMarkerRecord,
): LayerDiagnostic | undefined {
  if (marker.layerName !== "particles3") {
    return undefined;
  }
  return {
    kind: "unconsumed-marker",
    layerName: "particles3",
    gid: marker.id,
    message: "particles3 marker 尚未接入消费者",
  };
}
```

particles3（GID 69361）的 marker 被保留并明确报告"消费者未接入"。不会因为与 `protesters_rising` 计数吻合就宣称完成、也不会静默删除。

### 骨架 5：对称的放块/撤块

> 理解层说的是"怎么放的就怎么撤，一一对应不留残余"。
> 在  代码里，对称性由 marker 的 `chunk` 来源字段保证。

**对称性保证机制**：

每个 `LayerMarkerRecord` 都记录了 `chunk: ChunkCoordinate`——标记了"这个 marker 来自哪一块"。撤块时，按 chunk 来源撤销：

```
apply 放块：extractMarkerRecords() → 产出 marker 数组，每个带 chunk 来源
remove 撤块：按 chunk 坐标找到所有 marker → 全部撤销

关键：marker 不是全局唯一、没有名字的散装数据——每个 marker 都有"户口"（chunk 来源）。
这样撤块时不会多删（删了别人的 marker）也不会漏删（留下孤儿 marker）。
```

图层的 apply/remove 对称性在 PhaserWorldRenderer 中实现——apply 时创建 visual layer、登记 marker；remove 时清除对应 28×28 区域、撤销 chunk 来源的所有 marker 引用。

**代码在哪**：

|---|---|--|
| marker 的 chunk 来源 | [src/layer/markers.ts](../../src/layer/markers.ts) 第 18-27 行 | `LayerMarkerRecord` 的 `chunk` 字段 |
| Phaser 对称实现 | [game/PhaserWorldRenderer.ts](../../game/PhaserWorldRenderer.ts) | apply/remove chunk 的对称处理 |
