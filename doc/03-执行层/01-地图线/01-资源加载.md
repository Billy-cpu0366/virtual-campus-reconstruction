## 一、骨架落地 —— 每根骨头对应哪块代码

### 骨架 1：一条固定的流水线

> 理解层说的是"游戏从启动到能玩，要经过固定步骤"。
> 在代码里，这条流水线叫做 **AppRuntime**。

**它怎么工作的**：

```
BOOT（刚打开网页）
  │  用户啥也没干，自动进入 LOADING
  ▼
LOADING（正在下载资源）
  │  进度跑到 100% 后自动进入 READY
  ▼
READY（下载完了，等用户点 Play）
  │  用户点了 Play 按钮
  ▼
ENTERING_GAME（开场动画：火车+航拍）
  │  动画播完
  ▼
PLAYING（用户可以操控小人走路了！）
```

每一步之间的跳转都有"安检"——比如已经在 PLAYING 了就不能再跳回 LOADING，防止错乱。

**代码在哪**：

- 步骤定义：[src/app/contract.ts](../../src/app/contract.ts) —— 定义了 9 种状态（BOOT / LOADING / READY / ENTERING_GAME / PLAYING / MODAL_OPEN / ERROR / RETRYING / SHUTDOWN）
- 流水线引擎：[src/app/runtime.ts](../../src/app/runtime.ts) —— `AppRuntime` 类负责管状态跳转，但**它不碰任何 DOM、不碰任何 Phaser 代码、不碰任何定时器**，它是纯逻辑，可以脱离浏览器独立测试
- 粘合层：[game/main.ts](../../game/main.ts) —— 把 `AppRuntime` 和真实的 Phaser 游戏粘在一起。比如"进入 LOADING 状态时"实际要做的操作是创建 `Phaser.Game` + 创建 `CampusScene`

**怎么验证它做对了**：`tests/app/runtime.test.ts` 测试了所有状态跳转——从 BOOT 正常走到 PLAYING、中途 cancel、cleanup、retry，全部有自动化测试。

### 骨架 2：实时告诉你"下载到多少了"

> 理解层说的是"下载过程中不断告诉进度条到多少了"。
> 在代码里，这叫 **onProgress 回调**。

**它怎么工作的**：

Phaser 引擎每下载完一个文件，会自动报告"我又完成了一个"。我们的代码把这个内部数字换算成 0~1 之间的小数（0 代表 0%，1 代表 100%），然后交给 AppRuntime 去更新页面上的进度条。

**核心约定**：进度值**只能增加，不能倒退**。如果有代码试图报告一个比之前更小的值，`AppRuntime.reportProgress()` 会直接忽略它——防止进度条倒着走。

**代码在哪**：

- 回调接口定义：[src/app/contract.ts](../../src/app/contract.ts) —— `AppLoadCallbacks` 里有三个回调：`onProgress`（报进度）、`onReady`（全完了）、`onError`（出错了）
- 各阶段上报：[game/CampusScene.ts](../../game/CampusScene.ts) —— 多处手工上报：
  - 第 480-485 行：Phaser 下载图片时的进度，乘以 0.72 上报
  - 第 1311 行：master.json 下载完成 → 上报 0.80
  - 第 1382 行：World 对象创建完成 → 上报 0.88
  - 第 1516 行：开始下载 chunk → 上报 0.92
  - 第 1519 行：chunk 全部就位 → 上报 0.98
  - 第 1630 行：全部搞定 → 上报 1.00

**为什么分这么多阶段上报**：

因为加载过程不是一下子全下载完的。先下图片（快），再下数据（慢）。如果不分段报，用户看着进度条半天不动，会以为卡死了。

**现在的比例**：
```
图片部分：  ████████████████████████████████████████████████████████████████████████  72%
数据部分：  ████████████████████████████████                                            28%
```

### 骨架 3：图片和数据分开运输

> 理解层说的是"图片走引擎通道，数据走普通通道"。
> 在代码里，图片走 **Phaser Loader**，数据走 **fetch()**。

**为什么分开**：

- Phaser Loader 下载完图片后会自动做各种处理（比如把图片切成精灵帧、把 JSON 解析好存起来），这些处理只有它自己能做
- 纯数据（比如一块地图的坐标信息）不需要这些处理，直接用浏览器自带的 `fetch()` 下载就行，更轻量

**代码在哪**：

| 通道 | 代码位置 | 下载内容 |
|---|---|---|
| Phaser Loader | [game/CampusScene.ts](../../game/CampusScene.ts) `preload()` 第 585-593 行 | 地图底图、碰撞标记图、粒子图、玩家精灵表 |
| Phaser Loader | 各个 Runtime 的 `preload()` 方法 | 火车图、烟雾图、车辆图、NPC图、人群图……（总计 12 个 Runtime 各自注册自己要的图） |
| fetch() | [game/CampusScene.ts](../../game/CampusScene.ts) `initializeDynamicWorld()` 第 1303 行 | 通过 `ChunkDataStore` 下载 `master.json` 和 25 个 chunk JSON |

**要注意的坑**：Phaser Loader 下载的东西随场景销毁自动清理；`fetch()` 下载的东西需要手动管理（用 `AbortController` 取消、用 `ChunkDataStore.destroy()` 清理）。两套东西的生命周期不同，销毁时别忘了各管各的。

### 骨架 4：不写死要下载什么，按清单下载

> 理解层说的是"不写'下载第1到第16块'，而是读一份 JSON 清单，上面有什么就下载什么"。
> 在代码里，这叫 **discoverOptimizedTilesets（自动发现切块）**。

**它怎么工作的**：

```
① 先下载 final_map_small.json（一份"地图说明书"）
        │
        ▼
② 说明书里有一个 tilesets 数组，格式大概是这样：
   [
     { "name": "exterior-small",      "image": "exterior-small.webp" },
     { "name": "exterior-small-2",    "image": "exterior-small-2.webp" },
     { "name": "exterior-small-3",    "image": "exterior-small-3.webp" },
     ...
   ]
        │
        ▼
③ 代码执行 discoverOptimizedTilesets(tilesets)：
   - 跳过不含 "exterior-small" 的 → 不是我们要的
   - 跳过就叫 "exterior-small" 的 → 这是基础版，不是切块
   - 剩下的 → 按名字拆出编号，拼成 key（如 "exterior-2"）和 URL
        │
        ▼
④ 得到的结果：
   [
     { key: "exterior-2",  url: "/assets/maps/exterior-small-2.webp" },
     { key: "exterior-3",  url: "/assets/maps/exterior-small-3.webp" },
     ...
     { key: "exterior-16", url: "/assets/maps/exterior-small-16.webp" },
   ]
   共 15 个切块
```

**代码在哪**：

- 核心算法：[src/asset/tilesets.ts](../../src/asset/tilesets.ts) —— `discoverOptimizedTilesets()` 函数，约 20 行代码
- 类型定义：[src/asset/contract.ts](../../src/asset/contract.ts) —— `TilesetEntry`（输入格式）和 `DiscoveredTileset`（输出格式）
- URL 拼接：[src/asset/urls.ts](../../src/asset/urls.ts) —— `tilesetImageUrl(image)` 拼出完整 URL

**测试覆盖**（[tests/asset/tilesets.test.ts](../../tests/asset/tilesets.test.ts)）：
- ✅ 空列表 → 不崩溃，返回空
- ✅ 没有切块 → 返回空
- ✅ 基础项自身 → 被排除
- ✅ 单个切块 → key 和 URL 正确
- ✅ 完整的 15 个切块（2~16）→ 全部正确发现

### 骨架 5：可以随时"取消"和"清理"

> 理解层说的是"加载到一半不想要了，要知道怎么停、怎么收摊、怎么重来"。
> 在代码里，这三件事叫 **cancel / cleanup / retry**。

**三件事分别怎么做的**：

| 操作 | 什么时候触发 | 实际发生了什么 |
|---|---|---|
| **取消** (cancel) | 新的加载开始了，旧的还没完成 | 设一个 `cancelled = true` 标志位。之后所有"下载完了"的回调都会先检查这个标志，如果取消了就不往下走了 |
| **清理** (cleanup) | 用户关网页 / 点 Retry / 出错 | ① 先 cancel 旧的 ② 调场景的 `shutdownForGeneration()` 把所有 Runtime 逐个关掉 ③ `game.destroy(true)` 销毁 Phaser 实例并删掉 canvas |
| **重试** (retry) | 加载失败了，用户点 Retry 按钮 | ① cleanup 旧的那一代 ② 确认清干净了 ③ 重新 `beginLoading()` 开新一代 |

**代码在哪**：

- 状态机层：[src/app/runtime.ts](../../src/app/runtime.ts)
  - `shutdown()` 第 188-195 行 → 切到 SHUTDOWN 状态，触发清理
  - `retry()` 第 60-83 行 → ERROR → RETRYING → cleanup → 重新开始
  - `cleanupGeneration()` 第 236-275 行 → 先 cancel handle，再调 effects.cleanup，最后标"已清理"
- 实际执行层：[game/main.ts](../../game/main.ts) 第 245-260 行
  - `cancel()` → `active.cancelled = true`
  - `cleanup()` → `scene.shutdownForGeneration()` + `game.destroy(true)`
- 场景清理：[game/CampusScene.ts](../../game/CampusScene.ts) `performShutdown()` 第 1186-1282 行
  - 逐个 shutdown 所有 Runtime（入口动画、火车、喷水器、NPC、人群、烟雾、车辆、脚步……）
  - 移除键盘监听、窗口事件监听
  - 销毁动态世界（coordinator + worldRenderer + dataStore）

## 三、配置点 —— 现在硬编码，将来后端下发

这些值现在是直接写在代码里的（硬编码），将来后端管理系统可以改它们：

| 能改什么      | 现在硬编码在哪                                                                                      | 现在的值                                      | 将来                                   |
| --------- | -------------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------ |
| 资源清单地址    | 无，清单直接写在 `preload()` 和 12 个 Runtime 里                                                        | 分散在各处                                     | 一个 JSON URL 统一下发                     |
| 各类资源的进度占比 | [game/CampusScene.ts](../../game/CampusScene.ts) 第 173-178 行                                 | `0.72 / 0.80 / 0.88 / 0.92 / 0.98 / 1.00` | 后端配置                                 |
| 失败了要不要重试  | [src/app/runtime.ts](../../src/app/runtime.ts) `fail()` 方法                                   | 不重试，直接 ERROR                              | 可配：重试 N 次、间隔多久                       |
| 要不要缓存     | 无代码                                                                                          | 不缓存                                       | 可配：none / Service Worker / IndexedDB |
| 超时时间      | 无代码                                                                                          | 无（依赖浏览器默认）                                | 可配：每种资源单独设超时                         |
| 失败了怎么降级   | [src/app/runtime.ts](../../src/app/runtime.ts) `fail()` + [game/main.ts](../../game/main.ts) | 进入错误页，显示 Retry                            | 可配：错误页 / 静默跳过 / 占位图                  |
