## 一、骨架落地

### 骨架 1：按需加载——不把整张图一次性全塞内存

> 理解层说的是"不管地图多大，内存里只保留玩家周围一圈"。
> 在代码里，这套机制由 **`ChunkCoordinator`** 驱动，由 **`ChunkDataStore`** 负责数据存取。

**它怎么工作的**：

```
ChunkCoordinator.updateTargets(newTargets)
        │
        ├─ ① 更新内部目标集合（#targets Map）
        │
        ├─ ② 扫描已渲染块：不在新目标集合里的 → removeIfCurrent()
        │     └─ 调用 World.removeChunk() 从画面清除
        │
        ├─ ③ 扫描新目标集合：
        │     已经在画面上的 → 跳过
        │     已经在缓存里的 → applyIfCurrent()（直接写，不用重新下载）
        │     已经在下载中的 → 复用已有的在途 Promise（不重复请求）
        │     已经失败过且未重试 → 跳过（等待下次更新或手动 retry）
        │     全新的 → 发请求下载
        │
        └─ ④ 等待所有 Promise 完成（await Promise.all）
```

**`ChunkDataStore`** 封装了数据层的全部复杂度：

| 职责 | 实现 |
|---|---|
| master 加载 | `loadMaster()` —— 解析 `master.json`，缓存结果，失败可重试 |
| chunk 加载 | `loadChunk(coord)` —— 按坐标下载 `chunk{index}.json`，校验结构 |
| 在途去重 | `#inFlight` Map —— 同一坐标只保留一个 Promise，后续请求复用 |
| 失败记录 | `#failures` Map —— 记录坐标、错误类别、尝试次数 |
| 缓存管理 | `#cache` Map —— 成功下载的 chunk 数据缓存 |
| 取消支持 | `#aborController.abort()` —— 通过 `AbortSignal` 取消所有请求 |
| 销毁 | `destroy()` —— 清空所有缓存、失败记录、在途请求，触发 abort |

### 骨架 2：目标集合公式——玩家邻域 + 相机可见范围

> 理解层说的是"加载哪些块 = 玩家周围 3×3 + 相机能看到的多一圈"。
> 在代码里，公式的实现分布在三个函数中，最终由 **`targetChunks()`** 合并。

**三层计算**：

```
① playerNeighborhood(worldX, worldY, geometry, radius=1)
   玩家世界坐标 → 算出他站在哪块 → 外扩 1 圈 → 边界裁剪
   返回：比如 9 个坐标（3×3，如果不在边缘）

② cameraVisibleChunks(viewport, geometry, padding=1)
   相机 scrollX/Y + width/height/zoom → 算出可见 tile 范围 → 外扩 1 块边距
   返回：比如 6 个坐标

③ targetChunks(playerWorldX, playerWorldY, viewport, geometry)
   = mergeChunkCoordinates(  ← 合并去重
       playerNeighborhood(...),
       cameraVisibleChunks(...),
     )
   返回：比如 12 个坐标（9+6-3重叠=12）
```

**玩家邻域算法**（`playerNeighborhood`）：

```
worldToChunkCoordinate(worldX, worldY, geometry)
  → chunkPixelWidth = 28 × 16 = 448px
  → centerX = floor(worldX / 448)
  → centerY = floor(worldY / 448)

外扩 radius=1 → startX = max(0, centerX-1), endX = min(4, centerX+1)
遍历 (startX..endX) × (startY..endY) → 返回坐标数组
```

**相机可见算法**（`cameraVisibleChunks`）：

```
viewport: scrollX, scrollY, width, height, zoom

可见世界像素范围：
  endWorldX = scrollX + width / zoom
  endWorldY = scrllY + height / zoom

转 tile 坐标：
  startTileX = floor(scrollX / 16)
  endTileX   = ceil(endWorldX / 16)

转 chunk 坐标（外扩 padding=1）：
  startX = max(0, floor(startTileX / 28) - 1)
  endX   = min(4, ceil(endTileX / 28) + 1)
```

**合并去重**（`mergeChunkCoordinates`）：

```
用 Map<"x_y", ChunkCoordinate> 去重
最后按 y 再 x 排序返回
```

### 骨架 3：三种状态严格分开——下载了 ≠ 显示着 ≠ 正在请求

> 理解层说的是"三种状态有三个所有者，不能混"。
> 在代码里，这是通过三个独立的数据结构实现的。

**三态对照表**：

| 状态 | 所有权 | 数据结构 | 查询方式 |
|---|---|---|---|
| 已下载（缓存） | `ChunkDataStore` | `#cache: Map<string, ValidatedChunk>` | `store.getCached(coord)` / `store.hasCached(coord)` |
| 正在请求（在途） | `ChunkCoordinator` | `#requesting: Map<string, Promise<void>>` | `coordinator.requesting` getter |
| 已显示（渲染） | `WorldImpl` | `#rendered: Map<string, ValidatedChunk>` | `world.renderedChunks` getter / `coordinator.rendered` |

外加两个辅助状态：

| 状态 | 所有权 | 数据结构 |
|---|---|
| 加载失败 | `ChunkDataStore` | `#failures: Map<string, ChunkLoadFailure>` |
| 写入失败 | `ChunkCoordinator` | `#worldFailures: Map<string, ChunkCoordinatorFailure>` |

**状态可观察性**：

```
coordinator.state → ChunkCoordinatorState {
  targets,      // 当前目标集合
  rendered,     // 当前已显示（从 world.renderedChunks 映射）
  requesting,   // 当前在途请求
  cached,       // 当前缓存（从 store.cachedChunks 映射）
  failed,       // 所有失败记录（store.failures + worldFailures）
  destroyed,    // 是否已销毁
}
```

整个系统的状态可通过 `coordinator.state` 一行代码完整观察——这对调试和验证极其有用。

### 骨架 4：过期守卫——晚到的数据不准污染世界

> 理解层说的是"HTTP 请求回来时要再检查一遍——世界还活着吗、坐标还在目标集合里吗"。
> 在代码里，守卫分布在四个检查点。

**四层守卫**：

```
第一层：请求级别（ChunkDataStore）
  #throwIfDestroyed() → destroyed 或 abort 信号已触发 → 抛 ChunkRequestAbortedError
  位置：loadMaster() 第 216/232/236/242/306 行，loadChunk() 第 314/354/373/407/414/437 行

第二层：协调级别（ChunkCoordinator.#applyIfCurrent）
  检查 destroyed | !targets.has(key) | 已经在画面上了
  任一为真 → 直接 return，不写世界
  位置：coordinator.ts 第 240-48 行

第三层：写入级别（WorldImpl.applyChunk）
  检查 state !== "ready"
  不 ready → return { kind: "failure", reason: "世界未就绪，拒绝写入" }
  位置：world.ts 第 104-106 行

第四层：异步写入中间检查（WorldImpl.applyChunkAsync）
  每层写入之间检查 state !== "ready"
  变了 → 抛异常 → 触发回滚
  位置：world.ts 第 167-168 行 / 175-176 行
```

**请求取消**：

```typescript
// data-store.ts 第 177 行
#abortController = new AbortController();

// destroy() 第 273 行
this.#abortControler.abort(); // 取消所有在途 fetch

// destroy() 后清理
this.#master = undefined;
this.#cache.clear();
this.#inFlight.clear();
this.#failures.clear();
```

取消请求不会记录为"失败"——`isChunkRequestAbortedError()` 专门识别 AbortError，不进入 `#failures` 集合。

| 做什么 | 文件路径 + 行号 | 关函键数/类型 |
|---|---|---|
| abort 控制器 | [src/chunk/data-store.ts](../../src/chunk/data-store.ts) 第 17 行 | `#abortControlle` |
| destroyed 检查 | [src/chunk/data-store.ts](../../src/chunk/data-store.ts) 第 448-452 行 | `#throwIfDestroyed()` |
| apply 前过期检查 | [src/chunk/coordinator.ts](../../src/chunk/coordinator.ts) 第 242-248 行 | `#applyIfCurrent()` 守卫 |

### 骨架 5：首屏预载 + 运行时动态装卸的切捍

> 理解层说的"开场航拍一次性预载 25 块，航拍结束后切换回只加载周围"。
> 在代码里，预载和动态装卸使用同一套能力，只是目标集合口径不同。

**航拍预载流程**：

```
CampusScene 航拍开始
  │
  ├─ 汇总多个相机位置的视口范围
  ├─ 预载范围额外扩展 +2 块边距
  ├─ Set 去重 → 得到预载目标集合（在 Peter 1920×1080 下覆盖全部 5×5=25块）
  ├─ requestIdleCallback（不可用时 setTimeout）逐项加载
  └─ 全部预载完成 → 航拍可以流畅飞行

航拍结束 → Play 开始
  │
  └─ 目标集合切换回：targetChunks(playerPos, cameraViewport, geometry)
       = playerNeighborhood(...) ∪ cameraVisibleChunks(...)
       每约 500ms 更新一次
```

**同一个 `updateargets()` 方法**既处理预载也处理动态装卸——区别只在于传入的 coordinates 迭代器不同：
- 预载阶段：传全部 25 块的坐标
- 正常阶段：传 `targetChunks()` 的计算结果

| 航拍预载调用 | [game/CampusScene.ts](../../game/CampusScene.ts) | 航拍序列中调用 `updateTargets(预载坐标)` |
