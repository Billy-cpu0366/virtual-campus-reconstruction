## 一、骨架落地

### 骨架 1：精灵表动画映射

> 理解层的人话：一张大图切成 64 个小格子，8 方向 × 8 帧循环播放。
> 在代码里，这东西就是 **Phaser anims.create + 帧范围定义**。

**它怎么工作的**：
`player` 纹理是一张精灵表，总共 64 帧。8 个方向各占连续 8 帧：
- east [0-7]、north-east [8-15]、north-west [16-23]、north [24-31]
- south-east [32-39]、south-west [40-47]、south [48-55]、west [56-63]
- idle 默认帧 = 第 48 帧（south 的首帧）

每个方向创建一个 Phaser animation：`walk-{方向名}`，循环播放，`frameRate = 10`。方向名由 SYS-INPUT 的 8 方向字符串提供（north / south / east / west 等）。

原站玩家有两个 sprite——物理体（不可见，只撞墙）和 visualSprite（负责显示外观）。显示切换在 visualSprite 上做，不影响碰撞体。

**代码在哪**：

| 做什么 | 文件路径 | 关键常量/函数名 |
|---|---|---|
| 帧映射定义 | `src/player/appearance.ts` | 8 方向帧范围表 |
| 动画创建 | `game/CampusScene.ts` | `anims.create({key:"walk-...", frames:..., frameRate:10})` |
| 原站动画创建 | `sample/.../chunk-WMFY56ZM.js` | `Ue` / `xe` / `Fi` 函数 |

**怎么验证它做对了**：
- 单元测试：`tests/player/appearance.test.ts` —— 帧范围映射与方向名一一对应
- 浏览器 Smoke：各方向走动时动画正确播放、帧序不跳

### 骨架 2：动画状态机

> 理解层的人话：走路、发呆、坐下、换装、被抓——状态之间互斥。
> 在代码里，这个东西就是 **preUpdate 里的状态分支 + 互斥标志**。

**它怎么工作的**：
每帧 `preUpdate` 按优先级检查状态：

1. **被抓（最高优）**：`isGrabbed=true` → 停所有动画 + visualSprite 切 `player-holding` + `setDisplaySize(64,64)`（**本 CORE 未实现**，原站行为）
2. **换装中**：`status === "changing-clothes"` → 停移动（不能动）+ 播脱/穿动画，等 `completeClothingChange()`
3. **坐下中**：`status === "sitting"` → sleep 粒子 Z 跟随 + 等移动时 `completeStandingUp()`
4. **走路中**：有方向输入且未被挡 → `play("walk-{方向}")`
5. **空闲**：无输入 → 检查超时，触发小动作或坐下

空闲动画 3 种随机选（排除上一个）：`eating` / `scratching` / `tying-shoe`。

**代码在哪**：

| 做什么 | 文件路径 | 关键常量/函数名 |
|---|---|---|
| 动画状态契约 | `src/player/runtime.ts` | `PlayerStatus` 类型（9 态） |
| 空闲状态 | `src/player/idle.ts` | `IDLE_ANIMATIONS`, `IDLE_TIME_FOR_EATING/SITTING` |
| 朝向状态 | `src/player/facing.ts` | `getFacingDirection()` → `lastRequestedDirection \|\| "south"` |
| 换装状态 | `src/player/clothing.ts` + `src/player/runtime.ts` | `beginClothingChange()` / `completeClothingChange()` / `skipClothingChange()`，尺寸切换 `48×48 ↔ 64×64`，冷却 1000ms |
| 运行时 preUpdate | `game/CampusScene.ts` | 每帧状态分支 + 动画播放 |
| 原站证据 | `sample/.../chunk-WMFY56ZM.js` | 玩家类 `$e` 的 `preUpdate` |

**怎么验证它做对了**：
- 单元测试：`tests/player/idle.test.ts`、`tests/player/facing.test.ts`、`tests/player/clothing.test.ts` —— 各状态阈值与切换逻辑
- BASE-PLAYER-003：动画状态机可复现

### 骨架 3：动态深度

> 理解层的人话：depth 跟 y 坐标走，越往下 depth 越大。
> 在代码里，就是 **setDepth(500 + y × 0.1)，每帧更新**。

**它怎么工作的**：
`createPlayer` 里初次设置 `setDepth(500 + player.y * 0.1)`；构造里的 `setDepth(600)` 只是初始值，会被覆盖。

原站事实：`500 + y * 0.1`（`chunk-WMFY56ZM.js`）。
重构决定：采用 SYS-LAYER 已接受的 `500 + (y + 24) * 0.1`。

深度随玩家 y 坐标实时变化——走到地图下部 depth 变大（被建筑遮挡），走到上部 depth 变小。不写死固定值。

**代码在哪**：

| 做什么 | 文件路径 | 关键常量/函数名 |
|---|---|---|
| 原站深度公式 | `sample/.../chunk-WMFY56ZM.js` | `setDepth(500 + player.y * 0.1)` |
| 重构深度公式 | `game/CampusScene.ts` | `500 + (y + 24) * 0.1`（SYS-LAYER SSOT） |
| 深度更新时机 | `game/CampusScene.ts` | `preUpdate` 每帧或 y 变化时 |

**怎么验证它做对了**：
- BASE-PLAYER-001：动态深度可复现
- 浏览器 Smoke：走到建筑下方被遮挡、走到建筑上方遮挡建筑

### 骨架 4：空闲超时

> 理解层的人话：太久没动角色自己玩起来。
> 在代码里，就是 **按空闲时长分档切成 sitting / idle**。

**它怎么工作的**：
`src/player/idle.ts` 的 `idleAction(idleMs)` 按空闲时长分档：`≥ 30000ms` → `sitting`，`≥ 8000ms` → `idle`，否则 `none`。状态机每帧拿这个档位切状态：
- 切到 `sitting` → 播坐下动画，sleep 粒子 Z 跟随；动画播完由 `completeSittingDown()` 收尾
- 切到 `idle` → 从 `IDLE_ANIMATIONS` 里随机挑一个（排除上一个播过的），播完由 `completeIdleAnimation()` 收尾

玩家一移动，状态机就把空闲计时清零；起身由 `completeStandingUp()` 收尾并恢复走路帧。

**代码在哪**：

| 做什么 | 文件路径 | 关键常量/函数名 |
|---|---|---|
| 空闲阈值常量 | `src/player/idle.ts` | `IDLE_TIME_FOR_EATING = 8000`, `IDLE_TIME_FOR_SITTING = 30000` |
| 空闲动画池 | `src/player/idle.ts` | `IDLE_ANIMATIONS = ["eating","scratching","tying-shoe"]` |
| 分档规则 | `src/player/idle.ts` | `idleAction(idleMs)` → `sitting` / `idle` / `none` |
| 运行时超时检测 | `src/player/runtime.ts` | `update()` 里按 `now - lastMovementAt` 分档 |
| 坐下 / 起身收尾 | `game/PhaserPlayerRuntime.ts` | `completeSittingDown()` / `completeStandingUp()` / `completeIdleAnimation()`；Z 粒子 |
| 原站证据 | `sample/.../chunk-WMFY56ZM.js` | `preUpdate`、`playSittingAnimation`、`standUp`、`lastMovementTime` |

**怎么验证它做对了**：
- 单元测试：`tests/player/idle.test.ts` —— 阈值触发、动画排除重复、移动后重置
- BASE-PLAYER-003：动画状态机可复现

### 骨架 5：控制门

> 理解层的人话：有些时候不让玩家操作。
> 在代码里，就是 **`enableControls()` / `disableControls()` 开关 + 状态机自身互斥**。

**它怎么工作的**：
初始 `controlEnabled = false`——创建玩家后立即锁住。
- 放行 → `enableControls()`，状态重置为 `normal-idle`
- 锁住 → `disableControls()`，状态重置为 `disabled`，并触发 `resetKeyboard` / `resetJoystick` / `stopMovement` 三个副作用
- 航拍/过场期间：由 SYS-CAMERA 通过**控制权租约**（`GameplayControlLeaseRuntime` 的 `acquire` / `release`）压下控制门，不直接操作玩家
- 换装中：状态为 `changing-clothes` 时不接受输入，等动画播完收尾
- 被抓时：**本 CORE 未实现**——原站是 `setGrabbedByMonster(true)` 停一切动画 + 锁操作
- 窗口失去焦点：`blur()` → 等价于 `reset()`

**代码在哪**：

| 做什么 | 文件路径 | 关键常量/函数名 |
|---|---|---|
| 控制门契约 | `src/player/runtime.ts` | `controlEnabled` 标志 + `enableControls()` / `disableControls()` |
| 运行时控制开关 | `game/CampusScene.ts` | `playerRuntime.enableControls()` / `.disableControls()` |
| 换装互斥 | `src/player/runtime.ts` | `status === "changing-clothes"` 时不接受输入 |
| 控制权租约 | `game/GameplayControlLeaseRuntime.ts` | `acquire()` / `release()`（相机航拍、内容线各自占租约） |
| 被抓互斥 | **未实现** | 原站：`setGrabbedByMonster(true)` |
| 原站证据 | `sample/.../chunk-WMFY56ZM.js` | `setUseControls`、`createPlayer` 初始 false |

**怎么验证它做对了**：
- BASE-PLAYER-004：控制启用时机可复现（开场锁、完成放）
- 浏览器 Smoke：开场动画中方向键无效
