## 一、骨架落地 —— 每根骨头对应哪块代码

### 骨架 1：固定半径的"感应圈"

> 理解层说的是"每个 marker 有一个 30px 的感应圈，玩家踩进来就触发"。
> 在代码里，这叫 **ZoneRuntime 的 isInside 距离判定**。

**它怎么工作的**：

系统拿到玩家当前位置 (px, py) 和 marker 中心 (mx, my)，计算两者的直线距离：

```
dx = px - mx
dy = py - my
distance = √(dx² + dy²)
```

如果 `distance < interactionDistance`（默认 30）→ 触发。如果 `distance >= 30` → 不触发。

注意是**严格小于**（`<`），不是小于等于。玩家站在恰好 30px 的位置 → 不触发。29.999px → 触发。这个边界判定直接影响测试用例的预期行为。

距离阈值 `interactionDistance` 不是硬编码在类内部——它在构造函数里通过 `options.interactionDistance ?? DEFAULT_INTERACTION_DISTANCE` 注入，默认值 30 定义在文件顶部的常量区。

### 骨架 2：定期巡检（每 100ms）

> 理解层说的是"系统不是每帧都查，而是每 100ms 掀开眼皮看一眼"。
> 在代码里，这叫 **update() 合并 + scheduler.setTimeout**。

**它怎么工作的**：

```
调用 update(snapshot)  ← 可能每秒被调用 30~60 次（每帧）
        │
        ├─ 存下最新 snapshot（只保留最新一次的位置）
        │
        ├─ 没有定时器在跑？→ setTimeout(checkNow, 100)
        │
        └─ 定时器已经在跑了？→ 什么都不做（之前的定时器会读最新的 snapshot）
```

这样就实现了"合并"——不管 `update()` 被调用了多少次，`checkNow()` 每 100ms 最多执行一次。

如果调用方**不提供 scheduler**（比如测试环境或同步场景），`update()` 会直接同步调用 `checkNow()`，跳过定时器合并。

`tick()` 方法是备用入口——它可以立即执行一次检查（可选传入 snapshot），用于测试和确定性调用方。

**代码在哪**：

### 骨架 3：视口裁剪（只看眼前）

> 理解层说的是"只检查屏幕范围 + 100px 边距内的 marker"。
> 在代码里，这叫 **candidates() 视口筛选**。

**它怎么工作的**：

```
viewport + 100px padding 形成的矩形范围：
  left   = viewport.x - viewportPadding
  top    = viewport.y - viewportPadding
  right  = viewport.x + viewport.width + viewportPadding
  bottom = viewport.y + viewport.height + viewportPadding

筛选规则：
  ① 已经激活的 marker（residences 里有记录）→ 永远纳入候选
     （因为需要检测 leave，不能因为滚出视口就漏掉离开判定）

  ② 未激活的 marker → 必须在该矩形范围内才纳入候选

  ③ 既未激活又不在范围内的 → 跳过
```

**代码在哪**：

| 默认视口外扩 | [src/zone/runtime.ts](../../../src/zone/runtime.ts) 第 52 行 | `DEFAULT_VIEWPORT_PADDING = 100` |

### 骨架 4：进出状态机

> 理解层说的是"enter → 手动关闭 → 抑制 → leave → 重置"这条链。
> 在代码里，进出判定在 ZoneRuntime 中，抑制逻辑在 InteractRuntime 中。

**它怎么工作的**：

ZoneRuntime 负责"物理层"的进出判定：

```
checkNow() 遍历 candidates
  │
  ├─ 距离 < 30 且 residences 里没有 → enter(marker)
  │     ├─ 生成唯一的 residenceId（"residence-1", "residence-2"...自增）
  │     ├─ 写入 residences Map
  │     └─ 发出 { phase: "enter", markerId, menuId, residenceId }
  │
  └─ 距离 >= 30 但 residences 里有 → leave(marker, residence)
        ├─ 从 residences Map 删除
        └─ 发出 { phase: "leave", markerId, menuId, residenceId }
```

"手动关闭后不重弹"的抑制逻辑在 InteractRuntime（SYS-INTERACT 执行层）中：它维护 `suppressedResidences` Set，用户手动关闭时写入，收到 leave 事件时清除。ZoneRuntime 不感知抑制——它只是老实报告 enter 和 leave。

ZoneRuntime 单独维护 `visitedMarkers` 集合——这是纯统计计数器，通过 `acceptVisitReceipt()` 写入，通过 `hasVisited()` 查询。它**不参与**触发/抑制决策。

| leave 方法 | [src/zone/runtime.ts](../../../src/zone/runtime.ts) 第 263-271 行 | `leave(marker, residence)` |
| residences 存储 | [src/zone/runtime.ts](../../../src/zone/runtime.ts) 第 97 行 | `residences: Map<string, ResidenceState>` |

### 骨架 5：内容标识桥接

> 理解层说的是"ZoneRuntime 只负责喊一句'menuId 是 memo3'，不碰内容"。
> 在代码里，桥接数据格式叫 **ZoneResidenceEvent**。

**它怎么工作的**：

ZoneRuntime 内部通过 `emit()` 私有方法调用构造函数注入的 `onResidence` 回调，传递一个包含四个字段的事件对象：

```
{
  markerId:    "memo3",          // 哪个 marker 触发了
  menuId:      "memo3",          // 对应哪个内容
  residenceId: "residence-1",    // 本次"停留"的唯一编号
  phase:       "enter" | "leave" // 是进来了还是出去了
}
```

这个事件对象的类型定义不在 `zone/` 目录——它在 `src/content/contract.ts` 中，因为它是 SYS-ZONE 和 SYS-INTERACT 的**共享契约**。ZoneRuntime 不导入任何 DOM、UI 或内容相关的模块，它只依赖这个纯粹的数据结构。

`menuId` 的值被限定为 11 个合法常量（`ContentMenuId` 联合类型），构造 marker 时如果传入非法 menuId 会直接抛错。
