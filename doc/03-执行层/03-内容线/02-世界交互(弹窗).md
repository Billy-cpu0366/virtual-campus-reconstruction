## 一、骨架落地 —— 每根骨头对应哪块代码

### 骨架 1：单内容状态机（同时只显示一个）

> 理解层说的是"同一时间只有一个弹窗，新内容替换旧内容"。
> 在代码里，这个三态管理器叫 **InteractRuntime**。

**它怎么工作的**：

```
收到 ZoneResidenceEvent (phase: "enter")
        │
        ▼
    ┌─ suppressedResidences 里有这个 identity？
    │   YES → return "suppressed"（你手动关了，不烦你）
    │
    ├─ committedResidences 里有这个 identity？
    │   YES → return "ignored"（已经显示过了）
    │
    ├─ resolver.resolve(menuId) → 内容存在吗？
    │   "missing" / "invalid" → return（内容有问题，不弹）
    │
    ├─ 已经有 activeState 吗？
    │   YES → 复用现有的 lease（不重新 acquire）
    │   NO  → lease.acquire("modal-open")
    │         失败 → return "lease-failed"
    │
    ├─ ui.show({ menuId, residenceId, payload, presentation })
    │   失败 → 如果刚才 acquire 了新的 lease → release 掉
    │          return "show-failed"
    │          （注意：替换场景下，失败不丢旧状态）
    │
    └─ 成功 → 写 activeState + committedResidences → emit visit receipt
```

核心设计决策：**替换时保留旧状态直到新内容成功显示**。如果 show 失败，`activeState` 和 `activeToken` 不变——用户仍然可以看到之前的内容。这是生产级的防御策略：不能因为"换台失败"导致屏幕变黑。

状态踪迹：
- `activeState`：当前屏幕上显示什么（只有 1 个或 undefined）
- `activeToken`：当前持有的游戏控制租约
- `committedResidences`：已经显示过的 residence（按 identity 去重，防止同一 enter 重复处理）
- `suppressedResidences`：用户手动关闭的 residence（收到 leave 时清掉）
- `pendingReleaseTokens`：release 失败、等待重试的租约

### 骨架 2：内容查找（menuId → 标题+正文+图片）

> 理解层说的是"弹窗系统问 resolver 要内容，不自己拥有内容"。
> 在代码里，查找接口叫 **ContentResolverPort**，内容仓库叫 **CONTENT_REGISTRY**。

**它怎么工作的**：

```
interact 调用 resolver.resolve(menuId)
        │
        ▼
resolver 查 CONTENT_REGISTRY[menuId]
        │
   ┌────┼────┐
   │找到了     │没找到
   ▼          ▼
返回         返回
{ status:    { status:
  "resolved",   "missing" }
  payload: {
    menuId,
    title,
    body: [...],
    sections?: [
      { heading?, paragraphs?, image?, links?, tags? }
    ]
  }
}
```

内容结构支持两种模式：
- **简单模式**（body 数组）：直接拼成文本显示
- **富内容模式**（sections 数组）：每段可独立有标题、段落、图片、链接、标签

`DomModalGameUi` 在渲染时先尝试用 `replaceChildren()` 渲染富内容；如果富内容渲染失败或内容模块不存在，回退到 `body.textContent` 纯文本模式。

图片引用登记在 `CONTENT_RESOURCE_RECEIPTS` 中，每条记录包含 `src`、原始 `sourceUrl`、`localPath` 和 `SHA-256` 哈希——可以验证镜像文件完整性。

### 骨架 3：游戏控制租约（暂停/恢复）

> 理解层说的是"弹窗打开借走游戏控制权，关闭还回去"。
> 在代码里，这套借/还机制叫 **GameplayControlLeasePort**。

**它怎么工作的**：

```
打开弹窗时：                           关闭/离开时：
lease.acquire("modal-open")           lease.release(token)
        │                                    │
   ┌────┼────┐                          ┌───┼───┐
   │ok:true  │ok:false                  │ok  │fail│
   ▼         ▼                          ▼    ▼
拿到 token  返回 "lease-failed"      完成   token 进入
（游戏暂停） （弹窗不打开）                 pendingReleaseTokens
                                             │
                                       下次 handleResidenceEvent()
                                       或 destroy() 时 retryPendingReleases()
```

租约不是全局锁——允许多个调用方各自获取自己的 token。这意味着 SYS-INTERACT 可以和其他需要暂停游戏的系统（如大地图、航拍）共存，不会互相抢锁。

租约实现的"暂停"和"恢复"具体做什么，取决于调用方注入的 `GameplayControlLeaseEffects`：
- `disableControls()` → 禁用键盘/摇杆输入
- `enableControls()` → 恢复输入

这些效果由 `game/GameplayControlLeaseRuntime.ts` 实现——`InteractRuntime` 不碰输入层，它只调用接口。

release 可能失败（`reason: "enable-failed"` → 游戏控制恢复不了），此时 token 留在 `pendingReleaseTokens` 集合中等待重试。下一次任何 `handleResidenceEvent()` 调用都会先尝试 `retryPendingReleases()`——直到全部 release 成功或确认永久失败。

| 做什么 | 文件路径 + 行号 | 关键常量/函数名 |
|---|---|---|
| 租约接口 | [src/content/contract.ts](../../../src/content/contract.ts) 第 137-180 行 | `GameplayControlLeasePort` — acquire/release/shutdown |
| 租约 token | [src/content/contract.ts](../../../src/content/contract.ts) 第 143-147 行 | `GameplayControlLeaseToken` — branded type，不可伪造 |
| acquire 逻辑 | [src/interact/runtime.ts](../../../src/interact/runtime.ts) 第 189-201 行 | 只有 `activeState === undefined` 时才 acquire |
| release 重试 | [src/interact/runtime.ts](../../../src/interact/runtime.ts) 第 269-289 行 | `retryPendingReleases()` — 遍历 pendingReleaseTokens 逐个重试 |
| release 失败兜底 | [src/interact/runtime.ts](../../../src/interact/runtime.ts) 第 357-369 行 | `retainIfReleaseFailed()` — 先尝试 release，失败则加入 pending 队列 |

### 骨架 4：三路关闭 + 防误关

> 理解层说的是"关闭按钮 / ESC / 点遮罩三种关闭方式，menuId+residenceId 双重校验防误关"。
> 在代码里，事件监听在 **DomModalGameUi**，校验在 **InteractRuntime**。

**它怎么工作的**：

DOM 层（DomModalGameUi）注册三个事件源：
1. `closeButton.addEventListener("click", closeListener)` → source="close-button"
2. `backdrop.addEventListener("click", backdropListener)` → source="backdrop"（但只有 active.backdrop === "global" 时才真正发出）
3. `keyboard.subscribe(keyboardListener)` → ESC key → source="close-button"

每个事件源最终调用 `emitUserClose(source)` →通知所有订阅者（通过 `subscribeUserClose()` 注册的 handler）。

InteractRuntime 在构造时订阅 `ui.subscribeUserClose(handler)`，收到 UserCloseEvent 后：

```
handleUserClose(event)
        │
        ├─ event 合法吗？（menuId 合法 + residenceId 非空 + source 合法）
        │   NO → return（丢弃）
        │
        ├─ 和 activeState 匹配吗？（sameIdentity：menuId + residenceId 都一致）
        │   NO → return（旧弹窗的关闭事件，忽略）
        │
        ├─ ui.hide({ menuId, residenceId, reason: "user-close" })
        │   失败（target-mismatch / destroyed / 抛异常）
        │     → return（保持 activeState 不变，不抑制、不释放 lease）
        │
        └─ 成功 → suppressedResidences.add(identityKey)
                  activeState = undefined
                  release(activeToken)
```

**关键安全设计**：hide 失败时**保持一切不变**——不写 suppressed、不清 activeState、不释放 lease。屏幕上的东西还在，状态和数据一致。等 UI 层修好了（比如 DOM 元素恢复了），用户再点一次关闭就能正常走通。

### 骨架 5：安全生命周期（销毁不泄漏）

> 理解层说的是"销毁时把所有东西收干净，不能留僵尸"。
> 在代码里，两层的 destroy() 都实现了幂等 + best-effort 清理。

**它怎么工作的**：

InteractRuntime.destroy() 的销毁顺序：

```
destroy()
  │
  ├─ 1. 标记 destroyed = true（后续所有操作都被拒绝）
  │
  ├─ 2. unsubscribeUserClose()（不再接收关闭事件）
  │    失败 → 继续（不阻断）
  │
  ├─ 3. 如果 activeState 存在 → ui.hide({ reason: "shutdown" })
  │    失败 → 继续（不能因为 UI 挂了就不释放 lease）
  │
  ├─ 4. ui.destroy()
  │    失败 → 继续
  │
  ├─ 5. 收集所有待释放的 token：
  │    activeToken + pendingReleaseTokens 中的所有 token
  │    逐个尝试 release；失败的不阻塞
  │
  ├─ 6. 清空全部内部状态：
  │    activeState = undefined
  │    activeToken = undefined
  │    suppressedResidences.clear()
  │    committedResidences.clear()
  │
  └─ 注意：不会调用 lease.shutdown() —— lease 是外部注入的共享资源，
      InteractRuntime 只释放自己持有的 token，不关掉整个 lease 提供方
```

DomModalGameUi.destroy() 的销毁顺序：

```
destroy()
  │
  ├─ 1. 标记 destroyed = true
  │
  ├─ 2. removeListeners()（取消 closeButton/backdrop/resize/keyboard 所有事件监听）
  │
  ├─ 3. clearRichImageListeners()（取消所有图片 error 监听）
  │
  ├─ 4. hideDom()（隐藏所有 DOM 元素）
  │
  ├─ 5. restoreFocus()（焦点还给之前聚焦的元素）
  │
  └─ 6. subscribers.clear()（清空所有关闭事件订阅者）
```

两个 destroy 的共同特征：
- **幂等**：重复调用安全（`if (this.destroyed) return`）
- **Best-effort**：每一步失败都不阻断后续——用 try/catch 包裹每个可能失败的操作
- **不关别人的东西**：InteractRuntime 不调用 `lease.shutdown()`

| 做什么 | 文件路径 + 行号 | 关键常量/函数名 |
|---|---|---|
| InteractRuntime 销毁 | [src/interact/runtime.ts](../../../src/interact/runtime.ts) 第 292-331 行 | `destroy()` |
| DomModalGameUi 销毁 | [src/game-ui/dom-modal.ts](../../../src/game-ui/dom-modal.ts) 第 481-495 行 | `destroy()` |
| 事件监听移除 | [src/game-ui/dom-modal.ts](../../../src/game-ui/dom-modal.ts) 第 550-591 行 | `removeListeners()` |
| 图片监听清理 | [src/game-ui/dom-modal.ts](../../../src/game-ui/dom-modal.ts) 第 778-786 行 | `clearRichImageListeners()` |
| DOM 隐藏 | [src/game-ui/dom-modal.ts](../../../src/game-ui/dom-modal.ts) 第 871-928 行 | `hideDom()` — 逐个设 hidden=true / pointerEvents=none |
