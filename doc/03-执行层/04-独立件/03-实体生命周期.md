# 实体生命周期（SYS-ENTITY）—— 执行层细化

> 对照理解层的 5 个骨架 + 5 张皮，逐一落到代码位置。
> 本系统的骨架落在**我们自己的复刻代码**上（`game/` 和 `src/`），不是原站代码的逐行对应——原站没有这一层抽象，见 §1。

---

## 👀 先看这里（给 Human 的人话总结）

**当前状态**：5 个骨架全部落地，都有代码位置和测试。清理序列的 23 个 Runtime 调用、代际隔离、引用计数租约、18 字段清理收据都能在实际代码里逐条对上。

**还没做的**：没有统一抽象基类，靠的是"每个 Runtime 各自实现 `shutdown()`"的约定——加新 Runtime 时不会有人拦着你忘记写清理。另外 `performShutdown` 主体**没有**逐项 try/catch，某个 Runtime 抛错会中断后续清理（§4 详述）。这两条都挂在残余未知里。

## 一、骨架落地

### 骨架 1：统一的生命周期接口

> 理解层原话：就像公司里所有员工，入职、上班、离职、交接的流程一样。
> 在代码里，这个东西叫 **Runtime 的 shutdown / destroy 方法**。

**它怎么工作的**：
每个管着一批游戏对象的模块（我们叫 Runtime）都对外开一个"我要收摊了"的口子，方法名统一叫 `shutdown()`，少数叫 `destroy()`。谁调它，它就把自己名下的 Phaser 对象清干净——精灵、碰撞器、粒子发射器、计时器、监听器，各清各的。

**注意**：这是**约定**，不是继承。全项目没有 `Entity` / `GameObjectBase` 这样的统一基类，每个 Runtime 各写各的。原站也是这样（13 个类全部直接继承 Phaser 内置类，无自定义基类）——我们保留了原站的做法，没有额外造一层抽象。

### 骨架 2：有序清理序列

> 理解层原话：就像拆楼——不能先拆一楼的地基再拆二楼的墙，得从上往下拆。
> 在代码里，这个东西叫 **`CampusScene.performShutdown()`**。

**它怎么工作的**：
关停不是随便关，而是**一条写死的顺序线**。顺序的原则是"先关被依赖的，再关依赖别人的"——比如玩家依赖输入，就先关玩家再关输入；地图数据被玩家查询，就先关玩家再关地图数据。

**代码在哪**：[game/CampusScene.ts](../../../game/CampusScene.ts) 第 1186-1282 行。

实际执行顺序（第 1191-1239 行）：

```
① sceneDestroyed = true          ← 先立标志位，后续异步回调看到它就提前退出
② 入场动画 entryRuntime
③ 喷水器 sprayerRuntime
④ 路线人群 routeCrowdRuntime
⑤ 静态 NPC staticNpcRuntime
⑥ 静态人群 staticCrowdRuntime
⑦ 虫子群 bugCrowdRuntime
⑧ 场馆人群 venueCrowdRuntime
⑨ 跳舞人群 dancingCrowdRuntime
⑩ AI 烟雾 stopAiSmokeRuntime
⑪ 雾效 fogRuntime
⑫ disconnectPoliceCollisions()   ← 摘警车碰撞器
⑬ 车辆 vehicleRuntime
⑭ 工厂烟 smokeRuntime
⑮ 火车 trainRuntime（传入 this.time.now）
⑯ 相机 cameraRuntime
⑰ releaseCameraControlLease()    ← 释放相机控制租约
⑱ 地图 mapRuntime.destroy()
⑲ 区域触发 zoneRuntime.destroy()
⑳ 世界交互 interactRuntime.destroy()
㉑ 内容租约 contentLeaseRuntime.shutdown()
㉒ stopRoofTweens()              ← 停屋顶 alpha 补间
㉓ 脚印 footstepRuntime
㉔ 玩家 playerRuntime
㉕ 玩家插值器 playerVisualInterpolator
㉖ 摇杆 joystick
㉗ stopPlayerMovement()
㉘ mutationScheduler.destroy()
㉙ clearRuntimeTestHooks()
㉚ 摘 4 个原生监听器：window keydown / keyup / blur，document visibilitychange
㉛ await shutdownDynamicWorld()   ← 异步：分块数据 + 世界渲染器
㉜ this.scene.stop()
```

共 **23 个 Runtime 级 shutdown/destroy 调用**（第 1191-1232 行）。

**它做对的两件小事**：
- **幂等**：`beginShutdown()`（第 1180-1184 行）用 `shutdownTask` 缓存 Promise。重复调用不会跑第二遍，直接拿同一个 Promise。
- **先立标志位**：`sceneDestroyed = true` 放在最前面（第 1187 行），后面所有异步回调都靠它判断"是不是已经关了"。

**怎么验证它做对了**：
顺序本身没有独立单测（它是 Phaser 场景级的集成行为），靠 `npm run browser:lifecycle-smoke` 在浏览器里验证。

### 骨架 3：代际隔离

> 理解层原话：就像餐厅排队叫号——你拿的是 12 号，餐厅已经叫到 15 号了，12 号的菜就不会再上。
> 在代码里，这个东西叫 **`AppRuntime.generation`**。

**它怎么工作的**：
每次重新加载（点 Retry、或第一次进游戏）就发一个新号，号码 +1。所有异步回调在执行前先报上自己的号码，跟当前号一比——对不上就假装自己没被调用过，什么都不做。

这样旧一代的下载完成回调、错误回调，都不会污染新一代的状态。

**代码在哪**：

| 做什么 | 文件路径 + 行号 | 说明 |
|---|---|---|
| 发新号 | [src/app/runtime.ts](../../../src/app/runtime.ts) 第 199 行 | `beginLoading()` 里 `this.generation += 1`，从 1 开始 |
| 号码放进快照 | [src/app/contract.ts](../../../src/app/contract.ts) 第 24-29 行 | `AppSnapshot.generation` |
| 回调报号校验 | [src/app/runtime.ts](../../../src/app/runtime.ts) 第 162-169 行 | `fail()` 开头 `generation !== this.generation` 就返回 false |
| 关停 | [src/app/runtime.ts](../../../src/app/runtime.ts) 第 188-196 行 | 状态置 `SHUTDOWN`，并 `cleanupGeneration(generation)` |
| 页面关闭触发 | [game/main.ts](../../../game/main.ts) 第 315 行 | `window.addEventListener("pagehide", () => appRuntime.shutdown(), { once: true })` |
| 场景侧标志位 | [game/CampusScene.ts](../../../game/CampusScene.ts) 第 413 行 | `private sceneDestroyed = false`，在 10+ 处异步回调里被检查 |

**代际隔离在场景侧的表现**：`sceneDestroyed` 被检查的位置——第 496、514、523、611、680、692、978、1008、1042、1794 行。

**怎么验证它做对了**：[tests/app/runtime.test.ts](../../../tests/app/runtime.test.ts)，6 个用例。

### 骨架 4：引用计数控制租约

> 理解层原话：就像会议室预订——第一个到的人开灯，最后一个走的人关灯。
> 在代码里，这个东西叫 **`GameplayControlLeaseRuntime`**。

**它怎么工作的**：
弹窗打开时玩家不能动。但"要停住玩家"的来源可能不止一个（内容弹窗、地图弹窗）。所以不能谁开谁就停、谁关谁就恢复——那样会互相打架。做法是**数人头**：

- 第一个来的人（`acquire`）负责把玩家停住（`disableControls`），拿到一张"凭证"（token）
- 后面来的人也能拿到凭证，但不会重复执行"停"
- 走的时候交还凭证（`release`）
- **只有最后一个人走**（凭证数归零）才真的恢复玩家控制（`enableControls`）

凭证是个不透明空对象（`Object.freeze({})`），调用方拿不到凭证内部结构，没法伪造。

**代码在哪**：[game/GameplayControlLeaseRuntime.ts](../../../game/GameplayControlLeaseRuntime.ts)（全文 123 行）

| 做什么 | 行号 | 说明 |
|---|---|---|
| 拿凭证 | 第 56-74 行 | `acquire()`：凭证数为 0 时才真的 disable；失败则不发凭证 |
| 交凭证 | 第 76-100 行 | `release()`：还有别人就只减数；最后一人走才 enable |
| 强制收尾 | 第 102-114 行 | `shutdown()`：清空所有凭证、确保处于禁用终态、之后拒绝新凭证 |
| 契约定义 | [src/content/contract.ts](../../../src/content/contract.ts) 第 124、152 行 | `GameplayControlLeasePort` / `ShutdownResult` |
| 在场景里创建 | [game/CampusScene.ts](../../../game/CampusScene.ts) 第 894 行 | `new GameplayControlLeaseRuntime({...})` |
| 场景关停时释放 | [game/CampusScene.ts](../../../game/CampusScene.ts) 第 1217 行 | `contentLeaseRuntime?.shutdown()` |

**两个容易忽略的设计细节**：
- **两种失败分开**：`disable` 失败时**不发凭证**（第 64-67 行）——否则调用方会以为自己停住了玩家，其实没有。
- **关停是终态**（第 110-113 行）：即使注入的 enable/disable 效果抛异常，也强制把 `controlsDisabled` 置 true 并拒绝后续所有凭证——保证"场景已经关了"这个事实不会被一次效果失败推翻。

**怎么验证它做对了**：[tests/content/gameplay-control-lease-runtime.test.ts](../../../tests/content/gameplay-control-lease-runtime.test.ts)，7 个用例，覆盖：首个 token disable、非末 token release 不 enable、disable 失败不发 token、unknown/stale token 安全返回、末 token enable 失败可重试、shutdown 幂等且旧 token 全失效、无 token 时 shutdown 仍确保禁用。

### 骨架 5：清理收据

> 理解层原话：就像退房时的检查清单——床单换了✓、毛巾补了✓、垃圾倒了✓。
> 在代码里，这个东西叫 **`CampusSceneShutdownReceipt`**。

**它怎么工作的**：
关停跑完后，返回一份**冻结的**（`Object.freeze`）报告，把"关完之后应该是什么样"逐项记下来。这份报告用来回答一个问题：**是不是真的清干净了？**

比如 `physicsColliderCount` 记录物理世界还剩几个碰撞器——如果关完后这个数 > 0，说明有残留，清理没做干净。`sideFailures` 记录旁支系统的失败列表，正常应该是空数组。

**代码在哪**：

| 做什么 | 文件路径 + 行号 |
|---|---|
| 收据类型定义（18 个字段） | [game/CampusScene.ts](../../../game/CampusScene.ts) 第 313-332 行 |
| 收据构造 | [game/CampusScene.ts](../../../game/CampusScene.ts) 第 1250-1269 行 |
| 对外入口 | [game/CampusScene.ts](../../../game/CampusScene.ts) 第 1176 行 `shutdownForGeneration()` |

**18 个字段分四组**：

| 组 | 字段 | 检查什么 |
|---|---|---|
| 火车（6） | trainColliderActive、trainColliderCount、trainCollisionShapeCount、trainBlockingCellCount、trainSpriteActive、trainCollisionShapeActive | 火车精灵和碰撞体是否都撤了 |
| 人群与特效（5） | sprayerSpriteCount、staticNpcSpriteCount、staticCrowdSpriteCount、smokeEmitterActive、footstepActiveCount | 各类精灵/发射器是否清零 |
| 补间与 UI（5） | factoryRoofTweenActive、concertRoofTweenActive、mapHudHidden、mapRootHidden、mapLeaseActive | 屋顶补间是否停了、地图 UI 是否收起了、地图租约是否释放了 |
| 兜底（2） | sideFailures、physicsColliderCount | 旁支失败列表、物理碰撞器残留数 |

**怎么验证它做对了**：`npm run browser:lifecycle-smoke` 在浏览器里实际关停一次并核对收据字段。

| 能改什么 | 现在硬编码在哪 | 现在的值 | 将来 |

## 七、残余未知

| 未知 | 说明 | 影响 |
|---|---|---|
| 无统一抽象基类 | 加新 Runtime 时没有任何机制强制实现 `shutdown()`——忘记写就会泄漏，且不会被静态检查发现 | 换皮加新系统时的风险点 |
| `performShutdown` 主体无逐项 try/catch | 第 1191-1232 行任何一个 Runtime 的 shutdown 抛错，后续清理全不执行，收据也不会产出（Promise reject） | 单个 Runtime 的 bug 会放大成"整个关停失败" |
| `shutdownDynamicWorld` 抛错后的行为 | 它抛错时 `performShutdown` 会 reject，但此时前置的 23 个 Runtime 已经关完、`scene.stop()` 还没执行 | 场景停在半关状态，无收据可查 |
| 清理超时 | 不设超时，若某个异步清理永不 resolve，关停会永久挂起 | 页面已 pagehide，用户看不到，但测试可能超时 |

> 前两条是**设计选择**而非缺陷——它们和原站"不设统一基类"的做法一致。是否要改成更防御的写法（统一基类 / 逐项 try-catch），需要 Human 定。

## 八、原站对照（本节记录证据边界）

原站公开 Bundle 中的证据（`sample/original-public-build/mirror/`）：

- 游戏代码全部 **13 个类**，父类分布：`Phaser.Renderer.WebGL.Pipelines.PostFXPipeline` ×6、`Phaser.GameObjects.Sprite` ×3、`Phaser.Physics.Arcade.Sprite` ×2、`Phaser.Scene` ×1、本地类 `fe` ×1（自身继承 `GameObjects.Sprite`）。
- **没有任何自定义实体基类**——所有游戏对象直接继承 Phaser 内置类。这回答了 `Q-ENTITY-001`。
- 游戏包里 `shutdown` 只出现 **1 次**，用法是 Phaser Scene 的 `shutdown` 事件钩子，专门用来摘一个手动挂在 `document` 上的 `keydown` 监听器。
- 清理主要靠 Phaser 自带的 `.destroy()`（227 处）和 `.remove()`（60 处）。
- 第三方插件 `rexVirtualJoystick` 有 `shutdown()`/`destroy()`——那是 Phaser Plugin 基类强制的约定，不是 Peter 自建的系统。

**结论**：原站**没有**统一实体生命周期系统，也没有集中式有序关停序列和清理收据。本卡的 5 个骨架是我们复刻时建立的设计约定，落在 `game/` 和 `src/` 上。

`Q-ENTITY-001` 建议关闭（已有答案：原站不共享统一实体基类）。
