## 一、骨架落地 —— 每根骨头对应哪块代码

### 骨架 1：一条固定的页面状态流水线

> 理解层说的是"从打开网页到能玩游戏，中间要经过固定的状态步骤，不能跳步、不能倒退"。
> 在代码里，这条流水线叫做 **AppRuntime**。

**它怎么工作的**：

`AppRuntime` 是一个**纯逻辑状态机**——它不碰 DOM、不碰 Phaser、不碰任何定时器。它是一个"大脑"，只负责判断"现在是什么状态"和"能不能从 A 状态跳到 B 状态"。实际做事（创建游戏、渲染页面）是通过 `effects` 参数注入的。

状态之间的"允许跳转"规则是硬编码的：
- `start()`：只能从 BOOT 开始
- `markReady()`：只能在 LOADING 状态下被调用
- `play()`：只能从 READY 开始
- `openModal()`：只能从 PLAYING 开始
- `closeModal()`：只能从 MODAL_OPEN 开始
- `retry()`：只能从 ERROR 开始
- `shutdown()`：任何非 SHUTDOWN 状态都可以调用

**关键保护**：`reportProgress()` 的进度值必须单调递增——如果试图报一个比之前小的值，直接忽略。这防止了进度条"倒着走"。

### 骨架 2：网页壳与游戏画布分层

> 理解层说的是"网页UI（DOM）和游戏画面（Canvas）是两层独立的画布，叠在一起但互不干扰"。
> 在代码里，这体现在 `index.html` 的 DOM 结构和 CSS z-index 设计。

**它怎么工作的**：

HTML 结构分三大层：
- **`#app`**（z-index 默认）：放 Phaser Canvas，由 Phaser 自动创建
- **`#app-shell`**（z-index: 9000）：网页壳——加载页/Play页/错误页
- **其他 UI 层**：地图 HUD（6500）、引导浮标（7000）、地图弹窗（8000）、诊断面板（10001）

游戏运行时 `#app-shell` 的可见性由 `body.dataset.appState` 驱动：
- `LOADING` / `READY` / `ERROR`：shell 可见
- `ENTERING_GAME` / `PLAYING` / `MODAL_OPEN` / `SHUTDOWN`：shell 隐藏

### 骨架 3：Phaser 游戏实例的"生"与"死"

> 理解层说的是"点 Play 时创建游戏引擎，关网页或出错时完整销毁——生老病死有统一规矩"。
> 在代码里，这由 `game/main.ts` 的 `effects.startLoading` 和 `effects.cleanup` 负责。

**它怎么工作的**：

`gameConfig()` 函数定义 Phaser 的出生配置——逻辑分辨率 480×270、Arcade 30FPS 物理、ENVELOOP 缩放、pixelArt 渲染。每次 `startLoading` 触发时创建新的 `Phaser.Game`；`cleanup` 触发时调 `game.detroy(true)` 并删除 Canvas。

**核心约定**：Phaser 实例的创建和销毁必须成对。如果创建了但没销毁，Canvas 元素会一直留在 DOM 里且继续运行——这就是内存泄漏。

### 骨架 4：视口自适应

> 理解层说的是"窗口大小变了，页面和游戏都能跟着适配"。
> 在代码里，这靠 `DomAppViewort` 接口订阅 resize 事件 + `Phaser.Scae.refresh()` 完成。

**它怎么工作的**：

`viewport` 对象封装了 `window.inneWidth/innerHeight` 的读取和 resize 订阅/取消。`DomAppi` 在构造时订阅 resize 事件，每次触发时调 `applyViewort()` 更新 DOM 布局（padding、min-eight、max-Width），然后回调 `onViewortChange` → `currentGenration?.game?.scale?.efresh()`。

移动端断点 767px 在 `DomAppi` 中定义——≤767 时 padding 缩小。

### 骨架 5：取消、清理、重来

> 理解层说的是"加载到一半不想要了，知道怎么停、怎么收摊、怎么重来——而且是按代管理"。
> 在代码里，这涉及三个层次的协作：`AppRuntie` 的状态机层、`game/main.ts` 的粘合层、`CampusScne` 的场景清理层。

**三件事分别怎么做的**：

| 操作 | 什么时候触发 | 实际发生了什么 |
|---|---|---|
| **取消** (cacel) | 新加载开始，旧的回调还在跑 | 设 `cancelled = true`。所有回调执行前先调 `isCurren(generation)` 检查——代次不对就忽略 |
| **清理** (cleanp) | 用户关网页 / 点 Retry / 出错 | ① `cancelled = tre` ② `scene.shudownForGenertion()` 逐个关 Runtime ③ `game.detroy(true)` 删 Canvas |
| **重试** (retr) | 加载失败了，用户点 Retry 按钮 | ① `cleanupGenration(previous)` 清干净旧代 ② 确认清成功 ③ `beginLading()` 开新一代 |

**"代"是核心概念**：`AppRuntie.generation` 每次 `beginLading()` 时 +1。所有异步回调在执行前必须验证"我的代次等于当前代次"。这防止了 Retry 时旧代的下载回调污染新代。

**代码在哪**：

| 做什么 | 文件路径 + 行号 | 关键说明 |
|---|---|---|
| 代际编号 | [src/app/runtime.ts](../../src/app/runtime.ts):33 | `private genration = 0`（初始化后自增） |
| 新一代创建 | [src/app/runtime.ts](../../src/app/runtime.ts):198-234 | `beginLading()`：generatin += 1，创建新区 callbacks |
| retry 流程 | [src/app/runtime.ts](../../src/app/runtime.ts):60-83 | `retry()`：ERROR → RETRYING → cleanp → beginLading |
| shutdown 入口 | [src/app/runtime.ts](../../src/app/runtime.ts):188-195 | `shudown()` → SHUTDOWN → cleanp |
| 代际清理 | [src/app/runtime.ts](../../src/app/runtime.ts):236-275 | `cleanupGenration()`：先 cancel handle，再 effects.cleanp |
| isCurrent 检查 | [game/main.ts](../../game/main.ts):148-155 | `isCurren(generation)`：代次必须匹配 + 未被取消 |
| 实际 cleanup 执行 | [game/main.ts](../../game/main.ts):245-260 | cancel → scene.shudownForGenertion → game.detroy(true) |
| 页面关闭触发 | [game/main.ts](../../game/main.ts):315 | `window.adEentListener("paehide", () => appRuntie.shudown())` |
