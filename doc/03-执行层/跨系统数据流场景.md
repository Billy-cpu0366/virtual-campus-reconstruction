# 跨系统数据流场景

> **目的**：用 4 个典型场景串联 16 系统间的完整链路，让新加入的开发者不用从 60 个接口反推协作关系。
> **阅读方式**：每个场景用一条时序线标出经过的系统、调的接口、数据怎么流转；最后附一张速查表。

---

## 场景 1：玩家走进 memo3 区域 → 弹窗 → 关闭

这是最完整的一条"用户感知内容"链路，穿过 5 个系统。

```
玩家移动（每帧）
  │
  ▼
SYS-INPUT
  │ 键盘/摇杆 → 8 方向 Direction
  │ API-INPUT-001 / API-INPUT-002 / API-INPUT-003
  ▼
SYS-MOVE
  │ 方向 → 速度 (vx, vy) + 碰撞判定
  │ API-MOVE-001 / API-MOVE-002（这格能走吗 → SYS-LAYER walls）
  │ API-MOVE-003（blocked 方向 → 动画停/走）
  ▼
SYS-PLAYER
  │ 设置 velocity → Phaser Arcade 物理移动
  │ API-PLAYER-002（动态深度 → SYS-LAYER playerDepth）
  │ API-PLAYER-005（朝向更新）
  │ API-FX-003（如果在 footsteps 标记格 → SYS-FX 生成脚印精灵）
  ▼
SYS-ZONE
  │ 每帧检查玩家位置是否落入注册区域
  │ API-ZONE-002（玩家进入判定）
  │ 发现玩家进入 memo3 区域 → onEnter 回调
  ▼
SYS-INTERACT
  │ API-INTERACT-001（弹窗触发，传入 memo3 的 interactionId）
  │ API-INTERACT-003（查询弹窗内容：标题/正文/图片/按钮）
  ▼
SYS-GAME-UI
  │ API-GAME-UI-003（渲染弹窗 DOM）
  │ 暂停玩家输入
  │
  │ ... 用户读完、点关闭按钮 ...
  │
  ▼
SYS-INTERACT
  │ API-INTERACT-002（弹窗关闭）
  │ 恢复玩家控制
```

**关键数据**：交互配置（标题/正文/图片/按钮）由 SYS-INTERACT 维护；memo3 的坐标边界由 SYS-ZONE 注册时传入。换皮时只需改 INTERACT 和 ZONE 的"皮"那一层。

## 场景 2：航拍 → chunk 预载 → 动态装卸

穿过 4 个系统，揭示了 chunk 生命周期和相机联动的完整链路。

```
用户点 play 按钮
  │
  ▼
SYS-APP
  │ API-APP-002（场景切换：首页 → 游戏场景）
  │ API-WORLD-001（createWorld：创建 Tilemap + 24 层）
  │ API-ASSET-001（资源清单查询 → 拿 tileset URL）
  │ API-ASSET-002（瓦片集发现 → 切块 key 列表）
  │ API-ASSET-003（资源就绪检查）
  ▼
SYS-CAMERA
  │ API-CAMERA-003（航拍序列：6 点坐标+耗时+停留 → 总约 111s）
  │ 航拍期间相机不跟随玩家
  │
  ▼ 航拍结束
  │ API-CAMERA-001（startFollow：硬跟随玩家，lerp=1）
  │ API-FX-002（安装后处理管线 HeatHaze/Fire/Morph）
  ▼
SYS-CHUNK（每约 500ms 或显著移动时）
  │ API-CHUNK-004（相机可见范围 → ChunkCoordinate[]）
  │ API-CHUNK-003（玩家邻域 3×3）
  │ API-CHUNK-001（目标集合 = 玩家邻域 ∪ 相机可见 +1 边距）
  │
  │ 对新增的 chunk：
  │   ├─ fetch chunk_N.json
  │   ├─ 校验 layer 数量/GID 合法性
  │   ├─ API-WORLD-003（applyChunk：24 层批量写入 Tilemap）
  │   │     └─ 每层查 API-LAYER-001（图层策略：depth/可见性/碰撞角色）
  │   └─ 成功后加入 renderedChunks
  │
  │ 对离开的 chunk：
  │   ├─ API-WORLD-004（removeChunk：清除 24 层 Tilemap 区域）
  │   └─ 成功后从 renderedChunks 移除
  ▼
SYS-WORLD
  │ worldSpec（API-WORLD-005：只读查询世界尺寸/边界）
  │ 各 chunk apply/remove 时通过 LAYER 查 GID 碰撞策略
  ▼
SYS-LAYER
  │ API-LAYER-005（碰撞 GID 判定：69345 强制碰撞、69346 强制不碰撞）
  │ SYS-MOVE 由此确认哪些 tile 会阻止移动
```

**关键数据**：ChunkDataStore 维护在途请求去重、失败记录（坐标+错误类别+尝试次数）、AbortController 取消；重试上限 3 次。换皮时 chunk 网格尺寸（5×5、28×28 tile/chunk）是骨架，但 tileset 贴图内容、图层数量、GID 集合是皮。

## 场景 3：玩家上桥 → 深度切换 → 碰撞层切换

穿过 3 个系统，展示一个"区域触发 → 环境变化"的完整闭环。

```
玩家走向 bridge1 区域
  │ 每帧 SYS-MOVE 查 walls/bridge 碰撞
  │ API-MOVE-002（这格能走吗 → SYS-LAYER walls 层）
  ▼
SYS-ZONE
  │ API-ZONE-002（玩家进入判定 → 检测进入 bridge1 区域）
  │ onEnter 回调触发
  ▼
SYS-LAYER
  │ BRIDGE-003（roof/bridge 区域判定 → "bridge1" + "enter"）
  │
  │ API-LAYER-004（bridge 状态切换："bridge1", state="up"）
  │   同步执行三件事：
  │   ├─ 上层可见性 OFF、下层可见性 ON
  │   ├─ 上层碰撞 OFF、下层碰撞 ON
  │   └─ 设置玩家深度覆盖 = 1650（桥上）
  │
  │ 调用 SYS-PLAYER：
  │   API-PLAYER-002（动态深度 → 玩家 depth 切为 1650）
  │
  │ ... 玩家在桥上走动 ...
  │   每帧 SYS-MOVE 查下层的碰撞 tile（桥面可走、桥栏不可走）
  │
  │ 玩家离开 bridge1 区域
  ▼
SYS-ZONE
  │ API-ZONE-002（onLeave 回调）
  ▼
SYS-LAYER
  │ BRIDGE-003（"bridge1" + "leave"）
  │ API-LAYER-004（bridge 状态切换："bridge1", state="down"）
  │   上层可见性 ON、碰撞 ON
  │   下层可见性 OFF、碰撞 OFF
  │   深度覆盖移除 → 恢复常态公式 500 + (y+24)*0.1
```

**关键数据**：bridge 状态由 SYS-LAYER 保存；玩家在桥上时 depth=1650、桥墙层 depth=3500。换皮时 bridge 区域坐标是皮（需要换的校园定义哪些地方有桥、有几个桥），bridge 切换机制（同步三件事）是骨架。

## 场景 4：资源加载失败 → 全局错误页 → 用户重试

穿过 2 个系统，展示错误从检测到恢复的完整路径。

```
SYS-ASSET 加载阶段
  │ beginLoading() 启动 tileset/world 资源加载
  │ Phaser Loader 逐个请求
  │
  │ 某个资源下载失败：
  │   ├─ loaderror 事件触发
  │   ├─ requiredLoadError 标志置 true
  │   ├─ 状态机：LOADING → ERROR
  │   └─ AppRuntime.fail() 被调用
  ▼
SYS-APP
  │ API-APP-001 的异常处理分支
  │ 停止游戏循环
  │ 显示错误页 + Retry 按钮
  │
  │ ... 用户点 Retry ...
  │
  │ AppRuntime.retry()
  │   ├─ cleanupGeneration(previous) 清干净旧的一代
  │   ├─ 校验清理结果
  │   └─ beginLoading() 重新启动加载
  │       ├─ 已有缓存的不重复请求
  │       └─ 之前失败的重新下载
  ▼
SYS-ASSET
  │ 状态机：ERROR → LOADING → READY
  │ ... 如果再次失败 → 回到 ERROR → 显示 Retry
  │ ... 如果成功    → READY → 进入游戏
```

**关键数据**：ASSET 状态机仅 3 态（LOADING / READY / ERROR），不做自动重试。CHUNK 的失败策略与之不同（**每块最多 3 次尝试**，`data-store.ts:186`；另有目标级指数退避 + AbortController 取消），因为 chunk 是可恢复的动态资产、tileset 是必需的基础资产。详见[统一失败处理策略](统一失败处理策略.md)。
