# 换皮配置总表

> **这是什么**：全站**可配置项**的唯一清单。细小到「这个 NPC 长什么样、走哪条路」都有对应的配置键。
>
> **两条来源**：
> ① 16 张系统卡里的「皮 / 配置点」**照抄汇总**（§一~§六 各板块的明细，值以卡为准）；
> ② 由 ① 细化出来的**配置键与实例数据**——卡片没有的，以本表为准。
>
> **本版做了什么**（2026-09-17）：把原来「一行糊一类东西」的粗表，拆成「一行一个字段 + 一行一个对象」；补上生效时机、作用域、交付形态三列；去掉跨板块重复；补上页面壳与音乐会灯光等缺失项。
>
> **用途**：换皮 / 后台配置下发时的一站式清单——不用再翻 16 份文档，也不用再翻代码。

## 怎么读这张表

### 每个板块两张表

| 表 | 回答什么问题 | 一行是什么 |
|---|---|---|
| **字段定义** | 这个系统**哪些东西能配** | 一个**字段**（如「NPC 的缩放比例」） |
| **实例数据** | 现在**具体是谁** | 一个**对象**（如「special-reading 这个 NPC」） |

字段定义是「表格的列」，实例数据是「表格的行」。只有多实例的系统才有第二张表。

### 「字段」和「配置键」是同一个东西

**一个字段 = 一个能填的格子**，就像 Excel 里的一列。

**配置键 = 这个格子的门牌号**，用来指「到底是哪一个格子」。字段定义表的第一列就是配置键。

**怎么念**——只有三条：

| 符号 | 念成 | 例子 |
|---|---|---|
| `.` | 「的」 | <code>gameUi.mapMarker.color</code> = 游戏UI **的** 地图标记 **的** 颜色 |
| `[]` | 「每一个」 | <code>layer.strategies[].depth</code> = 图层 **每一个** 图层的 深度 |
| 末尾那个词 | 就是那个属性本身 | `spriteKey` = 用哪张贴图 |

最长的一个拆开走一遍：

```
gameUi . miniMap . hudSize . desktop
   ↓        ↓         ↓          ↓
 游戏UI 的  小地图  的  HUD尺寸  的  桌面那一档
```

**为什么非要有这串门牌号**：后台改完值要写回代码，得知道写去哪。人话说明告诉你「这是什么」，配置键告诉你「它在哪」——两列缺一不可。

### 三根轴

每个字段都带三个标签，回答「怎么改」「管多大」「后台用什么装」。表头分别简写为 **生效 / 范围 / 形态**：

**生效时机** —— 改完什么时候生效

> ⚠️ **先说清楚：这三种写的是「接上配置层以后」的目标行为，不是现在的能力。**
> 现在全站没有一个值能在运行中改——没有配置层，也没有热重载（代码里搜不到 `import.meta.hot`、配置监听之类的东西），
> 所有值都是写死在代码里的常量。**改任何一条，今天都得改代码 + 重新构建。**

| 值 | 意思 | 例子 |
|---|---|---|
| **随包** | 值属于某个资源包 / 内容包，换包就换 | 地图几何、NPC 外观、弹窗文案 |
| **启动** | 代码在**创建对象时读一次、存进实例里**，之后只用存下来的那份。改它得把这个对象重建（实际就是重载页面） | 分辨率、物理帧率、并发上限 |
| **热** | 代码在**用的那一刻现场去读**，没提前存。所以接上配置层以后不用重载页面就能改 | 走路速度、触发距离、淡隐时长 |
| **—** | 谈不上时机，三种情况都用它：值**根本没有**（缺口）、值有但**没人读**（声明未用）、值**还没查清**（未确认） | 换装超时保护、没被读取的摇杆阈值、高清层宽高比 |

**「启动」和「热」怎么分：只看一件事——这个值是提前「存起来」了，还是每次用的时候现读。**
存起来 = 启动，现读 = 热。代码上通常长这样：

```ts
// 启动：构造函数里存进 this，后面全用 this.interactionDistance
this.interactionDistance = options.interactionDistance ?? DEFAULT_INTERACTION_DISTANCE;

// 热：用的时候直接读常量，中间没有任何一份存下来的副本
return isDiagonal(direction) ? SPEED_DIAGONAL : SPEED;
```

**作用域** —— 这个值管多大范围

| 值 | 意思 | 例子 |
|---|---|---|
| **全局** | 一个值管全站 | 逻辑分辨率 |
| **每校园** | 每个学校一份值 | 资源根路径、主题色 |
| **每设备** | 手机 / 平板 / 桌面各一份 | 摇杆尺寸、弹窗高度比例 |
| **每实例** | 每个对象自己一份 | 每个 NPC 的坐标、每条路线的速度 |

**交付形态** —— 后台用什么界面装

| 值 | 意思 | 后台长什么样 |
|---|---|---|
| **数** | 一个值（数字 / 文字 / 颜色 / 开关） | 开个输入框 |
| **表** | 一组对象，每个多个属性 | 做成表格，多行多列 |
| **文件** | 一整份数据文件（地图 JSON、多边形坐标串……） | 只存路径，内容在文件里 |

### 去重规则

同一个值在多个系统里都出现时（比如世界尺寸同时属于 SYS-WORLD 和 SYS-CHUNK），**只在权威位置完整列出**，别处只留一行指向它，标 `[与 SYS-XXX 重复]`。这样「一共多少个配置点」这个数才是真的。

三处**权威归属**约定：

- **地址、超时、重试、并发** → §六 网络协议层权威（那是传输设计层）
- **世界几何、图层、深度** → §2 SYS-WORLD 与 §3 SYS-LAYER 权威
- **速度、深度基值、手机断点** → 分别由 §5 SYS-INPUT、§3 SYS-LAYER、§12 SYS-GAME-UI 权威

### 标记约定

- `[与 SYS-XXX 重复]` —— 该值在别处已完整列出，此处不重复
- `（未接线）` —— 代码里定义了、但运行期没有任何地方调用它
- `（声明未用）` —— 值写在那里，实际渲染 / 行为不走它
- `（缺口）` —— 设计上需要、但当前代码里没有

### 一条不删

本表**不做「这个值该不该配」的取舍**——凡代码里存在、且有可能因校园不同而不同的值，全部列出。判据是「能不能配」，不是「这次换校园要不要改」。

### 实例数据 —— 瓦片集切块（`master.json` 的 `tilesets`）

| key | 图片文件（Tiled 作图源） | 列数 | 行数 | firstgid |
|---|---|---|---|---|

> 运行期实际加载的是同名 `.webp`（`exterior` 对应 `exterior-final.webp`）。`master.json` 里的 `.png` 是 Tiled 作图源，运行期不用。代码只读 `tilewidth/tileheight` 和 `firstgid`，`columns/margin/spacing/tilecount` 写在文件里但不被读取。

**这张表在说什么（人话版）**

地图上每块草地、每堵墙、每个人，都是 **16×16 像素**的小图拼出来的。这些小图不存成几百个文件，而是**全部印在一张大图上**，像一版贴纸：

```
exterior.png（2816 × 6304 像素的一张大图）
┌────┬────┬────┬────┬────┬────┐
│ 1  │ 2  │ 3  │ 4  │ 5  │ …  │  ← 每格 16×16
├────┼────┼────┼────┼────┼────┤
│177 │178 │179 │180 │ …  │    │  ← 满 176 格换一行
└────┴────┴────┴────┴────┴────┘
```

游戏要用第 500 号贴纸，就按「176 格一行」算它在第几行第几列，从大图上切那一小块。

**这张表的每一行 = 一版贴纸**：

| 列 | 人话 |
|---|---|
| `key` | 这版贴纸的名字，代码用这个名字找它 |
| **图片文件** | 那张大图叫什么 |
| **列数** | 一行有多少格（`2816 ÷ 16 = 176`） |
| **行数** | 一共几行（`6304 ÷ 16 = 394`） |
| **firstgid** | **这版贴纸的编号从几开始** |

**`firstgid` 是关键——三版编号首尾相接，一个不差**：

| 版 | 有几块 | 编号范围 |
|---|---|---|
| exterior | 176 × 394 = **69,344** | 1 ～ 69344 |
| collisions-objects | 10 × 1 = **10** | **69345** ～ 69354 |
| tileset-particles | 7 × 1 = **7** | **69355** ～ 69361 |

第二版的 `69345` 正好是 `1 + 69344`，接在上一版屁股后面；第三版的 `69355` 正好是 `69345 + 10`。**排版没错位，编号就不会串。**

**这些编号在别处出现过**——[§3](#3-sys-layer-图层与遮挡) 的图层表里那一列 GID 就是它们：

| 编号 | 谁在用 | 地图里出现几次 | 干什么 |
|---|---|---|---|
| 69345 | `walls` / `cars` / `footsteps` / 4 个桥墙层 / `layer7` | 5733 | 「能撞」的墙 |
| 69346 | `walls` | 2865 | 「不撞」的墙 |
| 69350 / 69351 | `cars` | 9 | 两种车的碰撞形状 |
| 69353 | **只有 `walls`** | **595** | **沙滩换装触发区**——见下方 |
| 69355–69359 | `particles` / `particles2` | 2818 | 粒子贴图 |
| 69361 | `particles3` | 86 | 提取了但**没人用**（见 §3 与 [配置点总览](#配置点总览)） |
| 69347、69352、69354、69360 | **没人用** | 0 | 地图里就没出现 |

> **`69353` 是沙滩换装触发区**（不是墙，也不是漏处理的碰撞块）。原站每 3 帧查一次「玩家脚下是哪一格」，查到 `69353` 就触发脱衣换装；离开沙滩再踩回 `69353` 时触发穿衣。
>
> 所以这 595 格**必须是「不碰撞」的**——玩家得能站上去。本 CORE 里它落到 Phaser 默认值「不碰撞」，结果上是对的。触发逻辑在 `src/layer/beach-zone.ts`（`BEACH_TRIGGER_GID = 69353` + `isBeachTriggerTile()`），由 `game/CampusScene.ts` 每 3 帧查一次玩家脚下格子后调用。详见 [§7 玩家](#7-sys-player-玩家) 的换装条目。



**换校园要动这里的三样**：① 重画那两张图；② **重排编号**（新图多大，`firstgid` 全得跟着重算）；③ 重画地图数据（哪一格放哪张贴纸）。**列数、行数、每格大小必须和真图对得上**（`2816 ÷ 176 = 16`），对不上切出来的图就是花的。

> **「世界坐标 → 格子编号」的查询契约**（`PhaserWorldRenderer.tileIndexAtWorld(层名, 世界x, 世界y)`，`game/PhaserWorldRenderer.ts:276-296`）：把像素坐标除以格子尺寸得到格坐标，再除以每块格数定位到具体分块的图层，然后读那一格。
> **返回值就三类**：**数字** = 该格子的 GID（`walls` 层只会读到 `69345` 有碰撞 / `69346` 无碰撞 / `69353` 沙滩触发 这三种）；**`-1`** = 这一格是空的（格子存在、没内容）；**`null`** = **压根没查到**——那一块还没渲染出来，或者坐标越界。
> `-1` 和 `null` **语义完全不同**：`-1` 是「这里确实是空的」，`null` 是「我还不知道这里有什么」。谁把 `null` 当成「空」来用，在分块刚好没加载时会得到错的答案。
> 判定一个具体 GID 是否命中时用 `src/layer/beach-zone.ts` 的 `isBeachTriggerTile()`——它把 `null` / `undefined` / 别的 GID 一律判成「不是」，所以**不会因为分块没加载而误触发**。

### 实例数据 —— 后台必须做对的四件事

| # | 要求 | 为什么 |
|---|---|---|
| 1 | 分块 JSON 必须以 `application/json` 返回 | 返成 `text/html` 会让前端解析失败，然后走重试路径——3 次全废 |
| 2 | 404 必须真的是 404 | 不能返「200 + 一个 HTML 错误页」；前端靠状态码判断失败，返 200 会在解析环节以更难查的方式炸掉 |
| 3 | 资源挪到 CDN 必须配 CORS | 现在全部同源；`mapBaseUrl` 换成绝对网址后会直接全部失败 |
| 4 | 缓存按「名字有没有内容指纹」分档 | 前端产物名字带指纹可长缓存；地图数据固定名（`chunk0.json`）换校园就变，必须短缓存或协商缓存 |

### 实例数据 —— 地址推导的三条规则

| 规则 | 结果 |
|---|---|
| 推导一：索引文件名固定 | `{根}/chunks/master.json` |
| 推导二：瓦片图 = 根 + `master.json` 里写的 image 名 | `{根}/{tileset.image}` |
| 推导三：分块 = 相对索引地址解析 | `{根}/chunks/chunk{index}.json` |

> **为什么推导比清单好**：若后台下发一张「完整资源清单」，那张清单就得人为维护，早晚和磁盘实际文件对不上。而推导不会不一致——`master.json` 本身就是那份清单。**这是地址契约能压成一个字符串的原因。**
