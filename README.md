# 虚拟校园项目重构

> Phase 1：基于 Peter Oravec 公开前端恢复系统知识，并以原站复刻验证理解。

这是当前项目的**唯一 Git 仓库和总入口**。Human 从理解层和决策台账掌握目标，AI 从`doc/03-执行层/`读取精确工程知识；证据、代码、测试和状态都在同一仓库内保持可追溯。

## 项目目标

整体大目标（Human 9-7 复述）：

> 由于 Peter 这个只是可以看到前端，所以我们打算先逆向然后再补充一个后台管理系统，把整个过程给串起来，最终目的要实现可以换皮，把 peter 这个在本地完善后可以直接在这个框架上换各个校园的皮。做成各个校园的这些网站。

按阶段拆开：

| 阶段 | 目标 | 当前状态 |
|---|---|---|
| **Phase 1（当前）** | 逆向 Peter 公开前端 + 复刻验证理解；建立 16 系统骨架；为换皮提前准备可复用基础 | 已跑通：8/16 确定性 CORE ✅、可玩雏形 Human 视觉通过、动态分块+碰撞集成 Human 视觉通过、执行层 16 卡 15/16 designed |
| **Phase 2（远期）** | 在 Phase 1 骨架上补后端、后台管理系统、换皮能力；做成各校园可套用的网站 | 未启动 |

"骨架 / 皮"分离是这条主线的关键设计：CORE 是骨架的最小单元，集成是接上 Phaser/Vite/网络等"皮层"；换皮时只动"皮"那一层，骨架不动。

> 这一节是 9-7 复盘之后的项目目标定调。如果之后只看到"Phase 1 边界"里的"不在范围"列表，请先回到这一节理解"不在范围 = Phase 1 不做 ≠ 项目不做"。

## 每个大板块怎么开发（螺旋式迭代闭环）

> 从 2026-10-25 起，后台管理系统以及 Phase 2 的每个新功能板块，都按这条闭环走。**每转一圈交付一个能跑、能验收的小版本**，下一圈在上一圈的基础上补，不追求一次做完。游戏逆向的 16 个系统已有自己的六步循环（见 `doc/03-执行层/README.md`），不重复套用本节。

```text
需求收集 → 需求分析 → 概要设计 → 详细设计 → 测试（事件驱动）
    ↑                                              │
    └────────── 下一圈：补需求、改设计 ←────────────┘
```

### 五个阶段各交什么

| 阶段 | 要回答的问题 | 交付物 | 算完成的标志 |
|---|---|---|---|
| 1. 需求收集 | 客户/使用方到底提出了什么？ | 结构化需求清单；原始件（会议录音、合同、外部接入文档、定制需求 1.0/2.0/3.0、思维导图、任务计划表） | 每条需求有编号、来源、日期；"原话"和"我们的理解"分开记；没搞清的单列为待确认 |
| 2. 需求分析 | 客户到底想要什么？我们打算怎么做？ | PRD 或技术需求分析报告 | 每条需求都有对应方案；写清本轮做什么、不做什么；每条都有能验证的验收标准 |
| 3. 概要设计 | 系统由哪几块组成？页面怎么走？ | 页面清单（名称、用途、路径）、前后端边界、API 清单（接口定义、请求/响应、数据交互） | 每个页面都知道路径和用途；前端依赖后端的每个功能都有接口定义，不靠口头约定 |
| 4. 详细设计 | 每个页面、每张表具体长什么样？ | 页面结构、调用的 API、字段、状态（加载中/空/出错）、交互事件、样式约定；数据库表与对象字段 | 字段能一一对上数据库表；状态和事件列全；同类元素抽成模板，不在页面里重复定义 |
| 5. 测试（事件驱动） | 每个事件发生后，系统做得对不对？ | 事件清单 → 测试用例 → 自动化脚本 → 流程图 | 每个事件至少一条自动化用例；改完代码能一键重跑，不靠手点 |

### 贯穿始终的六条规矩

1. **需求先编号，再动手。** 没编号的需求不进设计——"说过"不等于"要做"。
2. **前后端解耦。** 前端要什么数据，用 API 文档写死。后端还没做时，前端按契约用假数据先跑通。
3. **按系统拆，不按页面堆。** 能独立变化的东西拆成系统（人物、NPC、任务、建筑、路线……），页面只是这些系统的组合。基础组件是模板，页面里的具体呈现是实例；改模板，所有实例一起变。
4. **数据库设计提前做。** 一个对象就是一张表，它的属性就是字段；每张表有主键，需要快速查找的字段建索引。不等到代码写完再补表。
5. **事件必须能测。** 事件 = 用户做了一个动作，或系统状态变了（登录、保存、校验失败、发布、回滚、点弹窗、撞墙）。事件触发什么后续动作，设计里写清，测试照着验。测试脚本可以让 AI 生成，配一张流程图看走位。
6. **技术约定和日志先行。** 技术栈、日志、错误处理、配置、支付等标准，板块开工前写进技术约定；日志单独建表，记谁、何时、从哪来、做了什么、结果如何，用于审计和追查。

## Phase 1 边界

> 从已确认的目标与范围抽取，作为本阶段的工作边界；动态状态只看 `doc/task_plan.md`。
> 这一节里写的"不在范围"= **Phase 1 不做**，**不是项目整体不做**。整体大目标（逆向 + 后端 + 后台 + 换皮）的后端、后台、换皮部分都放在 Phase 2；16 系统卡 + 写作规范 + CORE/完整系统分层 = 为 Phase 2 换皮提前准备的骨架。

- **整体目标**：逆向 Peter Oravec 公开前端恢复系统知识，用原站复刻验证理解；最终做成可换皮的各校园网站（Phase 2 实现，Phase 1 只做骨架准备）。
- **当前纳入（Phase 1）**：
  - 网站部分：页面启动与状态；页面结构与导航；作品、卡牌和弹窗展示；游戏嵌入；响应式与设备适配。
  - 虚拟世界部分（当前优先）：游戏启动与资源加载；地图、分块、图层和碰撞；玩家、输入、移动和相机；NPC、环境实体、车辆和路线；区域触发、世界交互、UI和动效。
  - 公共支撑：内容与配置；资源路径与命名；状态和事件通信；错误、兼容和调试。
  - 骨架准备：16 系统卡、CORE/完整系统分层、皮/骨架标记（详见 [`doc/02-接口层/API契约表.md`](doc/02-接口层/API契约表.md)）。
- **明确不在范围（= Phase 1 不做）**：最终虚拟校园业务、后台管理系统、换皮执行、Phase 2 后端基础设施、多人在线支持、未公开原始 TypeScript、私有仓库和 Git 历史；服务端、数据库、密钥和私有配置；未在公开文件或运行时出现的猜测资源。
- **公开证据边界**：只使用 `sample/` 公开镜像与运行时证据（`sample/original-public-build/mirror/`、`manifest.json`、`sample/analysis/runtime-network.json`、地图 JSON、公开 Bundle 和浏览器实际表现）；现有 Phaser 复刻只作为实现对照，不是事实源。
- **复用必须实践后确认**：第一次出现的逻辑先正确研究和实现；第二个独立实际场景出现相同行为或同一逻辑被重复修改时，才登记复用观察；只有多个真实场景显示出稳定部分和变化部分后，才允许提出提取方案；未经 Human 确认不得自行抽象。
- **正式代码逐项授权**：正式 `src/` 只在逐工作项 Human 授权下写入对应源码和测试，授权写清"这次只授权哪块"。已有先例：`WI-SYS-CHUNK-CORE-001` 在 `DEC-SYS-CHUNK-CORE-001` 授权下实现于 `src/chunk/`；其他系统未授权前不写代码。

## 协作模式

当前项目为**单人开发**（Human + 单个 AI 助手在主对话里推进；偶尔启动并行子任务处理独立小工作）。`AGENTS.md` 第 7.5 节"多人协作与 PR 交付"和第 7.6 节"API 协作规范审查与落盘"保留了"未来第二位协作者加入或外部 API 规范提交"时的扩展规则，但当前不默认启用。

具体表现：
- 没有"假设有第二位协作者"的强制 PR 流程。
- `git worktree` 在 WSL 沙箱里被拦截时由 Human 在 WSL 终端中转；其他 Git 操作（commit、push）由 Human 在主对话里授权。
- 6 个并行 AI 写文档的方式（9-1 那一周）按"独立子任务"对待，不套用完整 PR 流程。

## Human与AI怎样接力

```text
Human看懂系统并提出目标
→ 02-接口层说明系统之间交换什么
→ AI从sample取证并在03-执行层系统卡中填写事实、推断、设计和未知
→ Human确认本次范围与验收标准
→ task_plan和根决策记录登记授权
→ AI实现并运行测试/行为验证
→ 已确认结论回到理解层，精确细节和验证结果回写执行卡与总账
```

没有Human授权，不写超出当前工作项范围的正式代码。原站事实、推断、设计决定和未确认项须分别在文档中写清，不混淆。
