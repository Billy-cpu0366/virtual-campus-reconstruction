# 配置总方案

**一句话**：把游戏里「能改的值」从代码里拎出来，独立成文件。以后换校园改这里，不动 `src/`。

> **为什么写成文件**：这份方案原先只存在于对话记录里，结果两边理解慢慢跑偏，最后得翻旧账对质。
> 写进文件就不会再丢。**规矩以本文件为准，聊天里说的不算。**
>
> **配套文件**：[配置格式规范](配置格式规范.md)（配置文件长什么样）· [README](../README.md)（现状与已知缺口）

---

## 一、这件事的本质

**不是「搬文件」，是一次重构**——把散在逻辑里的值，改造成「独立文件 + 读取代码」。

| | 现在 | 改造后 |
|---|---|---|
| 值在哪 | `src/npc/staticNpc.ts` 里写着 `tileX: 72` | `config/.../数据/static-npc-configs.json` 里 |
| 游戏从哪读 | 直接读源码里那个常量 | 读配置文件 |
| 换校园怎么改 | 翻源码、改完还得重新构建 | 改 JSON、刷新页面就生效 |
| 谁在什么时候读 | 打包进去，跟着安装包走 | 游戏**运行时**才去取（NPC 数据层已经这样了） |
| 后台能不能管 | 管不了 | 能 |

## 二、四条铁律

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **`src/` 只许按第四节的红线动**，其余一字不改 | 它是 Peter 原版的复刻，是「我复刻得像不像」的唯一参照物 |
| 2 | **存 JSON 文件，运行时读取** | 终点是后台管理系统，后台要能读写文件。现在省事 = 将来返工 |
| 3 | **按板块分，不按层分** | 总表就是按板块分的（一、地图线 / 二、玩法线 / … / 五、旁支）。换皮的人和后台都按板块找东西 |
| 4 | **备份 = 版本快照**，不是「存一份」 | 以后会有 set1、set2 各套校园配置，靠日期比对 |

## 三、文件怎么摆

### 3.1 第一刀：把源码劈成「数据」和「逻辑」

- **数据** = 值本身。全是数字和文字，没有一句"怎么做"。
  例：这个静态 NPC 站在第 72 格；跳舞人群在 114~131 格活动；虫子有 10 只。
- **逻辑** = 拿这些值干活的代码。
  例：把文件读进来；检查 72 是不是合法格数；把值交给游戏。

**为什么这么劈**：值会随校园变（换个学校，NPC 站位全不一样），逻辑不会（读文件、查合法性的做法到哪儿都一样）。
把会变的和不会变的分开，换皮时只碰会变的那一半。

### 3.2 第二刀：按板块归位

```

├── game/                    ← 原样不动
├── doc/                     ← 原样不动
├── bak/                     ← 版本快照（不进版本库）
│   ├── 配置1-第一小步-2026-09-19/    ← 已存
│   └── 配置-<日期>/                  ← 第 4 步的正式冻版
│
└── config/                   ← 新工作区，与 src/ 平级

    │   ├── 配置格式规范.md      ← 配置文件长什么样
```

**一条规则管全部**：

> **跟板块无关的放「公共」。跟板块有关的，会随校园变的放「集 / 板块 / 系统 / 数据」，不变的放「骨架 / 板块 / 系统 / 逻辑」。**

**名字全部抄总表**——总表写 `# 五、旁支` `## 14. SYS-NPC`，这里就是 `05-旁支/SYS-NPC/`。两边编号对得上，翻的时候不用查表。

**空文件夹不建。** 做到哪个系统才建哪个，免得一堆空壳看着乱。

### 3.3 第三刀：按校园分「骨架」和「集」

3.1 只把源码劈成了「数据」和「逻辑」两半。真到换校园时，这两半的去处**不一样**：数据一个校园一套，逻辑到哪个校园都是同一份。所以再劈一刀，`config/` 底下分成两类：

| | 什么时候动 | 里面有什么 |
|---|---|---|
| **`骨架/`** | 换校园时**不动** | 公共零件 + 各系统的「逻辑」 |
| **一个集，一套**（`default/` 是默认那套） | 换校园就是**新加一个目录** | 只有各系统的「数据」 |

**为什么非分不可**：逻辑要是跟着集走，有五套配置就有五份一模一样的读取代码。改一处 bug 要改五处，漏一处就有一套行为跟别人不一样——正是 3.1 想避免的「改一边忘一边」。

**集名只用小写英文字母、数字、`-` 和 `_`。** 这条不只是为了好看：集名要拼进网址再拿去取文件，放任 `../` 之类就能越出 `config/` 读到别处。顺带白捡一条——`骨架`、`文档`、`工具` 是中文名，天然过不了这道关，不必再单独维护一张「哪些目录不算配置集」的名单。

**读哪一套在网址上说**：不带参数读 `default/`，带 `?config=set1` 就读 `default/` 旁边那个 `set1/`。认不出来的集名（拼错、带斜杠、中文）退回默认那套，并在控制台喊一声——不喊的话，拼错的人会以为「我指明了却没生效」，而游戏照常跑起来，最难查。

## 四、`src/` 的红线（第二小步才生效）

`src/` 是复刻基准，**默认一个字不许改**。第二小步接线时，只许按下面三类动。

### 许动的三类

| 类型 | 是什么 | 怎么动 |
|---|---|---|
| **① 把值搬走** | `src/npc/` 里 `export const XXX_CONFIG = {...}` 这类**具体数值**的常量 | 整个常量删掉（值已在 JSON 里） |
| **② 把藏着的值挖出来** | 4 个文件里**没导出**（模块私有）或**写死在函数体里**的值：<br>`routeCrowd.ts` 的 safeMargin · `sprayer.ts` 的两个 trigger · `venueCrowdRuntime.ts` 的 prewarm/recycle · `gridPathProvider.ts` 的四个 | 加 `export`，或从函数体提到顶层。<br>**只搬位置，不改数值、不改算法** |
| **③ 改「去哪儿取数」** | 8 个 Runtime 类 + `game/` 里 8 个适配器 | 从「`import` 那个常量」改成「从加载器拿配置」 |

第二条和第三条有个**连带结果**，值得单说一句，因为它看起来像改字段定义、其实不是：

> 值改成从外面递进来之后，源码里那些 `XXX?: number` 的**可选**字段必须变成**必填**。
>
> 为什么：留着默认值意味着「不给配置也能跑」，而跑起来的结果是**场景里悄悄少一群 NPC**——比直接报错难查得多。改成必填，少给一项就编译不过，当场就发现。
>
> 所以 options 里那些 `?` 去掉了、`constructor(options = {})` 里的 `= {}` 去掉了。**字段名和类型一个没变**，变的只是「给不给得起默认值」。

### 绝对不许动的

- 所有 `interface` / `type`（**字段定义**）—— 这是"有哪些字段、什么类型"，跟校园无关
- 所有算法（怎么走、怎么排、怎么算深度、怎么生成路径）
- Phaser 的一切
- 资产文件（webp、图片、音频）
- `doc/` 全部

### 怎么验证没手滑

第二小步做完，把改动 **diff** 出来逐条对照：**每一条改动都必须能归进上面三类里。归不进去的，就是越界了。**

## 五、分几步走

### 第 0 步 定地基 ✅

建目录骨架 + 写《配置格式规范》。

**为什么先做**：后面要抄几百个值。格式不先定死，抄到一半改格式，前面全白干。

### 第 1 步 试点 SYS-NPC ✅

**为什么只挑 NPC**：16 个系统一起铺，做错了就是 16 倍返工。先拿一个练手，把路走通。

#### 1.1 只抽文件，加载方式不变 ✅

- **抽文件** = 把 `src/npc/` 里散落的值，抄成 14 个 JSON，放进 `config/`。一个个对着原文抄，不凭印象。
- **加载方式不变** = **游戏还是读原来那份**。那 14 个 JSON 抄出来了、摆好了，但**没有任何代码去读它们**。

> 打个比方：仓库里的货，你照抄了一份台账放到隔壁柜子。台账抄得准不准可以核对，但**发货还是照原来的货架发**。

**为什么分两小步**：抽文件、换读法本来是两件事。一起做，出了毛病分不清是哪件坏的。分开做，每步只有一件事在变。

**验收两条**：① 抽得对不对 —— 测试把 14 个 JSON 里**每一个值**跟 `src/` 里的原值逐个比对（46 个区域轮廓、11 组路线、22 个火车下客点），错一个就报警。② 游戏有没有被搞坏 —— 编译干净、475 条测试过 474、打包通过。

#### 1.2 按板块重排目录 ✅

把原来的 `01-理解层/npc/`、`03-执行层/npc/`、`数据/npc/` 归位成 `05-旁支/SYS-NPC/{数据/, 逻辑/}`，通用零件挪进 `公共/`。

**14 张表的内容一个字没动，只换了位置**（跟快照逐字节比对过）。

重排时顺手改掉的两处：

- **`static-config-source.ts` 从「现成的对象」改成「工厂」**（这个文件在 1.3 换成了 `公共/fetch-config-source.ts`，`ConfigSource` 这个接口没动）—— 它原先直接 `import` SYS-NPC 的清单，那就是「公共」依赖「板块」，方向反了。改成由调用方把清单递进来。
- **配置的 key 改成「相对 `config/default/` 的真实路径」** —— 原先写成 `05-旁支/SYS-NPC/xxx.json`，可文件实际在 `.../SYS-NPC/数据/xxx.json`，中间差一段。那样将来换 fetch 就得靠"猜"补上这段。现在 key 就是真实位置，任何读法都能直接拿去取文件。

**验收**：编译干净、475 条测试全过、打包通过，而且**打包产物的哈希跟改之前一模一样**（`index-CG4cu_Up.js`，296.94 kB）——说明打包出去的东西没变。

**为什么排在接线之前**：骨架定错了就接线，等于接完再拆一次。

#### 1.3 换成运行时读取 ✅

让游戏真的去读那 14 份**数据**配置（后来加上「哪几块地方不站人」那份，共 15 份）。

**做完的效果：改一个数，不用重新构建，刷新页面就生效。**

动了三处：

1. `config/` 里：把「从安装包里读」换成「从网上取」（`fetch-config-source.ts` + `config-location.ts`）
2. `src/npc/` 和 `game/` 里：按第四节红线改「去哪儿取数」
3. 删掉 `src/` 里那份重复的值，只留字段定义

**一并处理的三件事**（都做了）：

- **拆掉旧的** —— `src/npc/` 里那份值删干净了。**不删干净就有两份真相**：改了一份，另一份还在，游戏读的可能还是旧的。
- **填掉"名不副实"的坑** —— `bugCrowd` / `dancingCrowd` 的配置原先**声明了但代码不读**，用的是另外写死的数。现在全读配置。
- **拿掉"不该做成配置"的** —— `bugCrowd.mode` 只有一个取值 `"wander"`，那是类型不是配置，已从配置、形状声明和 `src/` 里一并移掉。

**接线的顺序**（8 个系统一个一个来，每个都走同一套路子）：跳舞人群 → 虫子群 → 场馆人群 → 站位的人 → 路线人群 → 喷水器 → 寻路 → 静态人群。

**验收**：编译干净、490 条测试全过、打包通过。**关键的实测**：起开发服务器，改一个数（`sprayer-tuning.json` 的 `fleeSpeed` 从 140 改成 199），**服务器全程没重启**，游戏取到的就是新值。

**后来又补挖的 4 个值**（数据层最后一批）：`footballCount`、`coffeeRegionIndexes`、`activeRegionExtraMargin` 进了 `static-crowd-tuning.json`，`maxPlacementAttempts` 进了 `venue-crowd-tuning.json`。这 4 个原先不是常量，是**直接写在函数体里的裸数字**，所以当初搜「有名字的常量」时一个都没搜到，总表里也没有对应的行。补完之后 §14 字段数 66 → 70，全表 502 → 506。

**末尾又改了 3 处按名字认人的地方**：静态人群原先靠区域的名字认「哪几片是足球队 / 沙滩 / 车站」，换成靠序号认，新增 `footballRegionIndexes`、`beachRegionIndexes`、`stationRegionIndexes` 三个字段。理由是**新校园不一定沿用这些名字**。§14 字段数 70 → 73，全表 506 → 509。验收：编译干净、497 条测试全过（新增 3 条）。

**这一步没做的**：7 份呈现层表当时仍没接线，见 1.5。

#### 1.4 提前抽完呈现层 ✅

> 编号按「定的时间」排，不按「做的顺序」——这一条排在 1.3 前面定的，实际比 1.3 先做完。

补抽了 `game/` 里那 7 个 Phaser 适配器加 `CampusScene.ts` 的 SYS-NPC 配置，新增 8 份表，SYS-NPC 从 14 份涨到 22 份。

**为什么提前做**：这一条和 1.1 是同一件事——**只是把值抄出来，没有任何代码去读**。它不动 `src/`、不动 `game/`、不改打包产物。既然骨架已经在 1.2 定下，多抄几张表和接线之间没有先后依赖，早做不会让 1.3 变难。

**为什么本来排在后面**：原计划圈在 `src/npc/`（配置最集中的地方），想把模式先跑通再铺开。提前做等于把「铺开」里的 SYS-NPC 那一份先做了——**剩下的 15 个系统仍然按第 2、3 步走**。

**验收**：编译干净、494 条测试全过（新增 19 条）、打包通过，**打包产物哈希依旧一模一样**（`index-CG4cu_Up.js`，296.94 kB）——这 8 份表没有任何代码读，所以出货的东西一个字节没变。

#### 1.5 呈现层也接线 ✅

> 编号按「定的时间」排——这一条是 1.3 的另一半，和 1.4 同一天定的，所以排在 1.4 后面；做的顺序又在 1.3 之后。

让游戏真的去读那 7 份**呈现层**配置（用哪几张图、每帧切多大、气泡什么样式）。

**和 1.3 是同一类改动**——都归第四节红线第 ③ 类「改去哪儿取数」，只是这次落点在 `game/` 的 7 个 Phaser 适配器上，不在 `src/` 里。

**卡在哪，为什么必须提前读**：Phaser 里有条硬规矩——**贴图要在「加载阶段」就报上规格**（这图每帧多大、一共几帧），而那个阶段是**同步**的，等不了网络。配置又是异步取的。所以顺序只有一条路：

> **先读配置 → 再造 Phaser 游戏对象 → 加载阶段才有的可依。**

这条链子把 `game/main.ts` 整个改了：原先「同步造场景 → 造游戏对象」，现在变成「先发起取配置，读完的回调里再造场景 → 再游戏对象」。

**动了四处**：

| 改哪 | 怎么改 |
|---|---|
| `game/CampusScene.ts` | 构造函数多收一个 `npcConfigs`，**必填**；加载阶段 7 次登记贴图全部改成查这份配置 |
| 7 个 `game/Phaser*Runtime.ts` | 各自的 options 多收一份 `presentation`，**必填**；原来写死的常量整组删掉 |
| `game/main.ts` | 取配置挪到造游戏对象**之前**；`startLoading` 的对外契约没动（仍同步返回取消句柄），只是内部改成异步续体，取消和报错的路子照旧 |
| 测试 | 删掉 5 条「配置里的值 == `game/` 里的常量」的断言（常量已经不存在，没得比），换成「**递一份改过的配置进去，行为跟着变**」——这才是接线真的生效的证据 |

**必填这条要单说**：和 1.3 同一个道理。留默认值意味着「不给配置也能跑」，而呈现层的默认值一旦生效，表现是**贴图切错、人一帧一帧地花**，比直接报错难查得多。改成必填，少给一项当场编译不过。

#### 1.6 补掉最后两个漏网的值 ✅

> 编号按「定的时间」排——两处是 1.5 做完当天发现的，所以紧跟其后。

1.5 复查时翻出**两个值既不算「有名字的常量」也不算「写死的裸数字」**，所以前几轮一次都没被圈进来，22 份表里哪一份都没有：

|---|---|---|
| `CROWD_TRACK_BAND` | `game/PhaserStaticCrowdRuntime.ts` | `route-crowd-presentation.json` 的 `trackBand` |
| 动画速度，两处字面量 `6` | `game/PhaserSprayerRuntime.ts` 的 `createAnimations()` | `sprayer-presentation.json` 里每张图的 `frameRate` |

**第一处不是搬位置，是合并。** 查下来的事实和原先文档记的**正好相反**：两份配置里都写着「源码里两处共用同一个常量」，但翻快照逐字核对后确认——**是两个适配器各写了一遍一模一样的常量**，不是共用一个。原话记反了，已改。

为什么必须合并而不是再抄一份：这两处值都是 400 / 1471 / 304 / 319，指的是**同一根火车轨道**。再抄一份就等于留了两个真相——换校园挪了铁轨，改配置只会改一半，**静态人群照样站在旧位置上**，而且不报错、只是"看着有点不对"。这跟 1.3 里「不删干净就有两份真相」是同一条道理。

所以**合成一处**：两份共读 `route-crowd-presentation.json` 的那个 `trackBand`。铁轨在哪儿是**世界事实**，不是某一类 NPC 的属性——两类人群本来就该同步。

**第二处**是「画面快慢」。两张图各有一份 `frameRate`，因为站着喷水和跑动是两套动画。顺带记一个容易看错的地方：**喷水器是 6，人物走路那套是 10**，不一样。这是原版就有的差别，不是笔误，照抄没动。

#### 1.7 补掉三处漏网的值，并修掉一个只有真机才看得见的启动故障 ✅

1.6 复查时列了**五处**疑似漏网值。逐条找证据之后，**只有三处是真的**，另两处是记错了。

**三处真漏网**：

| 值 | 原先写死在哪 | 现在住在哪 |
|---|---|---|
| 静态人群每人卡新建上限 `16` | `game/PhaserStaticCrowdRuntime.ts` 的 `created >= 16` | `static-crowd-presentation.json` 的 `maxCreatePerSync` |
| 静态 NPC 动画帧数 `16` | `game/PhaserStaticNpcRuntime.ts` 的 `Array.from({ length: 16 })` | `static-npc-presentation.json` 每张图的 `frameCount` |
| 虫子每方向几帧 `6` | `game/PhaserBugCrowdRuntime.ts` 的取模 | 不单独存：由 `frameCount ÷ 方向数`（24 ÷ 4）算出来 |

共同点：**这三处坏起来都不报错**。换一张帧数不同的图，人照样出现、虫子照样爬，只是动画播不全、看着不对。这类值最该挪进配置，因为出错时没有警报。

**两处不是漏网，是不该动**（上一轮的名单里记错了，这里更正）：

- **造反者「空闲 2~6 秒后做个小动作」的间隔**：`venue-crowd-presentation.json` 的说明里白纸黑字写着**刻意没抽**——那是算法里的抖动，改了只影响随机感，不改变外观和行为。抽它等于推翻一个已经定过的决定。
- **喷水器的叠放层次 `500` / `24`**：这不是 NPC 的配置点，是**整个世界的深度规范**，唯一出处是 `src/layer/depth.ts` 的 `playerDepth()`，`换皮配置总表` §3 已经把它登记成 SYS-LAYER 的配置点，并写明「别把 +24 删掉去迁就原站」。再抽一份进 SYS-NPC，就是给世界规范造第二份真相——和 1.6 里铁轨带那次是同一类错，只是方向相反（那次是把两个真相合成一个，这次是差点把一个拆成两个）。

**顺带修掉一个真机才暴露的启动故障。** 这一轮第一次把游戏放进浏览器跑，结果是**进不去**：画面停在错误提示「sprayer runtime failed: missing-idle-texture」，也就是喷水器的贴图一张都没加载。

查下来的根因不在喷水器的逻辑上，而在**它的取图地址是拼出来的**：源码写的是 `new URL(\`../${asset.sourceFile}\`, import.meta.url)`，路径由配置里的字符串拼成。打包器认不出这种动态路径，会把它替换成一张「项目根目录下有哪些文件」的查表——**那张表里只有 README、package.json 这些，没有贴图**，于是地址取到空值，实际请求发去了 `/game/undefined`，图片一次都没下，Phaser 登记不到贴图，整个动态世界起不来。

这条改动还顺手堵了一个泄漏口：那张查表把 `package.json`、`package-lock.json`、`tsconfig.json`、`AGENTS.md` 一起打进了发布产物（构建日志里能看到 `dist/assets/package-lock-*.json`）。改完之后这些都不再进包，应用包体从 295.43 kB 降到 290.06 kB。

修法是让喷水器和其它 NPC 贴图走同一条路：图放 `public/sprites/`（由 `scripts/prepare-runtime-assets.mjs` 从原站镜像拷），配置里记运行期地址 `url`，和其它六份呈现层表写法一致。字段 `sourceFile` 就此改名成 `url`。

**验收**（这次的浏览器验证做成了）：

- 编译干净；**522 条测试全过**（78 个文件；本轮新增 3 条，都是「按递进来的配置算、不是写死的」这类）。
- 打包通过。`npm run browser:smoke` 对**开发服务器**和**生产构建产物**各跑一次，两次都是 `passed: true`：画面进入可玩状态、画布 480×270、没有报错、没有请求失败，并且网络记录里确实看到两张 `/sprites/npc-sprayer*.webp` 被请求——改动前它们一张都没请求过。
- 配置类改动的既定验收也做了：**改 `maxCreatePerSync` 16 → 6、第一张静态 NPC 图 `frameCount` 16 → 8，不重新构建，只刷新页面**，页面读到的新值就是 6 和 8，且照样进入可玩状态。改完把产物重新构建了一遍，恢复成源文件的值。
- 这项验收已经自动化成常驻冒烟：`npm run browser:config-live-smoke`（`scripts/browser-config-live-smoke.mjs`）。内置 10 条用例，覆盖 SYS-NPC 六份配置的五条读取路径；每条都是「改值 → 只刷新页面（不重新构建）→ 在真浏览器里量出来 + 截图 → 逐字节还原」，哪条量不到变化就整体判失败。2026-09-21 的首次实测记录在 `bak/配置实测-2026-09-21/`。

**顺带改了一处工程配置**：`vite.config.ts` 原来没有测试收集范围，vitest 默认扫全项目，于是 `bak/` 里备份的 `tests/` 副本会被当成真测试跑起来、必然失败（这一轮踩了两次）。现在加了白名单 `include: ["tests/**/*.test.ts"]`，和 `tsconfig.json` 用 `include` 列白名单是同一个思路。

§14 字段数 74 → 77，全表 510 → 513。

**还留着的一处小尾巴**（没删，因为删资产要单独定）：`src/npc/assets/` 下那两张喷水器图现在没人用了，图已改从 `public/sprites/` 取，两份文件内容逐字节相同（sha256 一致）。
