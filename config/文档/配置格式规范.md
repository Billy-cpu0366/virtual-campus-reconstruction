# 配置格式规范

> 这份规范定「配置文件长什么样」。所有 `config/default/<板块>/<系统>/数据/` 下的文件都照它写。
> 它是**地基**：地基改了，上面全部要返工。所以有意见现在提。

---

## 一句话

**配置文件里的字段 = TS 类型里的字段，一一对一，不增不减。**

这条是根。定下它，后面全跟着简单了：加载器不需要任何换算逻辑（只做「读出来 + 校验」），校验也不用另写一套规则——拿 TS 类型比一次就行。反过来，只要文件里多一个字段或改一个名字，加载器就得挂一张映射表，而映射表本身就是新的 bug 来源。

---

## 一、目录怎么分

```
config/
├── 文档/
│   ├── 换皮配置总表.md      ← 从 doc/ 复制过来，在它上面细化
│   ├── 配置方案.md          ← 整体方案与规矩
│   └── 配置格式规范.md       ← 本文件
├── 工具/                    ← 测试用：从磁盘直接读（游戏里不用它）
├── 骨架/                    ← 所有校园共用，换皮不动
│   ├── 公共/                 ← 所有板块都要用的零件（读文件、校验、冻结）
│   ├── 01-地图线/{SYS-ASSET, SYS-WORLD, SYS-LAYER, SYS-CHUNK}/逻辑/
│   ├── 02-玩法线/{SYS-INPUT, SYS-MOVE, SYS-PLAYER, SYS-CAMERA}/逻辑/
│   ├── 03-内容线/{SYS-ZONE, SYS-INTERACT}/逻辑/
│   ├── 04-独立件/{SYS-APP, SYS-GAME-UI, SYS-ENTITY}/逻辑/
│   ├── 05-旁支/SYS-NPC/逻辑/    ← 目前只有 SYS-NPC 有内容
│   └── 06-网络协议层/
└── default/                 ← 一个校园一套：只有「数据」
    └── 05-旁支/SYS-NPC/数据/    ← 22 个 JSON
```

**一条规则管全部：**

> **跟板块无关的放「公共」。跟板块有关的，会随校园变的放「集 / 板块 / 系统 / 数据」，不变的放「骨架 / 板块 / 系统 / 逻辑」。**

- **跟板块无关的** = 读文件、校验、冻结。这些零件哪个系统都要用，做法一模一样。放「公共」，只此一份。要是每个系统各存一份，改一处忘一处，就是 16 个 bug。
- **跟板块有关的** = 值本身放「数据」，处理这些值的代码放「逻辑」。**值会随校园变**（换个学校，NPC 站位全不一样），**逻辑不会**（读文件的做法到哪儿都一样）。分开之后，换皮时只碰「数据」那一半。
- **每个校园一套「数据」** = `config/` 底下一个英文名目录就是一整套（`default/` 是默认那套），换校园 = 新加一个目录。共用的「公共 + 逻辑」住 `骨架/`，换校园时不动。哪些目录算「一套」、不写网址时读哪套，见 [配置方案](配置方案.md) §3.3。

板块名、系统名、编号**全部抄总表**——总表写 `# 五、旁支` `## 14. SYS-NPC`，这里就是 `05-旁支/SYS-NPC/`。两边编号对得上，翻的时候不用查表。

**空文件夹不建。** 做到哪个系统才建哪个。

## 二、文件怎么切、怎么命名

| 规矩 | 说明 |
|---|---|
| 一个系统一个文件夹 | `05-旁支/SYS-NPC/数据/`、将来 `02-玩法线/SYS-CAMERA/数据/`…… |
| 一个「配置集合」一个文件 | 对应源码里一个常量 |
| 文件名 = 常量名的 kebab-case | `STATIC_CROWD_REGIONS` → `static-crowd-regions.json` |
| 顶层固定两层 | `meta`（这文件从哪来、什么单位）+ `data`（真正的数据） |
| 代码里怎么指一个文件 | 用**「相对 `config/<集名>/` 的真实路径」**，如 `05-旁支/SYS-NPC/数据/dancing-crowd-config.json`。代码里管它叫 `key` |

> **为什么 key 用真实路径、不另造一套简写**：读法是会换的（打包 → fetch → 后台下发）。
> 只要是真实路径，任何读法都能直接拿它去取文件，中间不用加一层"翻译"。多一层翻译，就多一个两边对不上的地方。

顶层长这样：

```json
{
  "meta": {
    "system": "npc",
    "source": "src/npc/staticCrowd.ts",
    "sourceConstant": "STATIC_CROWD_REGIONS",
    "verified": "exact",
    "units": { "outline": "pixel" },
    "notes": ["outline 是像素；旁边那个字段偏偏叫 tileCount，照名字推必错。"]
  },
  "data": [ /* …… */ ]
}
```

`meta` 不是装饰。它干三件事：**说清这文件是从哪儿抽出来的**（将来对不上时能回去查原始代码）、**说清每个字段的单位**（见第四节）、**说清这份文件的值可不可信**（见第七节）。

四个字段都是必填的（`units` 和 `notes` 可省），加载器会检查——缺了直接报错，不放行。

## 三、字段怎么命名

**camelCase，和 TS 类型的字段名逐字一致。**

`speedVariation` 就写 `speedVariation`，不写 `speed_variation`，也不写 `speedVariationRatio`。

理由还是第一条：改了名，加载器就得挂映射表。

枚举值同理——**逐字一致**。`"crowd_up"` 不许写成 `"crowdUp"` 或 `"crowd-up"`。

---

## 四、单位（这条最容易错，也最值钱）

**规矩：每个数值字段的单位，必须能从字段名或 `meta.units` 看出来。不许靠猜。**

为什么这条要单列——因为我实测了现有数据，**同名概念在不同系统里单位不同**：

| 系统 | 字段 | 实际单位 | 怎么确认的 |
|---|---|---|---|
| staticCrowd | `outline` | **像素** | 坐标最大 2216，且 855 个点不是 16 的倍数；`STATIC_CROWD_FACTOR = 0.004 ≈ 1/256`，正好「每格约 1 人」 |
| venueCrowd | `outline` | **像素** | 同一批原始数据，坐标 1672–2168 |
| routeCrowd | `startTiles` / `endTiles` | **格** | 值是 `[31, 81]` 这种小数 |
| bugCrowd | `startTiles` / `endTiles` | **格** | 换算写在代码里：`world(p) => p.x * 16 + 8` |
| staticNpc | `tileX` / `tileY` | **格** | 字段名 |
| sprayer | `tileX` / `tileY`、`escapeRoute` | **格** | 字段名 |
| dancingCrowd | `minTileX` / `maxTileY` 等 | **格** | 字段名 |

`staticCrowd` 就是那个坑：`outline` 是像素，但紧挨着的字段偏偏叫 `tileCount`。**照名字推，必错。**

所以**每个有单位的字段都必须在 `meta.units` 里写明**，单位取值只能是这八个词之一：

| 单位 | 含义 | 取值范围 |
|---|---|---|
| `tile` | 格 | 0–140（世界 140×140 格） |
| `pixel` | 世界像素 | 0–2240（140 × 16） |
| `ms` | 毫秒 | ≥ 0 |
| `pxPerSec` | 像素/秒 | ≥ 0 |
| `ratio` | 乘数/比例 | 无限制 |
| `count` | 个数 | ≥ 0 |
| `perFrame` | 每帧多少 | ≥ 0 |
| `text` | 文本（贴图 key 之类） | — |

**为什么必须是枚举、不能写「世界像素（不是格）」这种人话**：人话机器读不了，也就没法拿它当校验依据。人话写在 `meta.notes` 里——两个地方各司其职。

范围那一列是加载器真去比的：把像素坐标写进格字段，会得到一个 1784 格（地图外 12 倍远）的坐标。这种错在游戏里表现为「几个人不见了」，不查半天查不出来。校验器会当场拦下，还会在报错里点出「是不是把像素坐标写进了格字段」。

### 命名约定（是约定，不是硬规矩）

- **格**单位的字段，名字里带 `tile` / `Tiles`。
- **像素**单位的字段，名字里最好不带 `tile`。

**但这只是约定，`meta.units` 才是权威。** 定这条时我以为它能当硬规矩，直到试点撞上两处真实的例外：

| 字段 | 单位 | 名字 | 情况 |
|---|---|---|---|
| `sprayer.escapeRoute` | **格** | 不带 `tile` | 真实例外，按约定办就得改字段名，那违反第一节（名字要和类型逐字一致） |
| `path.tileSize` | **像素** | 带 `tile` | **最危险的一种**——它是「一格多少像素」这个换算基准本身，不是坐标 |

所以导出脚本在这两种情况下**只警告、不报错**。看到警告要人工确认一次，确认结果写进 `notes`。

## 五、坐标怎么写

**用 `{"x": 31, "y": 81}` 对象，不用 `[31, 81]` 数组。**

数组靠顺序，改配置的人把两个数写反一次，就是一个不报错的错位；对象自解释，后台表单也天然对应两个输入框。

> 注意：源码里 `routeCrowd` 写的 `[[31, 81]]` 是**位置参数助手**的写法，进 JSON 时必须摊成对象。同理 `bugCrowd` 的 `[[5,128]]`。

---

## 六、区间怎么写

**用 `{"min": …, "max": …}` 对象，不用 `[min, max]` 数组。** 理由同上。

现有两种区间，字段名不一样，别混：

| 长什么样 | 例子 | 出现在 |
|---|---|---|
| 乘数区间 `{min, max}` | `{"min": 0.75, "max": 1.25}` | `speedVariation` |
| 毫秒区间 `{minMs, maxMs}` | `{"minMs": 2000, "maxMs": 4000}` | `delay`、`afterDelay`、`wanderInterval` |

**存派生之后的值，不存派生之前的值。**

举例：源码 `routeCrowd` 的 `group(...)` 助手收的是 `variation = .25`，然后在函数体里派生出 `speedVariation = {min: 1-.25, max: 1+.25}`。

- ❌ 文件里存 `"variation": 0.25` —— 那加载器就得懂这个换算，多一份逻辑。
- ✅ 文件里存 `"speedVariation": {"min": 0.75, "max": 1.25}` —— 加载器照读，零逻辑；而且这和 TS 类型里写的字段一模一样（第一条规矩）。

「±25%」这种更符合人直觉的说法，是**后台表单**该干的事（表单可以显示成「速度浮动 ±25%」，存下来还是 min/max）。文件本身保持和类型一致。

## 七、可选字段、默认值，以及「这份文件可不可信」

### 7.1 可选字段和默认值

**TS 里可选（`?`）或助手函数带默认值的参数，在 JSON 里必须显式写全，不留空。**

理由：默认值住在代码里，等于这个值改不了、后台也看不见它。写进文件才有唯一出处。

实测 `routeCrowd.group()` 的三个默认值（不写就用这些）：

| 参数 | 默认值 |
|---|---|
| `pathRandomFactor` | `0.8` |
| `ignoreWalls` | `false` |
| `completionExit` | `false` |

那**真的没有值**的字段怎么办（比如「不限人数」）？JSON 没有 `undefined`，用 `null`，加载器负责还原成 `undefined`。
现有例子：`routeCrowd.maxActiveInViewport` —— `null` 表示不限。

### 7.2 `meta.verified`：说清这份文件可不可信

| 取值 | 含义 |
|---|---|
| `exact` | 每个值都是从源码的导出直接取的，测试能逐字段比对 |
| `mixed` | 一部分能比对，一部分在源码里没导出、是**手抄**的 |
| `manual` | 全部是手抄的，比对不了 |

**为什么要标**：手抄的值和抽出来的值**长得一模一样**。不标，就会以为「这份已经抽干净了」；标了，才知道哪儿还有活没干完。

判定方式很客观：源码里那个常量有没有 `export`。有 → `exact`；没有，就只能看着源码手打，标 `mixed`/`manual`。

`tests/config` 里有一条测试把这个边界钉死了——`exact` 的正好是哪些、`mixed`/`manual` 的正好是哪些，多一个少一个都失败。这样它就不可能悄悄变多。

### 7.3 接线之后，`source` / `sourceConstant` / `verified` 是在记「当初」

配置接上运行时读取之后，源码里那份常量就被删了——留着它就有两份真相。这时 `meta` 里这三个字段的含义要按下面理解：

| 字段 | 接线之前 | 接线之后 |
|---|---|---|
| `source` | 这份值现在还在那个文件里 | **当初是从这个文件抽出来的** |
| `sourceConstant` | 那个常量的名字 | 常量没了，改记**它对应哪个字段定义**（如 `StaticCrowdRuntimeTuning（八个字段）`） |
| `verified` | 现在能不能跟源码逐字段比对 | **当初是怎么取的**：导出的直接取，还是照着源码手抄 |

**为什么要改成这个读法**：接线之后，「跟源码比对」这件事在物理上已经不可能了——比对的另一边不存在了。但这段来历不能丢，将来发现某个值和原站对不上，还得靠它回去查原始代码。

**所以这三个字段定下来就不再改**，哪怕后来发现当初标 `manual` 的那个值其实抄对了。它记的是过程，不是判决。

## 八、什么该抽，什么不该抽

判据只一条：

> **将来后台要不要让人改它？** 要 → 抽。不要 → 别动。

这比「它是不是数据」准。因为有些数据永远不改（比如 tile 是 16×16 像素，这是引擎底层，抽出来只是让后台多一个不该给人碰的输入框）。

按这条，NPC 的东西分五类——上面三类抽，下面两类不抽：

| 类型 | 例子 | 怎么办 |
|---|---|---|
| **数值** | 站在哪个格子、几个人、走多快、缩放多少、区域多边形 | **抽成配置** |
| **图片的规格** | 一张雪碧图每帧切多大、一共几帧、锚点对齐到哪、四个方向的帧怎么排 | **抽成配置**——新校园美术给的排布多半不一样，不给人改的地方就得回来改代码 |
| **用到哪几张图** | 静态人群从哪十几张里随机挑、哪一组专用哪几张 | **抽成配置**——这是「每校园」的选择 |
| **图片文件本身** | `npc-special-reading.webp` 这个文件，以及它放在哪个目录 | **不当配置**，归[总表 §1 SYS-ASSET 的资源清单](换皮配置总表.md#1-sys-asset-资源加载)——换校园是把文件换掉，配置里写不写这个名字都改变不了图片 |
| **逻辑** | 寻路是 8 方向、每帧算 64 次 | 文档记一笔，**先不抽**——要么固定，要么将来做成一个开关 |

**最容易划错的是「图片的规格」那条。** 它的道理和「数值」是同一条：后台要不要让人改它？要——美术换一张 48×48、20 帧的图，配置里还写着 64，游戏就按 64 去切，人会出现但一帧一帧地花。所以要抽。

反过来，「用哪张图」确实不该做成配置：换校园就是拿新图片盖住旧文件名，配置项写不写都一样。**这两件事常被合成一句「素材不当配置」，那是划粗了**——前者的值真会随校园变，后者不会。

> 按这条，几张呈现层表里现在带着的图片路径（`static-npc-presentation.json` 的 `url`、`sprayer-presentation.json` 的 `url`）**将来要归 §1 的资源清单**。眼下先留在原地，因为那份清单还没做——留在这儿只是暂时的落脚点，不是破例。

### 一个推论：只有一个取值的枚举，不是配置

试点时撞见的：`bugCrowd.mode` 声明成 `"wander"`，而 `BugCrowdMode` 这个类型的合法取值**只有 `"wander"` 一个**。

一个「只能填一个值」的输入框，不是配置项，是类型。它该从配置里拿掉，留在类型里。

反过来看也成立：**如果一个字段有且只有一个合法值，那它就不可能被「配置」出任何变化**。判据还是那一条——后台要不要让人改它？只有一个选项的下拉框没有存在意义。

## 九、数值和注释

- 源码里的千分位下划线（`2_000`）**在 JSON 里不合法**，写 `2000`。
- JSON 不许有注释。需要解释的，写进 `meta`，或写进文档。

---

## 十、和 `src/` 的关系

**`src/` 原样不动，走复制派生。**

配置文件是 `src/` 里那份数据的**副本**。抽取期间两边并存、互为对照。等加载方式切成运行时读取（那是第 1 步的第二小步）之后，`src/` 里的那份数据删掉，只留类型定义。

之所以不移走：`src/` 一旦被搬空立刻编译不过（`index.ts` 和 `game/` 里 7 个适配器都引着它），而且复刻对照就没了基准。

### 样板 B —— 位置参数摊成具名字段（`routeCrowd` 第一条）

源码（`src/npc/routeCrowd.ts:166`）：

```ts
group("main-crowd", 10, [[31, 81], [32, 81], [33, 81]], [[73, 133]],
```

注意这里三个坑，全在样板里体现：

3. 这次调用只传了 12 个参数，后三个用默认值——按第七节，得显式补上。

```json
  },
```

### 样板 C —— 「调参」是一种新的配置形态（`sprayer` 的调参）

样板 A 和 B 都是**把源码里已有的一个对象搬过来**。调参不一样：源码里根本没有这个对象。

`src/npc/sprayer.ts` 顶部是四个各自独立的常量：

```ts
export const SPRAYER_TILE_SIZE = 16;
export const SPRAYER_FLEE_SPEED = 140;
export const SPRAYER_GROUP_DELAY = 300;
export const SPRAYER_SPRAY_DELAY_MAX = 3_000;
```

而「玩家进到多近触发喷水」写死在函数体里（`sprayer.ts:244-257` 的 `isInsideTrigger()`，竖直 `0..2`、水平 `±2`）。

这里第一次给它们**组织成一个对象**——因为后台就是这样工作的：一个「喷水器」面板，上面几个框。散着的常量做不出面板。

→ `数据/npc/sprayer-tuning.json`：

```json
{
  "meta": {
    "system": "npc",
    "source": "src/npc/sprayer.ts",
    "sourceConstant": "SPRAYER_FLEE_SPEED / SPRAYER_GROUP_DELAY / SPRAYER_SPRAY_DELAY_MAX",
    "verified": "mixed",
    "units": {
      "fleeSpeed": "pxPerSec",
      "groupDelay": "ms",
      "sprayDelayMax": "ms",
      "triggerVerticalMaxTiles": "tile",
      "triggerHorizontalTiles": "tile"
    },
    "notes": [
      "triggerVerticalMaxTiles / triggerHorizontalTiles 在源码里写死在 isInsideTrigger() 函数体里，不是模块常量。要让它可改，得先改函数签名。"
    ]
  },
  "data": {
    "fleeSpeed": 140,
    "groupDelay": 300,
    "sprayDelayMax": 3000,
    "triggerVerticalMaxTiles": 2,
    "triggerHorizontalTiles": 2
  }
}
```

注意三处：

1. `verified` 是 **`mixed`** ——前三个值在源码里是 `export` 的，能比对；后两个是**看着函数体手抄的**。同一份文件里两种可信度，所以标 `mixed`。
2. `SPRAYER_TILE_SIZE` **没进这个文件**。按第八节那条判据——它是「一格多少像素」的换算基准，后台不该让人改。
3. `sprayDelayMax` 源码写的是 `3_000`，JSON 里是 `3000`（第九节）。

## 十二、试点定下来的两件事

写规范时留了两个待定，现在试点跑完了，按下面的定（都是可改的，但如果要改，越早越省事）：

### 1. 「不限」写 `null`，加载器还原成 `undefined`

`routeCrowd.maxActiveInViewport` 在源码里是 `number | undefined`，11 组里有 3 组传的是 `undefined`（不限）。
JSON 没有 `undefined`，写 `null`。加载器负责还原——所以读出来的对象和源码那份**类型完全一致**。

### 2. 点很多的多边形，仍然用 `{x, y}` 对象，不破例

代价是真的：`static-crowd-regions.json` 因此有 **3765 行**，而 `venue-crowd-regions.json` 只有 4 个区域也要 663 行。

不破例的理由：一旦允许「点多的用数组、点少的用对象」，就会出现**同一份数据里两种写法**，然后每个读它的人都要先判断是哪一种。省下的是文件的体积，付出的是每次读都要多担的心。

文件大不是问题——它不给人肉眼读，是给程序读的，而且 gzip 之后很小（实测打出来 56 kB）。**规矩统一比文件短更要紧。**
