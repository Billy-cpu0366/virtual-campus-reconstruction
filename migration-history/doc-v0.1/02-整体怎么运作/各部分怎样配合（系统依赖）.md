# 各部分怎样配合（系统依赖）

> **一句话：这份文件说明各功能之间谁依赖谁，避免修改一处时误伤另一处。**

本文严格区分原站事实、机制推断和我们的重构决定。

## 1. 原站已确认结构（FACT）

- 页面公开发布文件包含 Angular 应用 Bundle。
- 虚拟世界使用公开的 Phaser 脚本和 gameplay 动态 Chunk。
- 运行时会请求地图主索引、25个地图分块和多种精灵资源。
- 地图存在碰撞、脚步、粒子轨迹和 tileset 等数据。

## 2. 原站机制推断（INFERRED）

```text
网页应用
→ 启动并装配游戏
→ 游戏资源加载
→ 创建世界和地图
→ 创建玩家及其他实体
→ 输入驱动移动
→ 碰撞约束位置
→ 相机和区域逻辑响应位置变化
```

具体类结构、模块边界和事件机制尚不能从公开 Bundle 完全确认。

## 3. 当前候选依赖关系（INFERRED）

```text
游戏生命周期
├─ 依赖资源加载
└─ 组合世界、玩家、输入、相机和UI

世界与地图
├─ 依赖资源加载
├─ 包含分块与图层
└─ 为碰撞、实体和相机提供世界信息

玩家
├─ 消费输入动作
├─ 使用移动与碰撞规则
└─ 被相机跟随
```

## 4. 重构设计原则（DECISION，待确认）

- 输入只产生动作，不直接修改玩家内部状态。
- 相机观察目标，不拥有玩家状态。
- 地图、图层和碰撞边界不写入玩家控制器。
- 可复用能力先留在所属系统，出现真实复用后再独立抽取。
- 正式源码结构由确认后的系统边界推导，不直接照搬 Bundle 或旧复刻目录。

## 5. 未知问题（UNKNOWN）

- 地图分块在玩家阶段的具体装卸时序、失败边界和性能指标；
- 图层深度和遮挡的完整规则；
- 页面与游戏状态之间的通信方式；
- NPC、车辆和区域触发的运行状态机；
- 原站是否存在统一事件总线或统一实体生命周期。

地图分块动态装卸机制已由 `Q-MAP-001` 关闭并写入 [[先做什么（P0系统对照与顺序）]]；这里只保留尚未解决的更窄问题。
