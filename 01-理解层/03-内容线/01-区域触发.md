# 区域触发（SYS-ZONE）—— "博物馆的动作感应器"

> 📌 进度：📐 设计已定稿 + 确定性 CORE 已实现 —— 11 个 marker、`<30px`、100ms 轮询和 `menuId` 桥接已查清，`ZoneRuntime` 纯逻辑已通过 5 项自动化测试（2026-09-02）

---

## 一句话讲清楚

**区域触发系统 = 散落在地图各处的"动作感应器"，玩家走近就自动亮灯。**

你去博物馆看展览，走到某件展品前面，感应器发现你靠近了，展品旁边的灯就亮了。你走开了，灯就灭了。区域触发系统做的就是这件事——它不是一堵墙让你撞上去，而是一个"看不见的圆圈"，跨过去就自动触发一件事（比如弹出介绍卡片）。

这个圆圈很小——半径只有 30 像素（大约一个玩家的脚那么大）。而且感应器不是一直全开——它每 100 毫秒（0.1 秒）扫一眼你还在不在附近，省电又高效。

---

## 它管哪些事

| 管的事 | 大白话 | 不管的事 |
|---|---|---|
| 检测玩家是否进入 marker 的 30px 范围 | "你靠近了" | 不负责显示内容——那是弹窗的事 |
| 进入时发出"打开内容"信号 | "该弹窗了，内容编号是 memo3" | 不负责弹窗长什么样 |
| 离开时发出"关闭内容"信号 | "你走远了，收起来吧" | 不负责 DOM 或文案 |
| 防止手动关闭后重复弹窗 | "你已经关掉了，我不烦你" | 不限制 visited 统计——那只是计数 |
| 视口外 marker 不浪费算力 | "屏幕外的感应器先不检查" | 不参与渲染——那是图层/分块的事 |
| 记录谁 visited 过 | "这个点你踩过了" | 不决定能否再踩——那是抑制状态的事 |

## 🎨 核心：皮与骨架拆分

> **骨架** = 换什么校园都不变的做事方式
> **皮**   = 跟 Peter 这个具体项目绑定的内容
> **配置点** = 将来后端管理系统可以改的参数

---

### 一、骨架（换什么校园都不变的东西）

#### 骨架 1：固定半径的"感应圈"

**大白话**：每个 marker 核心有一个半径 30px 的"感应圈"。玩家的脚踩进这个圈，就触发；踩在线外就不触发。

不管什么校园、什么内容，判定"近了还是没近"的方式都是圆心距离计算，这是通用的。

**为什么是骨架**：距离计算公式 `√((x₁-x₂)² + (y₁-y₂)²) < 半径` 是数学定理，换什么校园都长这样。

**实现形态**：`ZoneRuntime.isInside()` 方法做欧几里得距离比较，严格 `< interactionDistance`（默认 30），等于不算。

#### 骨架 2：定期巡检（不每一帧都查）

**大白话**：系统不是每时每刻盯着所有 marker 看——那样太费电。而是每 100 毫秒"掀开眼皮看一眼"。

就像大楼保安不是一直站在每个门口盯着，而是每隔几分钟巡逻一圈。100 毫秒巡检一次，既不会漏掉"你靠近了"，又不会让电脑风扇狂转。

**为什么是骨架**：定时轮询是处理"离散位置更新"的标准模式，跟具体校园无关。

**实现形态**：`update()` 方法把连续的位置更新"攒起来"，通过注入的 `scheduler.setTimeout(callback, 100)` 合并成一次巡检。如果 multiple 调用在 100ms 内，只触发一次定时器。

#### 骨架 3：视口裁剪（只看眼前）

**大白话**：系统不会检查地图上所有 marker——只看屏幕范围内（外加 100px 边距）的那些。

你在校园东边散步，西边的 marker 就先不查了。等你走过去，那个 marker 进入"视野范围"，系统才开始关注它。已经激活的 marker（你正站在里面）不受视口限制——哪怕你把屏幕滚走了，系统也知道你在里面。

**为什么是骨架**：视口裁剪是所有"大世界 + 散落交互点"场景的标准优化手段。

**实现形态**：`candidates()` 方法用视口 `±viewportPadding`（默认 100px）筛选 marker，但已激活的 residence 的 marker 不受筛选影响（防止漏掉 leave 判定）。

#### 骨架 4：进出状态机（含"别烦我"抑制）

**大白话**：每个 marker 在你的一次"停留"中，有三个关键状态：

```
你靠近了 → "enter"（弹窗）
    │
    ├─ 你手动关了弹窗 → "抑制状态"（不重弹）
    │     │
    │     └─ 你走远了 → "leave" → 抑制解除
    │
    └─ 你走远了（没手动关）→ "leave"（收弹窗）
```

手动关闭和自动离开是两回事——手动关闭后只要还没离开，就不能重新弹窗；但一旦离开再回来，又可以从头开始。

**为什么是骨架**：任何"走近触发 + 手动关闭 + 离开重置"的交互模式都需要这套逻辑。

**实现形态**：`residences` Map 记录当前所有"正在里面"的 marker；`suppressedResidences` Set（在 InteractRuntime 中）记录手动关闭但不让你走的；leave 时从 residences 删除、清除 suppressed。

#### 骨架 5：内容标识桥接

**大白话**：区域触发系统不知道弹窗里面显示什么——它只负责喊一句："弹 mome3 的内容！"

就像餐厅的服务员只负责告诉厨房"3 号桌点了一份牛排"，不负责做牛排。区域触发系统把 `menuId`（内容编号）传出去，弹窗系统自己去对应内容表里找到标题、正文、图片。

**为什么是骨架**：触发和展示解耦是通用设计——换校园不用改触发逻辑，换内容不用改 marker 坐标。

**实现形态**：`ZoneResidenceEvent` 携带 `{ markerId, menuId, residenceId, phase }`，通过 `onResidence` 回调传给 SYS-INTERACT。

## 跟谁接口（它和谁打交道）

```
                      ┌──→ [SYS-INTERACT 弹窗]
  [SYS-ZONE] ────────┤    给：{ markerId, menuId, residenceId, phase }
  区域触发             │    说："该弹 mome3 了" / "该收了"
                      │
  [SYS-ZONE] ←─────── [玩家位置]（来自 SYS-PLAYER 或游戏循环）
               ←─────── [相机视口]（来自 SYS-CAMERA，用于视口裁剪）
               ←─────── [marker 配置]（来自内容层/构建时注入）
```

**一句话**：SYS-ZONE 是"看门的"——它只判断"近不近"和"该不该弹"，不碰弹窗、不碰内容、不碰 DOM。它把结果打包成事件扔给 SYS-INTERACT，自己的活就干完了。

## 容易踩的坑

| 坑 | 为什么坑 |
|---|---|
| 把 marker 当成"碰撞体" | marker 是圆心+半径的距离判定，不是墙、不是矩形碰撞体。如果把它当碰撞体做，检测精度完全不对——玩家贴着 30px 边缘走可能不触发 |
| 离开后忘了重置抑制状态 | 手动关闭后 entry="suppressed"，但玩家离开区域时必须把 suppressed 清掉。忘了清 → 下次再来这个 marker 永远不弹窗 |
| 用 visited 阻止再触发 | visited 只是统计"踩过几次"，不参与"能不能弹"的判断。用 visited 来阻止再弹窗 → 每张卡片只能看一次，离开再回来就不弹了——这不是原站行为 |
| 把视口外扩当触发半径 | 视口外扩 100px 是"哪些 marker 值得检查"的优化范围，不是"多远触发"。触发永远是严格 30px |
| 相等距离的边界判定 | `distance < 30` 触发，`distance >= 30` 不触发。如果写成 `<=`，边界上多 1px 可能多弹一次——差之毫厘 |
| marker 来源弄错 | marker 不在 Tiled 地图 JSON 里，公开地图文件没有 objects/marker 层。它们硬编码在 Bundle JS 的 `markers` 数组中。去地图 JSON 里找 marker → 找不到 |
| pointerdown 误实现 | 原站 marker 的 `pointerdown` handler 是空的——不能通过点击 marker 触发弹窗。如果实现了点击触发 → 多了原站没有的行为 |
