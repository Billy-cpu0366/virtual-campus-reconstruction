# 实体生命周期（SYS-ENTITY）

> 📌 进度：📐 已设计＋no-code已核验 —— 当前不建统一Entity框架；`8ae7692b`无Entity抽象，Q-ENTITY-001继续open

## 它是什么

检查玩家、NPC、车辆分别由谁创建、更新和销毁，防止资源泄漏；它现在是一套跨系统审计边界，不是公共基类或实体管理器。

## 它管哪些事

- 要求每种真实对象写清创建者、所有者、更新者和销毁者
- 检查 Sprite/body/timer/tween/listener/route 引用是否清理
- 检查创建失败、晚到回调和重复 destroy
- 观察多个真实实现是否真的出现稳定重复

## 走一遍

未来先分别实现一个真实 NPC 和一辆真实车辆 → 各自在自己的系统里完成生命周期验证 → 如果两个独立实现确实共享同一清理合同，再讨论是否提取最小公共能力。

## 为什么这么设计

调查发现玩家、crowd NPC、车辆虽然都有“生到死”，但拥有者、route、physics 和可见资源差异很大。现在强行统一会把未知机制耦合在一起，反而更容易泄漏。

## 跟谁接口

当前没有公共 `EntityLifecycle` API。

- 玩家生命周期继续归 SYS-PLAYER
- NPC/crowd 归 SYS-NPC
- 车辆和路线归 SYS-ROUTE
- Scene 只发 shutdown scope，各系统清自己创建的资源

> 当前不在 API 契约表生成实体接口。

## 容易踩的坑

- CrowdManager 的车辆协作表不是全体实体 registry
- `cars` 地图层存在，不等于 chunk unload 会销毁车辆
- 文档审计清单不是 TypeScript schema 或运行时对象
- 没有两个已验证消费者前，不创建 `src/entity/**`

## 我要学什么

“**先证明重复，再抽象**”：生命周期责任必须严格，但统一框架只能来自多个真实实现，而不是来自未来设想。
