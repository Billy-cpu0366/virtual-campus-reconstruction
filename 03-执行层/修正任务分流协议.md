# 修正任务分流协议（AI机器合同）

> 本文件是“Human提出不满意、修改或Bug”时的唯一稳定分流权威。AI先分类，再选择流程；不得把三条流程混用，也不得为每个表面现象重复建立调查任务。动态分类与阶段只写根`task_plan.md`。

## 1. 适用与优先级

适用于Human提出的视觉不满意、行为错误、性能问题、内容修正和验收失败。安全、真实数据、破坏性操作、远端交付及项目其他Human Gate仍优先，不能被本协议降级。

每次修正任务开始或出现改变范围的新证据时，AI必须按以下优先级分类：

```text
systemic-failure > defect > adjustment
```

已有当前分类时不要每轮重开流程；只有触发升级/纠正条件才更新。

## 2. task_plan机器字段

`task_plan.md` frontmatter必须始终包含：

```yaml
issue-class: not-applicable | adjustment | defect | systemic-failure
active-route: standard-workflow | adjustment-flow | defect-flow | systemic-flow
correction-phase: none | <对应流程允许阶段>
classification-trigger: <短横线连接的触发依据>
classification-ref: none | DEC-AI-CORRECTION-ROUTING-001
```

固定对应关系：

| issue-class | active-route | correction-phase允许值 |
|---|---|---|
| `not-applicable` | `standard-workflow` | `none` |
| `adjustment` | `adjustment-flow` | `classify`、`desired-outcome`、`impact-check`、`implement`、`targeted-verify`、`completed` |
| `defect` | `defect-flow` | `classify`、`reproduce`、`diagnose`、`failing-proof`、`implement`、`regression-verify`、`completed` |
| `systemic-failure` | `systemic-flow` | `freeze`、`frozen-awaiting-wip-sync`、`audit`、`cluster`、`human-plan-gate`、`batch-implement`、`full-regression`、`human-acceptance`、`completed` |

修正类不能在`current-work-item: none`时进入实现阶段。`classification-trigger`必须能回指当前消息、失败收据、截图、测试或任务卡；不得写“AI认为”。

## 3. 分类判定

### 3.1 adjustment（普通调整）

同时满足：

- 没有违反原站FACT、已接受DECISION、冻结契约或明确验收标准；
- Human是在选择新的偏好、表现或优化目标；
- 影响范围可界定。

例：按钮想更大、动画想更慢、构图偏好改变。若Human只是说“不满意”而预期不清，先确认目标，不得擅自改成Bug。

### 3.2 defect（单一Bug）

同时满足：

- 已有明确expected source（FACT、accepted DECISION、冻结契约或验收标准）；
- actual与expected不一致；
- 能形成有界复现证据；
- 初步范围可收敛到一个问题链，不存在“还不知道缺多少”的迹象。

例：火车按已接受路线应移动但未移动；Retry后残留旧collider。

### 3.3 systemic-failure（系统性问题）

满足任一强触发，或多个弱信号共同出现：

**强触发：**

- 自动门禁通过，但Human对整体体验或完整性Gate判定失败；
- AI声称完整/可见/已形成纵切片后，Human连续指出多个相关遗漏；
- 同类修复连续两轮仍无进展或不断暴露同根新问题；
- 当前无法界定遗漏总量，`scope-confidence=unknown`。

**弱信号：**

- 多个系统同时表现异常；
- 多个表面问题可能来自同一启动、相机、图层、生命周期或性能根因；
- 单点测试收据与真实用户路径不一致；
- 修复一个点可能影响整条验收路径。

系统性判定不是“文件多”或“任务大”；核心是范围未知、证据冲突或零散修补已不可靠。

## 4. 三条执行路线

### 4.1 adjustment-flow

```text
desired-outcome → impact-check → implement → targeted-verify → completed
```

必需输出：Human目标、允许文件/影响范围、实际结果。低风险且目标明确时不增加方案Gate；主观视觉结果才请Human验收。不得强行写根因分析或失败测试。

### 4.2 defect-flow

```text
reproduce → diagnose → failing-proof → implement
→ regression-verify → completed
```

必需规则：

1. 先用最小复现、失败测试、截图、日志或行为收据证明Bug；不能复现就停止修改并报告缺什么。
2. 区分表面症状与根因；修复应保持最小，不夹带无关重构。
3. 用同一复现证明修改前失败、修改后通过；再跑受影响区域的回归。
4. 主观视觉Bug补同路径前后截图/录像；对象计数不能代替可见结果。
5. 低/中风险有界修复不为每步请求Human；产品取舍、高风险和最终主观效果仍走Human Gate。

### 4.3 systemic-flow

```text
freeze → audit → cluster → human-plan-gate → batch-implement
→ full-regression → human-acceptance → completed
```

必需规则：

1. 立即停止零散补丁、关闭和“自动PASS即完成”的口径；保留当前失败candidate。
2. 一次性审计完整Human路径，建立统一差异表；AI主动找全，不让Human逐项补漏。
3. 每条差异登记expected source、actual evidence、严重度、根因候选和UNKNOWN。
4. 按共同根因形成少数修复包；表面现象只作为清单行，不各自建立调查工作项。
5. Human只审一次整体修复范围、取舍、代价和主要风险；接受后AI连续实施有界修复包。
6. 每包完成后重放完整固定路径，不只验证被改点；所有严重/主要差异清零后进入Human整体验收。
7. Human未通过则回到同一差异表和根因包，不重新建立第二套流程。

## 5. 升级、纠正与降级

`adjustment`或`defect`在执行中出现任一强触发，必须停止当前实现并升级为`systemic-failure`。升级报告固定包含：

```yaml
previous-class:
new-class: systemic-failure
trigger:
evidence:
work-stopped-at:
next-required-step: audit
```

若原分类错误但范围仍有界，可在写代码前在`adjustment`与`defect`之间纠正，并说明expected source。系统性审计完成后，根因修复包可以按有界实现执行，但父工作项仍保持`systemic-flow`直到完整回归和Human Gate通过；不得通过拆子任务提前降级父状态。

## 6. 任务粒度

- 普通调整：通常不建独立WI；直接在当前授权范围内记录目标和验证。
- 单一Bug：一个可复现问题链对应一个有界工作项；内部诊断步骤不另建WI。
- 系统性问题：一个父工作项、一张差异表、少数根因修复包；不按页面、建筑、NPC或每条症状重复调查。
- 新发现先进入当前差异表；只有根因、owner、允许文件和客观停止条件独立时才拆执行包。

## 7. AI每轮必须报告

开始修正时先给短报告：

```yaml
classification:
reason:
evidence-known:
scope-confidence:
active-route:
current-phase:
next-action:
stop-condition:
```

完成汇报必须区分：已讨论、已接受、已落盘、已验证、Human是否通过、尚未解决。不得展示内部思考过程。

## 8. 当前项目的首次应用

P5 candidate `0fadf309`分类为`systemic-failure`，依据：自动门禁全绿但Human视觉Gate失败；Human连续指出Loading、卡顿、chunk reveal、火车、NPC、factory roof和细节FX；遗漏总量尚未收敛。当前父流程在冻结WIP快照交付期间为`frozen-awaiting-wip-sync`，之后进入一次完整视觉差异`audit`，不得退回逐点调查。

## 9. 验证与防漂移

- `scripts/check-state-consistency.py`校验frontmatter枚举、分类→路线→阶段固定映射、修正类工作项边界和决定引用。
- 状态变化后必须运行普通检查；脚本自测使用`python scripts/check-state-consistency.py --self-test`。
- 本协议变化必须重新取得Human接受并登记新DECISION；工作项不得自行改写分类规则。

## 10. 参考依据

本协议是项目DECISION，不把外部文章冒充项目事实。方法参考：

- GitHub Copilot CLI：复杂任务采用explore→plan→implement→verify，quick bug fixes不强制重流程；
- OpenAI Codex：明确Goal/Context/Constraints/Done，修复后运行测试并review；
- Anthropic Claude Code：追踪根因、实施修复、运行测试；
- Playwright视觉对比与Chrome Long Animation Frames：固定环境的前后证据及真实长帧归因；
- ISTQB defect clustering：缺陷常聚集在少数组件，测试资源应围绕高风险根因集中。
