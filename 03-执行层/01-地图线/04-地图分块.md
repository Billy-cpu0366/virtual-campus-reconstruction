# 地图分块（SYS-CHUNK）

> 一句话：玩家和相机现在走到哪里，哪些地图块必须显示、哪些可以从场景中移除；出错时怎么办。

## 👀 先看这里（人话总结，给 Human）

下面全是给 AI 看的精确结论（FACT / UNKNOWN 那套术语）。你**不用啃术语**，看这段人话就够审了。

**这卡在说啥**：玩家/镜头走到哪，就加载哪几块地图；走远的块就撤掉——"按需加载"。

**我查清的 4 件原站事实**（你审的就认这 4 条）：
1. **该加载哪几块**：玩家周围 3×3 块，加上镜头能看到的地方再多一圈（+1 块），两者合并。
2. **三种状态分开记**：一块地图有「已下载」「已显示在画面」「正在请求」三种状态，不能混（下载了 ≠ 显示着）。
3. **开场先预载**：开场航拍要用到全部地图，所以先一次性预载 25 块；游戏开始后才按需动态装卸。
4. **出错怎么办**：加载失败就记下来、不无限重试；坐标过期或世界拆了就坚决不往画面里写。

**当前状态**：确定性 CORE（✅ 26 项测试）与有界动态分块运行时集成已完成；master/chunk 请求、缓存、目标集合、在途去重、有限重试、World apply/remove/回滚、Phaser Tilemap 动态写入/清除、碰撞层装卸和基础销毁守卫均已验证。当前进入 `WI-SYS-MAP-LIFECYCLE-CLOSURE-001`，补齐可取消请求和销毁收敛。
**仍未完成**：完整原站 13 层语义、多视口量化和更深的 Phaser 资源生命周期证据仍未实现或验证。
**下一步**：本项只处理请求取消、过期结果、排队/在途 mutation、显式 Tilemap teardown 和固定场景边界指标；不实现 NPC、车辆、粒子消费者或完整玩法。

## 1. 逆向结论（从 sample 读出来的事实）

来源：
- `migration-history/doc-v0.1/03-具体怎么做/系统/地图分块：从原站查到了什么（SYS-CHUNK 调查记录）.md`
- `migration-history/doc-v0.1/03-具体怎么做/系统/地图分块：玩家移动时怎样加载地图（SYS-CHUNK）.md`
- `migration-history/doc-v0.1/04-怎么验证与还差什么/地图分块：怎样验证做对了（SYS-CHUNK 验证计划）.md`

### FACT（原站证实）

- 数据契约：master 明确每块 28×28 tile、横向 5 块、纵向 5 块、原图 140×140；tile 尺寸 16×16 像素；文件索引公式 `index = y * nbChunksHorizontal + x`，文件名为 `chunk{index}.json`；25 个 chunk 按行优先拼接后与整图的 24 层逐格一致。来源：调查记录 §3.1、验证计划 CHUNK-DATA-001（证据 `sample/original-public-build/mirror/assets/maps/chunks/master.json`、`chunk0.json`）。
- 两层职责：chunk manager（请求 master 和单个 JSON；成功后以 `x_y` 缓存数据；非法坐标、master 未就绪或 HTTP 异常返回 `null`）与 GameScene（计算需要的 chunk、把返回数据写入 Tilemap、维护场景已加载集合、清除不再需要的显示区域）。两层都叫 `loadedChunks` 但不是同一个 Map：前者表示已获得 JSON，后者表示已进入场景集合。来源：调查记录 §3.2（证据 `sample/original-public-build/mirror/chunk-RA2FASQA.js`、`chunk-WMFY56ZM.js`）。
- 目标集合与更新节奏：场景每约 500ms 检查一次（相机展示期间除外）；先以玩家世界坐标计算当前块，加入边界裁剪后的 3×3 邻域；再根据相机 `scrollX / scrollY / width / height / zoom` 计算可见范围；相机可见范围向四周额外扩展 1 块；二者合并为同一个目标集合。来源：调查记录 §3.3、正式设计 §2。
- 卸载实际行为：计算块在世界 Tilemap 中的起点，将 `layer1`–`layer10` 和 `walls` 的该块区域写为 `-1`，重新计算该区域碰撞面，从场景的已加载集合删除该块；已定位动态路径中没有发现同时删除 manager 的 JSON 缓存——"视觉/场景卸载"与"下载数据缓存删除"是两件不同的事。来源：调查记录 §3.4。
- manager 自身定义了 `unloadChunk`、`unloadDistantChunks` 和 `updateChunks` 等缓存淘汰方法，但在当前已检查的发布 Bundle 中没有找到调用方；不能据此断言 manager 缓存永远不会淘汰。来源：调查记录 §3.4。
- Play 前预载：master 成功后场景启动相机展示，约 100ms 后调用 `preloadChunksForCameraSequence()`；它汇总多个相机位置的视口范围，预载范围额外扩展 2 块，用 Set 去重，通过 `requestIdleCallback`（不可用时 `setTimeout`）逐项尝试加载；在既有 1920×1080 采集里这一范围覆盖 5×5 地图，因此 Play 前已请求 `chunk0.json` 至 `chunk24.json`。这不推翻玩家阶段仍按目标集合动态装卸的事实。来源：调查记录 §3.5、验证计划 CHUNK-PRELOAD-001。

### INFERRED（推断）

- 分块系统应只负责"数据块的目标集合、请求结果和写入/清除边界"；世界装配、完整图层语义、玩家参数和通用 Loader 不应被一并塞入。来源：调查记录 §4。
- 相机和玩家是计算目标集合的输入，不应反过来由分块系统定义其完整行为。来源：调查记录 §4。
- manager JSON 缓存和场景 Tilemap 状态应在设计中分开建模，避免把"已下载"误当成"当前显示"。来源：调查记录 §4。

### UNKNOWN（还没弄清）

- 同一块在响应前重复触发加载是否会合并请求（静态路径只在成功回调后写入 Map，未定位 in-flight 注册表）。来源：调查记录 §5。
- 是否支持取消加载（未定位 `AbortController`、保存订阅或 unsubscribe 路径）。来源：调查记录 §5。
- 失败后如何重试、记录或降级（已知失败会变为 `null`，但未证明重试策略）。来源：调查记录 §5。
- 场景销毁时如何处理缓存、空闲回调、tween 和未完成请求（当前范围未定位 shutdown/destroy 清理）。来源：调查记录 §5。
- 不同视口/缩放下相机预载的精确边界（已有一次采集，但没有多视口量化）。来源：调查记录 §5。
- 13 个未在卸载代码中处理的图层如何清除（已知清除 `layer1..10` 和 `walls` 共 11 层，完整图层语义仍未逆向，与 SYS-LAYER 边界一起调查）。来源：调查记录 §5、正式设计 §2。

### DECISION（重构设计，非原站事实）

- 保持"原始数据缓存 / 场景渲染状态 / 请求中的工作"三类状态分离（Human 已接受）。来源：正式设计 §2、§13。
- 一个坐标同一时刻只允许一个在途请求；请求完成后只在该坐标仍属于当前目标集合时写入场景。来源：正式设计 §2。
- 失败显式记录；不做无界自动重试；由下一次目标更新或明确重试操作触发有限重试。来源：正式设计 §2。
- 取消策略：不把"取消 HTTP 请求"假装成原站事实；若环境无法安全取消，请求可完成进入原始缓存，但结果只有在坐标仍是目标且系统未销毁时才能写入场景。来源：正式设计 §7。
- 正式实现授权独立留给 `GATE-SYS-CHUNK-IMPLEMENTATION`；13 个图层语义单列为后续工作。来源：正式设计 §13。

## 2. 数据与约定

### master / chunk 契约

- chunk 尺寸 28×28 tile；网格 5×5；原图 140×140；tile 16×16 像素。
- 文件索引：`index = y * 5 + x`；文件名 `chunk{index}.json`（`chunk0.json` … `chunk24.json`）。
- chunk 数据：24 层、每层 28×28（data 长度 784）。
- 世界坐标换算：块 `(x,y)` 覆盖世界 Tilemap 区域 `x*28 … (x+1)*28`、`y*28 … (y+1)*28`。

### 状态所有权（职责名称，不预先要求对应三个代码目录或三个可复用类）

| 状态 | 唯一拥有者 | 读取者 | 允许修改者 | 说明 |
|---|---|---|---|---|
| master 数据与已成功原始 chunk JSON | ChunkDataStore | ChunkCoordinator、WorldRenderer | ChunkDataStore | 已下载不等于已显示 |
| 当前目标 chunk 坐标集合 | ChunkCoordinator | WorldRenderer、诊断/验证 | ChunkCoordinator | 来自玩家邻域与相机集合并集 |
| 在途请求登记 | ChunkCoordinator | ChunkDataStore、诊断/验证 | ChunkCoordinator | 同坐标只保留一个在途工作，防止重复请求 |
| 每块失败记录与尝试次数 | ChunkCoordinator | UI/诊断、验证 | ChunkCoordinator | 不把失败伪装成已加载 |
| 已写入 Tilemap 的 chunk 集合 | WorldRenderer | ChunkCoordinator、诊断/验证 | WorldRenderer | 只表示场景当前显示状态 |
| 系统是否已销毁 | ChunkCoordinator | 所有异步回调 | ChunkCoordinator | 销毁后回调不得继续写入场景 |

### 子能力与输入输出

| 子能力 | 输入 | 输出 | 当前依据 |
|---|---|---|---|
| 数据目录 | master、坐标 | 块尺寸、地图边界、文件索引 | FACT |
| 目标集合计算 | 玩家世界位置、相机视口 | 坐标集合 | FACT（原站默认玩家 3×3 与相机 +1 边距） |
| 首屏预载 | 相机展示位置与视口 | 预载坐标集合 | FACT（原站默认额外 2 块边距） |
| 请求与缓存 | 坐标、目录 | 原始 chunk 数据或结构化失败 | FACT 有缓存；失败策略为 proposed |
| 场景写入/清除 | chunk 数据、坐标、图层策略 | Tilemap 区域变化 | FACT 有局部清除；完整图层策略 UNKNOWN |
| 生命周期收敛 | 新目标集合、场景销毁 | 加载、保留、清除或停止后续写入 | FACT + proposed |

## 3. 怎么做

### 协作流程（DECISION，accepted）

```text
玩家位置 + 相机视口
        ↓
ChunkCoordinator 计算目标集合
        ↓
对每个目标：数据已缓存？已渲染？正在请求？失败可否有限重试？
        ↓
ChunkDataStore 获取或返回原始 JSON
        ↓
仅当系统未销毁且该块仍在当前目标集合时
        ↓
WorldRenderer 写入对应 Tilemap 区域，登记已渲染
        ↓
对不再属于目标集合的已渲染块清除对应区域
```

### 重复、失败、取消与销毁

- 重复：同坐标在途时复用同一在途结果，不再发第二次请求；
- 失败：记录坐标、错误类别和尝试次数；当前轮不无限自动重试；
- 重试：只在仍属于目标集合时，经过有限次数或明确触发后重试；具体次数和退避参数在实现 Gate 前确定【TBD】；
- 取消：store/coordinator 销毁时使用 `AbortSignal` 取消 master/chunk 请求；取消不进入普通失败计数，也不把未完成数据写入缓存；目标变化但系统仍存活时允许请求完成进缓存。
- 过期：请求完成后再次检查系统未销毁且坐标仍在目标集合，才允许交给 World。
- 销毁：先停止目标更新和新 mutation，再取消请求；等待当前 mutation/调度器收敛，最后释放 World/Tilemap 资源。

这是为重构可控性提出的设计，并非声称原站也有同样错误策略。

### 当前生命周期收口（DECISION；Human 已于 2026-08-20 接受）

- `JsonLoader` 增加可选 abort signal，但保留现有 loader 的兼容调用形式。
- `ChunkCoordinator.destroyAsync()` 是正式销毁入口，旧 `destroy()` 只作为兼容的 fire-and-forget 包装；销毁后状态立即拒绝新请求/写入，异步结果必须收敛。
- `PhaserWorldMutationScheduler` 清空排队 mutation 并提供 active mutation 等待；renderer 逐层清理 collider/layer，最后销毁自身 Tilemap。
- 固定场景验证资源 URL 去重、渲染层/marker 上界、销毁后的异常和请求回写；不宣称完整 FPS、内存或原站特殊 13 层语义已解决。

### 首屏预载

master 成功后 → 相机展示序列汇总多个视口 → 预载范围额外扩展 2 块边距 → Set 去重 → `requestIdleCallback`（不可用则 `setTimeout`）逐项加载。

### 输入/输出边界

- 输入依赖：SYS-WORLD（Tilemap 和世界坐标空间）、SYS-PLAYER（只提供玩家世界位置）、SYS-CAMERA（只提供相机视口）、SYS-ASSET（仅提供分块所需的请求能力，不在此定义通用 Loader）、SYS-LAYER（定义完整图层策略前，分块只能按已确认范围写入/清除）。
- 输出：对 WorldRenderer——坐标和已验证的 chunk 数据；对验证——目标集合、请求、缓存、渲染、失败和销毁的可观察记录；不直接修改玩家、相机、NPC 或 UI 的私有状态。
- 不要求事件总线：立即需要加载结果或状态时使用直接调用；加载完成、失败、场景销毁等已发生状态才可作为通知记录。

## 4. 失败怎么办

- 原站已定位失败行为：非法坐标、master 未就绪或 HTTP 异常时，chunk manager 返回 `null`。来源：调查记录 §3.2。
- 失败显式记录（坐标、错误类别、尝试次数）；当前轮不无限自动重试；由下一次目标更新或明确重试操作触发有限重试；具体次数和退避参数在实现 Gate 前确定【TBD】。
- 重复：同坐标只保留一个在途请求，其余触发复用同一在途结果。
- 过期结果：请求完成但坐标已不在当前目标集合，或系统已销毁 → 不写入场景（可留在原始缓存）。
- 销毁清理：场景退出时停止本系统拥有的定时、空闲任务和后续场景写入；未完成结果不得访问已销毁场景；系统销毁状态是所有异步回调的守卫。
- 资源加载接口：图片怎么加载、失败怎么办（原站事实已定稿，见 SYS-ASSET；重构约定留待实现授权）。

## 5. 接口接口

- 与 SYS-WORLD：只给坐标和已验证 chunk 数据，由 WorldRenderer 写入/清除对应 Tilemap 区域；世界返回写入、清除或失败结果。
- 与 SYS-LAYER：按名称取得图层处理策略；完整图层策略确认前，只能按已确认范围写入/清除，不得绕过图层策略直接操作 Tilemap。
- 与 SYS-PLAYER：只读玩家世界位置。
- 与 SYS-CAMERA：只读相机视口。
- 与 SYS-ASSET：仅请求分块所需数据，不在此定义通用 Loader。
- 相机范围接口：相机 → 分块，目标集合 = 玩家 3×3 ∪ 相机可见 +1（已定死，见 §2）。
- 资源加载接口：图片怎么加载、失败怎么办（原站事实已定稿，见 SYS-ASSET；重构约定留待实现授权）。
- 加载完成、失败和销毁先作为系统状态通知记录；只有出现多个实际消费者后再评估独立事件文档。

## 6. 怎样算做对

原站事实基准（来源：SYS-CHUNK 验证计划 §1）：

- BASE-MAP-001：游戏世界请求 `chunk0.json` 至 `chunk24.json`（行为基准、运行时 Network、镜像文件）；
- CHUNK-DATA-001：master 是 5×5、每块 28×28，索引为 `y*5+x`（master、25 块重组与 `final_map.json` 对照）；
- CHUNK-RUNTIME-001：玩家 3×3 与相机范围+1 块边距共同形成玩家阶段目标集合（Bundle 搜索锚点 `getCurrentChunkIndex`、`getVisibleChunksForCamera`）；
- CHUNK-PRELOAD-001：Play 前相机序列预载与玩家阶段动态目标集合是两段不同流程（`startCameraSequence`、`preloadChunksForCameraSequence`、Network 时序）。

重构设计验收（CHUNK-DESIGN-001..006）：

1. 读取 master 与 25 块，按 `(x,y)` 计算文件名并重组，与 `final_map.json` 的 24 层逐格一致（索引、边界或任一格不一致为失败）；
2. 给定玩家位置和相机视口，目标集合等于边界裁剪后的玩家 3×3 与相机+1 集合并集（漏块、越界或集合来源混淆为失败）；
3. 同一坐标被重复请求时，同一时刻只有一个在途工作（多次请求或状态无法解释为失败）；
4. 块离开目标集合时执行场景清除，已渲染集合收敛，数据缓存与渲染状态可分别观察（将已下载误当成仍渲染，或遗漏清除为失败）；
5. 请求失败、结果过期或场景销毁时，不向错误/已销毁场景写入，失败可定位（静默吞错、旧结果写入或资源继续操纵已销毁场景为失败）；
6. 13 个图层语义未确认时，不报告为已正确支持（未证实图层被纳入通过结论为失败）。

CORE 实现结果（`GATE-SYS-CHUNK-IMPLEMENTATION` / `DEC-SYS-CHUNK-CORE-001`，提交 `f04568f953821e8cc56c33a694171ddab759051f`）：

- TypeScript strict typecheck PASS；`npm test` PASS（3 文件、26 项单元测试）；npm 官方源审计 0 漏洞；治理 sync 835 项、pilot 840 项 PASS；lightweight-verifier 只读复核 PASS，无 blocking/high/medium/low 缺陷。
- 本轮覆盖：master 关键契约、行优先索引、世界边界、玩家 3×3、相机 scroll/zoom +1 块边距和目标集合并集。
- CORE 阶段未覆盖的请求、缓存、重试、销毁和 Tilemap 写入/清除，已在 `WI-SYS-CHUNK-WORLD-INTEGRATION-001` 的有界集成中实现并验证；本次 `WI-SYS-MOVE-WORLD-COLLISION-001` 又验证了目标变化时 collider 先清理、Tilemap layer 后销毁；多视口量化、请求取消、完整 13 层语义仍未覆盖。
