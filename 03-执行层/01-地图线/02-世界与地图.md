# 世界与地图（SYS-WORLD）

> 一句话：世界系统拥有全局 Tilemap 和图层实例，以 master 与 chunk 为正式数据来源，并向分块系统提供可回滚的写入、清除和销毁能力。

## 👀 先看这里（人话总结，给 Human）

下面全是给 AI 看的精确结论（FACT / UNKNOWN 那套术语）。你**不用啃术语**，看这段人话就够审了。

**这卡在说啥**：整张游戏地图——它是一整张 140×140 的大图，由 5×5 块小图拼起来；这张卡管"地基"的建立和拆除。

**我查清的 3 件原站事实**（你审的就认这 3 条）：
1. **一整张图**：140×140 格、24 层，切成 5×5 块（每块 28×28），按顺序拼起来和原站整图**逐格零差异**。
2. **世界是地基**：它拥有全局 Tilemap 和所有图层实例，别的东西（分块、图层、NPC）都挂它上面。

**下一步**：本项只补可取消请求、过期结果守卫、异步销毁等待、调度器/Tilemap teardown 和固定场景资源边界验证，不扩展到粒子/NPC/玩法。

## 1. 逆向结论（从 sample 读出来的事实）

来源：
- `migration-history/doc-v0.1/03-具体怎么做/系统/世界与地图：从原站查到了什么（SYS-WORLD 调查记录）.md`
- `migration-history/doc-v0.1/03-具体怎么做/系统/世界与地图：游戏世界怎样建立和装卸（SYS-WORLD）.md`
- `migration-history/doc-v0.1/04-怎么验证与还差什么/世界与地图：怎样验证做对了（SYS-WORLD 验证计划）.md`

### FACT（原站证实）

- 世界是同一张 140×140、24 层地图：master 定义 5×5 个 chunk、每块 28×28 tile、tile 16×16 像素；25 个 chunk 的 24 层名称、顺序、类型、尺寸和 data 长度完全一致；按 `index = y * 5 + x` 行主序拼接后共 470400 格，与 `final_map.json` 逐格差异为 0。来源：调查记录 §3.1（证据 `sample/original-public-build/mirror/assets/maps/chunks/master.json`、`chunk0.json`–`chunk24.json`、`assets/maps/final_map.json`）。
- 发布 Bundle 先建立空 Tilemap：从 master 读取宽高后调用 `make.tilemap(tileWidth=16, tileHeight=16, width=140, height=140)`；世界像素范围 2240×2240，相机和物理世界边界也设置为该范围。来源：调查记录 §3.2（证据 `sample/original-public-build/mirror/chunk-WMFY56ZM.js`）。
- 普通 tileset 路径映射：`exterior` firstgid 1、`collisions-objects` firstgid 69345、`tileset-particles` firstgid 69355；优化路径读取 `final_map_small.json` 中 16 个 `exterior-small*` tileset 并建立原始 tile ID 到优化 tile ID 的映射，发布类字段 `USE_OPTIMIZED_TILESETS=!0`。来源：调查记录 §3.2。
- 发布保留两条不完整对称的写入路径并存：普通 fallback 有 `o=["layer1"]` 名称守卫，实际只把该层 28×28 数据写到 `x*28, y*28` 区域；优化路径读取完整 `final_map_small.json`（22 层），`layer1` 先同步写入、其余通过空闲回调分批写入。来源：调查记录 §3.3。
- 已定位卸载只清 11 层：`unloadChunk(x,y)` 把 `layer1`–`layer10` 和 `walls` 写成 `-1`、重新计算该区域碰撞面、从场景 `loadedChunks` 删除坐标；不清 cars/roof/bridge/particles/footsteps 等其余 13 层，也不删 chunk manager 的原始 JSON 缓存。来源：调查记录 §3.4。
- 失败与边界处理已定位：master 不存在、必要 tileset 或 texture 无法建立时记录错误并提前返回；单块回调返回 falsy 时直接停止本次写入；`loadChunksForCamera` 捕获异常但已定位分支未形成完整错误状态。来源：调查记录 §3.5。
- 未定位显式统一 teardown：Bundle 中没有 `cancelIdleCallback` 或 `tilemap.destroy` 调用；GameScene 的 shutdown 监听只移除一个 document keydown handler；Phaser 是否在场景生命周期中隐式释放部分资源仍未知。来源：调查记录 §3.5。

### INFERRED（推断）

- 责任边界：全局 Tilemap、世界坐标空间和场景图层实例归 SYS-WORLD（在单一世界生命周期中创建和销毁）；需要哪些 chunk、请求和原始 JSON 状态归 SYS-CHUNK；图层 depth、可见性、碰撞和 roof/bridge/cars 语义归 SYS-LAYER；地图 JSON、texture 和 tileset 可用性归 SYS-ASSET。来源：调查记录 §4。

### UNKNOWN（还没弄清）

- 特殊 13 层不随 chunk 卸载，是有意作为全局持久层还是发布实现的不完整路径。来源：调查记录 §5、正式设计 §1。
- 优化路径为何在每次 `loadChunk` 回调中使用完整 `final_map_small`、实际运行时是否重复写完整世界；普通 fallback 为何只允许 `layer1`。来源：调查记录 §5。
- 普通路径和优化路径的 depth 公式存在差异时，实际显示结果由哪一次创建决定。来源：调查记录 §5。
- 世界创建中途失败时，已创建图层和监听器如何回滚；场景关闭时 Tilemap、空闲回调、定时器、碰撞和特殊层的完整销毁顺序（静态代码未定位显式统一 teardown）。来源：调查记录 §5。
- 是否需要运行时截图或 Canvas 采样才能关闭图层前后遮挡顺序。来源：调查记录 §5。

### DECISION（重构设计，非原站事实）

- 第一版唯一运行数据来源 = `master + chunk JSON`；`final_map.json` / `final_map_small.json` 只作证据 Oracle 和兼容验证材料；不照搬发布 Bundle"优化路径在单块回调中重复读取完整整图"的结构。理由：25 个 chunk 已证明可无损重建整图；已实现的 SYS-CHUNK CORE 和后续动态装卸都以 chunk 坐标为边界；同时维护整图与 chunk 两条运行写入路径会增加状态分叉和失败面。代价：第一版不会逐字复刻发布 Bundle 的整图优化写法，需要用行为验证证明可见结果一致。来源：正式设计 §4。
- SYS-WORLD 的负责/不负责边界与状态所有权表（见 §2、§3）。来源：正式设计 §2、§3。
- 24 层先完整转换再写入、失败时回滚当前 chunk；世界生命周期边界先成为正式设计，图层视觉未知继续保留并单独补证。来源：正式设计 §9。

## 2. 数据与约定

### WorldSpec（创建后只读）

- 宽高：140×140 tile；tile 尺寸 16×16 像素；chunk 尺寸 28×28；网格 5×5。
- 世界像素范围：2240×2240。

### 数据来源

- 运行数据：`master.json` + `chunk{index}.json`（索引 `index = y * 5 + x`）。
- Oracle：`final_map.json`（24 层 140×140 对照）、`final_map_small.json`（优化整图）。

### 概念接口（仅表达能力，不指定 TypeScript 文件、类或公共库）

```text
createWorld(worldSpec, worldResources, layerPlan)
  -> WorldReady | WorldCreateFailure

applyChunk(coord, validatedChunk)
  -> Applied | AlreadyApplied | ChunkApplyFailure

removeChunk(coord)
  -> Removed | AlreadyAbsent | ChunkRemoveFailure

destroyWorld()
  -> idempotent completion
```

### 状态所有权（职责名称，不预先要求每行对应独立类或目录）

| 状态 | 唯一拥有者 | 说明 |
|---|---|---|
| WorldSpec | SYS-WORLD | 从已验证 master 得到；创建后只读 |
| Tilemap 与 tileset 句柄 | SYS-WORLD | 创建成功后统一持有，销毁后不可访问 |
| 运行时图层实例 | SYS-WORLD | 按 SYS-LAYER 策略创建；生命周期跟随世界 |
| 图层策略 | SYS-LAYER | 世界只消费，不自行硬编码语义 |
| 已完整写入世界的 chunk 集合 | SYS-WORLD 的 WorldRenderer 职责 | 只有 24 层策略均成功处理后才能登记 |
| 原始 master/chunk JSON 与在途请求 | SYS-CHUNK | 世界只接收已验证数据，不拥有网络状态 |
| 动态 roof/bridge 等图层状态 | SYS-LAYER | 世界保存实例，但不决定业务切换规则 |

## 3. 怎么做

### createWorld

1. 先校验 worldSpec、必要资源和 24 层策略完整性；
2. 创建 Tilemap 和 tileset 句柄；
3. 按固定策略创建所有运行时图层；
4. 全部成功后才发布 ready 句柄；
5. 任一步失败则销毁已经创建的实例，并返回可定位错误。

### applyChunk

1. 校验坐标、28×28 尺寸、24 层名称和 data 长度；
2. 先由 SYS-LAYER 把 24 层转换成可写网格或 marker 结果；
3. 所有转换成功后才修改 Tilemap；
4. 任一写入失败时清除本次坐标的所有 chunk-local 层和 marker 登记；
5. 只有完整成功才加入已渲染集合。

### removeChunk

1. 对所有被定义为 chunk-local 的 24 层策略执行清除或 marker 撤销；
2. 重新计算受影响碰撞区域；
3. 完成后删除已渲染标记；
4. 重复删除返回 AlreadyAbsent，不制造错误状态。

### 生命周期

```text
uninitialized
  -> creating
  -> ready
  -> destroying
  -> destroyed

creating / ready
  -> failed
  -> destroying
  -> destroyed
```

- 非 `ready` 状态拒绝写入；destroy 可重复调用；
- 世界销毁顺序：先禁止新写入，再取消本系统自己安排的任务，断开碰撞与监听，最后销毁图层和 Tilemap；
- SYS-CHUNK 的晚到请求结果必须在进入世界前检查自身销毁与目标状态；SYS-WORLD 不承担 HTTP 取消；
- 第一版不使用未保存句柄的 idle callback 进行关键写入。

### 与 SYS-LAYER 和 SYS-CHUNK 的接力

```text
SYS-CHUNK：决定目标坐标并取得 validatedChunk
         ↓
SYS-LAYER：按名称提供 24 层处理策略
         ↓
SYS-WORLD：原子写入/清除世界并返回结果
         ↓
SYS-CHUNK：根据结果更新协调状态和失败记录
```

世界不得自行重新计算目标集合；分块不得直接绕过图层策略操作 Tilemap。

### 当前生命周期收口（DECISION；Human 已于 2026-08-20 接受）

- 重构运行时把 24 层都视为 chunk-owned 结果，销毁时按显式策略清除；这不是对原站特殊 13 层事实的关闭。
- SYS-CHUNK 的数据请求在 store/coordinator 销毁时可取消；目标变化本身仍允许请求完成进入缓存，但过期结果不得写入 World。
- SYS-WORLD/Phaser 只在协调器停止新写入、所有在途/排队 mutation 收敛后销毁 Tilemap layer、Tilemap 和碰撞句柄。
- 固定浏览器场景只验证资源请求无重复失控、渲染层/marker 数量有界、销毁后无异常；不把这组边界数据宣称为完整 FPS 或内存性能结论。

## 4. 失败怎么办

| 风险 | 建议处理 |
|---|---|
| 24 层写到一半失败 | 清除当前坐标全部 chunk-local 结果，不登记已渲染 |
| 资源缺失 | 创建阶段失败，不发布半成品世界 |
| 晚到回调写入已销毁世界 | 世界状态拒绝；协调器也必须先检查自身状态 |
| 图层策略缺失 | 创建前阻塞，不静默忽略未知层 |
| 特殊 13 层是否全局持久仍未知 | 第一版按显式策略处理；未经接受不得复制发布 Bundle 遗漏清除行为 |
| Phaser 隐式销毁行为不清 | 正式实现必须用显式测试证明，无证据时不依赖隐式行为 |

## 5. 接口接口

- 与 SYS-LAYER：以 layerPlan 按名称取得 24 层处理策略；世界只消费，不自行硬编码语义。
- 与 SYS-CHUNK：接收 `(coord, validatedChunk)`，返回 `Applied / AlreadyApplied / ChunkApplyFailure` 等明确写入、清除或失败结果；不拥有网络状态。
- 相机范围接口：相机 → 分块（已定死，见 SYS-CAMERA：相机可见范围 +1 块边距）。
- 资源加载接口：图片怎么加载、失败怎么办（原站事实已定稿，见 SYS-ASSET；重构约定留待实现授权）。
- 接口名称仅表达能力，不指定 TypeScript 文件、类或公共库。

## 6. 怎样算做对

原站事实基准（来源：SYS-WORLD 验证计划 §1）：

- WORLD-FACT-001：master 为 5×5、chunk 为 28×28、世界为 140×140、tile 为 16px；
- WORLD-FACT-002：25 个 chunk 行主序拼接与 `final_map` 逐格比较差异必须为 0；
- WORLD-FACT-003：发布 Bundle 建立 140×140 空 Tilemap（锚点 `this.make.tilemap({tileWidth:`）；
- WORLD-FACT-004：保留只写 layer1 的普通局部 fallback 和默认优化 22 层整图写入两条路径（锚点 `USE_OPTIMIZED_TILESETS`、`o=["layer1"]`）；
- WORLD-FACT-005：已定位卸载只清 11 层且不删除原始 JSON 缓存（锚点 `unloadChunk(e,t)`）。

正式设计验收（WORLD-DESIGN-001..007）：

1. 对照 SYS-CHUNK、SYS-WORLD、SYS-LAYER、SYS-ASSET 责任表：每个状态只有一个修改者，没有请求、世界和图层策略互相越权；
2. 输入有效 master、资源和 24 层策略：只有全部创建成功才发布 ready 世界；
3. 输入完整 28×28、24 层 chunk：全部层转换和写入成功后才登记已渲染；
4. 让任一层转换或写入失败：当前 chunk 所有局部结果回滚，失败可定位；
5. 重复 apply/remove 同一坐标：返回 AlreadyApplied/AlreadyAbsent 且状态不漂移；
6. 世界销毁时存在晚到结果：禁止新写入、释放世界拥有资源、重复 destroy 安全；
7. 检查运行数据来源：第一版只使用 master+chunk，final_map 只作 Oracle。

未来实现测试（仍需补充）：WorldSpec 边界与像素尺寸；完整 Phaser 场景创建/销毁后的监听、空闲任务、Tilemap 和资源泄漏量化；多视口和完整 24 层运行语义。本次已覆盖并验证：单 chunk 写入/清除、重复写入/清除、同步/异步当前层失败补偿回滚、destroy 后晚到写入拒绝、master+chunk 动态加载、跨块浏览器行为以及碰撞层 collider 先清理后销毁。

保护边界：不为迁就实现修改 master、chunk 或 final_map 证据；不把浏览器画面相似代替数据和失败路径测试；不把只完成 11 层报告为世界装配完成；未经 level-2 Human Gate 不创建 Phaser 实现。
