## 一、骨架落地

### 骨架 1：统一建/拆的"总指挥"模式

> 理解层说的是"整张地图的建立和拆除全由一个总管经手，别人不能绕过它直接动地图"。
> 在代码里，这个总管叫 **`createWorld` 工厂函数 + `WorldImpl` 类**。

**它怎么工作的**：

```
createWorld(spec, options)
        │
        ├─ ① validateWorldSpec(spec) → 校验规格自洽
        │     │  世界宽高 = chunk 尺寸 × 网格数？
        │     │  像素范围 = tile 数 × tile 像素？
        │     └─ 不通过 → 返回 { kind: "failure", reason: "..." }
        │
        ├─ ② 检查 layerPlan（来自 options 或默认 LAYER_STRATEGIES）
        │     │  非空？层名不重复？
        │     └─ 不通过 → 返回 failure
        │
        ├─ ③ 全部通过 → new WorldImpl(spec, layerPlan, hooks)
        │     └─ 返回 { kind: "ready", world }
        │
        └─ WorldImpl 是唯一的 World 实例
             所有对世界的操作（applyChunk / removeChunk / destroy）
             都必须经过它
```

外部代码拿到 `World` 接口后，只能调四个方法：`applyChunk`、`removeChunk`、`destroy`，以及读 `state` 和 `renderedChunks`。不能直接操作 Tilemap——因为 `WorldWriteHooks` 是注入进去的回调，外部只能通过 `WorldImpl` 调用它们。

### 骨架 2：原子操作——要么全成，要么全滚

> 理解层说的是"放一块地图要写 24 层，全成功才登记，任一层失败整块回滚"。
> 在代码里，这由 **`WorldImpl.applyChunk()` 的 try/catch + 回滚逻辑** 实现。

**它怎么工作的**：

```
applyChunk(chunk)
        │
        ├─ ① 状态检查：state === "ready"？  → 不是 → 返回 failure
        │
        ├─ ② validateChunk(chunk, spec, layerPlan)
        │     │  坐标在网格内？层数 = layerPlan 长度？层名顺序对？每层 data 长度对？
        │     └─ 不通过 → 返回 failure
        │
        ├─ ③ 查重：rendered 集合里已有这块？ → 有 → 返回 already-applied
        │
        ├─ ④ 原子写入循环：
        │     for 每一层：
        │       written.push(layer)        ← 先登记（回滚时需要知道写了哪些）
        │       hooks.writeLayer(layer)    ← 实际写入
        │     │
        │     └─ 任一层抛异常 →
        │           for 已写入的每一层：
        │             hooks.clearLayer()   ← 逐层回滚（尽力而为）
        │           返回 failure（含原始错误原因）
        │
        └─ ⑤ 全部成功 → rendered.set(key, chunk) → 返回 applied
```

`removeChunk` 的逻辑是对称的：先校验坐标 → 找不到返回 already-absent → 逐层清除 → 任一层失败则回滚（重新写入已清除的层）→ 全部成功才从 rendered 集合删除。

**异步版本**（`applyChunkAsync` / `removeChunkAsync`）在每层写入之间额外检查 `state !== "ready"`，防止异步写入过程中世界被销毁。

### 骨架 3：生命周期状态机

> 理解层说的是"世界从不存在到可用再到拆掉，要经过明确的几个阶段，每个阶段能做什么有硬规矩"。
> 在代码里，状态定义在 **`WorldLifecycle` 类型**，状态检查散落在 `WorldImpl` 的每个方法入口。

**六个状态**：

```
uninitialized → creating → ready → destroying → destroyed
                              ↘ failed → destroying → destroyed
```

纯逻辑 CORE 实际只用 `ready` 和 `destroyed` 两个可观察状态（`uninitialized`/`creating`/`failed`/`destroying` 是异步或瞬态，留给 Phaser 实现）。

**状态守卫规则**：

| 操作 | ready | destroying | destroyed |
|---|---|---|---|
| applyChunk | ✅ 允许 | ❌ 拒绝 | ❌ 拒绝 |
| removeChunk | ✅ 允许 | ❌ 拒绝 | ❌ 拒绝 |
| destroy | → 进入 destroying | 幂等 | 幂等（直接 return） |

**destroy 的幂等性**：`destroy()` 第一行就检查 `state === "destroyed"`，如果是就直接 return。这保证了多次调用不会出错。

**代码在哪**：

| 做什么 | 文件路径 + 行号 | 关键函数/类型 |
|---|---|---|
| 生命周期类型定义 | [src/world/contract.ts](../../src/world/contract.ts) 第 45-51 行 | `WorldLifecycle` |
| 状态封装 | [src/world/world.ts](../../src/world/world.ts) 第 93-95 行 | `get state()` |
| destroy 幂等 | [src/world/world.ts](../../src/world/world.ts) 第 284-291 行 | `WorldImpl.destroy()` |
| applyChunk 状态守卫 | [src/world/world.ts](../../src/world/world.ts) 第 104 行、第 148 行 | `state !== "ready"` 拒绝写入 |
| removeChunk 状态守卫 | [src/world/world.ts](../../src/world/world.ts) 第 194 行、第 239 行 | `state !== "ready"` 拒绝清除 |

### 骨架 4：地基模式——别人挂我上面

> 理解层说的是"世界拥有 Tilemap 和所有图层实例，其他系统只使用不拥有"。
> 在代码里，所有权通过 **`World` 接口 + `WorldWriteHooks` 注入** 实现了清晰分离。

**所有权分离的具体实现**：

```
谁拥有什么（所有权表）：
┌─────────────────────┬──────────────────────────┐
│ 所有者               │ 拥有什么                   │
├─────────────────────┼──────────────────────────┤
│ SYS-WORLD (WorldImpl)│ WorldSpec（世界规格）      │
│                     │ renderedChunks 集合        │
│                     │ 通过 hooks 间接控制 Tilemap  │
├─────────────────────┼──────────────────────────┤
│ SYS-LAYER           │ LayerStrategy[]（图层策略） │
│                     │ 桥状态、屋顶状态             │
├─────────────────────┼──────────────────────────┤
│ SYS-CHUNK           │ ChunkDataStore（原始缓存）  │
│                     │ 目标集合、在途请求、失败记录   │
└─────────────────────┴──────────────────────────┘
```

World 不直接拥有 Tilemap 实例（那是在 Phaser 适配层 `PhaserWorldRenderer` 里），而是通过 `WorldWriteHooks` 注入——`writeLayer` 回调实际由 `PhaserWorldRenderer` 提供，它知道怎么往 Phaser Tilemap 里 `putTilesAt`。这样纯逻辑 CORE（`src/world/`）不依赖 Phaser，可以脱离浏览器测试。

| World 接口（所有权边界） | [src/world/contract.ts](../../src/world/contract.ts) 第 73-82 行 | `World` 接口 |
| 注入点（writeLayer / clearLayer） | [src/world/contract.ts](../../src/world/contract.ts) 第 54-65 行 | `WorldWriteHooks` |

### 骨架 5：安全拆解——反着建的方向拆

> 理解层说的是"拆世界的顺序必须反着来：先关门→再拔线→再拆墙→最后推地基"。
> 在代码里，纯逻辑层的销毁由 `WorldImpl.destroy()` 负责，Phaser 层的销毁由 `CampusScene` 的 shutdown 流程负责。

**纯逻辑层销毁**（`WorldImpl.destroy()`）：

```
destroy()
  ├─ state === "destroyed"？ → return（幂等）
  ├─ state = "destroying"    ← 先关门
  ├─ rendered.clear()        ← 清标记
  └─ state = "destroyed"     ← 标完成
```

**Phaser 层销毁**（`CampusScene` shutdown 流程）：

```
CampusScene.performShutdown()
  ├─ ① 停止调度器（PhaserWorldMutationScheduler）
  ├─ ② ChunkCoordinator.destroyAsync()
  │      ├─ 禁止新目标
  │      ├─ 取消所有请求（AbortSignal）
  │      └─ 等待在途请求和 mutation 收敛
  ├─ ③ 等待 mutation idle
  ├─ ④ PhaserWorldRenderer 清理
  │      ├─ 移除 collider
  │      ├─ 销毁所有 Tilemap layer
  │      └─ 销毁 Tilemap 自身
  └─ ⑤ 移除事件监听、销毁 Phaser.Game
```

**与骨架 1 的呼应**：建世界时顺序是 Tilemap → 图层 → 碰撞；拆的时候反着来：碰撞 → 图层 → Tilemap。

**代码在哪**：

| 做什么 | 文件路径 + 行号 | 关键函数/类型 |
|---|---|---|
| 纯逻辑 destroy | [src/world/world.ts](../../src/world/world.ts) 第 284-291 行 | `WorldImpl.destroy()` |
| coordinator 销毁 | [src/chunk/coordinator.ts](../../src/chunk/coordinator.ts) 第 178-198 行 | `ChunkCoordinator.destroyAsync()` |
| data store 销毁 | [src/chunk/data-store.ts](../../src/chunk/data-store.ts) 第 268-280 行 | `ChunkDataStore.destroy()` |
| mutation 调度器清理 | [game/PhaserWorldMutationScheduler.ts](../../game/PhaserWorldMutationScheduler.ts) | `PhaserWorldMutationScheduler` |
| Phaser 渲染器清理 | [game/PhaserWorldRenderer.ts](../../game/PhaserWorldRenderer.ts) | 逐层 collider → layer → Tilemap |
| CampusScene shutdown | [game/CampusScene.ts](../../game/CampusScene.ts) | `performShutdown()` |
