# 图层与遮挡（SYS-LAYER）

> 一句话：24 层使用一张完整策略表；每层明确是视觉层、碰撞层还是 marker 数据，并统一规定写入、清除、depth 和动态状态。

## 👀 先看这里（人话总结，给 Human）

下面全是给 AI 看的精确结论（FACT / UNKNOWN 那套术语）。你**不用啃术语**，看这段人话就够审了。

**这卡在说啥**：地图那 24 层各是干嘛的——哪些是看的、哪些是撞墙用的、哪些是隐藏的数据，以及玩家走到哪会被哪层遮住。

**我查清的 5 件原站事实**（你审的就认这 5 条）：
1. **24 层一张表管**：每层明确是「视觉层 / 碰撞层 / 隐藏数据层」，统一规定怎么写、怎么清、叠多高。
2. **玩家被遮挡是动态的**：玩家深度按 `500 + y×0.1` 算（越往下越深、被建筑遮得越对）；走到桥上临时抬到 1650。
3. **房顶会淡隐**：玩家进工厂/音乐厅，房顶在 300 毫秒内变透明，离开恢复。
4. **桥分上下层**：桥有上下两层，走上去切换碰撞和遮挡。
5. **脚印**：玩家踩在特定格子上会冒脚印（深度 450）。

这 5 条里，遮挡、房顶、桥、脚印 4 条已用原站截图**实拍验证过**；只有「抗议人群粒子」的完整链路还差一环（记在 Q-LAYER-002）。

**当前状态**：基础设计已定稿（2026-08-11 定稿 + 08-15 视觉补证通过）；本轮收束设计已由 Human 于 2026-08-20 通过，现由 `WI-SYS-LAYER-RUNTIME-SEMANTICS-IMPLEMENT-001` 做有界运行时实现。
**仍未完成**：完整地图节点仍不是 `implemented/verified`；particles3 消费链、特殊 13 层生命周期、请求取消、性能和完整 Phaser teardown 继续保持边界外。

### FACT（原站证实）

- 25 个 chunk 的层名、顺序、`tilelayer` 类型、28×28 尺寸和 784 项 data 完全一致；按行主序拼接后，24 层与 `final_map.json` 的 470400 个格子逐格差异为 0。来源：调查记录 §3（证据 `sample/original-public-build/mirror/assets/maps/chunks/chunk0.json`–`chunk24.json`、`assets/maps/final_map.json`）。
- 所有层实际字段只包含 `data/height/id/name/opacity/type/visible/width/x/y`，没有 `properties` 或 offset 字段。来源：调查记录 §3。
- 地图文件中的 visible 是发布数据字段，Bundle 会主动覆盖多个层的运行时可见性，因此不能仅凭该字段判断最终显示。来源：调查记录 §3、正式设计 §1。
- 初始 depth：layer1–5 = 100/200/300/400/500；layer6–10 = 1500/1600/1700/1800/1900。优化写入函数在"图层尚不存在"分支另有 layer6–10 = 1100–1500 的公式；正常初始创建已先建立这些层，静态证据不能把次级公式当成最终运行 depth。来源：调查记录 §4.1。
- walls：地图字段 visible、opacity 0.84；运行时创建后改为 hidden、alpha 1、depth 550；优化路径只保留碰撞 tileset 中的特定 GID；69345 被强制设为碰撞、69346 被强制设为不碰撞；发布代码按玩家世界坐标查询 walls tile 用于桥梁、海滩等特殊判断；chunk 卸载清除 28×28 区域并重算碰撞面。来源：调查记录 §4.2。
- cars：运行时 hidden、alpha .2、depth 550；优化路径只保留 69345–69352；`carTraffic()` 扫描该层 69350/69351 等标记建立车辆路径或放置车辆；已定位 chunk 卸载不清除 cars。来源：调查记录 §4.3。
- roof：四个 roof 层在地图文件中 hidden，但运行时创建为 visible、alpha 1、depth 3000–3300；玩家进入 factory 或 concert 固定区域时，对应 roof 在 300ms 内淡到 alpha 0，离开时恢复到 1。来源：调查记录 §4.4。
- bridge：四个 bridge wall 层使用 depth 3500；发布代码根据桥区在上下层之间切换可见性，并逐 tile 切换碰撞；bridge1/2 上桥时玩家 depth 为 1650；本次运行时按已定位的 tile 矩形和边沿规则接入并验证。来源：调查记录 §4.5、公开 Bundle offsets 324986–327217。
- particles/particles2：优化写入清单包含它们但只保留 69355–69359，未设置明确 depth，卸载时不清除；particles3（GID 69361）未进入已定位创建、写入或卸载清单。来源：调查记录 §4.6。
- footsteps：`footsteps-layer.json` 的 140×140 布尔 grid 与 24 层中 footsteps 的 368 个 GID=69345 位置逐格完全一致；发布运行时读取独立 `footstepsGrid`，在玩家移动、depth 低于 1000 且网格值为 1 时生成脚印；当前没有定位 footsteps tilelayer 本身的消费者。来源：调查记录 §4.6。
- `particle-trajectories.json` 含 88 个世界像素多边形 region；water、water2、protesters_rising 三类的全局 tileCount 分别与 69355、69356、69361 计数吻合，但其他类型、region bbox 和多边形均不能精确复现 tilelayer——只能确认有限数据关联，不能宣称轨迹由三层机械生成。来源：调查记录 §4.6。
- Bundle 独立加载 `particle-trajectories.json`，并由 `createAreaParticleEmitters`、`initCrowdStaticNPCs`、`updateProtestersRisingNPCs` 消费 trajectory region；这些调用链没有找到读取 `particles3`/GID 69361 或把 marker 转成 trajectory 的直接步骤。来源：`sample/original-public-build/mirror/chunk-WMFY56ZM.js` byte 337035–337162、551256、558928、565791；`Q-LAYER-002` 调查（2026-08-20）。
- 玩家常态 depth 不是固定值：已定位更新规则约为 `500 + (player.y + 24) * 0.1`；桥上可强制为 1650；怪物抓取设为 2001；龙卷风路径还会按发射器 depth 覆盖。玩家与基础层、roof 和 bridge 的最终遮挡关系必须同时考虑动态玩家 depth。来源：调查记录 §4.7。
- 1280×720 公开原站最小运行补证（`SRC-20260811-007`，13 阶段状态和 13 张截图）：layer8 遮挡、factory roof 淡隐恢复、bridge1 进出、footsteps 0→5 均 VERIFIED；particles3 marker 区域 PARTIAL（运行 Tilemap 无 particles3 层，画面有抗议人群并落入 protesters_rising region，直接消费者链仍 UNKNOWN）。来源：调查记录 §4.8、验证计划 §3。

### INFERRED（推断）

- 图层系统应拥有"图层定义到运行时策略"的映射，而不是让 SYS-CHUNK 硬编码所有名称；SYS-CHUNK 只负责目标坐标和触发写入/清除，每层怎样过滤 GID、设置 depth、碰撞和动态可见性由 SYS-LAYER 提供。来源：调查记录 §5。
- roof、bridge 和 cars 已有独立运行行为，但是否以后成为独立系统必须等真实实现复杂度和重复场景出现，当前不拆节点。来源：调查记录 §5。
- particles 和 footsteps 的 tilelayer 与独立动态数据可能是不同职责，不能为了凑齐 24 层而强行统一。来源：调查记录 §5。

### UNKNOWN（还没弄清）

- `particles3`/GID 69361 marker 是否被读取、转换为 `protesters_rising` region 或交给动态消费者，公开 Bundle 没有直接证据；86 个 marker 与 `protesters_rising` 的计数/空间关系只能记为 INFERRED，`Q-LAYER-002` 保持 open。
- 特殊 13 层为何不随原站 chunk 卸载，是有意全局持久还是不完整路径（归属 SYS-WORLD 生命周期 UNKNOWN）。来源：调查记录 §6。

### DECISION（重构设计，非原站事实）

- 24 层策略表作为唯一图层合同；所有 chunk 来源层都具有对称移除策略，不照搬发布代码"特殊 13 层永不卸载"的表现。来源：正式设计 §3、§10。
- layer6–10 第一版采用发布初始创建的 depth 1500–1900 作为设计默认（已由 `BASE-LAYER-001` 桌面运行补证验证），不采用"缺层补建"分支的 1100–1500。来源：正式设计 §3。
- footsteps 以 chunk 中的 tilelayer 为运行来源，外部 grid 只做一致性 Oracle，不维护两份可变运行状态。来源：正式设计 §7、§10。
- particles3 在消费者未知时保留 marker 并明确未完成，不得静默删除后宣称 24 层完成。来源：正式设计 §7、§10。
- 玩家 depth 常态使用与原站相同性质的 Y 排序规则，而不是每帧写死固定 depth；第一版默认以发布常态公式 `500 + (y + 24) * 0.1` 为行为参考。来源：正式设计 §6。
- roof/bridge 当前作为 SYS-LAYER 内部子能力，不因名称特殊就提前建立独立系统。来源：正式设计 §3。
- 本次运行时决定：bridge1 入口/出口重叠格入口优先，bridge2 两个区域必须离开后再次进入才翻转；层可见性、tile collision 和玩家 depth 作为同一状态切换应用。结果由 `WI-SYS-MOVE-WORLD-COLLISION-001` 负责实现验证。
- 实现 DECISION（`DEC-SYS-LAYER-CORE-001`，签字 `开工`，2026-08-16）：确定性纯逻辑 CORE，覆盖 24 层策略表（唯一图层合同）、玩家深度公式 `500+(y+24)*0.1`、桥上下/屋顶淡隐/墙壁碰撞 GID/脚印深度。玩家深度公式以本卡为准（契约表/SYS-PLAYER 写的 `500+y*0.1` 待对账）。落点 `src/layer/` + `tests/layer/`。不含 Phaser/Vite、网络、缓存、渲染、Tilemap 写入、旧项目修改。

## 3. 怎么做

### 本轮收束设计（DECISION；Human 已于 2026-08-20 通过）

1. **视觉层**：`layer1–10` 继续按策略写入 28×28 Tilemap，并按 depth 创建；apply 成功后必须能按 chunk 对称移除。
2. **动态 roof**：四个 roof 作为 chunk-local dynamic-visual 句柄保留；SYS-LAYER 负责幂等的 visible/alpha 状态应用和 300ms 参数，区域来源不在本项内；退出或 chunk 移除后恢复/撤销引用。
3. **碰撞/桥**：本次 `walls/bridge` 有界接线已经验证；后续完整图层实现仍需把可见性、碰撞和玩家 depth 覆盖作为同一状态结果，不在本轮重复实现。
4. **marker 层**：`cars`、`particles`、`particles2`、`particles3`、`footsteps` 不应被 `PhaserWorldRenderer` 静默丢弃；应按 chunk 来源产生可撤销的 marker/诊断结果。具体 TypeScript 签名暂不冻结。
5. **footsteps**：以 chunk 的 footsteps tilelayer 作为运行来源，外部 `footsteps-layer.json` 只做 368 个位置的 Oracle；脚印 Sprite 消费者不在 SYS-LAYER 本轮实现。
6. **particles3**：保留 GID 69361 marker，并报告“消费者未接入”；不得因为与 `protesters_rising` 计数吻合就实现转换或关闭 `Q-LAYER-002`。
7. **失败与原子性**：24 层中任一层转换、marker 登记或动态句柄建立失败，chunk 不登记成功；remove 必须撤销同一 chunk 的视觉、marker 和动态引用。当前 `WorldWriteHooks` 只有 raw layer hook，完整 marker 结果接口需在 Human review 后再定。

**本轮实现不包含**：particles3 动态人群、cars/NPC/车辆消费者、特殊 13 层生命周期、请求取消、性能量化和完整 Phaser teardown；这些仍需后续独立范围。

### 写入（chunk apply）

1. 输入 chunk 必须恰好含 24 层且名称、顺序、28×28 尺寸正确；
2. 每层先执行 GID 校验和转换，不直接把未知 GID 写入世界；
3. 视觉/碰撞层形成 28×28 可写网格；marker 层形成带世界坐标和 chunk 来源的 marker 集合；
4. 所有层转换成功后交 SYS-WORLD 统一提交；
5. 任一层失败则本 chunk 整体失败，不静默跳过该层后报告成功。

### 清除（chunk remove）

1. 视觉和碰撞层清除对应 28×28 区域；
2. marker 层按 chunk 来源撤销；
3. roof/bridge 清除图层数据并断开本 chunk 动态引用；
4. walls 和 bridge 碰撞区域重新计算；
5. 重复清除必须安全，不遗留半个 chunk 状态。

### 动态遮挡

- 玩家 depth：常态按 Y 排序公式计算；桥上、剧情抓取等覆盖必须通过显式状态进入和退出，退出后恢复常态计算，禁止多个系统无所有权地直接覆盖。
- roof：SYS-LAYER 拥有 roof 分组句柄和当前 alpha 状态；"玩家是否进入区域"的判定可来自后续区域能力，但图层系统负责幂等应用显示/淡隐结果（保留 Bundle 的 300ms 行为参数）。
- bridge：保存每座桥当前上下状态，一次状态切换同时更新：上/下图层可见性、对应 tile 碰撞、必要的玩家 depth 覆盖请求。桥状态来源和玩家移动规则不归图层系统。

### 与 SYS-WORLD / SYS-CHUNK 接力

SYS-CHUNK 决定目标坐标 → SYS-LAYER 按名称提供 24 层处理策略 → SYS-WORLD 原子写入/清除。分块不得绕过图层策略直接操作 Tilemap。

## 4. 失败怎么办

| 条件 | 结果 |
|---|---|
| 缺少任一已知层 | chunk 转换失败，列出缺失层 |
| 出现未知层 | 默认失败并记录名称；Human 接受兼容策略前不忽略 |
| GID 不属于允许 tileset 或策略 | 记录层名、坐标和 GID；本 chunk 不提交 |
| marker 消费者尚未实现 | 数据保留并标记未消费，不误报功能完成 |
| 动态状态指向已移除 chunk | 撤销引用并恢复安全默认状态 |
| 清除或碰撞重算失败 | 世界不删除已渲染标记，进入可定位失败状态 |
| particles3 无消费者 | 保留 marker 并明确报告未完成，不得静默删除后宣称完成 |

## 5. 接口接口

- 与 SYS-WORLD：以 layerPlan 提供 24 层处理策略（名称、tileset、GID 过滤、depth、动态状态）；roof/bridge 动态状态由 SYS-LAYER 保存并应用到图层实例。
- 与 SYS-CHUNK：SYS-CHUNK 只给目标坐标和触发写入/清除，具体每层怎样过滤 GID、设置 depth、碰撞和动态可见性由 SYS-LAYER 提供。
- roof 区域判定来源【TBD】："玩家是否进入区域"的判定可来自后续区域能力，精确形式未定死。
- bridge 状态来源与玩家移动规则：本次有界实现已采用公开 Bundle 证实的 tile 矩形边沿规则；更完整的玩家移动/区域系统仍不在本卡授权范围。
- 相机范围接口：相机 → 分块（已定死，见 SYS-CAMERA）。
- 资源加载接口：图片怎么加载、失败怎么办（原站事实已定稿，见 SYS-ASSET；重构约定留待实现授权）。
- 24 层视觉未知【TBD】：particles3 marker → trajectory 消费者直接关系（`Q-LAYER-002`）未关闭。

## 6. 怎样算做对

原站事实基准（来源：SYS-LAYER 验证计划 §1）：

- LAYER-FACT-001：25 个 chunk 均有同顺序 24 层（逐文件结构签名，必须 25/25 一致）；
- LAYER-FACT-002：24 层可无损拼成 final_map（470400 格逐格差异必须为 0）；
- LAYER-FACT-003：地图 visible 与运行时可见策略不同（对照 JSON 字段与 Bundle create/setVisible 调用）；
- LAYER-FACT-004：初始基础层、roof、walls、bridge 和 cars depth 可定位（Bundle 搜索 `createBlankLayer` 与 `setDepth`）；
