# 执行层（操作手册）

> 给执行 AI 照做。这里是 16 张系统卡 + 1 份总账 + 操作规则的唯一当前家。

## 八条规矩（先背下来，每轮照做）

1. **四色标记**（FACT/INFERRED/DECISION/UNKNOWN），推断不冒充事实
2. **两条状态线分开记**（理解 ≠ 做出）
3. **唯一事实源**：一件事一个家，别处只链接
4. **结论落地 = git 提交 + 完整同步《定稿落地清单》**，否则不算做完
5. **签字才写码**，签字写清"这次只授权哪块"
6. **sample 只读不抓**；遇异步/监听器/计时器必须写超时+清理
7. **先判任务体量**；非简单任务先分析并创建 Todo，分步执行且每步更新
8. **每轮改动走分支和 PR**；禁止在 `main` 开发、commit 或 push，只能提交并推送当前任务分支，再通过 PR 进入 `main`

## 任务体量判定

- **简单任务**：只读答复，或单文件、局部、低风险、意图明确且验证直接的微小修改。
- **非简单任务**：涉及多文件、代码或设计、调查、迁移、外部副作用、状态/协议变化，或范围与验收存在不确定性的任务。
- 拿不准时按非简单任务处理；先把范围和验收写清，再动文件。

## 非简单任务 9 步循环

```text
分析任务 → 创建Todo文档 → 分步执行 → 每步更新Todo
→ 校验检查 → 更新相关文档 → 更新版本与修订信息
→ 在任务分支提交 → 推送任务分支并创建/交付 PR
```

1. **分析任务**：确认目标、范围、禁止项、风险、验收和任务体量。
2. **创建 Todo 文档**：在 `task-todos/` 建 `YYYY-MM-DD-<task>.md`，记录范围、步骤、验证和 Git 计划；不得复制动态状态权威。
3. **分步执行**：按 Todo 顺序执行，一次只推进可验证的一步。
4. **每步更新 Todo**：动作完成并有证据后才勾选；失败或阻塞写清原因。
5. **校验检查**：运行与变更相称的结构、链接、状态、测试、类型、构建或行为验证。
6. **更新相关文档**：同步受影响的权威文档，不把结论只留在聊天或 Todo。
7. **更新版本与记录**：每份正式文档更新 `version`、`updated` 和修订记录。
8. **在任务分支提交**：检查 diff，只暂存本轮文件，使用准确提交信息；提交前确认当前分支不是 `main`。
9. **推送并交付 PR**：push 当前任务分支，创建或明确需要创建 PR；成功后再报告分支交付状态。失败则保留提交并明确报告待推送，禁止 force-push；未经 Human 明确要求不得合并 PR。

简单任务如果修改了文件，同样必须执行第 5–9 步；没有文件变化时不制造空提交。

## Git 功能分支与 PR 流程

### 任务开始

每个独立任务开始先执行：

```bash
git status
git branch --show-current
git checkout main
git pull --ff-only origin main
git checkout -b <branch-name>
```

分支按任务类型命名：

```text
feature/xxx   新功能
fix/xxx       Bug 修复
docs/xxx      文档修改
refactor/xxx  重构
```

若工作区已有无关修改，不得擅自 stash、reset、checkout、提交或覆盖；先保护现场并报告。若准备改文件时仍在 `main`，立即停止，先从最新 `main` 创建并切换到任务分支。同一任务的后续轮次继续使用原任务分支。

### main 保护

- 禁止直接在 `main` 上开发。
- 禁止直接在 `main` 上 commit。
- 禁止执行 `git push origin main`。
- `main` 只接受 Pull Request；Codex 不自行合并 PR，除非 Human 明确要求。

### 每轮提交与推送

```bash
git add <本轮修改文件>
git commit -m "<本轮修改说明>"
git push -u origin <当前任务分支>
```

远端跟踪分支建立后使用 `git push`。这里的 push 永远是“本地任务分支 → GitHub 对应任务分支”，不是上传 `main`。每轮只提交本轮文件，不制造空提交，不夹带无关修改，不 force-push，不改写历史。

### PR 与多人同步

固定交付路径：

```text
最新 main → 独立任务分支 → 开发 → Commit → Push 任务分支
→ Pull Request → 检查 / 处理冲突 → Human 确认 → Merge → main
```

若开发期间 `main` 已有其他成员的新合并：

```bash
git checkout main
git pull --ff-only origin main
git checkout <当前任务分支>
git merge main
```

处理冲突后重新校验、测试、commit、push，并更新 PR。最终回复必须给出当前分支、Commit、Push 目标和 PR 状态；已 push 任务分支不得误报为已进入 `main`。

## 最小 6 步循环（每张卡一个循环）

```text
选卡/查证据 → 填7格和未知 → Human签字定范围 → 实现对应src/tests
→ 按标准验证差距 → git提交并回写总账
```

1. **选卡/查证据**：从[总账](00-总账.md)挑一张卡，只读对应 `sample/` 证据；
2. **填 7 格和未知**：把逆向结论填进卡的一至七格（四色标记），没弄清的上[总账](00-总账.md)未知队列；
3. **Human 签字定范围**：书面写明"这次只授权哪块"，没签字不写码；
4. **实现对应 src/tests**：按卡的七格（尤其 §4 失败与清理、§7 代码位置）写代码和测试；
5. **按标准验证差距**：对照卡的 §6（原站基准 + 设计验收 + 旧版差距）逐条验证；
6. **git 提交并同步《定稿落地清单》**：在独立任务分支小步提交，并逐项同步下方《定稿落地清单》10 处，再 push 任务分支并交付 PR，否则不算做完。

## 定稿落地清单（一张卡 Human 签字「通过」后，逐项照做）

> 签字「通过」只代表「这卡内容对了」，**不算做完**。做完 = 下面 10 处全部同步并提交，缺一处不算落地。
> 以后每个系统照这份清单打勾，不靠记性；`scripts/check-state-consistency.py` 会兜底核对第 1/2/4/5 步的字段，第 6/7/8 步是内容级同步、脚本抓不到，更要自己照做。

1. **执行卡**：`status` → `designed`；补上 `## 👀 先看这里` 人话块（这卡在说啥 + 你审的就认这几条 + 下一步要单独授权）
2. **总账**（`00-总账.md`）：该系统行「工程状态」→ `designed`，备注写清已定稿结论摘要
3. **总账「未知队列」**：本系统查清的 `Q-` 从 open 挪到 closed（只留摘要 + 主定义链接 + 残余未知）
4. **进度总览**（`01-理解层/00-进度总览.md`）：该系统行图标 → 📐，顶头「全局一句话」计数同步
5. **理解卡**（`01-理解层/`对应路径）：标题下「📌 进度」行图标 → 📐，清掉底部滞留的旧 TBD / "待签字"话术
6. **系统地图**（`01-理解层/00-系统地图.md`）：若本系统动了「桥」（跨线接口），桥的状态同步成「已定死」
7. **API 契约表**（`02-接口层/API契约表.md`）：本系统入/出接口汇进「一、已定死」，删掉「二、还没定死」里已查清的老 TBD
8. **决策记录**（`决策记录.md`）：加一条 `DEC-SYS-XXX-DESIGN-001`；同系统 INVESTIGATION 那条「当前效力」列补"查证与填卡已完成"结果
9. **task_plan.md**：frontmatter `current-work-item` → `none`、顶部状态块同步、工作项写进「已关闭工作项索引」（含 `result-commit`）
10. **兜底闸门**：跑 `python scripts/check-state-consistency.py` 确认 0 漂移 → `git` 小步提交

## 代码 Gate

正式代码只在第 3 步签字且范围明确后进入 `src/` 和 `tests/`；`sample/`、旧项目和证据一个字节不碰；只在独立任务分支小步提交，禁止一次大提交，禁止直接提交或推送 `main`。
