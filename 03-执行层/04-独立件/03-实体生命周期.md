# 实体生命周期（SYS-ENTITY）

> 一句话：当前证据只支持“每类运行对象都必须明确自己的生命周期责任”，不支持玩家、NPC、车辆共享一个 Entity 基类、registry 或 runtime。本卡的正式设计结论是**暂不创建通用实体代码**。

## 👀 先看这里（人话总结）

- 玩家、crowd NPC、车辆确实都有创建、更新和销毁，但拥有者、资源、路线和 physics 形态明显不同。
- CrowdManager 的 `registeredCars` 只是车辆碰撞协作表，不是全体实体 registry；玩家不在这条链里。
- `Q-ENTITY-001` 继续 UNKNOWN。P3 C线是 no-code，不创建 `src/entity/**` 或 `PhaserEntityRuntime`。
- 现在只冻结一份“每个所属系统必须回答的生命周期审计清单”；它不是 API、基类或运行时对象。

**当前状态**：设计已定稿并以C线NO-GO/no-code收据验证；integration `8ae7692b` 未出现Entity API、registry、基类或schema。完整NPC/Route调查、两个真实实现后的复用提取仍未完成。

## 1. 逆向结论（从 sample 读出来的事实）

### FACT

- 玩家由 GameScene `createPlayer` 创建，是 Arcade Sprite 子类，拥有输入/动画/physics body 和自身 update；当前重构也由 `CampusScene` 创建并在 scene shutdown 收敛。
- CrowdManager 独立持有 `crowds: Map`、`registeredCars: Map`、`sceneNPCs` 和空间网格；其 update 推进 simulated NPC，并按可见性创建、更新或销毁 Sprite。
- 车辆从 route 结果创建，分别持有 display Sprite、可选轮子/灯附件、Arcade collision proxy、waypoint/route 状态；局部销毁会禁用 body、fade、逐项 destroy、移数组/registry 后补车。
- 当前重构 `798eda6` 的 chunk/world remove 只清 Tilemap layer/collider/marker/map，没有 NPC/车辆实体消费者。
- 公开 chunk 有 `cars` layer，但未证明 chunk unload 直接创建或销毁车辆。

证据：`chunk-WMFY56ZM.js` 玩家 byte 375796/415414；CrowdManager class/update/destroy 定位 line 378、byte 178033/186250/193985/194322/319081/443821/561182/564686；车辆 byte 518680–523500；当前实现 `798eda6:game/CampusScene.ts`、`PhaserWorldRenderer.ts`、`src/chunk/coordinator.ts`。

### INFERRED

- 三类对象共享“有状态、可见资源、更新、清理”的宽泛形状，但这不足以证明共享 class/interface/registry。
- `registeredCars` 服务 crowd/vehicle 碰撞协作，不能提升为全局实体所有权。

### UNKNOWN

- 玩家、NPC、车辆是否有未定位公共基类或 scene-level registry。
- 原站 scene shutdown 是否完整清除三类对象的 timer/tween/listener/body。
- chunk target 是否控制动态 NPC/车辆生灭。
- route/trajectory 的取消、失败、晚到回写和 teardown。

### DECISION

- `Q-ENTITY-001` 保持 open；不创建通用 Entity runtime、公共 registry、事件总线或基类。
- P3 C线实现为 NO-GO；只保留 no-code 收据。
- 每个未来对象在自己的系统（PLAYER/NPC/ROUTE）中实现并验证生命周期；出现两个独立实现共享稳定清理合同后，才重新提出提取方案。

## 2. 数据与约定

### 逐系统生命周期审计清单

每个真实对象的所属系统必须在设计/执行报告中回答：

- 创建者、唯一逻辑所有者、更新入口；
- Sprite/display、physics body/collider、timer、tween、listener；
- route/trajectory/asset/chunk/scene scope；
- disable/retire/destroy 顺序；
- 创建失败回滚、异步晚到保护、重复 destroy；
- scene shutdown 后残余引用和可验证收据。

这只是**文档审计清单**：不进入 `02-接口层/API契约表.md`，不生成 TypeScript 类型，不作为 registry schema 或运行时对象。

## 3. 怎么做

- 玩家生命周期继续归 SYS-PLAYER/CampusScene，不迁移到新 Entity 层。
- NPC/crowd 后续由 SYS-NPC 选择一个真实对象，查清 create→update→retire→destroy。
- 车辆后续由 SYS-ROUTE 选择一个真实 car，查清 route 输入、body/附件、fade/retire 和补车。
- 创建失败只回滚该对象已持有资源；异步回调先检查 scene/object generation。
- destroy 通常按“停止新 update/异步→取消 timer/tween/listener→移 physics→销毁 visual/attachments→移 registry/reference”审查；具体顺序仍由对象证据决定，不能强制统一接口。

## 4. 失败怎么办

- route/trajectory/asset/physics 任一步失败，不发布半实体。
- 晚到 callback/tween completion 不得复活已销毁对象。
- 原站完整 teardown 未证实，不能把建议顺序写成 FACT。
- 某对象没有可验证清理路径时，停止该对象实现，不以全局 Entity manager 掩盖。

## 5. 接口接口

当前**没有** `EntityLifecycle` 公共 API。

已确认边界：

- Scene 向各所属系统发 shutdown scope；各系统清自己创建的资源。
- SYS-ROUTE 提供已验证 route 或失败，不把车辆所有权交给 chunk。
- SYS-WORLD/CHUNK 提供已应用/移除范围事实，不直接拥有动态实体。
- 创建 physics body/collider 的对象所有者负责清理。

只有两个独立、已实现且验证的消费者显示同一稳定合同后，才能提出最小公共接口；该提取仍需新的明确范围。

## 6. 怎样算做对

### 当前设计验收

1. 玩家/NPC/车辆创建/所有/更新/销毁矩阵有可定位证据。
2. `Q-ENTITY-001` 保持 UNKNOWN，不把压缩类名冒充源码架构。
3. resource ledger 明确只是审计清单，不进入 API/代码。
4. P3 不创建 `src/entity/**`、`tests/entity/**`、`game/PhaserEntityRuntime.ts`。

### 未来单对象验收

- 创建失败无残留；update 唯一归属；destroy 幂等。
- shutdown 后无 timer/listener/tween/body/sprite/registry 引用。
- route/chunk 晚到结果不复活已销毁对象。
- 只有两个已验证消费者出现真实重复，才允许登记提取候选。
